Week 6 / Lesson 27 / Observability

Seeing what happened

The process is gone and someone is asking what the agent did. Everything you have left was written by a different writer at a different moment — and each piece can be missing on its own.

Skill reconstruct one agent run from the artifacts it left behind Time 35 min Needs Lesson 09, Lesson 16 Repos loomcli fleet-db

Why this exists

Lesson 16 asked what a test proves. This is the harder version of the same question, asked at 9pm: what does a run leave? You cannot attach a debugger to a subprocess that exited yesterday, and you cannot ask the agent — the failures that make you care are exactly the ones where the agent stopped being able to tell you anything (Lesson 09).

So the system writes evidence as it goes, at moments chosen so that the evidence survives the failure. That is the whole design, and it has one consequence that costs people hours: there is no single log. A run's record is scattered across a session directory, two log files, a host-local event stream, and two rows in fleet-db — written by three different processes.

The one idea

Every artifact has a writer, a moment, and a way of being absent. Name the writer before you believe the record. Several of these files are written by a process that is not the one you are investigating, and two of them are written by a reader, long after the run ended.

The inventory

Everything one supervised run can leave behind. The session directory is <workspace runtime dir>/sessions/<session id>/, and the session id is YYYYMMDD-HHMMSS-<agent>-<taskshort>-<8 hex> (internal/sessions/id.go:13-18, 36). The taskshort is hardcoded empty at the one call site (internal/sessions/store.go:66-68), so every session id carries the double dash and it tells you nothing about who created the session.

Four of those names contain transcript or events and end in .jsonl, and they are four different things — three with different writers, one with none at all. This is the failure mode Lesson 02 is about, in its purest form: say which file you mean, by path.

index.jsonl is append-only and normally collects two rows per run — one running at create (store.go:93-96, best-effort: a failed append is only a warning on stderr), one terminal at finalize (finalize.go:95-98). One row means nothing finalized; three means a reader healed it (query.go:127-129) or doctor --fix re-indexed it (finalize.go:136-147). Readers deduplicate by session id and keep the last row seen. internal/sessions/query.go:57-68 If any of those paths is unfamiliar, Finding Anything is the card for locating the package behind it.

Trap — daemon-agents.json is not evidence

It looks like the obvious place to start and it is the wrong one. The state file is rewritten wholesale every five seconds (internal/cli/daemon/daemon_run_helpers.go:23-33) and os.Removed when the daemon exits (internal/cli/daemon/daemon_cmd.go:258). It is a dashboard of what is running now, and the incident you are investigating is usually one where the daemon is no longer running. It carries one field worth remembering — last_error_class (daemon_cmd.go:42) — and that same value is durable in the fleet-db session row.

The trace: reconstructing one run

Start from the task: the endpoint and the fleet-db row are both task-keyed (fleet-db internal/api/control_plane.go:47, 235-251). It is not a universal key. The session record carries no task id until Finalize stamps it (internal/sessions/store.go:100-114 against finalize.go:27), so prompt.txt, the running index row and the first metadata.json have none; both log files are keyed by role and worktree instead (spawn.go:432; webui/log/paths.go:55).

  1. internal/webui/handlers/issues/module.go:58 → issues/journey.go:19-40 One endpoint folds most of it for you. GET /api/workspaces/{ws}/issues/{id}/journey, added by commit 7d1be8249. Call it yourself: the React timeline is a separate, client-side fold (internal/webui/frontend/src/components/IssueDetailPanel/sections/Journey.tsx:210 → journeyFold.ts beside it) whose only caveat is a one-line window note (Journey.tsx:449-453), not the structured block below.
  2. internal/webui/service/journey.go:51-73 Four blocks from two sources. spans[] is folded from the issue's fleet-db event history; agent_windows[] is an overlay read from a host-local JSONL; lead_time is decomposed from both; honesty says how much of the first two you are allowed to believe.
  3. journey.go:16-19, 84-99, 161-163 The history read is bounded on purpose. A tail of 500 first; if that does not prove completeness (hasKnownCompleteJourneyHistory) it pages forward, up to 100 pages of 200. A truncated read is always labelled — never served as if it were whole.
  4. journey.go:196-227 → internal/webui/service/issue.go:191-204 A span is a stage. One contiguous run of the same status, owner and needs-revision flag, plus the actor of the event that opened it — a boundary event closes the previous span and becomes the new one's actor (journey.go:288-295). Derived, never stored — the glossary's stage entry is the definition, and on the Go side the word is span.
  5. journey.go:297 → fleet-db internal/service/claim_reaper.go:23-25, 34-40 stalled is the highest-signal field in the whole fold. It is true only for an issue.release whose actor matches system case-insensitively, after trimming (journey.go:297) — in practice fleet-db's ClaimReaper, the only emitter that puts that actor on a release (internal/service/issue_service.go:736-745), taking the task back because neither a claim lock nor a live agent session vouched for it (claim_reaper.go:42-56). Nobody released that task. It was confiscated.
  6. journey.go:346-353, 385-387, 399-418 The agent-window overlay. task.claimed opens a window, task.completed or task.failed closes it, and a second claim marks the earlier window superseded. It is read from this host's events JSONL, resolved at internal/cli/serve/serve.go:646 → observability.ResolveEventsDir (cli/serve/observability/observability.go:235-248).
  7. fleet-db internal/api/control_plane.go:47, 235-251 Task to session. GET /api/v1/{workspace}/agent-sessions?task_id=<id>. This row is the run index that outlives the worktree, the daemon and the host: status, exit_code, error_class, finished_at, node_id, and a free-form metadata map (internal/models/control_plane.go:195-216).
  8. internal/cli/daemon/supervisor/supervisor.go:626-650, 692, 699-705 What the supervisor put in that map. backend, task_id, epic_id, repo, attempt_kind, transcript_path, log_path; then the diff stats (internal/sessions/diff_metadata.go:24-34); then transcript_ref, whose value is artifact://transcript-<session id> (supervisor.go:733-754). Those two path fields are your bridge back to the disk.
  9. internal/sessions/finalize.go:16-101 On the owning host, the session directory. metadata.json is rewritten with task id, exit code, error class, ended_at, duration, diff stats, files touched and token counts; diff.patch lands beside it when files changed. The diff is recomputed from git against the HEAD captured before the spawn (supervisor.go:511-516), not streamed — which is exactly why finalize has to run before post-mortem recovery touches the worktree.
  10. spawn.go:354-368, 407-435, 447-453 The two logs, last. Same bytes, two files: the daemon log whose mtime the watchdog stats and whose tail the crash classifier reads, and the archive the web UI Logs tab serves. If both sinks fail to open, the child's output goes to /dev/null and the daemon prints a loud NO LOG SINK line — because the silent version of that state once made a real bug undiagnosable (spawn.go:382-395).

Read the honesty block before you read the fold

This is the part of the design worth stealing. The journey endpoint does not present a partial reconstruction as a complete one; it ships a block that states what it could not see.

Six reason strings mean the issue history was bounded: history_page_cap_reached (journey.go:125), history_paging_unavailable (:134), history_paging_failed (:136), history_page_missing (:139), history_count_mismatch (:148) and history_cursor_stalled (:155). Four more mean the agent-window overlay is unavailable: events_dir_not_configured and events_read_failed (:357, :361) — the reader could not look — and no_task_lifecycle_events and no_claimed_window (:377, :380) — it looked, and this host had nothing. All four set agent_windows_available: false, so the flag alone distinguishes none of them.

Two further admissions ride on the data itself. When the history was bounded, or when the earliest event is not an issue.create, the first span is stamped approximate and unknown_start (journey.go:222-225). And the four lead-time buckets may sum to less than the total: deferred and open-but-assigned intervals, and the gaps between attempts, satisfy no settled category, so they fall out of the classifying switch (journey.go:498-514) rather than being forced into a confident but false bucket (internal/webui/service/issue.go:218-222). On a clean closed trace they do sum exactly to the total (journey_test.go:133-141) — an exact decomposition is not a bug.

Where the two halves come from

The spans[] half is folded from fleet-db's durable issue event log, so it describes the task wherever it ran. The agent_windows[] half is read from a JSONL file on this machine (journey.go:63, 75-82). A run supervised by another node leaves no window here, and the fold says so rather than implying the attempt never happened.

Where the evidence lies to you

Trap — the four-hour run that never ran four hours

A record reading status: aborted, duration_s: 14400 and ended_at exactly four hours after started_at was not written by the run. It was written by a reader: any Store.Query heals stale rows on the way past (internal/sessions/query.go:98-99), and so does SweepOrphans at daemon start (stale.go:41-59). The timestamp is an invention. What it actually tells you is that nothing ever finalized this session — the process died between CreateSession and Finalize. The near-miss that makes this dangerous: there really is a four-hour ceiling on a run (daemon/supervisor/run_duration.go:44-46, 61), and it is an unrelated number that happens to be equal. A duration kill goes through markRunDurationExceeded and lands as error_class: Timeout with a genuine ended_at (supervisor/classify.go:42-48, 119-131). Its status is not fixed: status is derived from the child's exit code alone (internal/sessions/finalize.go:29-33; supervisor.go:673-676) and the kill sends SIGTERM first, so a harness that handles it exits 0 and leaves a completed record carrying error_class: Timeout (classify.go:93-103). The class is the tell, not the status.

Trap — the session says failed, the event stream says exit 0

Both are correct. When a run exits cleanly but one of its on_complete hook writes fails, the supervisor demotes the run to a synthetic failure — LastExitCode = -1, class CompletionHookFailure (session_finalize.go:771-785) — so the owned task reopens and retries under normal policy. The agent.stopped event had already gone out carrying the factual exit code (spawn.go:495-519), and nothing rewrites an emitted event. The comment at session_finalize.go:234-240 says exactly this. Debug hook failures through error_class, never through the event's exit code.

Trap — the run that used zero tokens

The fleet-db session row has no token or cost fields. The update struct's ten are NodeID, TaskID, Status, Phase, LastHeartbeat, FinishedAt, Summary, ErrorClass, ExitCode and Metadata, identical in both repos (internal/store/control_plane_store.go:82-93; fleet-db internal/storage/storage.go:342-353); the completion path sets six of them (supervisor.go:709-716). Usage stays on disk — the session's metadata.json, plus an appended row in <workspace runtime dir>/usage.jsonl for automode and daemon runs (internal/cli/automode/automode_usage.go:45-48). Neither reaches the control plane. A UI showing 0 tokens for a daemon run is reporting an absent field, not an idle model.

Two more places the contract doc outruns the code. docs/product/session-artifact-contract.md:265-268 requires a ?parent_session_id= query; the fleet-db filter accepts only agent_id, node_id, task_id, status and limit (fleet-db internal/storage/storage.go:334-340), though the model does store parent_session_id. And its stable error-class list (:200-216) is not what lands in error_class: that field gets Outcome.String(), a different set of strings that the code commits to keeping byte-stable (internal/agenterr/outcome.go:22-39, 73-82).

What LOOM_TRACE=1 actually does

Four things follow from those ten lines. The service name is chosen from os.Args[1], so a dashboard can separate long-running daemons from one-shot invocations: serve → loom-serve, daemon → loom-daemon, plan|task|agent|lead → loom-agent, everything else loom-cli (root.go:261-274). Export is synchronous for loom-cli and loom-agent, because those processes can leave via os.Exit and skip a batched flush (root.go:231-234; internal/observability/tracing/tracing.go:86-90, 186-189). The whole invocation is one root span, renamed to loom.cli.<subcommand> (root.go:179, 190-192). And the trace crosses a process boundary by environment variable: the daemon injects LOOM_TRACE_PARENT when it spawns an agent (daemon/supervisor/spawn.go:78-83), and the child's BootstrapContext extracts it before opening its own root span (tracing.go:33-49).

Trap — LOOM_TRACE=1 prints nothing

It is not a verbose flag. It turns on an OTLP exporter aimed at localhost:4318, and with no collector listening there you get no output, no error you will notice, and no trace. Setting it after the incident is equally useless: tracing is per-process and nothing is retained. What is durable is the traceparent field on every emitted event row (internal/events/event.go:51-73), filled from the ambient context at emit time (internal/events/emitter.go:50-52) and left empty when the emitter had no active span. So the JSONL can still name the trace id long after the collector is gone — which is the only reason writing a trace id down during an incident is worth anything.

Check yourself

From memory: a run finished two days ago on a machine you do not have, and its worktree has been deleted. Name the one record that still ties the task to that run, the request that lists it, and the fields on it that tell you how the run ended and where the rest of the evidence went.

The fleet-db AgentSession row. GET /api/v1/{workspace}/agent-sessions?task_id=<id> — fleet-db internal/api/control_plane.go:47, 235-251.

How it ended: status, exit_code, error_class, finished_at (fleet-db internal/models/control_plane.go:195-216). Where the rest went: the metadata map's log_path, transcript_path and transcript_ref, written at internal/cli/daemon/supervisor/supervisor.go:626-650, 699-705 — plus node_id, which tells you whose machine to ask.

What it will not tell you: token usage. That field does not exist on the wire (session_finalize.go:103-110).

A session record reads status: aborted, duration_s: 14400, ended_at exactly four hours after started_at. What happened?

  • The run hit the four-hour duration ceiling and was stopped
  • A reader found it still running and invented the ending
  • The supervisor finalized it once the watchdog had killed it
  • The daemon restarted and closed out the run it had orphaned
Nothing finalized this session. A later Query or SweepOrphans healed the row and synthesised ended_at = started_at + 4h (internal/sessions/stale.go:24-39). The first option is the sharp one: a real four-hour run cap does exist (run_duration.go:61), but it lands as error_class: Timeout with a genuine end time (classify.go:119-131) and a status derived from the child's exit code — never aborted, which only stale healing writes (stale.go:31). The two four-hour numbers are unrelated constants.

A journey response has agent_windows: [] and agent_windows_available: false. What have you learned?

  • Only that the local overlay is missing; read its reason string
  • Only that no agent ever claimed this task on any node at all
  • Only that the fold stopped at its page cap before any claim
  • Only that the events file exists but its rows were unreadable
Four different reasons set that flag false: two mean the reader could not look at all, two mean it looked and this host had nothing (internal/webui/service/journey.go:346-383). The second option is the trap — the overlay is read from this machine's JSONL (journey.go:63, 75-82), so it can say nothing about another node. The page cap belongs to the history half and surfaces in honesty.reason, not here.

The event stream records exit 0, the session says failed, and the task went back to open. Which one is wrong?

  • The session record, demoted by a finalize that ran too late
  • The event, whose exit code the supervisor failed to rewrite
  • Neither — a completion hook failed after a clean process exit
  • The task status, reset by recovery before the hooks had a turn
A failed on_complete write demotes the run to exit -1 with class CompletionHookFailure so the task reopens (session_finalize.go:241-262, 771-785), while the already-emitted agent.stopped event keeps the factual 0 (spawn.go:495-519). The disagreement is designed. The second option is the one worth arguing with: an emitted event is immutable, and rewriting it would destroy the only record of what the subprocess actually did.
Before you go looking at a real stack

Every step below is read-only and touches no running system. When you do go poking at a live stack later: this is a shared machine. Never make local-mode-up or local-mode-down a compose project you did not create — pick your own project name and an unclaimed port block, check podman ps first, and treat every stack you find as someone else's. The same rule covers agent-browser sessions and dev servers on fixed ports. Reading files your own stack wrote is fine; podman and port state is not yours to change.
