Week 6 / Lesson 28 / Cross-repo

One change, two repos

Nothing generates the wire between loomcli and fleet-db. Two hand-written mirrors, shipped from two repositories on two schedules — so the order you land them in is part of the design, not an afterthought.

Skill sequence a cross-repo change, and name the compatibility window it assumes Time 40 min Needs 07, 15, 21 Repos loomcli fleet-db

Why this exists

Lesson 15 walked one field from a YAML schema to a rendered pixel inside loomcli. That worked because one hand-written spec generates a Go type file and a TypeScript type file, and make check-go regenerates the Go one into a temp dir and diffs it (scripts/check-go-api-staleness.sh:1-7, wired in at Makefile:610). Three files change together or the build fails.

Across the repo boundary, none of that exists. The three things you would reach for first:

  • A shared module? No. grep fleet go.mod in loomcli returns zero lines — loomcli does not depend on fleet-db at all.
  • The server's Go client? fleet-db ships one at fleet-db pkg/client/, and its only non-test consumer in either repo is fleet-db's own CLI (cmd/fdb/main.go:17-19).
  • The server's OpenAPI spec? It generates nothing, on either side — a search for oapi-codegen or go:generate across fleet-db returns nothing. Its only trace in loomcli is prose: three comments name it by repo-qualified path (internal/backend/fleet/params.go:167, internal/backend/fleet/params_test.go:285, internal/infra/fleetdb/control_plane.go:149), and three more reference it in passing (internal/backend/fleet/params.go:253, internal/backend/fleet/convert.go:490, internal/backend/fleet/params_test.go:52). Not one line of code reads it.

So the contract lives in two hand-maintained mirrors facing each other across an HTTP boundary: fleet-db's request structs and models on one side, loomcli's internal/backend/fleet (17 non-test files, of which convert.go is 605 lines) and internal/infra/fleetdb on the other. They agree because people keep them agreeing.

The one idea

Before you write either half, name the compatibility window: the set of (loom build, fleet-db build) pairs that must interoperate while your change rolls out. The two repos are never deployed atomically, so at least one mismatched pair always exists. Your ordering exists to make that pair harmless. "We'll ship them together" is not a window — it is a wish.

Three deployments, three windows

Loom runs in three shapes, and each gives you a different window. Which one you are protecting decides how much ordering discipline the change needs.

ShapeHow the pair is chosenWindow you must survive
Local mode loom forks whatever binary discovery finds: FLEET_DB_BIN → PATH → sibling of the loom binary → <LoomDir>/bin/fleet-db (internal/bootstrap/embedded.go:526-532) Any pair at all. Two engineers with different checkout dates are a different pair.
Cloud mode LOOM_FLEET_DB_URL points the same client at a remote fleet-db (Lesson 07) Every loom build any operator still runs, against the one deployed fleet-db.
Desktop bundle One workflow checks out fleet-db and bundles it as a sidecar (.github/workflows/desktop-release.yml:45-50) Exactly one pair, fixed at build time.

The repo says this in its own words, in the comment above the only cross-repo job that gates a release:

That job gates the release: goreleaser declares needs: skills-compatibility (.github/workflows/release.yml:50). It runs on v* tags only. Two other loomcli workflows check out fleet-db and neither blocks anything: desktop-release.yml:45-50 bundles the sidecar, and nightly.yml:99-107 runs the daemon playground against it under continue-on-error: true (:94). fleet-db's five workflows never check out loomcli, so a fleet-db change merges green with no loom in sight.

The asymmetry that decides every ordering

One line of Go governs almost all of this. fleet-db decodes every request body strictly:

One unrecognised key rejects the entire write with a 400 and the message unknown field "x" (internal/api/request.go:145-146). Query strings are the opposite: parseReadyFilter reads exactly the twelve parameters it knows about and never errors on anything else (internal/api/ready.go:124-225). Headers are laxer still — unknown ones are simply ignored, and fleet-db's own governance doc lists "adding new HTTP headers" as non-breaking (docs/api-governance.md:71).

Body drift fails loudly and totally. Query drift fails silently and wrongly. The best paragraph in either repo about this is the comment on the test that pins fleet-db's request structs to its spec — read it twice:

That test covers exactly two schemas, UpdateIssueRequest and CreateIssueRequest (internal/api/openapi_request_parity_test.go:51-52). It keeps fleet-db honest with itself. Nothing anywhere keeps fleet-db honest with loomcli.

The ordering table

This is the lesson. For each kind of change, which repo lands first, and the line of code that forces it.

ChangeOrderWhat forces it
New response field fleet-db first, loom whenever Old clients ignore unknown JSON keys — encoding/json's default, and a written client obligation (docs/api-governance.md:48, 107).
New request-body field fleet-db first, never the reverse DisallowUnknownFields (internal/api/request.go:132). A new client against an old server loses the whole write, not the field.
New query parameter fleet-db first Nothing rejects it, so shipping the client first produces a filter that returns wrong rows and no error (internal/api/ready.go:124-225).
New route fleet-db first An old server has no such route, and fleet-db registers no catch-all — its mux is built bare (internal/api/server.go:24) and no Register*Routes function claims the "/" pattern — so http.ServeMux answers with plain-text 404 page not found. loom cannot parse that as JSON (internal/backend/fleet/fleet.go:214-216) and reports fleet server communication failed (errors.go:150) — an error about the connection, not about the missing route.
New header Either Unknown headers are ignored both ways. This is why idempotency signals travel as headers — see the pattern below.
Renaming a JSON key Do not rename. Add the alias on both sides and keep both forever. The live example is repo ∥ source_repo, implemented twice — see below.
Removing anything loomcli stops using it first; fleet-db removes it later Pre-1.0 removals get a 30-day deprecation window (docs/api-governance.md:29, 46). Read the trap below before you trust that machinery.
Rewording an error message Check the client's string tables first — there are two loom classifies unrecognised codes by English substring (internal/backend/fleet/errors.go:116-132), and backend.IsAlreadyClosedConflict matches on the message even when the code was recognised (internal/backend/errors.go:99-108).
Renaming a fleet-db CLI flag Keep the old flag until every loom on the machine is upgraded loom hard-codes four flags and at least four env vars when it forks the binary (internal/bootstrap/embedded.go:373-383, with the Redis pool defaults appended at :596-599). The identification probe will not catch the rename for you: it accepts a real fleet-db on the Usage of fleet-db: banner alone (:657-661, reached from :634), and the auth-dev-mode/redis-addr clause beside it never fires, because the probe keeps only the first 500 bytes of --help (:630-631) and neither flag is in them.

Read the table's second column again. Almost every row says fleet-db first — because the server is the side that can be strict, and the strict side has to move first. The rule generalises: the participant that can reject goes first; the participant that can only be ignored goes second.

The trace: a compatibility shim you can run in one second

This is not hypothetical. At the two commits this course is pinned to, loomcli sends a create-body field that fleet-db does not accept, gets rejected, and recovers — on every single create that carries an external reference.

  1. internal/cli/data/create.go:98, 128 The flag. --external-ref lands on backend.CreateParams.ExternalRef. A thin Lesson 06-shaped leaf: no logic here.
  2. internal/backend/types.go:430-452 The body is a hand-built map. FleetCreateBody sets a key only when the caller set the field, so unset fields are absent rather than zero. It puts "external_ref" in at :448. Note what it deliberately leaves out — id, acceptance_criteria, created_by, estimated_minutes, dependencies — pinned by a negative-assertion test at internal/backend/fleet/params_test.go:240-259.
  3. internal/backend/fleet/fleet.go:532-534 The request. createIssueOnce POSTs that map to /issues, with the idempotency values carried as headers.
  4. fleet-db internal/api/issues.go:89-90 → internal/api/request.go:130-132 Total rejection. CreateIssueRequest (request.go:36-53) has no ExternalRef field, so the strict decoder fails the whole body: 400, code invalid_json, message unknown field "external_ref" (request.go:145-146). Every other key in that body is collateral damage.
  5. internal/backend/fleet/errors.go:69-73 Classification preserves the sentence. classifyErrorCode maps invalid_json onto ErrValidation(op, msg), and ErrValidation copies the server's message onto BackendError.Message verbatim (internal/backend/errors.go:122-124). The English string is now load-bearing.
  6. internal/backend/fleet/create_compat.go:12-19 → fleet.go:517-520 The shim decides. An exact string comparison against one constant. If it matches — and only then — Create retries.
  7. internal/backend/fleet/create_compat.go:25-43 Recover in two calls. Blank the field, re-derive the idempotency key from the new body (the key is a hash of the exact bytes — internal/backend/types.go:456-466), POST again, then PATCH the external ref on — because UpdateIssueRequest does accept it (fleet-db internal/api/request.go:68). Create and update disagree about the same field name; the shim exists to bridge that.

That is what a compatibility window looks like in code: a constant, a predicate and a two-call recovery that make one specific server mismatch survivable — keyed on a sentence the other repo formats. Four tests cover it (internal/backend/fleet/fleet_create_external_ref_test.go:14, 46, 102, 137), and every one of them drives it with a stub server. The unsupported case feeds the shim its own constant (:60); the negative case sends unknown field "foo" (:141) to prove the match is exact. So the tests pin loom's branch. They cannot notice fleet-db rewording the sentence.

The sentence is not even produced in one place. The claim handler rolls its own strict decoder and formats the failure as "invalid JSON: " + err.Error() (fleet-db internal/api/claim.go:55, 57), where the shared path normalises it to unknown field %s (internal/api/request.go:145-146). Same failure, two sentences, depending on the route.

The pattern to copy

  1. To rename, alias on both sides. fleet-db emits Repo under two keys and accepts it under either, with repo winning a collision:

    loomcli does the mirror image: fleetIssueWire declares both keys and a two-line accessor picks (internal/backend/fleet/convert.go:24-25, 99-104), from commit af23eac3e parity(fleet): accept fleet-db's `repo` json key as source_repo alias. Once both sides accept both spellings, deploy order stops mattering for that field — which is the whole point of paying for an alias.

  2. Put anything the other side might not know in a header, not the body. The idempotency values travel that way, and the comment says exactly why: "the X-Idempotency-Key / X-Idempotency-Force values travel as request headers — fleet-db's strict JSON decode rejects unknown body fields" (internal/backend/fleet/idempotency.go:13-17).
  3. Build request bodies as maps keyed on set-ness, never as structs. updateParamsToPatchRequest sets a key only for a non-nil pointer (internal/backend/fleet/params.go:323-338, setStrField at :386-390). Its doc comment states the rule: fields fleet-db's UpdateIssueRequest lacks "must be omitted entirely, not just zeroed" (:314-322).
  4. Pin a query-parameter name with a negative assertion. When loom sent ?issue_type= where fleet-db reads ?type=, the filter was ignored and --type=epic returned tasks (internal/backend/fleet/params_test.go:284-287). The regression test asserts the wrong key is absent, not just that the right one is present (:289-298). Copy that shape; a positive assertion alone would have passed throughout the bug.
  5. Prefix the commit parity(...) and cite the other repo's issue ID. There are 57 such commits in loomcli (git log --grep='^parity') and fleet-db uses the same prefix (0712db1). Cross-repo TODOs name an ID — // TODO(fleet-q6ox): fleet-db does not yet return unblocked issues on close at internal/backend/fleet/fleet.go:850-851. It is how the other half of a two-repo change gets found later.

The case study: a change that shipped in the right order

loomcli's client used to build ready/blocked paths by appending to its workspace base URL, producing /api/v1/{ws}/ready. fleet-db only served /api/v1/{ws}/issues/ready, so those calls 404'd — and surfaced one layer up as a 503 "workspace not registered", because the canonical /issues path worked and ready did not. That is the route row of the table above, playing out: a missing route does not present as a missing route. Two dates, both readable with git show in your pinned checkouts:

  1. fleet-db 0712db1 — 2026-04-23 Server first, additively. parity(fix): add /ready and /blocked workspace-root aliases registers the two extra paths on the same handlers, behind the same middleware and permission (internal/api/ready.go:34-38). Nothing is removed; both shapes now work. The doc comment at :15-26 records that the aliases exist only to match a client's URL shape.
  2. loomcli 3418bbe70 — 2026-05-04, eleven days later Client second. The client moved to the canonical path, which is what it builds today — "/issues/ready?" at internal/backend/fleet/fleet.go:382 and "/issues/blocked" at internal/backend/fleet/blocked.go:12.

Now notice the residue. The aliases are still registered and no live loom client uses them. They cannot be deleted on a whim either, because any loom binary from before 2026-05-04 still constructs the old shape, and local mode will happily pair one of those with a fleet-db built today. That is the compatibility window outliving the change that needed it — and the reason the removal row in the table sends loomcli first and fleet-db second, with a written waiting period in between.

Trap — "non-breaking" is a statement about parsing, not behaviour

docs/api-governance.md:63-71 lists "adding new error codes for new conditions" as non-breaking. It is, in the sense the doc means: an old client still parses the response. But fleet-db declares 24 ErrorCode constants (fleet-db internal/api/errors.go:15-52) and loom's classifyErrorCode recognises 14 of them (internal/backend/fleet/errors.go:69-82). The other ten — including forbidden, precondition_failed, lease_expired and rate_limit_exceeded — fall through to a substring match and then to a status switch, where a 403 becomes ErrUnavailable("authentication failed: …") (errors.go:49-50): the wrong story to tell an operator. Adding a code is non-breaking and ships a client behaviour nobody chose. When you add one, add the arm on the loom side in the same pair of PRs.

Trap — the deprecation machinery is written down and not wired up

docs/api-governance.md:73-85 specifies the removal process: deprecated: true in the spec, then Deprecation, Sunset and Link response headers, then a 30-day window. At 000793b, api/openapi.yaml contains zero occurrences of deprecated: true, and grep -rn Deprecation --include='*.go' internal cmd is empty in both repos: nothing sends those headers and nothing reads them. The window is a promise between people, not a mechanism. Plan on telling the client yourself.

What actually proves a pair compatible

Two things, and it is worth knowing exactly how far each one reaches.

  1. The release gate. make test-skills-release-compat builds both binaries and drives a real embedded fleet-db through loom workspace add, eight loom skill import calls, one expected binary rejection, loom skill list and loom skill materialize, comparing bundled files byte for byte (scripts/test-vercel-skills-compat.sh:47-166). It is a genuine end-to-end proof — of the skills path. It never calls loom data, so it proves nothing about the issue seam this lesson traced.
  2. The conformance suite. TestE2E_IssueBackendConformance_AllModes runs a shared suite against four backend modes — fleetdb-local, fleetdb-cloud, fleet-direct, api-server — with a real fleet-db binary (internal/cli/issue_backend_conformance_e2e_test.go:30, 34, 57, 76, 100). The suite runs three subtests (internal/backend/backendtest/issue_backend_suite.go:34-42) but pins two: CreateListGetUpdateCloseReopen and ReadyAndBlockedAgreeOnUnblockedIssue. The third, ExplicitCreateID, opens with if !cfg.SupportsExplicitCreateID { t.Skip(…) } (:81-83), and nothing in the repository sets that field true — none of the four mode configs do. It is still the closest thing to a contract test either repo has — and it is behind the build tag issuebackend_e2e, which appears in exactly two places in the tracked source at ce4df56fb: the two build-tag lines of that file. No Makefile target and no workflow runs it; the only place that hands you the command is this course's own first-task workflow card.
It also calls t.Skip when it cannot find a fleet-db or loom binary (internal/cli/issue_backend_conformance_e2e_test.go:132, 146). A skipped run and a passing run both end in ok. Reaching back to Lesson 16: read the SKIP lines before you claim real evidence. And note the package it lives in: go test … ./internal/cli is not a read-only command on a shared machine — that package's TestMain calls killTestTmuxSessions before and after the run, killing every tmux session on the host named loom-test-* or loom-e2e-test-* (internal/cli/testmain_test.go:21, 28, 34-46), including another engineer's in-flight run. Lesson 26 has the full story.
Trap — the half-crossed field

A cross-repo field can be added at both ends and still do nothing, with both builds green. estimated_minutes is that today. fleet-db declares it on models.Issue, validates it and stores it (fleet-db internal/models/issue.go:84, 160-161; internal/storage/marshal.go:64-65). loomcli declares it on types.Issue (internal/types/issue.go:33) and on backend.IssueDetailData, CreateParams and UpdateParams (internal/backend/types.go:85, 387, 509), and the projection copies it (internal/backend/fleet/convert.go:257). But no fleet-db request struct accepts it (internal/api/request.go:36-69), and fleetIssueWire — the mirror Get, List, Ready and Blocked read through — never declares it (internal/backend/fleet/convert.go:15-43), so toIssue leaves it nil on every Get, Ready and List. Both ends of the pipe have the field. The pipe has no hole for it, in either direction. Nothing fails; nothing works.

The comment at internal/backend/fleet/params_test.go:13-19 explains the omission by saying acceptance_criteria and estimated_minutes "have dedicated endpoints". At 000793b fleet-db's internal/api/ has no route for either. Dropping the keys is still right; the stated reason is stale.

Check yourself

From memory: you are adding an optional field to the body of a fleet-db write endpoint, and loom needs to send it. State the order you land the two PRs, the single line of code that forces that order, and what the wrong order does to a user.

fleet-db first, loomcli second. Ship the field on the request struct and in api/openapi.yaml — the reflection test fails otherwise for the two issue schemas (internal/api/openapi_request_parity_test.go:51-52). Only once that server build is everywhere your loom talks to do you start sending the key.

The forcing line is dec.DisallowUnknownFields() at internal/api/request.go:132.

Wrong order: an old fleet-db rejects the whole body with 400 unknown field "x" — not just your new field. Every other key in the same write dies with it, which is the failure already recorded at internal/api/openapi_request_parity_test.go:24-25. The compatibility window you are protecting is every fleet-db build any loom you ship might reach.

loomcli starts sending ?owner_hint=alice on the ready query. fleet-db does not read that parameter yet. What happens?

  • A 400 response naming the query key it did not recognise
  • A 200 response, and the client re-applies the filter itself
  • A 200 response, and the filter has no effect whatsoever
  • A 500 response, because the filter parser fails to parse
parseReadyFilter reads a fixed list of parameters and never inspects the rest (internal/api/ready.go:124-225), and filterReadyIssues only re-applies the fields it is written to know about (internal/backend/fleet/deferred.go:36-47). The second option is the sharp wrong answer: client-side re-filtering is real, but you have to add your field to it. mol_type and unassigned are shipped today by readyOptsToQuery (params.go:222-241), read by nobody, and re-applied by nobody.

Reaching back to Lesson 15: loomcli's own api/openapi.yaml generates a Go type file and a TypeScript type file. What does fleet-db's api/openapi.yaml generate?

  • A Go client package that loomcli imports and calls
  • Nothing at all, on either side of the boundary
  • A Go models file that loomcli's gate diffs
  • A TypeScript types file for the loom web app
No generator runs against it: a search for oapi-codegen or go:generate across fleet-db returns nothing, and every loomcli reference to that spec is a prose comment. The first option is the near miss worth remembering — fleet-db really does ship a Go client at pkg/client/, and loomcli really does not use it (cmd/fdb/main.go:17-19 is its only consumer).

fleet-db renames one error message from "issue is already closed" to "issue was closed earlier". Which repo's CI fails?

  • Neither — loom quietly stops matching the text
  • fleet-db's, because the harness pins messages
  • loomcli's, because its stubs assert the text
  • Both, because the message is a shared constant
Nothing fails, and the damage is subtler than "the error kind changes". The kind survives: fleet-db answers 422 with code invalid_transition (fleet-db internal/api/errors.go:244-251) and loom maps that code to KindConflict (internal/backend/fleet/errors.go:74-76). What breaks is backend.IsAlreadyClosedConflict, which additionally requires the substring "already closed" or "is closed" (internal/backend/errors.go:99-108) — and loom data close uses exactly that to stay idempotent (internal/cli/data/close.go:33-40). After the reword, a doubled close exits non-zero. loomcli's tests pass because they stub the server with their own strings — the same reason the external_ref shim's four tests would survive a reword (internal/backend/fleet/fleet_create_external_ref_test.go:60).

Every fleet-db Get, List, Ready and Blocked response reaches loom's canonical types through one hand-written mirror. Adding a response field to loom means editing — the file that declares fleetIssueWire.

fleetIssueWire at internal/backend/fleet/convert.go:15-43 and toIssue at :46-73. It exists because types.Issue tags the field as issue_type while fleet-db emits type, so embedding loom's own struct would drop the type on every response (:12-14). Skip this file and your new field is unreachable on those four paths no matter what the server sends. Two paths do not go through it at all — Create and Close unmarshal straight into types.Issue (internal/backend/fleet/fleet.go:544-545, 860-861), which is why a created issue comes back with its type dropped.
Before the exercise — the standing rule

Everything below is read-only: greps, file reads, and one single-package go test that spins up an in-process stub server. Do not bring up a stack for this. When you do need one, the rule from Lesson 03 stands: local stacks are shared machine state. Run podman ps first, pick your own LOCAL_MODE_COMPOSE_PROJECT and an unclaimed port block, and tear down only the project you created. Never up, down or --build a compose project you did not start.

Read next, in full

fleet-db docs/api-governance.md — 111 lines, and the only written statement of the rules your cross-repo PRs will be judged against: URL-path versioning, the explicit breaking-versus-non-breaking lists, the 30-day pre-1.0 deprecation window, and the five client expectations at :105-111. Read it beside this lesson's second trap: two of those expectations tell clients to check Deprecation and Sunset headers that nothing in either repo sends. Knowing which parts of this doc are enforced, which are conventions and which are aspirations is the difference between a change that lands and one that gets rewritten in review.
