Week 1 / Lesson 04 / Conventions

The gate is the spec

Nobody will hand you this repo's style guide, because it is executable. By the end of this lesson you can read make gate as a statement of the team's conventions, and predict which check your change will trip before you run it.

Where the conventions actually live

You asked, reasonably, "what are this repo's implementation patterns?" There is no document that answers that. There is something better: nineteen automated checks, most of them written by this team for this codebase, that fail your build when you violate a convention. Reading them is the fastest way to learn what good code looks like here.

The one idea

Thirteen Go checks, six frontend checks. The first three or four on each side are the industry-standard ones you already expect. Everything after that is this team encoding a lesson it learned the hard way. Those are the interesting ones.

The ratchet pattern

Checks 5, 6, 7 and 9 would fail today on code that already exists. Rather than weaken the rule or rewrite the world, 5, 6 and 7 each carry an allowlist of grandfathered entries with a recorded ceiling:

The same shape appears for package size and for import fanout. There the rationale lives in the guard script's own header rather than in the list file: check-package-size.sh says the default answer to a violation "is still split the package", and that a recorded ceiling is "a ratchet to shrink or remove when the package is sub-split, never to raise silently". scripts/check-package-size.sh:3-5

Check 9 is the odd one out. Its grandfather file is a flat list of exempt paths with no ceiling column — a file is either baselined or it is not, and once baselined it is exempt outright rather than capped. scripts/log-printf-baseline.txt:1-4; scripts/check-no-log-printf.sh:20

Trap

When check 5 fails on your change, the tempting fix is to add your file to .loc-allowlist. That one is explicitly forbidden — "No new entries allowed. Split large files instead." .loc-allowlist:6 The package-size and fanout lists are not closed, but they are close: each takes a new or raised entry only with the reason written into the file itself, which means defending it in review. scripts/package-size-allow.txt:8-9; scripts/import-fanout-allow.txt:9-10 The other escapes are the per-line //nolint:norawexec and //nolint:nologprintf pragmas for checks 8 and 9 — type them exactly. scripts/check-no-raw-exec.sh:4,27; scripts/check-no-log-printf.sh:5,39

Check 12 also explains why your gate fails and CI's does not

The test step runs through scripts/with-clean-loom-env.sh, and AGENTS.md has a whole section on why. If you launch a shell from the Loom desktop app, you inherit variables — LOOM_WORKSPACE, LOOM_CONFIG_DIR, LOOM_FRONTEND_DIR, LOOM_NOTIFY_TOKEN and friends — that make tests resolve your real desktop workspace instead of their isolated fixtures. Makefile:622; AGENTS.md:44-61; scripts/with-clean-loom-env.sh:4-16 A local-only failure is very often this, not your code.

AGENTS.md documents a manual env -u … incantation, and it is not the same job: it also runs the gate under a throwaway HOME, so tests cannot reach real home-directory state. The script only unsets the thirteen LOOM_* variables. Prefer the script, and reach for the manual version when a failure survives the gate and you suspect your home directory. AGENTS.md:54-61; scripts/with-clean-loom-env.sh:4-18

Check yourself

From memory: name four of the eight custom Go guards (checks 4-11) and, for each, the convention it exists to enforce.

Any four of: control-plane paths (only the two legal runtime paths); LOC (≤1000 source, ≤2500 test); package size (≤25 non-test files per internal/ package); import fanout (≤18 module-internal imports per internal/ package, bar recorded ceilings); no raw exec (DI interfaces in unit tests); no log.Printf (use log/slog); no beads in prod; generated API staleness. (Coverage ≥60% is real but is check 13, outside the 4-11 range.)

Your new file is 1,100 lines and check 5 fails. What does the repo expect you to do?

  • Add the file and its ceiling to the .loc-allowlist ratchet
  • Add a per-line nolint pragma above the declarations that push it over
  • Split the file, because the allowlist takes no new entries at all
  • Raise the threshold argument the Makefile passes to the check script
The allowlist header is explicit: "No new entries allowed. Split large files instead." It is a record of existing debt, not a mechanism for adding more. The nolint pragmas are real but belong to checks 8 and 9, not this one. .loc-allowlist:6

make gate fails on your machine and passes in CI, with tests reading unexpected workspace state. Most likely cause?

  • Your coverage profile was corrupted by a concurrent gate run
  • Your shell inherited LOOM_* vars pointing at a real workspace
  • Your generated API code drifted from the source it derives from
  • Your package exceeded the module-internal import fanout ceiling
Inherited desktop/runtime env makes tests resolve the real workspace instead of isolated fixtures — which is why step 12 runs through with-clean-loom-env.sh. The first option is the sharp near-miss: it is also a real local-only failure, but it shows up as cover: line "..." doesn't match expected format, not as tests reading the wrong state.

You want to know whether an architectural invariant is really enforced. Where do you look first?

  • In scripts/, for a guard the gate runs against it
  • In docs/adr/, for the decision record that declares it
  • In AGENTS.md, which collects the operating rules
  • In docs/design/, for the document that specifies it
All three docs are worth reading, but only the guard scripts tell you what is enforced rather than intended — and you have already seen a doc in this repo cite a file that does not exist.

Make the gate teach you

  1. Open scripts/check-import-fanout.sh. The gate passes it 18, but the script's own default is 10. Work out what that gap tells you about the repo's direction of travel. scripts/check-import-fanout.sh:10; Makefile:602
  2. Read scripts/import-fanout-allow.txt, then run the fanout check by hand at the stricter default: ./scripts/check-import-fanout.sh 10. Which packages fail? Note what the run cannot show you: a package with a recorded ceiling is measured against that ceiling, not against the number you pass, so the four most cross-cutting packages in the repo never appear no matter how low you go. Read those four in the allow file, pick one from either place, and form an opinion on whether it is genuinely cross-cutting or just overgrown. scripts/check-import-fanout.sh:58-60
  3. Do the same with ./scripts/check-package-size.sh 15, reading scripts/package-size-allow.txt alongside it for the same reason — the two biggest packages by file count are in that file, not in the run's output. Then compare against the package-size list you saw in Lesson 01 — do the biggest packages by line count match the biggest by file count? scripts/check-package-size.sh:60-62; scripts/package-size-allow.txt:10,15
  4. Time the static half of the gate, which only reads files: time ./scripts/check-loc.sh 1000 2500, time ./scripts/check-package-size.sh 25, time ./scripts/check-import-fanout.sh 18 — the last shells out to go list, so it is the slow one. That is the fast half of your feedback loop; step 12 adds a race suite with a 15-minute timeout on top. Makefile:598,600,602,622
Not in this checkout

Do not run make gate here. This is a shared course checkout holding other people's uncommitted work, and check-frontend depends on ensure-frontend-deps, which fires an npm install into internal/webui/frontend/ whenever the node_modules/.package-lock.json marker is missing or older than the lockfile — it is missing here. Step 12 then runs a 15-minute race suite in the same tree. Time the full gate later, in your own clone. Makefile:194-201,628,622

You succeeded when You can name at least one package that passes at 18 and fails at 10, name the four packages the fanout run can never report, and say in one sentence why the team set the ceiling above its own default. Steps 1-4 all exit without touching the tree, and step 4's three guards finish in seconds, not minutes. (The fanout guard is a ratchet: the shipped 18 is where the codebase is now, its own default of 10 is where it is going. Note that check-package-size.sh has no such gap — its default is 25, exactly what the gate passes — so step 3 is you inventing a stricter bar, not discovering one. scripts/check-package-size.sh:11; Makefile:600)
