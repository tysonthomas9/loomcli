Week 3 / Lesson 09 / Runtime

When a run dies

Lesson 08 got a task claimed. This one is about everything that happens when the agent holding it crashes, hangs, runs for four hours, or exits zero without finishing. By the end you can predict where the task lands.

Skill predict what happens to a task when its agent run fails Time 35 min Needs 08 Repos loomcli fleet-db

Why this exists

An LLM run is not a function call. It can wedge, loop, exhaust a context window, print nothing for an hour while thinking, or announce it is finished and then exit with the task still claimed. None of those are exceptional; all of them happen in a week of production. So the question the daemon has to answer is not "did it work" but "what is true about the task now" — and that answer can never come from the agent's prompt, because the failure modes that matter are exactly the ones where the agent stopped being able to tell you anything.

The one idea

The supervisor, not the agent, owns every state transition that matters. The agent produces text; the supervisor decides what that means for the task, the session record, and the retry budget. A run that dies mid-turn must not leave a task ambiguous — so the code buys unambiguity with ordering.

The exit sequence, and why its order is load-bearing

Everything in this lesson hangs off nineteen lines. After cmd.Wait() returns, the supervisor runs this — in this order, every time:

  1. supervisor.go:818 → classify.go:17 Classify. Reads the worktree .agent.lock before recovery deletes it. Branches, in order: a run-duration kill (from the stop reason); no task and exit 0 or a watchdog stop → NoWork; non-zero → classify the log tail; exit 0 with the fleet claim still held → IncompleteRun; otherwise clean success. classify.go:45-66
  2. supervisor.go:825 → quarantine.go:136 Ledger the kill, with the factual exit code. This is the only point where the classified error, the lock file, and the fleet session id are all still observable together.
  3. supervisor.go:829 → session_finalize.go:241 Completion hooks. The supervisor performs the agent's issue writes. A failure here rewrites exitCode for everything below it.
  4. supervisor.go:830-831 Finalize and checkpoint. The session record lands on disk and in fleet-db; a non-zero exit (or an IncompleteRun) saves a checkpoint of the worktree diff before recovery can touch it. classify.go:224-247
  5. supervisor.go:832 → internal/cli/agent/recover.go:186 Post-mortem recovery. Kill survivors, release the fleet issue lock, and — on a non-zero exit — reset the task to open. That reset is conditional: resetTask reads the current status first and refuses to stomp review, closed, or a quarantined blocked. internal/cli/agent/recover_helpers.go:149-165
  6. supervisor.go:835 → quarantine.go:319 Sweep quarantine, deliberately last: recovery has just put the task back to open, so the quarantine write is a legal open→blocked transition rather than a fight with in_progress.

There is no transaction against the issue store. Sequence is the crash-safety mechanism, and each of those comments is a bug that was paid for once.

Counting is per-cycle and persistent: recordResumeOutcome runs after every supervised run, clears ResumeFailures on a clean exit and advances it otherwise, and ignores cycles that were not recoveries at all. resume_recovery.go:120-131

The resume TTL defaults to 30 minutes (LOOM_RESUME_TTL overrides it) — a carried backend session older than that is not worth resuming. internal/cli/agent/daemon_resume.go:12-27
Trap — "recovery" sounds like it recovers things

The cold branch calls s.recoverAgent(ap, 0, false), and that false is the destructive flag. Inside RecoverWorktree, the final step is cleanUntrackedFiles(worktreePath, true), whose own comment says it excludes only cli.ProtectedRuntimePaths, so "everything the turn produced but had not committed yet — new files, scratch notes, generated fixtures — is exactly what it deletes."

That is correct for a crash you are abandoning and catastrophic for a run you meant to continue, which is precisely why incomplete is an explicit argument rather than a read of the last classification. supervisor.go:440-448, internal/cli/agent/recover.go:250-260

Tier two: the policy table decides, the supervisor counts

Classification produces an agenterr.Outcome — a single value that is either a harness error class (AuthFailure, RateLimited, Timeout, ContextOverflow, …) or a loom domain outcome (NoWork, LockConflict, SpawnFailure, BackendUnavailable, CompletionHookFailure, IncompleteRun). Exactly one side is meaningful, and that value is the key into one table. internal/agenterr/outcome.go:12-20, 41-53

The Disposition the table returns carries more than a verdict: a backoff bucket (not a duration), whether to honour the harness's Retry-After hint, what a counted retry becomes OnExhaustion, and a BlockBudget — the number of block cycles without progress before an agent escalates to FastFail. internal/agentpolicy/policy.go:62-76

The split, stated in both files

The package doc says the layers "keep their own attempt counters and configured backoff values; they consult this table only for the verdict + the backoff bucket to use" internal/agentpolicy/policy.go:1-7. The supervisor's side says the same thing from the other end: "The table owns the per-class verdict; this layer owns its counters (RestartCount/RateRetryCount/NoWorkCount/BlockCount) and its configured budgets." internal/cli/daemon/supervisor/restart.go:30-34

So shouldRestart reads as a switch over agentpolicy.Decide(outcome).Decision with one apply-function per arm, and the arithmetic lives entirely on the supervisor side — applyCountedRestart increments RestartCount, compares it to the configured max_retries, and only then consults d.OnExhaustion and d.BlockBudget. restart.go:35-93, 168-198

Trap — shouldRestart returning true does not mean healthy

A blocked agent returns true: applyMaxRetriesBlock resets RestartCount, increments BlockCount, sets StopReasonMaxRetriesBlocked, and lets the goroutine keep retrying on a fixed 60-second interval rather than being abandoned. False is the loaded direction too: StopFatal, FastFail (a spent BlockBudget included), an exhausted Failover, the max_retries == 0 opt-out, a counted class whose OnExhaustion is neither Block nor FastFail — and stopAfterEphemeralTask, the one case where false means an ephemeral agent finished its single task cleanly. Read StopReason, not the boolean. restart.go:22-28, 41-43, 98-108, 183-198, 201-219

One worked example, because it is the one people get wrong. IncompleteRun — exit 0, claim never released — is a counted retry, while NoWork is uncounted. The table explains itself: "an agent that keeps handing back unfinished turns without ever signaling completion is the exact spiral max_retries exists to catch, and the clean-success reset would otherwise zero the budget every cycle." internal/agentpolicy/policy.go:159-169

Tier three: three ceilings, each blind to what the others catch

Nothing in the two tiers above bounds a run that never exits. Three separate mechanisms do, and none of them subsumes another.

The silence watchdog takes the freshest of three liveness signals — the live PTY heartbeat delivered over agent IPC, the session transcript's mtime, and the stdout log's mtime — and kills if the newest is older than output_timeout. Tier 0 exists because the interactive RunTurn path updates neither file, so a busy agent would look silent. health.go:143-157

But silence is only evidence of a hang when nobody asked the agent to be quiet. A harness parked on a dialog emits no output by design, so applyIdleKill suspends itself while an interactive request is outstanding. The signal is a counter, not a flag — with a boolean, the first answer in a multi-question dialog would clear the suspension underneath a still waiting agent — and the suspension carries its own 15-minute bound anchored to the 0→1 transition, so a harness that re-prompts on a timer cannot hold the watchdog off one question at a time. input_wait.go:21-44, 109-115, 146-161

The run-duration cap exists because of that suspension. Its comment is explicit that the asymmetry is the point: applyIdleKill suspends during a wait, "so during a wait this cap is the only bound left standing over the run; suspending it too would rebuild, one layer up, exactly the open-ended hold-off that inputWaitMax exists to prevent." health.go:267-275 It lives in the supervisor rather than the child's context on the same logic — "a wedged agent is precisely the one that may never observe its own cancellation." run_duration.go:25-29

Trap — why a four-hour kill gets its own StopReason

It would be tidy to fold the duration kill into StopReasonWatchdog. It is also wrong, and classifyAgentExit shows why: a watchdog stop with no claimed task lands in the NoWork arm, and NoWork's disposition is an uncounted retry on a fixed poll interval. The cap would then fire every four hours forever and change nothing. So StopReasonRunDurationExceeded is checked first, before every exit-shaped branch, and classified as Timeout — counted, on the timeout backoff, and quarantine-eligible. classify.go:42-48, 86-119, types.go:102-112

Task quarantine catches what neither run-scoped ceiling can see: a backend that silently stalls, gets killed, has its task reset to open by recovery, and is immediately re-picked by a sibling — an infinite boomerang in which every individual run looks like an ordinary timeout. The ledger counts consecutive quarantine-eligible kills per task, across agents, and evicts the record the moment the task shows progress (a clean exit, a new commit, or a changed design/notes hash). At the threshold, the sweep writes blocked + unassigned + the loom:quarantined label + a kill-timeline comment. quarantine.go:22-34, 152-173, 444-466

Eligibility is declared in the policy seat and counted here — the same split as BlockBudget. Domain outcomes are never eligible, on the grounds that they are coordination signals rather than task-fault; IncompleteRun is the instructive case, since it neither increments the ledger nor resets it. internal/agentpolicy/policy.go:119-141, quarantine.go:152-162

The on_complete pipeline, and the demotion

loomcli A clean, self-concluded, task-bearing run is the only shape that earns hooks — completionHookTarget refuses a non-zero exit, a classified error, a yield, and any stop reason meaning the turn was cut short. session_finalize.go:220-229, 404-438

The vocabulary is closed on purpose — agent definitions are remotely writable control-plane data, so "accepting an executable path or shell string would be daemon-host code execution." Seven actions: comment, write_design, add_label, remove_label, set_status, close, cycle. internal/domain/agent.go:42-46, 209-217 fleet-db mirrors the same seven in internal/models/agent.go:150-155; when you change one, change the other.

executeCompletionHooks runs them in stored order, stops at the first error, and re-validates the pipeline before executing it rather than silently reordering a definition written by an older peer. The rule it enforces is write before stamp: every body write (comment, write_design) precedes every stamp (add_label, remove_label, set_status, cycle), so a routing label is never observable without the artifact it certifies. session_finalize.go:441-455, internal/domain/agent.go:261-268

And then the part that makes this a lesson about failure:

The agent did everything right. One label write failed. The whole run is demoted, the task goes back on the queue, and the retry is bounded by the same policy table as any other failure — CompletionHookFailure is a counted retry escalating to a capped block, because a transient write error clears and a permanent one must stop rather than spin. internal/agentpolicy/policy.go:153-158

Trap — the events stream and the session status disagree, by design

The AgentStopped process event is emitted inside waitForAgent, carrying the factual exit code — which for a hook failure is 0. The demotion happens two calls later. So the event says the run succeeded and the session record says failed with class CompletionHookFailure, and both are correct. Debug hook failures via last_error_class, never via the event. spawn.go:516-518, session_finalize.go:238-240

Where failing closed would create an unbreakable loop, the code skips loudly instead: hooks configured with no issue backend at all log a warning and skip, because "no retry can conjure a backend: demoting would only reopen the task and loop until the agent's block budget is gone." session_finalize.go:412-421

Check yourself

From memory: name the three independent ceilings on a single run. For each, say what it is blind to, and say which one a pending human prompt suspends.

Silence watchdog — no liveness signal newer than output_timeout (default 900 s) across three tiers: IPC heartbeat, transcript mtime, log mtime. Blind to an agent that keeps producing output forever. This is the one a pending interactive prompt suspends, and the suspension is itself bounded at 15 minutes. health.go:143-157, 236-258

Run-duration cap — wall clock since spawn, default 4 hours. Deliberately not suspended by a pending prompt, because during a wait it is the only bound left standing. Blind to anything shorter than the cap. health.go:280-303, run_duration.go:46-61

Task quarantine — 3 consecutive no-progress kills of the same task, counted across agents, ending in blocked + unassigned + label + kill timeline. Blind to everything happening inside a single run; it only sees the pattern between them. quarantine.go:22-42, 444-466

An agent finishes cleanly, exits 0, and its configured add_label hook fails against the issue backend. What happens to the task?

  • The run stays successful and the label write is retried later
  • The run is demoted to a failure and the task returns to open
  • The run is demoted but the task keeps its in_progress status
  • The run stays successful and the failed hook is logged only
markCompletionHookFailure sets LastExitCode = -1 and class CompletionHookFailure before finalize, checkpoint and post-mortem recovery run — so recovery sees a non-zero exit and resets the task to open. The last option is the sharp near-miss: skipping loudly is exactly what happens when there is no issue backend at all, because no retry could fix that — but a failed write is retryable and therefore demotes. session_finalize.go:771-781, 412-421

Quarantine sets the task to blocked and unassigns it. What stops another agent from picking it straight back up?

  • The picker's ready query only ever returns status=open tasks
  • The loom:quarantined label is excluded from every ready query
  • The claim script rejects blocked as a non-claimable status
  • The supervisor holds the fleet-db issue lock until it expires
The interlock is the ready query, not the label and not the claim script. fleet-db's IsReadyEligible returns false for any status but open, and loomcli's ReadyOpts has no status field to widen it — every untargeted claim goes through Ready, so the picker never sees a blocked task. The third option is the sharp near-miss: from Lesson 08, claim_issue.lua lists open, blocked, deferred and review as claimable, which is exactly why the quarantine comment says a manual claim "works (blocked is claimable) -- it will re-quarantine after 3 fresh no-progress kills". Quarantine bars the automatic boomerang, not a human with a task id. fleet-db internal/storage/ready_eligible.go:35-38, internal/backend/types.go:290-302, quarantine.go:508-512, fleet-db internal/storage/lua/claim_issue.lua:44-46

A daemon agent crashed mid-task. The lock survives with a dead PID and a carried session id, and ResumeFailures is 1. What does the next supervise cycle do?

  • Cold-starts: destructive recovery, then claims a fresh task
  • Resumes: preserves the lock, the worktree, and the fleet claim
  • Checkpoints: re-claims the task after clearing the session id
  • Blocks: waits on a fixed interval for a human to release it
detectRecovery's switch checks the counter before the session id, and 1 is under maxResumeFailures (2), so this is a resume. The third option is the sharp near-miss: it is what happens at exactly two failures, and it deliberately clears the carried session id so the agent cold-starts from the saved checkpoint instead of arming --resume. resume_recovery.go:52-68, 91-104
