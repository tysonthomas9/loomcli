Shipping a vertical slice

One field, from a line of YAML to a rendered pixel. Every layer you met separately in weeks 2 to 4, in the order you will actually touch them, with the two gates that fail if you skip a step.

Skill take one field from OpenAPI schema to rendered pixel Time 40 min Needs 13, 14 Repos loomcli

Why one YAML

The Go server and the TypeScript app are two programs that have to agree on the shape of every JSON body they exchange. Loom does not solve that with discipline. It solves it with one hand-written file that generates a type file on each side: api/openapi.yaml produces a Go models file and a TypeScript types file, and a gate step per side refuses the build if either committed file has drifted from the YAML.

The one idea

Three files change together or the build fails: the spec, and the two generated files it produces. You never edit the generated two — you edit the spec and rerun both generators. Everything else in this lesson is just the order in which you touch the layers after that.

Our specimen is the smallest thing in the PR review screen: the additions count on one changed file. It is a number in a YAML schema, a Go struct field, a JSON key, a TypeScript property, and finally a green +3 next to a filename. Here is every hop it makes.

The trace

  1. api/openapi.yaml:4852-4865 The schema. PullRequestDiffFile declares five properties, all of them in required. This YAML is hand-maintained — nothing generates it, and it is the only place the field is decided.
  2. Makefile:426-432 make gen-go-api. scripts/openapi-to-30 downgrades the 3.1 spec to 3.0 (oapi-codegen v2.6.0 does not fully support 3.1), then oapi-codegen runs against api/oapi-codegen.yaml — generate: models: true, so types only, no server or client scaffolding.
  3. internal/backend/api/gen/types.gen.go:2619-2625 The Go struct. gen.PullRequestDiffFile, fields alphabetised by the generator, JSON tags taken from the property names. Line 3 of that file says DO NOT EDIT and means it.

  5. internal/webui/handlers/prreview/module.go:101 → handlers.go:59-105 The handler. GET …/pull-requests/{owner}/{repo}/{number}/diff resolves and authorises the PR, dispatches a PR read, then a compare read pinned to the head sha it just learned, and hands the response body to the mapper.
  6. internal/webui/handlers/prreview/handlers.go:254-266 Untyped map to generated struct. pullRequestDiffFileFromBody is the seam where the connector's map[string]any becomes the spec's type. This is the function you edit when you add a field.
  7. internal/webui/handlers/prreview/errors.go:17-27 The envelope. writeJSON wraps the payload as {"success":true,"data":…} — which the spec also declares, at api/openapi.yaml:2744-2751, so the generated TypeScript knows to expect it.
  8. internal/webui/frontend/package.json:35 npm run generate:types. openapi-typescript reads the same YAML — via the relative path ../../../api/openapi.yaml — writes src/types/generated/openapi.ts, then reformats it with prettier so the committed file is byte-comparable.
  9. internal/webui/frontend/src/types/generated/openapi.ts:2534-2540 The TypeScript type. Reachable as components["schemas"]["PullRequestDiffFile"]. This generated file sits at the bottom of the frontend DAG: it imports nothing.
  10. internal/webui/frontend/src/api/workspace/prReview.ts:5, 33-47 The api facade. One line aliases the generated schema into a usable name; the function calls api.GET with the literal spec path, throws on error, and strips the envelope with unwrapResponse. No hand-written URL, no hand-written shape.
  11. internal/webui/frontend/src/hooks/workspace/usePullRequestDiff.ts:25-59 The hook. Three pieces of state, one effect keyed on workspaceId/owner/repo/number/refreshKey, and a cancelled flag in the cleanup so a late response cannot write into an unmounted component.

  13. internal/webui/frontend/src/components/IssueDetailPanel/PRCompareDiffPane.tsx:139-163 Pixel. One button per file: a status badge, the path, and +{file.additions} rendered only when it is above zero. That span is where the YAML line ends up.
The screen this lands on is /ws/:workspaceId/prs → PRsPage → PRReviewWorkspace → PRCompareDiffPane (src/router.tsx:152-156, src/views/PRsPage.tsx:469, src/views/PRReviewWorkspace.tsx:544).

The three files that must agree

That produces gen.PullRequestDiffFile on the Go side and components["schemas"]["PullRequestDiffFile"] on the TypeScript side. A property listed in required becomes a plain field (Additions int, additions: number); one left out becomes a pointer with omitempty in Go and a ?: property in TypeScript — compare PullRequestReviewRequest.body, which is optional in the spec and arrives as Body *string at internal/backend/api/gen/types.gen.go:2629.

The pattern to copy: spec first, then outward

Every vertical slice in this repo goes in the same order, and the order is what keeps the two generated files honest:

  1. Edit api/openapi.yaml.
  2. make gen-go-api — regenerates internal/backend/api/gen/types.gen.go.
  3. npm run generate:types in internal/webui/frontend — regenerates src/types/generated/openapi.ts.
  4. Populate the field where the untyped upstream body becomes the generated struct — for this endpoint, pullRequestDiffFileFromBody.
  5. Surface it in the src/api/ facade (usually nothing to do: the facade returns the generated type, so a new property arrives for free).
  6. Render it in the component, and add a test at each layer you touched.

And the facade, which is the shape every typed call in src/api/ copies:

The path string is not a URL you invented — it is a key of the generated paths type, so a typo, a missing path parameter, or a renamed endpoint is a compile error rather than a 404 at runtime.

Trap — "I'll just add the field to the generated file"

Both generated files are readable, both are committed, and editing one directly appears to work: the Go compiles, the TypeScript typechecks, the app runs. Then the gate rejects it. Each generator has its own staleness check, and each one regenerates into a temp directory and diffs against what you committed: step 11 of thirteen on the Go side (Makefile:609-610 → scripts/check-go-api-staleness.sh, which prints FAIL: … is stale relative to api/openapi.yaml and Run: make gen-go-api) and step 5 of six on the frontend side (Makefile:637-638 → scripts/check-openapi-staleness.mjs, which prints Run: npm run generate:types). Both run under make check, which make gate is an alias for (Makefile:644, 668). There is no path where you edit a generated file and keep it.

Trap — regenerating types does not create data

The natural belief after a clean regeneration is that the field now flows. It does not: the types describe the contract, they do not populate it. On this endpoint the data crosses a connector boundary that rebuilds each file as a fixed five-key map, so anything you did not add there is gone before the handler ever sees it.

Its doc comment says so outright — "projects the /compare response's files[] array into a sanitized camelCase list (filename, status, additions, deletions, patch)" internal/connector/providers/github.go:377-380. Note also that it emits filename, not path: that is why the mapper at hop 6 has a fallback, and the fallback is the branch that actually fires.

Check yourself

make gen-go-api from the repo root writes internal/backend/api/gen/types.gen.go Makefile:426-432. npm run generate:types from internal/webui/frontend writes src/types/generated/openapi.ts internal/webui/frontend/package.json:35.

The gates are check-go step 11 (Makefile:609-610) and check-frontend step 5 (Makefile:637-638). Both regenerate into a temp directory and diff against the committed file, so "it compiles" tells you nothing about whether they will pass.

You add a property to a schema in api/openapi.yaml and regenerate the TypeScript types only. What fails?

  • Nothing; the Go gate only inspects hand-written source
  • Step 11 of check-go, the generated Go staleness check
  • Step 4 of check-go, the golangci-lint and depguard run
  • Step 5 of check-frontend, the generated TS staleness
The Go generator never ran, so the committed types.gen.go no longer matches the spec and step 11 diffs them apart. The last option is the near-miss worth remembering: that gate exists and is real, but you did regenerate the TypeScript side, so it is the one step that still passes. Makefile:609-610, 637-638

PRCompareDiffPane lives in src/components/ and imports from @/api/workspace. Why does the boundaries lint allow that?

  • The import is type-only, and type edges are legal everywhere
  • Components may import api as long as they import no store
  • The file sits in a barrel directory, which lint treats apart
  • An allowlist entry grandfathers this particular import path
Rule 2 of the DAG: type-only imports are allowed across every edge, because import type is erased and adds no runtime coupling — which is why consistent-type-imports is an error, so the escape hatch can be trusted. The last option is the sharp wrong answer: rule 4 says there is no allowlist at all. internal/webui/frontend/eslint.config.js:20-22, 33-41

You add previous_path to the schema, regenerate both sides, and map it in pullRequestDiffFileFromBody. It is always empty. Where did the value go?

  • unwrapResponse discards keys missing from the envelope type
  • compareFiles rebuilds each file as a fixed five-key map
  • openapi-typescript omits any property absent from required
  • The dispatcher strips fields outside the connector grant
The connector sanitises before the handler runs, so the key never reaches body. The first option is the plausible one and is wrong on the facts: unwrapResponse checks success and returns envelope.data as it stands — it filters nothing. internal/connector/providers/github.go:396-402; internal/webui/frontend/src/api/common/client.ts:295-321

Add one field, end to end, and make the gates prove it

Work in your own loomcli checkout on a scratch branch, not in the pinned course worktree. This exercise needs no podman stack and no dev server — do not start one. If you later want make dev, check lsof -nP -iTCP:3000 -sTCP:LISTEN first: Vite binds 3000 with strictPort: true (internal/webui/frontend/vite.config.ts:177-180) and another checkout may already own it.

  1. Prepare. cd internal/webui/frontend && npm install. A git worktree does not inherit node_modules; without it npm run check:generated reports openapi-typescript is not installed rather than anything about your spec (internal/webui/frontend/scripts/check-openapi-staleness.mjs:42-49).
  2. Edit the spec. In api/openapi.yaml:4852-4865, add a previous_path property of type: string to PullRequestDiffFile. Leave it out of required — GitHub only sends a previous filename for renames.
  3. Watch a gate catch you. From the repo root, run ./scripts/check-go-api-staleness.sh. Read the failure text and the command it tells you to run. Then run make gen-go-api and rerun the check until it prints OK: generated Go types match api/openapi.yaml.
  4. Predict, then look. Before opening the file, write down what shape your optional property took in Go. Now open internal/backend/api/gen/types.gen.go:2619 and check, using PullRequestReviewRequest.Body at line 2629 as the precedent.
  5. The other side. In internal/webui/frontend, run npm run check:generated (it fails as stale), then npm run generate:types, then rerun it. Open src/types/generated/openapi.ts:2534 and find your property.
  6. Populate it. Set the new field in pullRequestDiffFileFromBody (internal/webui/handlers/prreview/handlers.go:259-265) from body["previous_filename"]. Add "previous_filename" to the fake GitHub compare payload at internal/webui/handlers/prreview/handlers_test.go:117-132 and an assertion for it in TestGetPullRequestDiff (line 1089). Run go test ./internal/webui/handlers/prreview/ -run TestGetPullRequestDiff.
  7. It still fails. Find out why before reading further. When you have found it, add the key at internal/connector/providers/github.go:396-402 and rerun the test.
  8. Render it. In src/components/IssueDetailPanel/PRCompareDiffPane.tsx:154, show the previous path beside the file name when it is present. Extend the makeDiff fixture at src/components/IssueDetailPanel/__tests__/PRCompareDiffPane.test.tsx:19-40 and assert the rendered text, then run npx vitest run src/components/IssueDetailPanel/__tests__/PRCompareDiffPane.test.tsx. That file's first three lines are a @vitest-environment jsdom docblock — vitest's default environment is node (internal/webui/frontend/vite.config.ts:221), so without it you get document is not defined.
  9. Reaching back to Lesson 04: before you run anything else, list every numbered gate step your change touched — on both sides. Then run make check and compare your list against what it actually ran.
  10. Revert your scratch branch when you are done.
You succeeded when ./scripts/check-go-api-staleness.sh prints OK: generated Go types match api/openapi.yaml, npm run check:generated prints its up-to-date line, go test ./internal/webui/handlers/prreview/ -run TestGetPullRequestDiff passes with your new assertion, and your vitest run asserts the previous path appears in the rendered file row — and you can name, without looking, the one file outside the spec-and-generators chain that had to change before any of the data arrived.
