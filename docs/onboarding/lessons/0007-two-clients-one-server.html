Week 2 / Lesson 07 / Control plane

Two clients, one server

loomcli talks to fleet-db through two entirely separate client stacks with two different error models. Knowing which one you are in is the difference between a five-minute change and an afternoon of confusion.

Skill pick the right client stack and error model Time 30 min Needs 06 Repos loomcli

loomcli is a client, not a store

You established this in Lesson 05: workspaces, repos, roles, agent definitions, daemon profiles, issues, sessions, leases, drivers, skills — all rows in fleet-db, reached over HTTP/JSON.

It was not always so. A migration commit — 4d37ff8cb, "migration(fleet-db): clean architecture, no yaml config" — moved the config-file half of that list out of YAML and into fleet-db as first-class entities: workspaces, repos, agents, roles, daemon profiles. Sessions, leases, drivers and skills arrived later, as further sub-stores of store.Store internal/store/store.go:21-56. Most of the architectural oddities in this area are scars from that migration, including the fossil YAML tags from Lesson 05. When something here looks strange, "it used to be a config file" is a good first hypothesis.

Local and cloud are the same code

The one idea

Local mode and cloud mode are not different storage engines. They differ only in where fleet-db is running. Local runs the fleet-db binary as a child process on a loopback port internal/bootstrap/embedded.go:360,373 — or, when a healthy one already owns this data directory, reuses it instead of spawning a second internal/bootstrap/openstore.go:124-126,145-160. That subprocess is backed by default by a miniredis running inside loom's own process, snapshotting to <dataDir>/fleet-db/redis-snapshot.json; local settings can point it at an external Redis instead internal/bootstrap/embedded.go:339-357, internal/localsettings/settings.go:48-55. Cloud points the identical HTTP client at a URL. The switch is one env var, read by one function internal/bootstrap/mode.go:51-59, and OpenStore builds the same fleetdb.Config either way — only the base URL differs internal/bootstrap/openstore.go:94-119.

That is why local-mode reproductions are trustworthy, and why "does this work in cloud mode?" is usually not an interesting question about your change. The store client is the part that does not branch. A handful of call sites outside bootstrap still do, for non-storage reasons — loom doctor's fleet-db check internal/cli/doctor/doctor_fleetdb.go:120, and the per-workspace issue backend, which caches one backend per workspace in cloud and degenerates to the global backend in local internal/cli/issue_backend_workspace.go:28-34. Neither threads a Mode through; each re-derives it at the call site.

The split that actually matters

Here is what nobody tells you on day one. There are two client stacks against fleet-db:

internal/infra/fleetdbinternal/backend/fleet
Implements store.Store internal/infra/fleetdb/client.go:169 backend.IssueBackend internal/backend/fleet/fleet.go:43
Owns Control-plane entities: workspaces, repos, agents, nodes, sessions, leases, drivers, skills internal/store/store.go:21-56 Issue tracking: issues, comments, dependencies, labels, mutations internal/backend/issuebackend.go:19-182
Errors map to domain.Err* sentinels — compare with errors.Is internal/domain/errors.go:16-50 *backend.BackendError kinds internal/backend/errors.go:20-34
You reach it via cmdstore.WithActiveWorkspace → h.Store internal/cli/cmdstore/cmdstore.go:124-131 The issue backend on the command's deps internal/cli/deps.go:73

They talk to the same fleet-db server and share request plumbing through internal/fleethttp. But they deliberately do not share error classification — the package doc says so in as many words, and lists exactly what is shared (header construction, body marshaling, error-message extraction) and what is not (status→sentinel mapping) internal/fleethttp/fleethttp.go:1-14. That is the trap:

Trap

Code that reaches for domain.ErrNotFound after an issue operation will never match, and vice versa. The two stacks are parallel, not layered — neither wraps the other. Before writing an error branch, check which stack produced the error. This maps directly onto the object model from Lesson 05: control-plane objects hang off Workspace, and issues live on a different axis. Two axes, two clients, two error models.

The boundary is machine-enforced

The "only two control-plane paths" rule from Lesson 01 is not aspirational. scripts/check-control-plane-paths.sh runs inside make check — step 4 of 13, via check-go Makefile:594-596 — and fails the build on five things:

  1. check-control-plane-paths.sh:36-53 Any non-test file under cmd/ or internal/ that imports the test-only in-memory store internal/infra/memstore.
  2. check-control-plane-paths.sh:55-71 Any non-test file that imports internal/infra/fleetdb — with exactly two exemptions: internal/bootstrap/openstore.go, and the package itself.
  3. check-control-plane-paths.sh:73-98 Any call to fleetdb.New( in a non-test file under cmd/ or internal/, outside internal/bootstrap/openstore.go.
  4. check-control-plane-paths.sh:100-110 Any ModeXxx identifier in internal/bootstrap/mode.go other than ModeLocal and ModeCloud. The enum is closed on purpose.
  5. check-control-plane-paths.sh:112-129 Six literal topology anchors that must all still appear in openstore.go — including case ModeLocal:, StartEmbedded(ctx, dataDir, logger) and fleetdb.New(cfg). Change the shape and the guard demands an explicit architecture decision.
Worth saying plainly

Exactly one non-test file is allowed to construct the fleet-db store client: internal/bootstrap/openstore.go scripts/check-control-plane-paths.sh:76-98. That is what keeps mode selection centralised, and it is why every command goes through the cmdstore wrapper instead of opening its own client. If you find yourself needing a client, you have taken a wrong turn several steps earlier. Tests are outside the rule and do build their own against an embedded server internal/bootstrap/embedded_smoke_test.go:33 — do not read those as precedent.

Two packages that are historical residue

You will find these and try to build a mental model around them. Do not:

  • internal/rpc — a client for a Unix-socket issue daemon that this repo no longer ships a server for (the only listenRPC is reached from a test internal/rpc/transport_unix.go:12), and that loom serve disables whenever a store is wired internal/cli/serve/serve.go:709, internal/webui/app/server.go:175. Note the shape: the types are still compiled into live code — ListIssues, ListKanban and cross-workspace MoveIssue have not been migrated off the pool internal/webui/service/issue_impl.go:54-57 — but there is no daemon on the other end of the socket.
  • internal/kv — direct Redis. Its one runtime use is the multi-node stale detector under --fleet-mode internal/cli/serve/daemonwire/stale.go:17-33, gated at internal/cli/serve/serve.go:217; the rest is diagnostics — loom doctor internal/cli/doctor/doctor_checks_redis.go:23 and loom workspace status internal/cli/workspace/status.go:249. Never for control-plane data.
This is a recurring shape in this codebase: something that looks central, is well written, and is no longer on any live path. Lesson 05 met another one in the type entity.Agent internal/entity/agent.go:42-66 — and note that it is the type that is dead, not the internal/entity package, which still carries entity.Issue, entity.Comment and entity.Dependency through the whole issue path. Check for callers before you build on something, and check at the right granularity.

Check yourself

From memory: name the two client stacks, what each owns, and the error type each produces.

internal/infra/fleetdb implements store.Store for control-plane entities (workspaces, repos, agents, nodes, sessions, leases, drivers, skills) and maps failures onto domain.Err* sentinels.

internal/backend/fleet implements backend.IssueBackend for issue tracking (issues, comments, dependencies, labels, mutations) and produces *backend.BackendError kinds.

Same server, shared plumbing via internal/fleethttp, deliberately separate error classification.

You need a fleet-db store client inside a new web UI service. How do you get one?

  • Import internal/infra/fleetdb and call its constructor
  • Copy the construction code from openstore.go into your service
  • Add your file to the guard script's exclusion glob list first
  • You do not — take the store handle bootstrap already gives you
Exactly one non-test file may construct the client, and the guard fails the build on the other three approaches — rule 3 filters on the file name, so widening rule 2's glob does not help. Needing a client is a signal you took a wrong turn upstream; the handle is passed down to you. scripts/check-control-plane-paths.sh:55-98

An issue-fetch fails. Your code checks errors.Is(err, domain.ErrNotFound) and never matches. Why?

  • Issue reads bypass classification and return the raw HTTP error
  • Issues come from the other client stack with its own error type
  • The sentinel is only set for writes, never for read operations
  • The embedded fleet-db returns a different status code in local mode
Issues are served by internal/backend/fleet, which produces *backend.BackendError kinds internal/backend/errors.go:20-34. The domain.Err* sentinels belong to the control-plane store stack internal/domain/errors.go:16-50. The two are parallel and neither wraps the other — the shared plumbing deliberately stops short of classification internal/fleethttp/fleethttp.go:11-14.

What is the difference between local mode and cloud mode, from the store client's point of view?

  • Only where fleet-db runs — the store client code is the same
  • Local uses an embedded store; cloud uses the HTTP client stack
  • Local talks to fleet-db over gRPC; cloud talks to it over HTTP
  • Local skips auth headers; cloud adds the API key and actor quad
One env var, read by DetectMode, decides whether fleet-db is a child process or a URL; OpenStore then builds the same fleetdb.Config either way and only swaps the base URL — which is exactly why a local reproduction is worth something. internal/bootstrap/openstore.go:94-119
Read-only — and it has to be

The obvious way to learn this guard is to plant a violation and watch it fire. Do not. This checkout is shared with other people and other agents and usually carries uncommitted work; "edit it, then revert" is how somebody else's afternoon disappears. Every step below reads the repo or runs a copy of the script outside it. Nothing under either checkout changes.

Try to break the boundary

  1. The guard is ripgrep, so you can run its rules by hand. Rule 2, verbatim: rg -n 'github\.com/tysonthomas9/loomcli/internal/infra/fleetdb' cmd internal --glob '*.go' --glob '!**/*_test.go' --glob '!internal/bootstrap/openstore.go' --glob '!internal/infra/fleetdb/**'. No output — that is what passing looks like. Now drop the last two globs and re-run. Exactly one file comes back: that is the only exemption that matches anything, and you have just read it off the tree instead of the script.
  2. Now rule 3: rg -n 'fleetdb\.New\(' cmd internal --glob '*.go' --glob '!**/*_test.go'. Four hits, all in one file. Drop '!**/*_test.go' and count what comes back — that is the boundary the guard actually draws, and it is narrower than "one file in the repository".
  3. Want to see it fail? Copy, never edit. In a throwaway directory outside both repos, make scripts/, cmd/ and internal/bootstrap/; copy in check-control-plane-paths.sh, openstore.go and mode.go; write a stub Go file under internal/probe/ whose only content is a blank import of the fleetdb path; run the copied script. It prints the real rule-2 failure and exits 1. Then delete your throwaway directory.
  4. Find one caller of each client stack in the wild. For each, note the error type it branches on. Are there any files that touch both?
  5. Reaching back to Lesson 04: this guard is check 4 of 13. Name two other guards from that lesson that, like this one, encode an architectural rule rather than a style rule.
You succeeded when Rule 2 returns nothing on the real tree, rule 3 returns four non-test hits and more than that with tests included, your throwaway copy fails with fleet-db store client imported outside internal/bootstrap/openstore.go, and you can name a file that uses each stack. If you found a file touching both, read it carefully — that is where the two error models meet, and it is the most interesting code in this domain.
