Week 4 / Lesson 12 / Web layer

How serve is put together

There is no framework here. loom serve is a composition root: a config struct, a pile of nil checks, and two muxes. Learn its four-file shape and you can add an endpoint without asking anyone where things go.

Skill add an API endpoint that follows the module and service layering Time 30 min Needs Lesson 06 Repos loomcli

Why this exists

The web layer has no DI container and no init()-registered route table; the single use of reflection is normalizePool (internal/webui/handlermux/handlermux.go:47-59), which turns a typed-nil daemon.Pool into a real nil so the handlers' pool == nil checks fire. Everything the server can do is decided by one struct — webui.ServerConfig — which the CLI fills in and hands to NewServer. Optional features are literally if x != nil. internal/webui/server_config.go:47-48

The consequence is the thing you have to internalise: the wiring is the documentation. A route exists because some line of Go appended a module to a slice, and that line usually sits behind a condition. You cannot answer "is this endpoint mounted?" from a doc. You answer it by reading three short files.

The one idea

A route is one line — a pattern mapped to a handler — inside some module's Register. The handler is a closure over a service interface and does nothing but translate HTTP. So adding an endpoint is always the same four edits, in the same order, and finding one is always the same move: grep the URL path string, never the package name.

Hop 5 is why your curl localhost:8080 can hit a different serve process than the one you just started. The port the server actually took is in its server listening log line (internal/webui/app/server.go:298).

The three shapes to copy

1. A module is pattern lines and nothing else

A module is a struct of dependencies, a New…Module constructor, and a Register that contains only registrations plus nil guards. If you find yourself writing an if about request data inside Register, you are in the wrong file.

The registration protocol is a single-method interface, and deliberately a type alias rather than a defined type, so the facade packages' []interface{ Register(*http.ServeMux) } return values stay assignable to []wsModule (internal/webui/modbuilder/modbuilder.go:48, 78) — with a defined type, append(app.wsModules, modbuilder.NewIssueModules(…)...) would not compile:

2. A handler is a closure over a service

The dominant signature is func HandleX(svc service.T) http.HandlerFunc — 80 of the 124 exported handler constructors under internal/webui/handlers have exactly that shape, and ten more take a service plus a hub or store. The other 34 take no service at all and close over a pool, a hub or a cache instead — among them HandleBlockedWithBackend and HandleStatsWithBackend, the two handlers behind the grep trap below. Write new ones in the service shape. internal/webui/handlers/git/graph.go:140, internal/webui/handlers/health/health.go:225

The body does four things: read the workspace and path values, decode with handler.ReadJSON, call one service method, write with handler.WriteJSON or handler.HandleServiceError.

Note middleware.WorkspaceFromContext, not r.PathValue("ws"). The {ws} in the URL may be a name; the middleware resolves it and the context holds the canonical value.

3. Services return kinds, handlers return status codes

A service never mentions HTTP. It returns a *service.ServiceError carrying an ErrorKind, and the handler layer owns the one table that turns kinds into statuses.

Sixteen kinds, one map. KindUnavailable and KindStarting both become 503; KindValidation becomes 400. Constructors are service.ErrNotFound, service.ErrUnavailable, and friends — the "no Redis" guard at internal/webui/terminal/service_tabs.go:21-24 is the pattern to copy for a missing dependency. internal/webui/server/handler/errors.go:13-30

The two muxes

There is the outer mux (app.mux, the one the middleware chain wraps) and the nested workspace mux (wsMux, mounted once at /api/workspaces/{ws}/). Nearly every workspace-scoped route belongs on the nested one. Four routes are the deliberate exception — three PATCH plus the GET …/config/backend that rides along with them (internal/webui/app/routes.go:155), which is the duplicate the trap below is about. Trap — the same pattern on both muxes does not panic

You know Go 1.22 panics on duplicate ServeMux patterns, so you assume a clash would be loud. Duplicate detection is per-mux. Two ServeMux values share no registration table, so registering the same pattern on the outer mux and on wsMux is silently fine — and the outer registration wins, because an exact pattern beats the /api/workspaces/{ws}/ subtree mount. Your nested route becomes dead code that every test on the module still passes.

This is not hypothetical: GET /api/workspaces/{ws}/config/backend is registered twice — internal/webui/app/routes.go:155 and internal/webui/handlermux/handlermux.go:98. Only the first one ever serves a request.

The codebase avoids the same-mux version of this by making the two registrations of GET …/agents/{name}/queue mutually exclusive: agentQueueH is only built when the server is not store-backed (server_modules.go:32), and agents.NewModule is only appended when it is (server_modules.go:129-131). Break that condition and you get a startup panic, not a silent override.

Trap — the depguard rule is narrower than its name

The handler-layer-isolation rule in .golangci.yml denies internal/store, internal/webui/store, internal/backend, internal/notify and internal/webui/daemon, each with the message "use the service layer (internal/webui/service)". It is easy to read that as "the gate stops me reaching past the service layer from a handler". It does not.

Its file glob is "**/handler/**" (.golangci.yml:62-66), and handler is a literal path segment: find . -type d -name handler returns exactly one directory, internal/webui/server/handler — the shared request/response plumbing. The domain packages under internal/webui/handlers/ are not matched, which is why internal/webui/handlers/health imports internal/backend and golangci-lint run --enable-only depguard reports 0 issues for it. The layering is a convention your reviewer enforces; the gate only backstops one package.

Trap — grep the path, not the package

You want the code behind GET /api/workspaces/{ws}/blocked, so you open internal/webui/handlers/issues/. It is not there. That route is registered by WorkspaceOpsModule in internal/webui/handlermux/handlermux.go:92 and served by githandlers.HandleBlockedWithBackend — a blocked-issues query living in the git handler package. Its neighbours are just as scattered: …/stats goes to healthhandlers, …/ready to issues, …/issues/graph back to githandlers.

Package names predict nothing here. The URL string is the only reliable index, and it appears verbatim in the source, so grep -rn 'workspaces/{ws}/blocked' --include='*.go' internal/ is a one-hit search.

The recipe

To add GET /api/workspaces/{ws}/terminal/tabs/summary, in order:

  1. Interface. Add the method to the service interface — internal/webui/service/terminal.go:15 — and any result struct beside PatchTabResult (terminal.go:36-39).
  2. Implementation. Implement it in internal/webui/terminal/service_tabs.go, guarding a missing dependency with service.ErrUnavailable(…) exactly as ListTabs does at line 22.
  3. Handler. Add the closure to internal/webui/handlers/terminal/tabs.go, reading the workspace from context and writing through handler.WriteJSON / handler.HandleServiceError.
  4. Route. One line in tab_module.go's Register.
  5. Fakes and tests. Every test double implementing TerminalService needs the new method, then a route-registration test and a handler test.

The route test is the cheap one people skip. It asserts a pattern is registered at all and with the right method, by checking the two codes a mux produces on its own:

For a whole-server test, setupTestRoutes(t, app) runs buildHandlers, buildModules and registerRoutes against a real mux — the same three calls as hop 6. internal/webui/app/routes_test.go:34-50

Check yourself

From memory: name the four files you edit, in order, to add a workspace-scoped GET endpoint — and say what a Register method is allowed to contain.

The service interface (internal/webui/service/terminal.go:15), the implementation that returns service.ServiceError kinds (internal/webui/terminal/service_tabs.go:21-24), the handler closure over that interface (internal/webui/handlers/terminal/tabs.go:24-39), and one pattern line in the module's Register (internal/webui/handlers/terminal/tab_module.go:27).

Register may contain only pattern-to-handler lines and nil guards on its dependencies — see internal/webui/handlers/agents/module.go:20-23, where a nil service returns early and silently omits the whole route family rather than panicking.

You register a pattern in a module's Register, and the same pattern is already registered on the outer mux in routes.go. What happens?

  • The server panics on the duplicate pattern while registering routes
  • Neither route matches and requests fall through to the JSON 404
  • No panic: the outer registration wins and yours is never reached
  • Both handlers run in registration order and the last one responds
Go 1.22 duplicate detection is per-mux, and the two registrations live on different ServeMux values, so there is nothing to conflict; the exact outer pattern then beats the /api/workspaces/{ws}/ subtree mount. The panic option is the near-miss worth remembering — a duplicate on the same mux does panic, which is why the two …/agents/{name}/queue registrations are made mutually exclusive. internal/webui/app/routes.go:155 and internal/webui/handlermux/handlermux.go:98

  • A method on the internal/webui/service interface it closes over
