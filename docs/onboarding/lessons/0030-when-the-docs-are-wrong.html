Week 6 / Lesson 30 / Judgement

When the docs are wrong

Thirteen claims in these repos' own documentation are false at the commit you are reading. This lesson is the four-step procedure that finds the fourteenth, and the list of the thirteen so you do not lose an afternoon to one of them.

Skill verify a documentation claim against the code before you act on it Time 25 min Needs 01, 02, 04 Repos loomcli fleet-db

Why this exists

Lesson 01 told you that a doc in this repo is not automatically true, and gave you one example. That was a warning. This is the method, and the reason the warning generalises.

Look at where this team spends its enforcement budget. There are fourteen scripts/check-*.sh files in loomcli. Not one of them reads a document. They check line counts, package size, import fan-out, raw exec.Command, log.Printf, control-plane paths, coverage — and one of them, check-go-api-staleness.sh, regenerates internal/backend/api/gen/types.gen.go from api/openapi.yaml into a temp file and fails the build if the two differ (scripts/check-go-api-staleness.sh:31-56). That is gate step 11 of 13 (Makefile:609-610).

So one machine-readable description of the API cannot drift, by construction. The 4,188-line prose description of the same API in docs/api.md can drift as far as it likes, and has. This is not carelessness; it is the predictable shape of a codebase where the gate is the spec (Lesson 04). A guarded claim stays true. An unguarded claim is exactly as old as the last person who cared about it.

The same asymmetry holds on the frontend side: npm run check:generated is frontend gate step 5 (Makefile:637-638) and pins the TypeScript types to the same spec. Generated artifacts are the safest text in the repo.
The one idea

A document records what somebody believed on the day they wrote it. The only text the machine ever read is a function body. Before you act on a documented claim, name the function that decides it — and if you cannot name it, you have not checked anything yet.

The procedure

Four steps, in this order. It costs about ten minutes and it is the difference between "the README says" and "I checked".

  1. Name the deciding function, not the package. Turn the claim into a grep -rn "func Name" that returns one hit. If the claim does not reduce to a function you can grep for, it is too vague to be true or false, and you should be suspicious of it for that reason alone.
  2. Read the body, not the doc comment. A comment is a doc that happens to live in a .go file. It drifts the same way — see the first trap below.
  3. Ask which process runs that function. This is the step people skip, and it is where most "wrong" docs turn out to be right about somewhere else. loomcli has a CLI, a server, a daemon and a task runner in one binary; the same English sentence can be true in one and false in the others.
  4. Ask whether a guard would have caught the drift. ls scripts/check-*.sh, .golangci.yml, an AST test like the SSE seam test from Lesson 13, or a plain unit test. If a guard exists, the code is trustworthy and the doc is the bug. If none exists, neither text is evidence and you go read the code.

Then file the finding. Every conflict in the table below is a small, self-contained, verifiable issue — which makes it good practice for the workflow as well as a genuine repair.

Trap — proximity is not accuracy

The instinct is that text nearer the code is safer. Sometimes; not reliably. internal/cli/root.go:46 is a Go string literal, compiled into the binary, printed by loom --help — and it advertises loom task create --title="Add login feature", a subcommand that has never existed (internal/cli/agent/task.go:27-28). src/router.tsx:4-20 is a route-tree comment roughly a hundred lines above the routes it describes, in the same file, and it is missing four of them. Nothing compiles a comment. Distance from the code is not the variable — whether a check reads it is.

Trap — length is not existence

docs/api.md:4063-4130 documents POST /api/csp-report with an auth model, two accepted content types, a per-IP rate limit, a 10 KB body cap, a 415 response, and its exclusion from the global limiter. Sixty-eight lines of confident specificity. grep -rn "csp-report" internal/ cmd/ api/ returns nothing, and the entire CSP header is one fmt.Sprintf you can read in fifteen seconds (internal/webui/server/middleware/security.go:34-35) — there is no report-uri in it. Detail is evidence of care at writing time. It says nothing about read time.

The honest counterweight

Do not walk out of this lesson believing the team writes bad docs. The distribution is sharper and more useful than that.

In the very conflict traced above, serve's own Long text is correct where the README is wrong: "The frontend is served externally (reverse proxy, CDN, Vite preview, etc.)" (internal/cli/serve/serve.go:104-108). Somebody who changed that behaviour updated the text they had to touch to ship the change, and did not go looking for the README. That is the whole mechanism. The ADR you read in Lesson 13 is accurate for the same reason: it was written as part of the change it describes.

The other repo fleet-db

Run the same check on fleet-db's AGENTS.md:19-35 and every one of its fifteen named paths resolves — four agent docs, the prompts/ directory, loom.yaml, three role prompts, harness/policy.yaml, scripts/harness/, two contracts, docs/architecture.md, docs/glossary.md. The one document that moved left a tombstone: ARCHITECTURE.md is thirteen lines that say it is retired, name its replacement, say where the history went, and close with "Do not add content to this file" (ARCHITECTURE.md:1-13) — and AGENTS.md:36 lists it as "Retired pointer (do not use)". These two trees are pinned a day apart. The difference is not diligence; it is that this list is the file agents are told to read first, so it gets exercised on every run.

Back in loomcli, the pattern that falls out of all thirteen rows is worth stating plainly, because it tells you what to trust on sight:

  • Generated from a checked artifact — types.gen.go, openapi.ts. Cannot drift; a gate step regenerates and diffs them.
  • Written as part of the change — ADRs, a command's Long text, the long Makefile comments. Usually right, and right about the thing they were written for.
  • Written once, for a reader — README.md, docs/api.md, top-of-file route comments. Strong evidence of intent, weak evidence of behaviour. This is where all thirteen rows live.

The "Where decisions live" table on the navigation card sorts some of the same sources (navigation.html:209-222), but by topic, and its six rows cover only the middle tier: no row for a generated artifact, and none for README.md or docs/api.md. The ranking by decay rate is the one above.

A README line and a command's own Long help text disagree about the same behaviour. Which do you trust?

  • The README, because it is the user-facing contract
  • The help text, since it ships inside the binary
  • Neither one — read the function that decides it
  • Whichever of the two was committed most recently
Both are prose and neither is checked. The help text happens to be right for serve (internal/cli/serve/serve.go:104-108) and wrong for the root command's loom task create --title=… (internal/cli/root.go:46), in the same binary. "It ships in the binary" is the tempting wrong answer: compilation checks the string's syntax, never its truth.

README.md:261 puts the workspace daemon profile in the backend resolution chain. What is actually the case?

  • No code anywhere reads a profile to choose a backend
  • Agent-spawning code reads it; your command never does
  • The CLI reads it after the flag and before the env
  • It was read once, and the field has since been dropped
ResolveBackendName is flag, env, codex — no profile (internal/cli/backend.go:84-94). But DaemonProfile.AgentBackend is alive and is read wherever an agent is spawned: resolveTaskRunnerBackend (internal/driver/task_bridge.go:754-772), ResolveLocalBackend (internal/runtimepreflight/preflight.go:50-67), and the daemon supervisor's GetEffectiveBackend (internal/cli/daemon/supervisor/backend.go:130-147).
