Week 5 / Lesson 18 / fleet-db

The event log is the truth

One Redis STREAM per workspace holds every mutation fleet-db has ever made. Almost everything else in Redis is a cache the server can rebuild from it — and the interesting engineering is in the keys that are not.

Skill classify any fleet-db key as authoritative or derived, and name what rebuilds it Time 35 min Needs 05, 08 Repos fleet-db

Why this exists

Every path in this file is in fleet-db except the four Makefile lines in the safety box, which are loomcli's. This is your first lesson inside fleet-db, and the whole repo turns on one decision, so learn the decision before any of the structure.

fleet-db could have been an ordinary Redis-backed tracker: HSET the issue, then fix up whichever indexes mention it. It is not. Every mutation is appended to a stream first, and every queryable structure — issue hashes, the eight index families, the ready queue, the blocked set, comment lists, the full-text index — is a projection written afterwards by a handler reading that event. The service layer never writes an issue hash. It cannot: not one of the ports it is constructed from has a method that would let it.

You already know why an event log is nice in the abstract. What you need is narrower and far more useful in an incident: given a key, is it truth or is it a cache? Wrong in one direction, you delete real data. Wrong in the other, you spend an afternoon hand-repairing a set one API call would have rebuilt.

This is Lesson 05's question one level down. There, fleet-db was the single authoritative tier of three. Open it up and the same shape repeats inside: one authoritative thing, a lot of regenerable things around it.
The one idea

In the tracker core, exactly one key per workspace is durable truth: fleet-db:{ws}:events, a Redis STREAM (internal/storage/keys.go:906-912). Everything a projection handler writes is a function of that stream and can be thrown away. The keys worth knowing by name are the ones that are neither — written outside the log, and deleted anyway when the log is replayed.

The write path is three steps long

Every issue command — create, update, close, claim, defer, add a dependency, add a label, add a comment: 17 of the 43 actions — funnels through one function. Read it in full. The other first-class entities do not call it: repo, agent, role, skill, skill pack, workspace and daemon each repeat the same append-then-project pair inline in their own service (internal/service/repo_service.go:55-58 and six siblings).

Three facts fall straight out of that.

The append is the write. Once Append returns, the mutation happened. docs/architecture.md:839 states it as a durability rule: "Events are the source of truth. Once Append succeeds, the write is durable regardless of whether projection succeeds or fails."

Projection is best-effort. A failing ProjectEvent is retried once — unless the context is already done, in which case it is not retried at all, because a context failure fails again (internal/service/issue_service.go:84-93). Whichever branch runs, a failure that survives is logged at ERROR with severity=projection-lag and executeCommand still returns nil (issue_service.go:87-93, 100-110). The client gets its 201, the read model is briefly wrong, the background projector fixes it. A deliberate availability-over-consistency trade, not a bug.

The service has no read-model writer. NewIssueService takes six ports — StateReader, WorkspaceReader, Locker, WorkerRegistrar, storage.EventStore and EventProjector (internal/service/issue_service.go:50-59; service.go:65, 88, 95, 103, 109) — plus an optional seventh, SoftDuplicateStore (issue_service.go:36-39), wired only on the Redis backend (cmd/fleet-db/main.go:411-412). EventStore is the one carrying Append (internal/storage/storage.go:610) — the write this lesson is about. No method on any of the seven writes an issue hash directly; EventProjector reaches one only by projecting an event. StateReader is eighteen methods and not one writes an issue — though two of them, NextIssueID and NextCommentID, are INCRs hiding on a port named reader (service.go:82-83). The missing writer is the design; hop 2 of the trace is where the exception shows.

Three non-event writes got their own ports: the issue lock, worker registration, and the soft-duplicate guard — a plain SET on fleet-db:{ws}:softdup:{fingerprint} (storage/idempotency.go:161-162, keys.go:880-883). Locker's comment says why the first is separate — "Separated from StateReader because lock acquisition/release are write operations, not reads" (service.go:92-94). The lock and the worker records come back later in this lesson.

What an append actually does

One Lua script, two XADDs, one round trip:

KEYS[1] is the global workspace stream fleet-db:{ws}:events; KEYS[2] is the per-issue stream fleet-db:{ws}:events:issue:{id} (redis_eventstore.go:70-73, keys.go:909, 917). The second XADD reuses the first one's generated ID, so a cursor from one stream is meaningful in the other. Redis returns that ID and Append writes it back onto the in-memory event (redis_eventstore.go:78) — which is how the projector gets something to dedup on.

That ID is the EventID, "<ms>-<seq>" — the same value that reached your browser as an opaque SSE cursor in Lesson 13. GET /events/mutations rejects any ?since= that is not "0 or a stream ID like 1707001234567-0" (internal/api/mutations.go:93-97), and the c1. token is base64url of exactly that (internal/cursor/codec.go:13, 41-46). That opaque blob is a position in this stream.

The trace: one create, and who writes what

Every hop below is in fleet-db. Watch for the moment the request stops writing and starts appending.

  1. internal/api/issues.go:57 → :68 Route and decode. POST /api/v1/{workspace}/issues lands on createIssue, which builds a service.CreateIssueCmd (:94-114) and validates it before reserving an idempotency key (:116-122).
  2. internal/service/issue_service.go:157 → internal/storage/sequence.go:36-42 The ID is minted — a Redis write that is not an event. NextIssueID is an INCR on fleet-db:{ws}:seq:issues returning "FLEET-42". It happens before any event exists and nothing records it. Remember this hop.
  3. internal/service/issue_service.go:204-241 Build the issue, then the event. The models.Issue is assembled in memory and marshalled into the event's After field. For a create that is the full state; for an update it is only the changed fields (internal/models/event.go:441-444).
  4. internal/service/issue_service.go:80 → internal/storage/redis_eventstore.go:65-79 Append. The write is now durable. If the process died on the next line, this create would survive.
  5. internal/projection/projector.go:223-276 Inline projection. Find the handler for the action, take the per-workspace mutex, open a TxPipeline, run the handler, queue the cursor SET into the same pipeline (:269-271), exec. Read model and cursor commit together or not at all.
  6. internal/projection/handlers.go:68-143 The handler writes everything you can query. handleIssueCreate writes the issue HASH (:81), the status SET (:88), the priority ZSET (:95), the type, assignee, label, repo and parent indexes (:99-121), the deferred set (:125), the ready ZSET if storage.IsReadyEligible passes (:137-138), and the full-text index (:143). Handlers touch only a ProjectionContext, never a Redis client (internal/projection/writer.go:38-41).
  7. internal/service/issue_service.go:110 Return nil either way. Hops 5 and 6 could have failed twice over and this line still returns success, because hop 4 already made the write durable. The background projector catches up from fleet-db:{ws}:projector:cursor later.

The test that settles every classification

You do not have to reason about which keys are derived — the repo maintains the list, because disaster recovery needs it. FullReplay deletes all derived state, resets the cursor, and replays the global stream from the beginning (internal/recovery/service.go:86-168), and its delete step is a literal enumeration of everything this project considers a cache.

The two-question test

1. Does FlushDerivedState delete it? That list (redis_recovery_store.go:58-77) is the repo's own definition of "derived". 2. Does a registered projection handler write it? One map answers that — registerHandlers, internal/projection/handlers.go:15-63.

Deleted and handler-written → a cache; replay restores it. Kept and handler-written → replay rewrites it without clearing it first. Kept and not handler-written → authoritative, or outside the log's scope. Deleted and not handler-written → the dangerous quadrant, and the reason for this lesson.

Trap — "derived" and "replay restores it" are not the same claim

Four of the thirteen entries in that flush list have no projection handler behind them: the per-issue streams, the sequence counters, the snapshots and the worker records. All four are deleted; none is restored by projecting events. The counter is the cleanest case — it is INCRed at issue_service.go:157 before the event exists, so no handler could write it even in principle. Delete that step and every workspace comes out of recovery ready to mint FLEET-1 on top of a live FLEET-1. A test pins exactly that, and you will run it in the exercise (internal/recovery/service_test.go:334-369).

Worker records are the harsher case: no action, no handler, no repair step. A replay deletes them and they stay deleted until an agent claims something — survivable only because worker state is ephemeral by design, written with a lease so it expires on its own anyway.

Where the rule stops

"The event log is the truth" is a rule about the tracker core. The platform half of fleet-db inverts it. Driver runs still append events, but only as audit records, and a doc comment above their no-op handler says so. Drivers and task runs do not invert the rule so much as sit outside it: neither appears in the action list at all (internal/models/event.go:16-93), so their state is only ever a command-time Redis write.

Scope

Seven of the 43 actions — every driver_run.* — are registered to that no-op (handlers.go:44-50). For those the event is an audit record and the Redis write is the truth. "Which is authoritative" is therefore a property of the subsystem, not of fleet-db, and you check it the same way each time: find the handler, read what it writes. The harness:noop-ok marker lets a repo gate tell a deliberate no-op from a forgotten one.

Back to claiming, with sharper eyes

Lesson 08 showed you internal/storage/lua/claim_issue.lua: lock, status check, status and assignee write, then five index repairs including the ready-queue ZREM (claim_issue.lua:58-78) — one atomic script. That script is real and correct. It is also not what runs when an agent claims a task.

POST /api/v1/{workspace}/issues/{id}/claim calls service.ClaimIssue (internal/api/claim.go:34, 79), which does three separate things: acquires the lock with a smaller script — GET, then either SET … EX or EXPIRE, returning OK/REFRESH/HELD; there is no NX, because the GET is the guard and Lua makes the pair atomic (internal/storage/locks.go:19-30); reads the issue after the lock, to avoid TOCTOU (issue_service.go:517-518); emits an issue.claim event. Lesson 08's guarantee survives intact — the lock is still acquired atomically and still breaks the race. What does not survive is "no intermediate state to observe": between the lock and the pipeline's commit, a reader of queue:ready still sees the issue. It just cannot claim it.

Check yourself

From memory: someone hands you a fleet-db Redis key and asks whether it is authoritative. State the two questions that decide it, name the function that answers the first, and name the quadrant that gets people hurt.

1. Does FlushDerivedState delete it? redis_recovery_store.go:58-77 is the repo's own definition of derived — eleven SCAN patterns plus {ws}:blocked and {ws}:labels.

2. Does a registered projection handler write it? registerHandlers, internal/projection/handlers.go:15-63. If no handler writes the key, replaying the log cannot restore it, however derived it looks.

The dangerous quadrant is deleted-but-not-handler-written. Four of the thirteen entries land in it, with four different answers: {ws}:events:issue:* (rebuilt from the global stream by FullReplay step 4), {ws}:seq:* (re-derived by step 6), {ws}:snapshots:* (nothing rebuilds them; the compactor writes new ones), {ws}:workers:* (nothing at all; live traffic and a TTL). {ws}:locks:issue:{id} is a fifth, different case: a handler does rewrite it, but from an old event's TTL, so the key comes back and its meaning does not. Authoritative in the tracker core means fleet-db:{ws}:events, and nothing else.

The repo's own list of what counts as derived state is the pattern slice inside , at internal/storage/redis_recovery_store.go:58.

Its doc comment carries the maintenance rule as well: a new derived key pattern anywhere in the storage layer must be added here, or a full replay will silently leave stale keys behind (redis_recovery_store.go:51-53).

Redis is up, the workspace is healthy, and you delete exactly one of these keys. Which one can no replay or repair step rebuild?

  • fleet-db:{ws}:queue:ready — the ready ZSET
  • fleet-db:{ws}:events — the mutation STREAM
  • fleet-db:{ws}:issues:{id} — the issue HASH
  • fleet-db:{ws}:seq:issues — the ID counter
The global stream is the one key FlushDerivedState exists to preserve (redis_recovery_store.go:48-49). The ID counter is the sharp near-miss: it is deleted too, and nothing replays it — but step 6 re-derives it from the rebuilt issue hashes (recovery/service.go:166, 262-285). The stream has no such step; recovering it means importing an export or an archive, a different subsystem (recovery/import.go:39-47).

A full replay finishes cleanly on a busy workspace. Which of these is gone afterwards and stays gone?

  • Comment lists — LPUSH order cannot be replayed
  • Blocked set — only the Lua rebuild restores it
  • Worker records — no event action ever writes one
  • Label registry — no replay ever re-fills that SET
None of the 43 actions is a worker.* (models/event.go:16-93), no handler touches a worker key, and WorkersKeyPattern is in the flush list — deleted, and only live claim traffic brings them back (storage/worker.go:44). The blocked set is the plausible wrong answer: handlers do write it during replay (handlers.go:512, 825), and FullReplay then runs a Lua blocked/ready rebuild as step 5 for exact consistency (recovery/service.go:161 → storage/ready.go:244).

Reaching back to Lesson 08: a runner wins the claim lock. Before the projection pipeline commits, what does a second runner reading the ready queue see?

  • The issue removed, since the lock script does that ZREM
  • The issue still listed, but marked as a claim pending
  • The issue removed, because the event has been appended
  • The issue still listed, because the ZREM has not run
The production lock script does nothing but the lock — GET, then SET … EX or EXPIRE, no NX (internal/storage/locks.go:19-30). The ZREM lives in handleIssueClaim (handlers.go:611) and runs later, in the projector's pipeline. The first option is the real trap: claim_issue.lua does contain that ZREM and it is the script Lesson 08 showed you, but it has no production caller. Appending the event does not move the queue either — only a handler does.
