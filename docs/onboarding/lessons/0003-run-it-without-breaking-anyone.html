Week 1 / Lesson 03 / Environment

Run it without breaking anyone

By the end of this lesson you can bring up a full local Loom stack that is provably yours — and you will know exactly which two commands can destroy a colleague's work if you type them with the defaults.

Skill stand up an isolated local stack safely Time 35 min Needs 01, 02 Repos loomcli
Read this before you run anything

Local stacks on this team are shared machine state, not per-session sandboxes. Several people and several agents run them on the same host at once. Two commands in this lesson will silently destroy someone else's running work if you take the defaults. Both are named below. Do not skim past them.

Two different things called "running it locally"

This is the first trap, and it is a vocabulary trap of exactly the kind Lesson 02 warned about. "Run it locally" means two unrelated setups here:

Trap — "zero install" is not quite true

The README describes local mode as zero-install README.md:22, 322. It is not: loom does not bundle fleet-db, it discovers it. DiscoverFleetDBBinary checks, in order, FLEET_DB_BIN, then fleet-db on PATH, then a sibling of the loom binary, then <LoomDir>/bin/fleet-db — and if none exists it fails with fleet-db binary not found; checked … plus a remediation line. Your first local-mode run on a fresh machine will hit exactly this. internal/bootstrap/embedded.go:526-532, 575-579

The two dangerous defaults

Everything about the compose stack is driven by variables at the top of the Makefile, and their defaults are shared names:

Read those two facts together and the hazard is exact:

Danger 1 — make local-mode-up

Compose identifies a stack by project name, and every local-mode target passes one with -p. Makefile:17; test/local-mode/docker-compose.yml:10 The default project name is a fixed string, and the default up flags include --build. So running make local-mode-up with the defaults, while somebody else already has a stack under that name, silently rebuilds and recreates their containers — killing their running work. You will see no warning, because from compose's point of view you asked for exactly that.

Danger 2 — make local-mode-down

Look at what down actually runs:

$$compose $(LOCAL_MODE_COMPOSE_ARGS) down -v --remove-orphans

-v removes volumes. Tearing down a project you did not create does not just stop it — it destroys its data. Makefile:286-289

The rule

Three steps, every time, no exceptions:

  1. before anything Run podman ps. Treat every stack you see as owned by someone else. Note which ports are bound.
  2. choose your own coordinates Pick an unclaimed port block and a project name with your run in it. The Makefile's own help text shows the shape: LOCAL_MODE_COMPOSE_PROJECT=name LOCAL_MODE_UI_PORT=8383 LOCAL_MODE_API_PORT=8382 LOCAL_MODE_FLEETDB_PORT=8380 Makefile:769
  3. tear down only yours Pass the same project name to down. LOCAL_MODE_COMPOSE_PROJECT=<yours> make local-mode-down. Never down a project you did not create this session.

The 8380 block in the Makefile help is an example, not a reserved slot for you — someone may already be on it. That is what step 1 is for. The default 8280/8282/8283 block should be treated as taken.

The same principle, three more places
  • Dev servers on fixed ports. Vite's 3000 is host-global. Before trusting a Playwright run with reuseExistingServer, check lsof -nP -iTCP:3000 -sTCP:LISTEN and confirm the listener is your checkout — otherwise your e2e silently tests someone else's build. Never kill a process you did not start. internal/webui/frontend/vite.config.ts:177-180; internal/webui/frontend/playwright.config.ts:163-166
  • Browser automation profiles and sessions are shared host state too. Pass a dedicated --profile per stack and close only that profile. Never close all. .agent-skills/loom-pr-test/SKILL.md:179, 274
  • The git stash stack is shared across every worktree of a repo — refs/stash is not one of git's per-worktree refs (git-worktree(1), REFS: only refs/bisect, refs/worktree and refs/rewritten are). So a bare git stash / git stash pop can pop a colleague's work; the agent task prompt bans running it outside your own worktree. internal/cli/agent/prompts/task.md:12 Prefer a temporary WIP commit.

Check yourself

From memory: name the three environment variables you must set before make local-mode-up, plus the project-name variable, and say what each protects you from.

LOCAL_MODE_COMPOSE_PROJECT — protects against recreating someone else's containers, because compose identifies a stack by project name and up defaults to --build.

LOCAL_MODE_FLEETDB_PORT (default 8280), LOCAL_MODE_API_PORT (8282), LOCAL_MODE_UI_PORT (8283) — protect against colliding with ports another stack already binds.

And the project name has a second job: it is what you pass back to local-mode-down so you tear down only your own.

A colleague's stack is running. You run make local-mode-down with no variables set. What happens?

  • Compose refuses, because the project was created by another user
  • Your own stack stops; theirs is untouched under its project name
  • Their containers stop but their volumes and data are preserved
  • Their containers stop and their volumes are deleted with them
You inherit the default project name, so you address their stack — and down runs -v, which removes volumes. The third option is the near-miss worth remembering: a plain down would preserve data, but this one does not. Makefile:286-289

Your Playwright e2e passes against localhost:3000 with reuseExistingServer. What must you check first?

  • That the listener on that port belongs to your own checkout
  • That the port is free and no listener is bound to it yet
  • That the frontend dist was rebuilt before the test run started
  • That no other compose project has claimed that same port
With reuseExistingServer, a listener owned by a different checkout means your test silently exercised someone else's build and told you nothing about your change. Check with lsof and, if the port is taken, start your own server on a unique port rather than killing theirs.

Read the addressing mechanism without starting anything

This exercise starts no containers, binds no ports and deletes no volumes. Standing up a real stack belongs to the runbook below, with your coordinates claimed out loud first — not to a lesson every reader runs at once.

  1. Run podman ps --format '{{.Names}} {{.Ports}}' and save the output to a scratch file outside both repos. This is your map of who else is on the machine, and your before-picture.
  2. Read it. Every container name carries its compose project as a prefix, and every 0.0.0.0:8xxx->8080/tcp is a host port you cannot have. Which of 8280/8282/8283 and the Makefile's 8380 example block are already taken, and by which project?
  3. Run make -n local-mode-down. -n prints the recipe and executes nothing. Read the last line: that is the exact command that would delete a stack, project name and all. Dry-run down rather than up — the up target's dist check is a recipe line containing $(MAKE), and make runs those even under -n. Makefile:173-175
  4. Run it again with coordinates of your own: LOCAL_MODE_COMPOSE_PROJECT=loomcli-local-mode-<you> make -n local-mode-down. Diff the two printed lines. Exactly one string changed, and that string is the entire difference between tearing down your stack and tearing down someone else's.
  5. Reaching back to Lesson 02: write the one-line evidence-class claim you could honestly make about what you just did. It is not even deterministic — say what it actually is, and what you would have had to run to earn deterministic.
You succeeded when Your two printed down commands differ only in the string after -p, and a second podman ps in the same format is identical to step 1's — same containers, same ports, nothing started and nothing gone. You learned the addressing mechanism and left the host exactly as you found it.
