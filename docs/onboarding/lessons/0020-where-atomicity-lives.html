Week 5 / Lesson 20 / fleet-db

Where atomicity lives

Redis runs one command at a time. Every promise this system makes across two commands was bought on purpose — with a pipeline, or with a Lua script. Buying the wrong one fails silently, and only under load.

Skill decide whether an operation needs a Lua script, and locate any state from the key schema Time 35 min Needs 05, 08 Repos fleet-db

Why this exists

One issue is not one thing in Redis. Creating FLEET-42 writes an issue hash, a status set, a priority ZSET, a type set, an assignee set, one set per label plus the workspace label registry, a repo set, a parent set and a children set, a deferred set, the ready ZSET, and a full-text-search set for every token in its text — how many keys exactly depends on the issue, and the count is never one (internal/projection/handlers.go:68-145). Redis will not roll any of that back for you, and it has no transaction that can read a value and then decide what to write next.

So every invariant that spans more than one command is paid for explicitly. The repo says so in one sentence, and it is the sentence worth keeping: the platform scripts follow the same pattern — one script per invariant that must hold atomically docs/architecture.md:1222-1223.

The one idea

Atomicity is bought per invariant, not per operation. Name the invariant, count the keys it spans, and ask whether any step depends on a value you had to read. That answer picks the tool — not the size of the operation, and not how many keys it happens to touch.

Half the skill is finding the state at all

You cannot reason about an invariant until you can name the keys it covers. fleet-db makes that cheap by forbidding key construction everywhere except one file:

1,694 lines, 216 functions, and 185 of them carry a // Pattern: comment — most of those also a // Redis type: line naming the Redis structure. Read the comments, skip the bodies, and you have the data model. Prefix is the constant "fleet-db" (keys.go:18), and {ws} is an uppercase workspace key — ^[A-Z]([A-Z0-9-]{0,30}[A-Z0-9])?$, from models.ValidateKey (internal/models/workspace.go:12, 98). So a real key looks like fleet-db:FLEET:issues:FLEET-42.

Lesson 05 placed fleet-db's Redis in the state tiers. This is what is inside it — the eleven keys you will actually go looking for. Three steps get you from a noun to every line of code that touches it:

  1. Find the builder. grep -n 'func .*Key' internal/storage/keys.go and search for your noun. Read its // Redis type: and // Pattern: comments.
  2. Grep the builder name. grep -rn 'ReadyQueueKey(' --include='*.go' internal/ finds every Go reader and writer.
  3. Grep the key suffix in Lua. Step 2 misses the Lua scripts, because they never call a Go builder. grep -rl 'queue:ready' internal/storage/lua/ finds six more scripts that step 2 cannot see.
Nearly every builder that skips assertValidWorkspace — the guard that panics on a malformed workspace key (keys.go:20-28) — is a *Pattern or *Prefix helper for SCAN. WorkspacePrefixKey is the conspicuous exception: it is not a SCAN helper, and of the builders whose output is handed to a script that concatenates freely it is the only one that skips the guard. TriggerEventKeyPrefix (keys.go:184-186, passed at await.go:249) and DriverRunKeyPrefix (keys.go:272-274, passed at platform.go:1376) validate first. Validate upstream.

Three tools, and the question that chooses between them

ToolWhat it buysWhat it cannot doLive example
One command Atomicity for one key, free. Anything spanning two keys. INCR …:seq:issues mints an issue id — sequence.go:36-42
TxPipeline
(MULTI/EXEC)		 All queued writes land together, with nothing else interleaved. Branch on a read. Reads go to the client and see committed state; writes are buffered and land later. The whole projector: projector.go:259-276
Lua script Read, decide, and write inside one uninterrupted execution. Nothing — but Redis is single-threaded, so the whole server waits on your script. 47 of them, in internal/storage/lua/

The question is not "how many keys?" It is: does a later step depend on a value or a decision that came from a read? If yes, Lua. If no, a pipeline is enough however many keys you touch.

The repo states this itself, in the one place where it kept both implementations of the same algorithm side by side — once in Go over several pipelines, once in Lua:

Same phases, same output. The Go version reads a snapshot in phases 0–3 and writes it in phase 4; anything created in the gap is deleted. Lua closes the gap because the read and the write are one execution (internal/storage/lua/rebuild_blocked_cache.lua:11-136). Note what did not decide it: both versions write the same two keys, …:blocked and …:queue:ready.

One key can still need Lua

The clearest counter-example to "multi-key means Lua" touches exactly one key:

One key, one field, and unavoidably Lua: the value written is a function of the value read. Two concurrent metadata writes done as HGET-then-HSET in Go would lose one. This is also the only script the projector runs inside its pipeline — pipe.Eval(ctx, storage.MetadataMutationLua, …) (internal/projection/redis_writer.go:123) — an atomic unit nested in a transaction, which is exactly what you want when the value is opaque to the caller.

And a dozen keys can be fine without it

handleIssueCreate writes the issue hash and every index, queue and search key the issue needs, through a plain TxPipeline and no Lua at all (internal/projection/handlers.go:68-145). Look at what it branches on: status, priority, type, labels, parent_id — every one of them read out of the event, never out of Redis. Nothing it writes depends on anything it read from the database, so a pipeline is sufficient and correct.

Where a handler does read Redis, the seam shows. The ProjectionReader doc comment states the rule plainly — Reads return persisted state, not in-flight buffered writes (internal/projection/writer.go:8-9) — and reevaluateAfterBlockerRemoved pays for it by hand, subtracting one from a count because the SREM that would have changed it is still sitting uncommitted in the pipeline (internal/projection/helpers.go:281-283, 309). That code is correct only because the projector holds a per-workspace mutex across the whole projection — cursor check, handler, pipe.Exec, cursor update — serializing projections within a workspace (internal/projection/projector.go:218-222, 249-285). Not for the whole of ProjectEvent: the lock is released before the post-mutation cache rebuild (projector.go:283-290), and the workspaceLock doc comment that still says otherwise (:40-42) is stale.

That mutex is process-local. I found no statement in docs/architecture.md about whether two fleet-db processes may project the same workspace concurrently, and did not verify it either way — treat "single projector per workspace" as an assumption to confirm before you rely on it.

So the second input to the decision is who else writes this key, and from which process. In-process serialisation is a real substitute for a script. A race between two agents on two machines is not.

The third case: you need the result of your own write

The second XADD needs the id Redis generated for the first. A pipeline cannot express that at any level of cleverness — the arguments of every queued command are fixed before the batch is sent. That is why the two streams share entry ids, and why an event id from one is a valid cursor into the other. internal/storage/redis_eventstore.go:22-26, 65-79

The trace: what the live claim actually buys

Every hop below is in fleet-db. Watch the atomic units open and close — there are three, and none of them spans another.

  1. internal/api/claim.go:34, 79 The route. POST /api/v1/{workspace}/issues/{id}/claim builds a ClaimIssueCmd and calls the service, not storage.
  2. internal/service/issue_service.go:510 → internal/storage/locks.go:19-30, 37 Atomic unit 1 — one key. acquireIssueLockLua takes the built lock key as KEYS[1] and does GET; absent ⇒ SET … EX ⇒ "OK"; same holder ⇒ EXPIRE ⇒ "REFRESH"; anyone else ⇒ "HELD" ⇒ ErrLockHeld ⇒ ErrAlreadyClaimed. This is the entire cross-agent guarantee, and it covers exactly one key.
  3. internal/service/issue_service.go:517-518 A read, deliberately outside every atomic unit. The comment says why: Read current state after lock acquired to avoid TOCTOU. Holding the lock is what makes an ordinary unprotected read safe.
  4. internal/service/issue_service.go:571 → internal/storage/redis_eventstore.go:65 Atomic unit 2 — two keys. executeCommand validates the event and appends it with append_event.lua. This is the durable write; everything after it is derived. issue_service.go:76-110
  5. internal/projection/projector.go:259-276 → handlers.go:589-621 Atomic unit 3 — a pipeline, about a dozen keys. handleIssueClaim HSETs status and assignee, SREMs from every non-terminal status index, moves the assignee index, ZREMs the ready queue and re-SETs the lock with the TTL from the event metadata. No Lua: every value comes from the event. The projector cursor is queued into the same pipeline (:269-271), so read model and cursor commit together or not at all.

Three atomic units, fifteen-odd keys, and a claim is still correct — because only one invariant needed protection against another process, and that invariant lives on one key. If projection fails outright, executeCommand logs at ERROR with severity=projection-lag and returns nil anyway (issue_service.go:83-110): the log is the truth and the background projector catches up. Buying atomicity across all three units would buy nothing you do not already have, and would cost a script long enough to stall the server.

The rule, as a checklist

Before you write a script, answer four questions. 1. What is the invariant, in one sentence someone could test? 2. Which keys does it span? 3. Does any write depend on a value or decision that came from a read? 4. Who else writes those keys, and from which process? Only 3 and 4 can force Lua. If both answers are "no" and "only this goroutine", you want a pipeline.

Two traps

Trap — the file in lua/ is not what runs

There is no //go:embed of internal/storage/lua/. The only embeds in the repo are SQL migrations (internal/archive/migrate/embed.go:5, 8; internal/storage/postgres/migrate/embed.go:5), and the only Go code that names that directory is a harness checker (scripts/harness/cmd/check_lua_call_arity/main.go:36). What executes is a backtick const in a .go file, compiled in — redis_eventstore.go:21 says so outright: Embedded here to avoid filesystem dependency at runtime. The package then contradicts itself about which copy is canonical: thirteen .lua files say the Go constant is (lua/create_workspace.lua:3), while claim.go:13, status_transition.go:12, redis_pubsub.go:61 and redis_pubsub_durable.go:28 — the last of those heading six constants at once — say the .lua file is. The absence of an embed settles it. Edit the Go constant and the .lua file, or the gate below fails you.

Three harness gates hold that duplication together, and they are worth knowing by name because they are what will actually stop your PR:

  • check_lua_go_sync.sh — pairs each .lua file with a Go constant by lowercasing, stripping a trailing lua and dropping non-alphanumerics (so claim_issue.lua ↔ claimIssueLua), then diffs them with comments and blank lines stripped. It fails in both directions: a constant with no file, or a file with no constant. scripts/harness/check_lua_go_sync.sh:33-42, 165-223
  • check_lua_key_patterns.sh — extracts every ":…" literal from every script and requires it to appear as a string literal in keys.go, or to start with one that ends in :. That is how ":idx:status:in_progress" passes on the strength of ":idx:status:". scripts/harness/check_lua_key_patterns.sh:39-51, 78-101
  • check_lua_call_arity — parses KEYS[n] and ARGV[n] out of each script and compares the maxima against the argument counts at the Go Run() callsite. scripts/harness/cmd/check_lua_call_arity/main.go:16-18, 79-89

Together with make lint-keys (Makefile:125-146), which forbids a "fleet-db:…" literal in any non-test .go file outside internal/storage/ and separately forbids storage.Prefix concatenation there (Makefile:128-131, 137-145), that is a closed loop: Go builds keys only in keys.go, Lua builds keys only from suffixes that exist in keys.go, and the two copies of every script are identical. The loop closes over one directory. The sync and arity gates scan only internal/storage/ (scripts/harness/check_lua_go_sync.sh:102; scripts/harness/cmd/check_lua_call_arity/main.go:36-37), and inside it the pairing is exactly 47 scripts to 47 constants. A constant outside it is unchecked: tokenBucketLua (internal/api/ratelimit.go:51) has no mirror file and no gate.

Trap — a script that exists is not a script that runs

Lesson 08 read claim_issue.lua as the claim, and as a piece of single-script design it is the clearest example in the repo. It is also not on the path an agent takes. claimIssueLua is run from exactly one place, RedisStorage.ClaimIssue (internal/storage/claim.go:95), and that method has no production caller: every non-test hit for .ClaimIssue( is either the backend-agnostic contract suite in internal/storage/storagetest/worker_tests.go or a differently-typed ClaimIssue on the service or the client SDK. The live path is the five-hop trace above. RedisStorage.TransitionStatus and status_transition.lua are the same story with zero non-test callers at all.

This matters beyond trivia, because the two implementations have drifted. claim_issue.lua:64-69 moves the issue out of its previous assignee's index; handleIssueClaim removes it only from idx:assignee:unassigned (internal/projection/handlers.go:607), even though the claim event carries the old assignee in its Before fields (internal/service/issue_service.go:548-551) and every sibling handler uses it (handlers.go:205, 339, 396, 643, 681). I found no other handler that repairs the old index entry. Whether that is a live bug or something the periodic rebuild covers is a good question for your teacher — and it is the reason "which one actually runs?" is a habit, not pedantry.

The habit, in two commands: grep -rn '<scriptField>' --include='*.go' . to find the Run() callsite, then grep the callers of the method that owns it. If they are all tests, you are reading documentation, not behaviour. Finding Anything has the general version of this move.

The pattern to copy when you do write one

  1. Pass built keys unless the key set depends on a read. If you can name every key before the script runs, build them in Go and pass them: AcquireIssueLock passes IssueLockKey(ws, issueID) (locks.go:41, 48) and append_event.lua takes two built stream keys. Only when the key names come out of data the script reads — a status you have not seen, an id you are about to discover — do you pass WorkspacePrefixKey(ws) as KEYS[1] and concatenate inside (claim.go:92, 95; rebuild_cache.go:153, 156). Exactly seven of the 47 scripts need the prefix; grep -rl 'workspace prefix' internal/storage/lua/ names them.
  2. Return "OK" or "ERR:CODE[:detail]", and map it to a sentinel in Go. That is the convention when the caller has to tell failure modes apart — 10 of the 47 scripts carry an ERR: literal, and claim.go:102-121 is the reference parse. Not a rule, though: acquireIssueLockLua returns "OK"/"REFRESH"/"HELD" (locks.go:18-30). The cost of skipping it shows in the six scripts that use redis.error_reply (grep -ln error_reply internal/storage/lua/*.lua): their Go sides have to match on a substring of an error message (metadata.go:47-52; redis_pubsub.go:130; redis_pubsub_durable.go:371-377).
  3. Register the constant once at construction. redis.NewScript(claimIssueLua) in NewRedisStorage (redis.go:1138-1160), so the script is SHA-loaded once rather than shipped per call.
  4. Write the mirror file, and say which copy is canonical correctly. Copy the wording from lua/create_workspace.lua:3, not from claim.go:13.
  5. Bound the work. Redis is single-threaded. The rebuild script caps its BFS at depth 50 and batches SADD/ZADD a thousand members at a time (lua/rebuild_blocked_cache.lua:63, 118-136) — an unbounded script is an outage.

Check yourself

From memory: name the three tools this codebase has for making Redis writes hold together, and the one question that chooses between them.

One command (atomic for one key, free — e.g. INCR on …:seq:issues, sequence.go:36-42); TxPipeline (every queued write lands together, nothing interleaves, projection/projector.go:259-276); and a Lua script (read, decide and write in one uninterrupted execution, the 47 files in internal/storage/lua/).

The question: does any write depend on a value or a decision that came from a read? If yes, Lua. If no, a pipeline, however many keys. Number of keys is not the test — metadata_mutation.lua touches one key and needs Lua; handleIssueCreate touches a dozen and does not.

Second input: who else writes those keys, and from which process. The projector gets away with reading inside a pipeline only because a per-workspace mutex serialises it (projector.go:218-222, 249-285).

You are adding an operation that writes three keys and reads none — all three values come from the request payload. What do you reach for?

  • A Lua script, so the three writes cannot interleave
  • A TxPipeline, since no write depends on a read value
  • Three plain calls, since Redis orders them anyway
  • A Lua script, since more than one key gets written
A TxPipeline already guarantees the three land together with nothing interleaved; Lua would buy nothing and would occupy the single-threaded server. The last option is the trap worth remembering — key count is not the test. handleIssueCreate writes a dozen keys through a pipeline (internal/projection/handlers.go:68-145); metadata_mutation.lua writes one and still needs Lua.

metadata_mutation.lua touches exactly one key. Why is it a script at all?

  • Because a single hash field write is not itself atomic
  • Because it re-encodes a value it had to read first
  • Because a pipeline cannot buffer an HSET on a hash
  • Because the metadata JSON is spread over several keys
It HGETs the metadata JSON, decodes it, edits one entry and writes the re-encoded blob back — the value written is a function of the value read, so two concurrent HGET-then-HSET pairs in Go would lose one. The first option is the plausible miss: a single HSET is atomic, which is exactly why the problem is the read, not the write. internal/storage/lua/metadata_mutation.lua:11-27

An agent claims a task via POST /issues/{id}/claim. Which script decides whether that claim wins?

  • claim_issue.lua, loaded from internal/storage/lua on boot
  • claimIssueLua, the Go constant declared inside claim.go
  • acquireIssueLockLua, the Go constant declared in locks.go
  • acquire_issue_lock.lua, loaded from internal/storage/lua
The service acquires the lock through acquireIssueLockLua (internal/storage/locks.go:19-30, 37) and then emits an event; the status and index writes happen later, in the projector's pipeline. Both .lua options are wrong for the same reason — nothing reads that directory at runtime, there is no //go:embed of it, and the Go constants are what execute. And claimIssueLua, though real and tested, has no production caller (internal/storage/claim.go:95).

When a script's key names depend on data it has to read, Go cannot build them for it. It is handed the workspace namespace from (ws) as KEYS[1] and concatenates the suffixes itself.

internal/storage/keys.go:433-438. Its doc comment states the convention: Lua scripts receive this as KEYS[1] and construct specific keys via concatenation. Seven of the 47 scripts work this way; the rest are handed keys already built, however many — including two-key append_event.lua (internal/storage/redis_eventstore.go:70-73).

Locate the state, then prove which script owns it

Before you start

Everything below is read-only: greps, a Makefile target that runs only grep, and one package's tests against an in-memory Redis. Do not start a stack for this. If you ever do need one, the week-1 rule stands — pick your own compose project and your own unclaimed port block, and never up, down or --build a stack you did not create. Nothing here writes to either repo.

Work in the pinned fleet-db tree.

  1. Run make lint-keys, then grep -c '^func ' internal/storage/keys.go. Now read Makefile:128-131 and write down which files are allowed to contain a "fleet-db:" literal. Then answer: how do the Lua scripts build keys without breaking that rule?
  2. Locate one piece of state end to end. Take fleet-db:{ws}:queue:ready. Find its builder in keys.go, then run grep -rn 'ReadyQueueKey(' --include='*.go' internal/ | grep -v _test, then grep -rl 'queue:ready' internal/storage/lua/. Say why the second command cannot find what the third one does, and which of the six Lua files you would have missed.
  3. Check the key-pattern gate by hand: grep -oE '":[a-z_]+[a-z_:]*"' internal/storage/lua/claim_issue.lua | sort -u. Confirm each result appears as a literal in keys.go. One of them does not appear literally and still passes — find it, and explain the rule at scripts/harness/check_lua_key_patterns.sh:88-93 that lets it through.
  4. Reaching back to Lesson 08: re-read claim_issue.lua with the question "who runs this?" Run grep -rn 'claimScript' --include='*.go' . | grep -v _test.go, then grep -rn '\.ClaimIssue(' --include='*.go' . | grep -v _test.go. Classify every hit in the second list as (a) the contract suite, (b) a different ClaimIssue on another type, or (c) a production caller of RedisStorage.ClaimIssue.
  5. Prove the guarantee the script does carry, without a stack: go test ./internal/storage/ -run 'TestClaimIssue_IndexConsistency|TestClaimIssue_LockCleanupOnNotClaimable' -v.
