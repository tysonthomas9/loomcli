Week 4 / Lesson 17 / Surroundings

The edges

Everything that is not the CLI, the web layer, or fleet-db: sdk/, services/auth/, desktop/, and the shipping channels. One of them you need in week one. The rest you can ignore until something forces you to care — and knowing which is which is the whole lesson.

Skill place the SDK, task runners, desktop app and packaging in the system Time 30 min Needs 10 Repos loomcli fleet-db

Why these exist

The centre of Loom is Go. Every directory here is a boundary drawn around it, and each boundary faces a different way. sdk/ is the contract leaving the Go process going down into JavaScript subprocesses. services/auth/ is an identity provider sitting above it. desktop/ wraps the same cmd/loom binary in a macOS shell. The packaging files are different ways to hand that binary to someone.

Read them in directory order and you meet a Tauri Rust file before you meet the one edge that carries a real invariant. So triage first.

DirectoryWho executes itWhen you need it
sdk/ — @loom/sdk, two dependency-free JS clients Node subprocesses serve spawns: workflow bundles and task-runner harnesses Week one. The runner credential invariant lives in one file here.
services/auth/ — a Node/Hono/Better Auth identity provider Nobody, unless deployed. No Go file imports it. Only for human auth, and only when --auth-url is set.
desktop/ — a Tauri macOS shell (332 lines TS, 638 Rust) A user double-clicking. It shells out to a bundled loom. Rarely. The half that matters is Go and lives elsewhere.
npm/, scripts/install.sh, .goreleaser.yml CI, on a tag push Not until you cut a release — but know the SPA ships separately.
The one idea

Only loom serve holds fleet-db credentials. Everything that looks odd out here — a serveMode branch on every SDK method, a deny-list that runs before an allow-list, a launcher whose env blanks LOOM_FLEET_DB_URL — exists to keep that sentence true.

sdk/: two clients, three credentials

Loom executes code at three levels and each gets its own credential. A workflow bundle uses a run-scoped LOOM_RUN_TOKEN and imports the driver client (sdk/driver.js:68-75). A task runner — the leaf that drives an LLM CLI over a worktree — uses a per-task-run lease token and imports the runner client. A human uses an RS256 JWT and imports nothing. Both clients ship under separate entry points of one package (sdk/package.json:6-25).

Only the bundled workflows import it statically: epic-runner.ts and github-review-agent.ts take the driver client on line 1, daytona-task-runner.ts the runner client on line 6. The built-in local runner imports it lazily, inside a try, so the module stays loadable and testable outside a bundle — copy that shape, not a top-level import. internal/workflows/builtin/local-task-runner.ts:1630-1642

The package is unpublished (sdk/README.md:223) and consumed by symlink: a generated workflow build gets node_modules/@loom/sdk pointed at LOOM_SDK_ROOT or $CWD/sdk. Run serve from a directory with no sdk/ sibling and every build fails with "local @loom/sdk package not found". internal/workflows/workflows.go:618-627, 674-686

The trace: a runner that holds no fleet-db credentials

  1. internal/cli/serve/serve.go:414-425, 314-321 Serve computes its own URL and hands it down. driverAPIBaseURL() returns LOOM_DRIVER_API_URL if set, else http://<bind>:<port> with 0.0.0.0 and :: normalised to loopback. It becomes TaskWorker.APIBaseURL, then HostBridgeTaskExecutor.APIBaseURL (internal/driver/task_worker.go:88-91).
  2. internal/driver/env.go:137-139 The subprocess env is filtered deny-first. subprocessEnvAllowed consults subprocessEnvSensitive before the allow-list, so the allow-list can never re-admit a denied name. LOOM_FLEET_DB_URL and LOOM_FLEET_DB_API_KEY are denied by name (env.go:44-45), the whole FLEET_ prefix by prefix (env.go:63). A denied name comes back only if something re-adds it after the filter, by name: the local-task-runner entrypoint re-adds the provider credentials (env.go:111-123), and no fleet-db name is among them.
  3. internal/driver/task_bridge.go:661-688 Then the LOOM_* set is added back. taskRunnerEnv injects the request as JSON, the lease tuple including LOOM_TASK_RUN_LEASE_TOKEN (line 682), and — only when APIBaseURL is non-empty — LOOM_TASK_RUN_API_URL (line 688).
  4. sdk/runner.js:34-61, 374-384, 411-419 The runner branches on that one variable. Serve mode posts to /api/workspaces/{ws}/task-run/<op> with Authorization: Bearer <lease token> plus four identity headers, and no X-API-Key, no X-Actor. Legacy mode posts to fleet-db's own /api/v1/{ws}… routes with a deployment key.
  5. internal/webui/server/middleware/auth_routes.go:74-86 Those routes skip the human-JWT middleware. /api/task-run/ is in hasOwnAuthPrefix, and stripWorkspacePrefix normalises the workspace-scoped path down to it — so even with --auth-url set, a lease token never reaches the RS256 validator.
  6. internal/webui/handlers/taskrunapi/module.go:145-148, 202, 248-259 Serve authenticates, then proves ownership. Two routes; authenticate parses the lease tuple; and for any op without a fenced store call of its own, verifyLease issues a real no-op fenced heartbeat rather than re-implementing the check.
  7. internal/api/platform.go:2499-2507 fleet-db has the last word. It hashes the X-Lease-Token header and passes {LeaseTokenHash, NodeID, LeaseID, FencingToken} to the store — the plaintext token exists only in serve's memory and the runner's env (internal/api/control_plane.go:1230-1233).

The operational consequence is written where operators read it: stop provisioning LOOM_FLEET_DB_URL and LOOM_FLEET_DB_API_KEY to task runner wrappers. Serve exports the serve URL automatically; direct fleet-db survives only as the fallback when that URL is absent. AGENTS.md:78-83

Trap — the silent downgrade

You will assume a missing LOOM_TASK_RUN_API_URL is an error. It is not: serveMode is simply false, with no warning (sdk/runner.js:60). The client then reaches for LOOM_FLEET_DB_URL, which hop 2 already stripped, and throws TypeError: baseUrl is required (sdk/runner.js:486-489) — naming neither the real cause nor the real variable. The question to ask is "why is APIBaseURL empty on this serve process?"

The pattern to copy — the SDK is optional

A harness owes the bridge two things only: read LOOM_TASK_RUN_REQUEST_JSON, and print one terminal JSON object as the last stdout line. deploy/podman-stack/e2e/task-runner.mjs does it in 60 lines importing nothing but node:fs and node:path. Copy that when you need a new harness; reach for the SDK only for mid-run reporting — heartbeats, streamed logs, artifacts. Note it reads request.task_run_id: the request JSON is snake_case, and so is every legacy direct-fleet-db body — only serve's task-run API is camelCase on the wire (internal/webui/handlers/taskrunapi/module.go:9-10).

services/auth/: off by default

No Go file imports it — the only in-repo references are a Makefile test target (Makefile:536-538) and an e2e script. Loom reaches it over HTTP or not at all, and everything is gated on one value: loom serve --auth-url, defaulting from LOOM_AUTH_URL (internal/cli/serve/serve.go:175). Set, it builds a JWKS cache against <auth-url>/api/auth/jwks and installs the JWT middleware (internal/webui/app/server_app_helpers.go:13-16), and serve reverse-proxies /api/auth/* to the service so cookies stay same-origin (internal/webui/app/routes.go:68-80). Unset, middleware.Auth returns a passthrough — "open mode" — and binding to a non-loopback address then produces a Warn log and nothing more. internal/webui/server/middleware/auth.go:113-118, internal/webui/app/server_app.go:93-94

Trap — the role claim is not authorization

Better Auth puts a role claim in every JWT it mints (services/auth/src/auth.ts:153-159), which is tempting to build on. Do not: the Go side declares exactly two custom claims, email and name, so role is parsed and dropped, and UserIdentity carries only {UserID, Email, Name}. internal/webui/server/middleware/auth.go:21-25, 44-48

desktop/: a launcher, and where it stops

"The desktop app is a shell and controller, not a second Loom implementation" (docs/product/desktop-app-runtime-spec.md:25) — and the code holds. Rust exposes four commands (desktop/src-tauri/src/lib.rs:56-61); TypeScript calls the bundled loom sidecar exactly twice, ever: local status --json and local start (desktop/src/main.ts:133-138, 159).

The half that matters is Go, in internal/cli/local/. loom local start re-execs the same binary as loom local service, detached (internal/cli/local/local_cmd.go:501-509), which spawns loom serve --bind 127.0.0.1 --port N --fleet-mode as another detached child (local_cmd.go:236-244) — with an env that blanks LOOM_FLEET_DB_URL, prepends the bundle's own directory to PATH, and points FLEET_DB_BIN and LOOM_FRONTEND_DIR at siblings inside the .app (internal/cli/local/runtime.go:434-461). That is two long-lived processes from one binary, plus a third from a different one: the embedded fleet-db, resolved FLEET_DB_BIN-first (internal/bootstrap/embedded.go:526-533).

The LaunchAgent keeps that alive across logout and reboot: a per-user ~/Library/LaunchAgents/com.loom.local.plist with RunAtLoad and KeepAlive on non-zero exit (internal/cli/local/launchagent.go:15, 55-61, 183) — deliberately not a system-wide LaunchDaemon (desktop-app-runtime-spec.md:257-258). The app never installs it — only loom local install-service does — and the rendered argv is loom local --data-dir <dir> service, not the bare loom local service the docs print (launchagent.go:43-51).

Trap — loom local drain does not drain

The spec says it will "stop new claims, let active agents finish" (desktop-app-runtime-spec.md:233) and both docs make it step 2 of the update flow (spec:203, desktop-installation-runbook.md:320). All the subcommand does is write ClaimsPaused into runtime.json and return (internal/cli/local/local_cmd.go:694-703). Grep ClaimsPaused across internal/: four hits — the writer, two struct fields, one copy, and no consumer (internal/cli/local/runtime.go:43, 69, 99). Both product docs are marked Draft on line 3. Read them for intent, the code for truth.

The fact to carry away: the SPA is not inside the binary's archive. GoReleaser builds two — loom-binaries, and a metadata-only loom-frontend holding internal/webui/frontend/dist — and the release notes tell operators to extract it to a static host and proxy /api/* to a running loom serve. .goreleaser.yml:27-45, 86-91. deploy/docker-compose.yml is the checked-in reference for that shape.

Building the DMG yourself wants a sibling fleet-db checkout: desktop/scripts/prepare-sidecar.sh:8 defaults FLEET_DB_REPO to ../fleet-db and only warns when it is missing (prepare-sidecar.sh:68), so you get an app whose runtime cannot start.

Check yourself

From memory: a task runner subprocess appends a log line to its task run. Name the credential it sends, the variable that decides which server receives it, and the two things that would both have to be true for it to reach fleet-db directly instead.

Its per-task-run lease token, as Authorization: Bearer plus four X-Loom-Task-Run-* identity headers and no API key (sdk/runner.js:411-419).

The decider is LOOM_TASK_RUN_API_URL: present means serveMode, and the request goes to POST /api/workspaces/{ws}/task-run/log-append on serve (sdk/runner.js:60, 374-384).

Legacy needs that variable absent and LOOM_FLEET_DB_URL present — but the deny-first filter strips exactly that name, so on a bridge-spawned runner the second cannot hold. You get TypeError: baseUrl is required. internal/driver/env.go:44, 137-139

In Lesson 06, LOOM_FLEET_DB_URL being set is what selects cloud mode for a CLI command. What does the same variable do for a bridge-spawned task runner?

  • The same thing — it selects the direct fleet-db transport for the runner
  • It is renamed by the bridge and arrives as the serve task-run API URL
  • Nothing — the bridge strips it, so the runner never sees the variable
  • It is forwarded, but only for the bundled local-task-runner entrypoint
The filter denies it by name before the allow-list is consulted, so the runner's environment has no such variable (internal/driver/env.go:44, 137-139). The first option is the trap: that branch does still exist in the SDK and would fire if the variable were present — it just cannot be, on this path. The fourth describes a real mechanism aimed elsewhere: the local-task-runner widening admits provider credentials such as ANTHROPIC_API_KEY, and pointedly no fleet-db ones (env.go:76-83).

An op on the task-run API has no fenced store call of its own — artifact-list, say. How does serve establish that the caller owns the run?

  • It issues a real fenced heartbeat and lets fleet-db reject it
  • It reads the task-run row and compares the lease id itself
  • It validates the bearer token against the JWKS cache first
  • It trusts the identity headers the task bridge injected earlier
verifyLease performs a no-op heartbeat through the store so fleet-db's lease-hash and {node, lease, fencing} checks stay the single authority — serve proxies that authority rather than duplicating it (internal/webui/handlers/taskrunapi/module.go:243-259). Reading and comparing is the near-miss, and the package doc says not to. The JWKS option fails twice over: /api/task-run/ bypasses the human-JWT middleware entirely.

You deploy a tagged release and the web UI is a blank page, though loom serve answers on /api/*. Most likely cause?

  • The desktop release workflow ran instead of the GoReleaser one
  • The npm wrapper installed a stale binary from an older release
  • The frontend build needs --auth-url set before it renders
  • The separate frontend archive was never extracted to a static host
GoReleaser publishes the SPA as its own loomcli-frontend_<version>.tar.gz, not inside the binary archive (.goreleaser.yml:36-45, 86-91). The second option is sharpest because the npm wrapper really is pinned to v0.1.0 (npm/install.js:6) — but nothing publishes that package, so it is on no deploy path at all.

Watch the invariant hold, then place each edge

  1. Run the credential-removal end-to-end test: go test ./internal/webui/handlers/taskrunapi/ -run TestBridgeRunnerCompletesTaskRunViaServeSurface -count=1. It spawns a real node process running the real sdk/runner.js. (Needs node on PATH; it skips otherwise.)
  2. Open runner_e2e_test.go:27-42 and find the two guards in the embedded runner script that are the invariant: one exits 2 if any LOOM_FLEET_DB* variable is visible, the other exits 2 if the client did not select the serve transport.
  3. Isolate the SDK half: cd sdk && node --test runner.test.mjs, then read runner.test.mjs:422-432 and say in one sentence what it pins. (Use node --test, not npm test — the latter also runs tsc, which needs npm install first.)
  4. Reaching back to Lesson 10: name the three processes in the desktop chain and cite where each is started. Two are in internal/cli/local/local_cmd.go; the third is a different binary, and internal/cli/local/runtime.go:451-455 is where the launcher tells serve which copy to use.
  5. From memory, for each of sdk/, services/auth/, desktop/ and npm/: which process executes it, and does a backend-first newcomer need it in week one? Check against the table above.

internal/webui/handlers/taskrunapi/module.go, starting with the package doc on lines 1-28.
