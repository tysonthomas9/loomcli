Week 3 / Lesson 10 / Execution

What actually runs your code

Five objects in this domain read like a thing that runs. Only two ever become an operating-system process. Learn which, and you can answer the question every incident starts with: where is this actually running?

Skill name the three execution levels and place any running thing on one Time 40 min Needs 09 Repos loomcli fleet-db

Why this exists

Loom runs other people's programs: a TypeScript workflow that decides what work exists, and an AI CLI that does the work. Different programs, different lifetimes — so Loom keeps two run objects, two queues and two claim loops, plus a third path, the daemon-supervised agent, that predates both. The cost is vocabulary: DriverRun, DriverStep and TaskRun sit within a few dozen lines of each other in internal/domain/platform.go and all read as "a thing that runs". One of them runs nothing at all.

The one idea

Loom runs code at three levels, and only the outermost can be containerized. L1 is the workflow bundle that decides what tasks exist; L2 is the task leaf that invokes the backend CLI and edits your repository; L3 is the daemon-supervised agent. Every "where does this run?" resolves to one of those three. docs/design/execution-isolation.md:9-19

"Behind a seam" versus "a literal spawn" is the entire mechanism, and it is visible in the Go without reading a word of prose. Executor carries a swappable launcher:

HostBridgeTaskExecutor, the L2 equivalent, has no launcher field of any kind (internal/driver/task_bridge.go:47-81). That struct diff is the whole L1/L2 story.

Worth knowing, not memorising: RunBundledTaskRunner (internal/driver/bundled_runner.go:79) is the one-shot path the daemon leaf uses to delegate a backend run to the same TS runner — same spawn, no worktree provisioning, no patch-back.

The five objects

ObjectIsBecomes a process?
Driver platform.go:64 A named program, with an ActiveVersionID and a TrustLevel No — a pointer
DriverVersion platform.go:87 One immutable built bundle: BundleRef, BundleDigest, ValidationStatus No — an artifact
DriverRun platform.go:396 One execution of one pinned version, with node, lease and fencing token Yes — L1
DriverStep platform.go:462 A ledger row inside a run, optionally naming the TaskRunID it produced No — see the trap
TaskRun platform.go:498 One execution attempt of one FleetDB task, with its own lease and placement Yes — L2

The nesting is Driver → DriverVersion → DriverRun → TaskRun, with DriverStep off to the side: a TaskRun carries both DriverRunID and DriverStepID as optional back-links (internal/domain/platform.go:498-502).

Trap — DriverStep is not an execution level

It has a status enum containing running (internal/domain/platform.go:442-450) and a store interface with a Create method (internal/store/platform_store.go:610-617), so it reads like something Loom runs. At the pinned commit, no production code in loomcli creates one. Every production call site is an Update, each guarded by a step id the workflow supplied: if opts.DriverStepID == "" { return nil } internal/driver/task_request.go:601-604. It is bookkeeping the workflow opts into. Prove it in the exercise.

The trace: from a POST to a running codex

  1. internal/webui/handlers/workflows/module.go:36, 135, 173 Route, then resolve. POST /api/workspaces/{ws}/workflows/{name} → createWorkflowRun → resolveWorkflowDriverID, which for a builtin name runs EnsureBuiltinWorkflow — a lazy self-heal, not a lookup.
  2. internal/workflows/workflows.go:337, 368 → internal/driver/register.go:412-444 Build and register a version. BuildAndRegister runs flue build --target node (workflows.go:737) in a temp npm project; stageFlueBundle stamps manifest["trust_level"] (register.go:433), digests the manifest plus every file under dist/ in sorted order (register.go:796), and derives versionID = <driverID>-v-<digest12>. The identifier is the digest, so re-registering identical sources is idempotent.
  3. internal/driver/run.go:38, 76, 98 Create the run, pinning the version. CreateDriverRun refuses a version whose ValidationStatus is not passed, then writes DriverVersionID onto the row; the handler returns 202 Accepted (module.go:170). Nothing has executed yet.
  4. internal/cli/serve/serve.go:325-333 → internal/driver/executor.go:125, 627-631, 160 Claim, verify, mint. A 2-second ticker calls Executor.RunOnce, which claims one queued run with a node id and lease id (ErrAlreadyClaimed is a skip, not an error — the losing-the-race-is-normal shape from Lesson 08), re-computes the bundle digest against the one pinned on the version and fails the run bundle_verification if it differs (:156-158), and only then mints the run token (:160). A tampered bundle never reaches the mint.
  5. internal/driver/executor.go:743-758 → internal/driver/sandbox/launcher.go:236 Launch — this is L1. runBuiltFlueServer picks r.Launcher, else the default process launcher. In process mode that is exec.CommandContext(ctx, node, launcherPath) with cmd.Env = spec.Env — the launcher adds and drops nothing, because the runner already reduced the host env to an allowlist (executor.go:802); in container mode the identical spec goes to the container launcher.
  6. internal/workflows/builtin/epic-runner.ts:298 → sdk/driver.js:295, 309 The workflow asks for work. loom.taskRuns.request(...) POSTs to …/driver/exec-task with enqueueOnly: true and deferCompletion: true — a request, not an execution. Serve creates a queued TaskRun row and returns (module.go:594-599 → task_request.go:265).
  7. internal/cli/serve/serve.go:385, 457 → internal/driver/task_request.go:300-313 A different loop claims it. startDriverTaskWorkers runs N goroutines (default 2) on a 1-second ticker; each claims a queued TaskRun with its own lease id and lease token, not the parent's.
  8. internal/driver/task_bridge.go:366 → internal/workflows/builtin/local-task-runner.ts:456, 513 Spawn — this is L2. exec.CommandContext(ctx, "node", launcherPath) in the worktree: a string literal, not a variable, because there is no launcher to substitute. The runner then execFiles the backend binary — for codex, ["exec", "--json", "--dangerously-bypass-approvals-and-sandbox", "-"]. That process reads and writes your repository.

Hops 4 and 7 are the two claim loops; hops 5 and 8 are the two spawns. Everything else is bookkeeping — and that ratio is the point.

Run-scoped auth: LOOM_RUN_TOKEN

An L1 bundle is someone else's TypeScript in a process Loom started, and it must call back into serve. Its credential is scoped to exactly one run:

Because the lease is inside the claims, fenced verification doubles as revocation: a superseded lease rejects the token regardless of expiry, with no denylist anywhere. It is minted at claim, not at create (internal/driver/executor.go:160, 184) and reaches the child only as an env var (:827-828). Nothing inherited rides along with it: the workflow env is assembled from an allowlist of names rather than by stripping suspicious ones — scopedSubprocessBaseEnv keeps only PATH, HOME, TERM, LANG, TZ, LC_* and a handful of named LOOM_* vars, and rejects outright any name containing SECRET, TOKEN, PASSWORD, PRIVATE_KEY, ACCESS_KEY or API_KEY (internal/driver/env.go:67-74, 125-151). It is not yet the only token there: serve appends its static bearer alongside it whenever it has one and the legacy fallback below is on (internal/driver/executor.go:795-796). On the wire it does travel alone: with a run token set, #identityHeaders returns { Authorization: "Bearer " + this.runToken } and nothing else (sdk/driver.js:587-590), and serve derives identity from the claims, treating a conflicting X-Loom-Driver-Run-Id as 401 identity_mismatch (internal/webui/handlers/driverapi/token_auth.go:64-68).

Trap — LOOM_DRIVER_API_TOKEN still works, and is still deprecated

"Workflows authenticate with a run token" reads as "the node-wide static bearer is gone". It is not. A token-carrying run drops it only while LOOM_DRIVER_LEGACY_AUTH_ENV is off, and that switch defaults ON — legacyDriverAuthEnvEnabled returns true for everything except 0/false/off/no (internal/driver/executor.go:697-703). A run with no minted token always gets the legacy env, because it is that run's only auth (:688-692). The deprecation is also scoped: deprecated for workflow runtimes, while the CLI/ops header quad (X-Loom-Driver-Run-Id / -Node-Id / -Lease-Id / -Fencing-Token, internal/webui/handlers/driverapi/module.go:49-52) is unaffected. The other way a DriverRun is born

Hop 3 above is the operator path. The event path produces the same object through three rows, in a contractual order — TriggerRouteDispatcher "persists ONE TriggerEvent, then per matched binding enqueues a queued DriverRun and records a TriggerDelivery, in that order" (internal/store/platform_store.go:398-402):

  1. internal/domain/platform.go:214, 227-228 TriggerBinding — standing config, pairing a route key or event-type pattern with a DriverID and DriverVersionID.
  2. internal/api/platform.go:86, 1302 In fleet-db, POST /api/v1/{workspace}/trigger-routes/{route_key} lands on createTriggerRouteRun, which fans out to every matched binding and answers with deliveries[] (:1332).
  3. internal/domain/platform.go:274-277, 348-361 TriggerEvent is the durable record of what happened, persisted before any dispatch; TriggerDelivery is one binding's reaction to it, carrying the DriverRunID it enqueued.

Note what that produces: a queued DriverRun, identical to the one hop 3 created. From hop 4 onward the two paths are the same code. Triggers are a source, not a level.

The pattern to copy

Put the swappable part behind an interface and let the wiring choose once, at startup. ResolveSandboxLauncher is called in exactly one production place (internal/cli/serve/serve.go:353), and an invalid configuration disables the executor rather than degrading to a host process (:347-357). Isolation is declared by an interface, not a boolean — IsolatingLauncher{ SandboxLauncher; Isolates() bool } (internal/driver/sandbox/policy.go:39-47) — and only the container launcher implements it (internal/driver/sandbox/container.go:157). That marker is the hinge of the trust policy, which is the next lesson. For now note where the hinge is, and that L2 and L3 have no local equivalent: their only isolation option is remote, selected by runner entrypoint rather than by launcher (daytona-task-runner, internal/driver/bundled_runner.go:16-20; docs/design/execution-isolation.md:136-151).

L1 the DriverRun bundle (the orchestration program), L2 the TaskRun leaf that invokes the backend CLI and edits code, L3 the daemon-supervised agent. Only L1 can be containerized. docs/design/execution-isolation.md:9-19

epic-runner → L1, through the sandbox seam (sandbox/launcher.go:236). local-task-runner → L2, spawned at task_bridge.go:366, which execFiles the backend CLI (builtin/local-task-runner.ts:513). loom task <worktree> --auto --daemon-mode → L3, cli/daemon/supervisor/spawn.go:101-109 — that form is gated on BuiltInRoles, which is exactly {plan, task} (supervisor/types.go:170-173); any other role is spawned as loom agent … instead. A DriverStep has no level — a ledger row production code only ever updates (task_request.go:601-604).

You set LOOM_DRIVER_SANDBOX=container. Which process ends up inside the container?

  • The workflow bundle that decides which tasks exist
  • The task leaf that invokes the CLI and edits code
  • The daemon agent the supervisor spawns per role
  • Every node subprocess the driver package spawns
Only L1 goes through the launcher seam, so only L1 can be swapped for a container. The second option is the tempting one, and it is why this lesson exists: the L2 spawn is a string literal with no launcher to substitute, and its executor struct has no launcher field at all. internal/driver/task_bridge.go:47-81, :366

A DriverRun and the TaskRun it requests both reach a runner by being claimed. What is true of those two claims?

  • Separate loops, each minting its own lease and fence
  • One loop; the task claim reuses the parent's lease
  • The task run inherits the parent run's fencing token
  • Both are claimed by the same goroutine inside serve
Two loops: a 2-second ticker calling Executor.RunOnce (internal/cli/serve/serve.go:325-333) and N task-worker goroutines, default 2 (:385, :457). The task claim generates its own lease id and lease token (internal/driver/task_request.go:300-313). The last option is the near-miss: the driver-run loop really is one goroutine, but the task workers are separate ones. The Lesson 08 claim shape, applied twice at different granularities rather than shared.

A token-carrying workflow bundle calls exec-task on serve. What does the SDK put on the request?

  • The node-wide static bearer and the four identity headers
  • Only an Authorization: Bearer header with the run token
  • The run token as a header plus the lease id for fencing
  • The task-run lease token issued when a worker claimed it
With a run token present the SDK returns exactly one header and ignores everything else (sdk/driver.js:587-590); a conflicting X-Loom-Driver-Run-Id is 401 identity_mismatch (internal/webui/handlers/driverapi/token_auth.go:64-68). The first option is the sharp wrong answer because it is still live — it is the legacy header quad plus LOOM_DRIVER_API_TOKEN, which serve still accepts for CLI and ops — but it is not what a token-carrying runtime sends.
