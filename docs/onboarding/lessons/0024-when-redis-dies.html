Week 5 / Lesson 24 / fleet-db

When Redis dies

Four recovery paths, and the only property that matters about each one: what it deletes before it rebuilds. Say the deletion out loud before you run the command.

Skill choose a recovery path and state what it destroys first Time 35 min Needs 09, 05 Repos fleet-db loomcli

Why this exists

Lesson 09 was this lesson one layer up. A run dies; the supervisor answers "what is true about the task now" by walking an escalating ladder — resume, checkpoint, cold — where only the last rung is destructive, and where the destruction is a deliberate argument rather than a side effect: s.recoverAgent(ap, 0, false), and that false is what lets git clean run.

Now the store dies instead. Same ladder shape, one layer down, with two differences that make it more dangerous. There is no supervisor — you are the thing that classifies the failure and picks the rung. And where loomcli hides its destructive step behind a boolean parameter, fleet-db puts it in the first two statements of the function body, where it is easy to skim past.

Everything here is Redis-backend-only. With --backend postgres the recovery routes are not registered at all and the server logs "disaster recovery routes not available for postgres backend" — cmd/fleet-db/main.go:739-746.
The one idea

Every recovery path in fleet-db is defined by what it deletes before it rebuilds. Nothing here is transactional and nothing takes a backup for you, so the deletion is the whole risk. Before you run one, say the sentence: "this deletes ___, and if it fails halfway I am left with ___."

First: is there a log left to replay from?

fleet-db Replay rebuilds the read model from the global event stream (Lesson 05: the only authoritative tier). If Redis came back empty, every path below rebuilds nothing from nothing. What decides that is one config value applied once at startup, before any writes:

Six profiles exist (none, development, balanced, durable, critical, managed), each a concrete AOF/RDB pair in the same map — five of them applied with CONFIG SET, and managed applied with nothing at all — durability.go:15-43, 61-92, 132-182. Two facts about that call are worth more than the table:

  • A profile mismatch is a boot failure, not a degradation. ApplyDurabilityProfile returns an error if CONFIG SET appendonly or save is rejected, and run() propagates it — the process refuses to start. durability.go:160-178, cmd/fleet-db/main.go:247-254
  • managed means fleet-db configures nothing and verifies nothing. It returns before the first CONFIG SET, having logged one WARN. durability.go:149-153 Cloud Run ships with it: FLEET_REDIS_DURABILITY_PROFILE = "managed" at deploy/terraform/modules/cloud-run/main.tf:74, and the runbook spells out the consequence — free-tier Upstash is best-effort persistence. docs/deployment-gcp.md:416-423
Trap — the checker that would have caught this never runs

docs/architecture.md:1540 says the persistence health checker "Runs at startup and logs warnings for mismatches." storage.RunPersistenceChecks (internal/storage/redis.go:1198) has no non-test caller — main.go calls only ApplyDurabilityProfile. Its own failure message says "aborting startup", from a function that never runs at startup, and FLEET_REDIS_PERSISTENCE_LAG_THRESHOLD is parsed into config (internal/config/config.go:1269-1275) and then never read outside that dead path. Verify persistence at the provider; do not expect fleet-db to tell you.

loomcli By default the embedded stack has no Redis at all: unless local settings enable an external one (internal/bootstrap/embedded.go:239-245, 346), internal/bootstrap starts miniredis. Either way it passes --redis-durability-profile=managed because "miniredis rejects CONFIG SET" (embedded.go:366-378). In that default mode durability is loomcli's own JSON snapshot — atomic rename plus a .bak generation, and a sweep that cannot read every key aborts rather than write a truncated file (internal/webui/localredis/manager.go:1-11, 275-283). It keeps only the newest 10,000 entries per stream; older ones "remain in the running miniredis but won't survive a restart" (manager.go:64-70, 632-637).

Tier zero: what heals with nobody driving

Three things happen on every boot, before you have decided anything. Try a restart before you reach for the ladder.

  1. Projector catch-up. Start reads the persisted cursor, replays every event after it in batches of 100, then subscribes. This is what repairs an inline projection that failed during a write. internal/projection/projector.go:102-143
  2. In-Redis data migrations. MigrateAllDepMetaKeys and MigrateAllDriverTrustLevels run unconditionally on the Redis backend and log-and-continue on failure. On this backend, "schema migration" means an idempotent startup sweep over live keys — there is no version table. cmd/fleet-db/main.go:771-788
  3. Blocked-set reconciliation, and its comment names our exact situation: a "snapshot-restored or otherwise-diverged blocked set" would otherwise stay wrong until the next close or dependency event in that workspace. cmd/fleet-db/main.go:790-796

Catch-up has one sharp edge worth carrying: a catch-up event whose handler fails is skipped, with only the in-memory cursor advanced (projector.go:131-141, 329-340), so the read model silently misses it for the life of the process. The skip itself does not advance the Redis cursor — but the next event that projects successfully writes its own, later ID over it (projector.go:269-271), so a restart retries the failed event only if nothing after it succeeded. In a workspace still taking writes, the gap is permanent until a full replay.

What "derived" actually means, in one function

Two more go by name rather than pattern — fleet-db:{ws}:blocked and fleet-db:{ws}:labels (redis_recovery_store.go:74-77). Then SCAN + DEL, batch by batch, no transaction (:91-128). Read that NOTE at :50-53 as a live hazard rather than a housekeeping remark: the list is maintained by hand, so a derived key family added without touching this function survives the flush and is then stale rather than rebuilt — which is worse than being deleted.

The trace: one POST to /admin/replay

  1. fleet-db internal/api/recovery.go:42-43 The route. POST /api/v1/{workspace}/admin/replay, wrapped by AuthzWrap(mw, az) and required permission workspace.update — which appears in exactly one role block, RoleAdmin (internal/auth/permissions.go:177, 275, 397). See the trap below for when that check is not there at all.
  2. recovery.go:54-66 One replay per process. A second POST while one is running gets 409 replay already in progress. The replay's context descends from the server-lifetime context, not the request's — closing your curl does not stop it. (Export is the opposite: it runs on r.Context(), :123.)
  3. recovery.go:68-95 202 Accepted, immediately, with a status_url. Every destructive step below runs in the goroutine launched at :68; the 202 is written at :92-95, and nothing orders the two — by the time the response reaches you the flush may already be done.
  4. recovery/service.go:90-93 → redis_recovery_store.go:58-99 The deletion. This is the only irreversible moment in the whole path, and it is step 1 of 6. Nothing is snapshotted first; the return value is a count of deleted keys.
  5. service.go:95-99 Both cursors, not one. DeleteKeys on fleet-db:{ws}:projector:cursor (internal/storage/keys.go:1115) and projector.ResetCursor for the in-memory dedup value. The interface comment says why: it "Must be called alongside Redis cursor deletion during replay/recovery to prevent the dedup check from silently skipping replayed events." internal/projection/projector.go:29-32, 251-257
  6. service.go:110-153 Replay in batches of 500 (:22) through the same ProjectEvent the write path uses. The first handler error returns immediately with EventsFailed: 1 — leaving the workspace flushed and only partly rebuilt.
  7. service.go:155-158 → :204-257 Per-issue streams rebuilt from the global stream with AppendWithID, preserving original IDs. Note the direction: after a replay, each per-issue stream contains exactly what the global stream still holds — no more, no less.
  8. service.go:160-168 → :262-326 Blocked cache, then sequence counters. The issue sequence is recovered from the numeric suffix of projected issue keys, the comment sequence from comment.add event metadata; both are set forward-only.
Trap — "replay only rebuilds, it cannot lose anything"

LocksKeyPattern is on the flush list, and an issue claim lock is fleet-db:{ws}:locks:issue:{id} (internal/storage/keys.go:859-861, 1097-1099). A replay deletes every claim lock in the workspace. They come back — the issue.claim projection handler re-creates the lock from the event's lock_ttl metadata (internal/projection/handlers.go:613-618) — but with the TTL restarted at replay time, for every claim the log does not show being released or deleted. Closing is not releasing: handleIssueClose never touches the lock — only handleIssueRelease and handleIssueDelete delete it (handlers.go:648, 582) — so a replay resurrects the claim lock on a closed issue too. From Lesson 08: a lock with 20 seconds left on it comes back with the full TTL, so a replay can quietly extend a dead agent's hold on a task.

Trap — "202 Accepted, so it worked"

The 202 tells you nothing about the flush — it races it. If the replay fails at event 40,000 of 50,000, the derived state is already gone and there is no rollback; your only signal is GET …/admin/replay/status, which returns the string "replay failed". The real error is deliberately not serialized — internalErr error // raw error for server-side logging; not serialized (internal/api/recovery.go:30, 79-88) — so the diagnosis is in the server log, not in the response. Poll the status endpoint until done is true, and read result.EventsProcessed: ReplayResult carries no JSON tags, so its fields go over the wire in Go case (internal/recovery/service.go:36-41). pkg/client's ReplayStatusResponse asks for events_processed (pkg/client/client.go:210-216), a key the server never emits.

Trap — "verify came back consistent, so the projection is fine"

VerifyProjection is genuinely read-only, and genuinely narrow. It compares exactly five fields — status, priority, type, title, assignee (internal/recovery/verify.go:86) — against its own simplified in-memory applier, not against the projector's handlers; in that applier, "dep.*, label.*, comment.*, workspace.* actions don't affect issue state" (verify.go:224-226). A dependency graph or label set that diverged is reported as consistent: true. It does detect missing and orphaned issues (verify.go:75-83, 101-116). And docs/architecture.md:1428 describes it as checking "archive consistency against the live event stream" — it never touches any archive.

Trap — "/admin/ is an authorization boundary"

Straight out of Lesson 11. AuthzWrap drops the permission check entirely when the authorizer is nil (internal/api/authz_wrap.go:12-19), and a nil authorizer is exactly what --authz-enabled=false produces (cmd/fleet-db/main.go:555-562) — which is what loomcli's embedded fleet-db passes (internal/bootstrap/embedded.go:373-378). Compare GlobalAuthzWrap, whose comment says it rejects unauthenticated requests even with authz off "to prevent open admin access on misconfigured deployments" (authz_wrap.go:21-32). The recovery routes do not use that one. admin in the path is a naming convention.

The pattern to copy: rehearse it in a workspace nobody owns

The repo's own answer to "how do I test a destructive path" is the drill: mint a throwaway workspace, register its cleanup in the very next line, and run the real destructive code against it.

FullDrill then exports the live workspace, calls ImportAndReplay into drillWS, verifies, and reports (restore.go:115-176). The live workspace is only ever read. Copy the shape whenever you add a destructive operation: the precondition, the throwaway target, the deferred cleanup, and a report rather than a boolean.

…and read its exit conditions

FullDrill returns Passed: true immediately when the export produced zero events (internal/retention/restore.go:134-138). A drill against an empty or wrong workspace passes vacuously. Check EventCount, not Passed — the same lesson as Lesson 16: a green result is only worth what its preconditions assert.

Check yourself

From memory, without scrolling: name the four recovery paths in order of what they destroy, and for each one say the deletion in a single clause.

1. Verify — deletes nothing. Replays events in memory and compares five fields against the projected issue hashes. internal/recovery/verify.go:32, 86

2. Import — deletes nothing, and refuses to run at all unless the global stream is empty: ErrStreamNotEmpty, surfaced as 409. recovery/import.go:57-63, api/recovery.go:146-149

3. Full replay — deletes 11 derived key patterns plus :blocked and :labels, plus the projector cursor; keeps the global event stream and the ACL keys. Rebuilds the read model, per-issue streams, blocked cache and sequences. internal/storage/redis_recovery_store.go:48-77, recovery/service.go:86-168

4. Import-and-replay — deletes the global event stream first, then everything full replay deletes. It is a cold-start replace, not a merge, and it has no HTTP route. recovery/import.go:286-297

A full replay calls FlushDerivedState first. Which of these does that call actually do?

  • It deletes every issue claim lock in the workspace
  • It deletes the global event stream of the workspace
  • It deletes the ACL role assignments of the workspace
  • It deletes the SQL archive rows for that workspace
LocksKeyPattern(workspace) is on the list (redis_recovery_store.go:66) and an issue lock is fleet-db:{ws}:locks:issue:{id} (keys.go:859-861). The global stream is preserved by design — only ImportAndReplay deletes it (recovery/import.go:292). ACL keys are excluded deliberately, with the reason stated in the doc comment (redis_recovery_store.go:55-57). The archive is a separate subsystem that recovery never touches.

You hold a JSONL export and a workspace that already has events. Which operation replaces that workspace's history with the file?

  • Import — it appends the file after the events already present
  • Import-and-replay — it deletes the stream, then loads the file
  • Full replay — it reads the file back through the projector once
  • Verify — it compares the file against the live projected state
ImportEvents checks StreamLen and returns ErrStreamNotEmpty → 409 (import.go:57-63); it is designed "for disaster recovery into a truly fresh Redis, not workspace-to-workspace copying" (MANUAL_TESTING.md:455). Full replay and verify never read a file — both work only from the stream already in Redis. And note the sting: the right answer has no HTTP route (api/recovery.go:43-47), so over the wire the honest answer is "you cannot".

Reaching back to Lesson 09: what protects a worktree from cleanUntrackedFiles, and what protects a workspace's ACL keys from FlushDerivedState?

  • A caller-passed flag; an exclusion the code states in writing
  • A caller-passed flag; a lock the recovery service takes first
  • A dry-run pass first; an exclusion the code states in writing
  • A dry-run pass first; a lock the recovery service takes first
loomcli skips the clean when incomplete is true — "destruction of live work when the agent simply ran out of turn" (internal/cli/agent/recover.go:250-259). fleet-db has no flag and no lock: ACLKeyPattern is simply left off the list, with the reason written above the function — ACL state "is not derived from the event stream and is not rebuilt by replay" (redis_recovery_store.go:55-57). Neither path has a dry run, and the only workspace-level recovery lock in the repo belongs to the retention sweep, not to this code.

The thirteen key families a full replay destroys are listed in exactly one function: RedisRecoveryStore..

Eleven SCAN patterns plus two named keys, all in internal/storage/redis_recovery_store.go:59-77. That list, and not the docs, is the definition of "derived state" in this repo.
