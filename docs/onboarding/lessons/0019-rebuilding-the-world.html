Week 5 / Lesson 19 / fleet-db

Rebuilding the world

One create, eleven derived structures, and the question you will eventually be asked at 2am: if I flush this workspace and replay the log, what comes back? The answer is not "everything", and the parts that do not come back are the interesting ones.

Skill trace a mutation to every structure it derives, and predict what a replay restores Time 35 min Needs Lesson 18, 05 Repos loomcli fleet-db

Why this exists

Lesson 18 left you with the rule: the event is the write, everything else is derived. This lesson makes that rule operational. "Derived" is not a mood — in this repo it is a property you can check in two places, and a key that satisfies only one of them will betray you the first time someone runs a recovery.

The word is already in the course glossary, used of stage: "a derived view, not a stored object … folded out of an issue's event history". Same idea, one level down. There, the thing folded out is a view a client renders; here it is every queryable structure in Redis.

The whole write path is three calls. Every command method in the tracker ends in the same function, and that function never touches an issue hash:

Note the shape of the third call: a projection failure is logged and swallowed. executeCommand returns nil even when the read model was never updated, because the append already succeeded and the log is the thing that matters. That is only a defensible trade if the read model can be reconstructed from the log on demand. So it can — mostly.

The background projector is the "mostly". One goroutine per workspace catches up from the stored cursor in batches of 100 and then tails the in-process event hub — internal/projection/manager.go:112-145, internal/projection/projector.go:103, 121-143, 158-182. It re-projects events the inline call already handled; the dedup at projector.go:254 makes that a no-op.
The two-part test for "derived"

A Redis key is derived only if both are true: it is matched by a pattern in FlushDerivedState (internal/storage/redis_recovery_store.go:58-77), and some handler in internal/projection/handlers.go writes it. Fail the first and a replay leaves stale state behind. Fail the second and a replay deletes it and only a hand-written post-pass can bring it back — steps 4 and 6 of FullReplay do that for two key families, and nothing does it for the worker registry or snapshots.

The trace: one create, all the way to the ready queue

Our specimen is the command you will run a hundred times:

loom data create --title "Fix the retry budget" --type task
  1. loomcli internal/cli/data/create.go:63-77 The command. RunE builds CreateParams from flags, resolves the issue backend, and calls ib.Create(ctx, params) — the wrapper shape from Lesson 06. By default it sends an X-Idempotency-Key: sha256 over today's UTC date and the marshalled create body (create.go:139-146 → internal/backend/types.go:456-465).
  2. loomcli internal/backend/fleet/fleet.go:79, 516, 532-534 One of the two client stacks. FleetBackend builds its base as baseURL + "/api/v1/" + workspace at construction time, so createIssueOnce only has to POST "/issues", carrying the idempotency headers.
  3. fleet-db internal/api/issues.go:57, 68-78 The route. POST /api/v1/{workspace}/issues, wrapped in the PermIssueCreate authz check. The handler reads the raw bytes before decoding, so the idempotency layer can fingerprint exactly what the client sent; and it validates the command before reserving an idempotency key (issues.go:116-122).
  4. internal/service/issue_service.go:157 → internal/storage/sequence.go:36-42 The ID — and the first thing that is not in the log. NextIssueID is a plain INCR fleet-db:{ws}:seq:issues, formatted as "FLEET-42". No event describes this. Hold that thought; it is half of this lesson.
  5. internal/service/issue_service.go:204-241 The event. The service builds the models.Issue, forcing the non-nil Labels/ Metadata invariants, marshals it, and sets that JSON as the event's After. Action issue.create, entity type issue, entity ID FLEET-42.
  6. internal/storage/redis_eventstore.go:22-26, 65-79 Append. One Lua script does two XADDs: fleet-db:{ws}:events with *, then fleet-db:{ws}:events:issue:FLEET-42 with the ID Redis just generated. The two streams therefore share entry IDs. That ID is written back onto event.ID at :78 — which is what makes the next hop's dedup possible.
  7. internal/projection/projector.go:223-276 The projector. Look up the handler by action; take the per-workspace mutex (:249); skip only if the cursor is exactly this event ID (:254 — strict equality, not a range check, so out-of-order inline projections are not silently dropped); open a TxPipeline; run the handler; queue the cursor SET into the same pipeline (:269-271); one Exec. Read model and cursor commit together or not at all.
  8. internal/projection/handlers.go:68-145 The handler. handleIssueCreate is the only code in this whole trace that writes a queryable structure. It writes the eleven families in the table below, with no fixed key count: the FTS index alone writes one SET per unique token across five text fields (internal/storage/search.go:51-65), so the create above lands eleven keys and an issue with a description lands dozens. It sees no Redis client: it writes through a ProjectionContext (internal/projection/writer.go:22-41), which buffers into the pipeline. That indirection is why a Postgres projector could be added later without touching a single handler.
  9. internal/service/issue_service.go:247 → internal/storage/idempotency.go:162 And one more write outside the log. After the event, the service remembers a soft-duplicate fingerprint at fleet-db:{ws}:softdup:{fp} with a TTL. Like the ID counter, no event carries it and no handler writes it.

POST /api/v1/{workspace}/admin/replay exists (internal/api/recovery.go:43-47). It returns 202 and runs FullReplay in a goroutine. That function is 100 lines and it is the entire answer to this lesson's question — six steps, in this order:

Read steps 4, 5 and 6 as a confession. If replaying the log rebuilt the world, the function would end at step 3. Three post-passes exist precisely because the projector cannot produce those structures from events alone.

Step 1 is the other half of the two-part test, and it is a hand-maintained list:

Backend note

All of this is the Redis backend. In Postgres mode the recovery routes are not registered at all — cmd/fleet-db/main.go:740-746 logs disaster recovery routes not available for postgres backend. "Replay the workspace" is not an answer you can give an operator without first asking which backend they are on.

Trap — "a replay is a pure function of the log"

It is not. The ready-queue decision reads the wall clock:

	readyInput := storage.ReadyInput{
		Status:     models.Status(status),
		Type:       models.IssueType(issueType),
		Assignee:   assignee,
		DeferUntil: deferUntil,
		Now:        time.Now().UTC(),
	}
	if storage.IsReadyEligible(readyInput) {
		pc.AddToSortedSet(ctx, storage.ReadyQueueKey(ws), float64(priority), id)
	}

internal/projection/handlers.go:130-139, and IsReadyEligible compares DeferUntil against that Now (internal/storage/ready_eligible.go:42-47). An issue created last month with defer_until set to last Tuesday was excluded from the queue when the event was first projected and is included when the same event is replayed today. Same log, same handler, different answer. Meanwhile the deferred index replays faithfully, because isDeferredIndexState asks no question about time (internal/projection/helpers.go:123-125). Two structures that look like they encode the same fact do not replay the same way.

Trap — "locks are runtime state, a replay cannot resurrect one"

Exactly three lines in handlers.go touch the lock key: :582 (delete, on issue.delete), :648 (delete, on issue.release), and this one:

	// Set lock if TTL specified.
	if ttlStr := event.Metadata[models.MetaLockTTL]; ttlStr != "" {
		if ttl, err := strconv.Atoi(ttlStr); err == nil && ttl > 0 {
			pc.SetValue(ctx, storage.IssueLockKey(ws, id), actor, time.Duration(ttl)*time.Second)
		}
	}

internal/projection/handlers.go:613-618. The claim event carries lock_ttl_seconds in its metadata, defaulting to 300 (internal/service/issue_service.go:500-503, 566-568). So a claim from three hours ago is replayed into a live lock with a fresh 300-second TTL, measured from the replay. And nothing clears it on close: handleIssueClose (handlers.go:305-367) never mentions the lock key, because in normal operation the lock is simply left to expire. A replay restores a lock whose real-world life ended long ago — the ghost of Lesson 08's race.

Trap — "verify says consistent, so the replay was clean"

GET /api/v1/{workspace}/admin/verify replays the log into an in-memory map and diffs it against Redis (internal/recovery/verify.go:32-116). Read what it actually compares: five fields — status, priority, type, title, assignee — on issue hashes, plus orphan detection (verify.go:86, 101-116). It never looks at an index, the ready queue, the blocked set, a dependency edge or the FTS sets. Worse, applyEventToState (verify.go:140-226) is a second, simpler implementation of the fold that handles ten issue actions and ignores every other one. "consistent": true means those five fields agree with that simplified model. The real structural checker is RedisStorage.VerifyInvariants (internal/storage/invariants.go:51), which has no HTTP route: its only invocation is the test target at Makefile:86-89.

The pattern to copy when you add an event

  1. Write the handler, or the gate stops you. Every ActionXxx Action = "…" constant in internal/models/event.go must appear in the handler map in internal/projection/handlers.go — 43 constants, 43 registrations, checked by scripts/harness/cmd/check_action_handler_coverage/main.go:48-57. A deliberate no-op is legal; it must say so and carry the harness:noop-ok marker.
  2. Then update the flush list. If your handler writes a new key family, FlushDerivedState is the second half of the contract and nothing enforces it — the source comment asks you by hand (redis_recovery_store.go:51-53).
  3. Keep the handler a function of the event. Every time.Now() and every read of unprojected state is a place where replay and live projection diverge. Where the event carries the value — close_reason, lock_ttl_seconds, the assignee in Before/After — use it.
  4. Write through ProjectionContext, never a raw pipeline. Reads see committed state, writes buffer into the transaction (internal/projection/writer.go:8-35). It is the seam that lets one handler serve two backends.

The authoritative list of what counts as derived state is the patterns slice in .

Eleven glob patterns plus two exact keys, at internal/storage/redis_recovery_store.go:58-77. It lives in the storage layer on purpose: key knowledge stays where the key builders are (:51-53). Nothing generates or checks it, so it is the first place to look when a recovery leaves something stale.

Which of these keys is flushed by a full replay and rebuilt by no projection handler?

  • fleet-db:{ws}:idx:status:open
  • fleet-db:{ws}:fts:registry
  • fleet-db:{ws}:workers:active
  • fleet-db:{ws}:queue:ready
workers:* is in the flush list (redis_recovery_store.go:65) but there is no worker.* action in internal/models/event.go at all — the registry is written directly by the service on claim (internal/service/issue_service.go:579-595). The other three are all written by handleIssueCreate (handlers.go:88, 143, 138). The FTS registry is the sharp near-miss: it looks like an auxiliary cache, and it is fully derived.

FLEET-7 was claimed at 08:00 with the default TTL and never released. You replay the workspace at 10:00. Its lock key is now:

  • absent: the flush removed it, no handler rewrites it
  • present: the claim handler rewrote it, expiring 10:05
  • present: rewritten by the handler, still expiring 08:05
  • absent: locks are outside the flushed key namespace
handleIssueClaim re-SETs the lock with the TTL from the event's metadata, applied at projection time (internal/projection/handlers.go:613-618; default 300s at issue_service.go:500-503). The third option is the tempting one — the event does carry a TTL, but it carries a duration, not a deadline, so the clock restarts.

Reaching back to Lesson 13: a browser holding an opaque mutations cursor reconnects after a full replay. What happens?

  • It resumes: replay never writes the global event stream
  • It 400s: replay renumbers events and invalidates cursors
  • It resumes: the projector rewrites client cursors on replay
  • It 400s: the flush deleted the stream that cursor indexes
The cursor is a fleet-db:{ws}:events entry ID, and the mutations endpoint reads that stream through GetEvents (internal/api/mutations.go:129, internal/storage/redis_eventstore.go:83-84). FullReplay only ever reads it; the flush list contains no pattern matching it, and a test pins that (internal/recovery/service_test.go:178-202). The per-issue streams are deleted and rewritten — under their original IDs (internal/recovery/service.go:228-236).

Prove the ID counter is not derived, then predict a replay

Before you start

Every step here is read-only: greps, file reads, and one go test of a single package against an in-process miniredis. Do not run make local-mode-up or local-mode-down, do not start a server on a fixed port, and do not touch a podman stack or agent-browser session you did not create. If you ever do bring a stack up, pick your own compose project name and an unclaimed port block first. These machines are shared.

  1. In the pinned fleet-db checkout, read the derived-state list: sed -n '48,78p' internal/storage/redis_recovery_store.go. Write down the eleven patterns and two exact keys. Which one surprises you?
  2. Now prove the issue-ID counter is on the wrong side of the line: grep -rn "IssueSeqKey" --include="*.go" internal/ | grep -v _test.go. Read every hit. Which package is conspicuously absent from the results?
  3. Run the two tests that pin both halves of this lesson: go test ./internal/recovery/ -run 'TestFullReplay_SequenceRecovery|TestFlushDerivedState_PreservesGlobalEventStream' -v. Then open internal/recovery/service_test.go:334-369 and name the step number of FullReplay that makes the assertion at :366 pass.
  4. Predict before you read. A workspace has FLEET-1 through FLEET-9, all still open. Someone deletes FLEET-9, then runs a full replay. What is fleet-db:{ws}:seq:issues afterwards, and what ID does the next create mint? Justify it from exactly two lines: internal/recovery/service.go:267 and internal/projection/handlers.go:462.
  5. Reaching back to Lesson 08: a claim writes the issue lock twice — once on the command side, once on the projection side. Find both (internal/service/issue_service.go:510 and internal/projection/handlers.go:616) and say which one a replay repeats, and which one it cannot.
  6. Finally, run the two-part test yourself on a key you have never seen: fleet-db:{ws}:idx:deferred. Find the builder in internal/storage/keys.go, find the handler that writes it, and decide in under two minutes whether a replay restores it.
