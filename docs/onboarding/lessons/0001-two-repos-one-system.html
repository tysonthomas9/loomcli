Two repos, one system

By the end of this lesson you can say what each repo owns, and find the source file for any loom command in under two minutes without asking anyone.

What Loom is

One sentence, from the README:

Unpacked: Loom runs many AI coding agents at once. Each gets its own git worktree and its own branch. Each picks tasks from a shared issue tracker, works independently, and integrates back through a structured push/pull/sync workflow. The hard problem is not calling a model — it is that N agents sharing one issue tracker must never both claim the same task, and that when one dies mid-run you must be able to tell what it actually did.

That framing explains most of the architecture you are about to meet. Atomic claiming, ownership leases, event sourcing, and the session-artifact contract all exist to answer "who owns this work?" and "what really happened?" under concurrency.
The one idea

loomcli orchestrates. fleet-db remembers. Every piece of durable shared state lives in fleet-db; loomcli is the thing that decides what to run, runs it, and shows you what happened. When you cannot remember where something belongs, ask which of those two sentences it fits.

The two legal paths

There are exactly two valid control-plane paths, and the README states them as a rule rather than a description — runtime code that invents a third is wrong:

Read what those two lines have in common: HTTP client appears in both. loomcli never reaches into fleet-db's storage directly. Even in local mode — where fleet-db is a subprocess Loom spawned itself and Redis may be an in-process miniredis — the call still goes out over HTTP to fleet-db.

You will grep for "redis" in loomcli and find hits — an optional client in internal/kv, and an in-process miniredis that loom serve boots for terminal state. Those are a different Redis from fleet-db's, used for node-local concerns. internal/kv/client.go:36-42 internal/webui/localredis/manager.go:1-4 internal/cli/serve/daemonwire/localredis.go:17 The rule above is about the control plane, and it holds — CI enforces it. scripts/check-control-plane-paths.sh:12-18
Why this matters on day one

Local mode is not a mock. It is the same service, the same HTTP surface, the same storage layer — just spawned for you and pointed at an embedded Redis. So a bug you reproduce locally is usually a real bug, and code you write against local mode usually works in cloud mode. That is a deliberate design property, and it is why "it worked locally" carries weight here.

Local mode is the default and needs no Redis or Postgres installed — the README's "zero install" means that, not zero binaries. It still needs a fleet-db executable, resolved in order from FLEET_DB_BIN, PATH, a sibling of the loom binary, then <loom-dir>/bin/fleet-db; miss all four and the first command fails with fleet-db binary not found. internal/bootstrap/embedded.go:526-542

Cloud mode is selected by setting LOOM_FLEET_DB_URL before running any command, and DetectMode is the only place in the tree that distinction is made. internal/bootstrap/mode.go:51-58

Finding anything: the CLI

Start with the question you will actually have — "where is the code for loom task?" The answer comes from one convention.

internal/cli holds 31 subdirectories (ls -d internal/cli/*/ | wc -l) alongside 87 files at its own top level, every one of them a .go file (ls internal/cli/*.go | wc -l). Most of those subdirectories are command families — though nine of them (automode, backendcheck, clitest, cmdstore, config, daemonregistry, envfilter, sessionfinalize, testdata) are shared plumbing or fixtures and define no command at all — grep -rn 'cobra.Command{' finds nothing in any of the nine, and none of them calls cli.RegisterCommand:

Each family registers itself. There is no central list of commands to grep — which is exactly why newcomers get stuck. The mechanism:

So the full wiring for any command is:

  1. internal/cli/<family>/<name>.go — func init() The subpackage builds its *cobra.Command and calls cli.RegisterCommand(cmd). There are 39 such call sites under internal/, plus the loop in cmd/loom/main.go:49 that registers the data family.
  2. internal/cli/root.go:284 RegisterCommand appends it to the package-level pendingCmds slice. Nothing is wired to the root command yet — Go has only run init().
  3. internal/cli/root.go:288-290 registerPendingCommands() attaches the whole slice to rootCmd in one shot, at startup.

Which raises the obvious question: if each package registers itself in init(), what makes init() run? Go only runs it if something imports the package — so main imports all of them, for no reason except the side effect:

That blank-import block is the closest thing to a master list of commands that exists: 26 entries, inside cmd/loom — the only main package that builds the loom binary — whose main.go is 58 lines long in total. cmd/loom/main.go:13-38 The repo's other two package main files, internal/harness/fakeharness/mock and scripts/openapi-to-30, build something else. The block's own comment overstates it, though: automode is blank-imported at cmd/loom/main.go:16 and has no init() at all.

Trap

You will be tempted to look for a file that declares every command. There isn't one; there is only the blank-import block that activates them. So if you add a subpackage and its command never appears, the cause is almost always a missing blank import in cmd/loom/main.go — not a bug in your cobra.Command. Nothing will warn you: a package nobody imports simply never runs.

The exception that teaches the rule

internal/cli/data does not self-register. It is an sdk-only command surface and the depguard data-isolation lint rule forbids it from importing its own parent internal/cli — so it cannot call cli.RegisterCommand at all. Instead it exports Commands(), and main's own init() loops over them and registers each by hand. cmd/loom/main.go:41-51 .golangci.yml:174-180 internal/cli/data/doc.go:15-19

Remember this one. loom data is the command family you will use most — it is how you find, claim, and close work — and it is the one command family that is wired differently from all the others.

The recipe

To find the code behind loom <X>, in order of speed:

  1. ls internal/cli/ — if X names a subdirectory, start there. Confirm rather than assume: internal/cli/config/ exists but declares no command at all — it is the config loader. The only config command is loom daemon config, and it lives in a different package. internal/cli/daemon/daemon_cmd.go:131
  2. Otherwise grep for the command string in its Use: field: grep -rn 'Use:\s*"X' internal/cli/
  3. For a subcommand (loom data ready), the family is the first word: look in internal/cli/data/.

Trap

A doc in this repo is not automatically true. AGENTS.md cites docs/testing-terminology.md twice as canonical AGENTS.md:20,35 — and that file does not exist at ce4df56fb: git ls-files | grep testing-terminology returns nothing. Treat checked-in docs as strong evidence of intent and weak evidence of current behaviour. When a doc and the code disagree, the code wins and the doc is a bug worth filing.

Check yourself

From memory, without scrolling: what are the two valid control-plane paths, and what do they have in common?

Local mode: loomcli → HTTP client → fleet-db subprocess → RedisStorage → miniredis or external Redis. Cloud mode: loomcli → HTTP client → fleet-db service → Redis/Postgres.

Both go through the HTTP client — loomcli never touches storage directly, so local mode exercises the real service rather than a mock. README.md:25-33

You add a new subpackage under internal/cli/ with a correct cobra.Command and an init() that calls cli.RegisterCommand. The command does not appear. Most likely cause?

  • The command was added after registerPendingCommands ran
  • The command needs adding to a central command list file
  • Nothing imports the package, so its init() never ran
  • The command name collides with an existing registered command
Registration is decentralised: init() only runs if something imports the package. The near-miss is the central-list option — it feels right because most CLIs work that way, but here no such file exists, and looking for it is the classic newcomer time sink. internal/cli/root.go:278-290

Which statement about local mode is correct?

  • It replaces fleet-db with an in-process mock of the HTTP surface
  • It spawns a real fleet-db subprocess reached over the HTTP client
  • It lets loomcli read and write the Redis read model directly
  • It requires an external Redis server to be running beforehand
Local mode spawns the real service and still goes through HTTP. Storage underneath may be miniredis, but the service and its API are real — which is why local reproductions are trustworthy here. README.md:25-33

Find three commands cold

Reading — not editing — your onboarding worktree, locate the file that defines each of these, and write down the path:line of its cli.RegisterCommand call:

  1. loom doctor
  2. loom monitor
  3. loom serve — this one is bigger than the others; note which subpackage owns it.

Then answer without opening the file: for loom data ready, which directory would you open first, and why?

You succeeded when grep -rn "RegisterCommand(" internal/ --include="*.go" | grep -v "func RegisterCommand" returns 39 call sites, and your three paths are among them. loom data ready is a real command, so the directory is internal/cli/data/ internal/cli/data/ready.go:18. If you found all three in under two minutes without opening the README, you have the skill this lesson was for.
