Week 5 / Lesson 22 / fleet-db

Auth at the boundary

Since Lesson 03 you have been running fleet-db with --auth-dev-mode --authz-enabled=false. This lesson says exactly what those two flags switch, one at a time, and exactly what they do not.

Skill say what authenticates and what authorizes a request, in each mode Time 30 min Needs 03, 06, 11 Repos fleet-db loomcli

Why this exists: "auth" is two words

fleet-db's own doc opens by splitting the word, and the split is the whole lesson: authentication answers who is calling, authorization answers may they do this. They are separately switchable, they live in different places in the request path, and — the part people get wrong — their "off" positions are not symmetric. docs/auth.md:1-3

The word belongs on the trap words card for the same reason trust level does. "Auth is off in local mode" is a sentence with three possible meanings — one per flag — and the three have different consequences, including one that makes the server stricter.

The one idea

Authentication is chain middleware; authorization is a per-route wrapper. The auth middleware runs before the mux matches, so it cannot know which route you asked for — it only establishes an Actor and puts it in the context. The authorizer runs after the mux matched, inside the registered handler, so it knows the route and its one permission — and it cannot see the request body. Everything else in this lesson follows from those two positions.

Concretely, in the chain built by NewServer: RequestID → metricsOuter → Logging → auth → RateLimit → ContentType → Recovery → routeCapture → mux. The auth middleware is one of the extra entries appended by main; the mux sits at the far end. internal/api/server.go:34-41, cmd/fleet-db/main.go:508-535

The workspace validator is a handler wrapper rather than chain middleware for the same structural reason, and the code says so: "Go 1.22 ServeMux only populates PathValue after route matching." internal/api/workspace_middleware.go:24-25

What each flag actually switches

Three booleans, all in one struct, all defaulting to the secure position — which for DevMode means false:

The flags are --auth-enabled, --auth-dev-mode and --authz-enabled, and the flag help is unusually honest about the middle one: "enable X-Actor dev-mode header source". internal/config/config.go:462-464. Environment equivalents are FLEET_AUTH_ENABLED, FLEET_AUTH_DEV_MODE, FLEET_AUTHZ_ENABLED (config.go:1327-1354).

Enabled: install the identity middleware

Enabled is what builds the Redis key store and installs auth.Middleware into the chain. Turn it off and no HTTP code path puts an Actor in a request context — there are exactly two lines in the whole repo that do, and only this middleware is behind this flag. The other is the RPC socket's connection handler, which the flag does not reach — "Two doors", below. cmd/fleet-db/main.go:483-514, internal/auth/middleware.go:95, internal/auth/conn_handler.go:59

The trace: loom repo add, in local mode

Hop 9 of Lesson 06 was "the write — which is two HTTP calls". Here is what happens to those two calls at fleet-db's front door, under the flags Lesson 03 gave you.

  1. internal/bootstrap/openstore.go:94-98, 176-185 One client config, both modes. APIKey comes from LOOM_FLEET_DB_API_KEY; Actor comes from resolveActor() — LOOM_FLEET_DB_ACTOR, else LOOM_AGENT_NAME, else $USER. Local and cloud differ only in BaseURL.
  2. internal/fleethttp/fleethttp.go:35-46 Headers, empty fields skipped. Authorization: Bearer when a token is set; X-API-Key and X-Fleet-API-Key when a key is set; X-Actor when an actor is set. With no key configured — the normal local case — the only identity on the wire is your Unix username.
  3. internal/bootstrap/embedded.go:366-378 loom spawned the server it is talking to. The embedded fleet-db is launched with --auth-dev-mode and --authz-enabled=false, with the reasoning in a comment right above the args ("single-user mode skips RBAC"). Lesson 03's compose stack passes the same two flags (test/local-mode/docker-compose.yml:56-57).
  4. fleet-db cmd/fleet-db/main.go:483-514 Sources assembled once, at boot. Enabled is true (nobody passed --auth-enabled=false), so the key store is built and the middleware installed; DevMode is true, so HeaderSource is appended after APIKeySource. Priority is list order.
  5. fleet-db internal/auth/middleware.go:64-78 Skip paths first. The three defaults — /healthz, /readyz, /metrics — pass straight through with no actor in context, which is why an admin route must never be put behind a skip prefix: it would 403 permanently rather than open up (docs/auth.md:91-93). Note the r.Header.Del("X-Actor") on this path too: anti-spoofing is not skipped along with the authentication.
  6. fleet-db internal/auth/middleware.go:81-111 First success wins. APIKeySource sees no X-API-Key and returns ErrNoCredentials, so the chain continues; HeaderSource returns Actor{ID: "tyson", AuthMethod: "header"}; the middleware validates it, deletes X-Actor (line 93), and stores the actor in the context. Authentication is now complete and nothing was verified.
  7. fleet-db internal/api/repos.go:64 → internal/api/authz_wrap.go:12-19 Call one: POST /api/v1/{workspace}/repos, registered as wrap(auth.PermRepoCreate, h.create). authorizer is nil, so AuthzWrap returns mw(next): the workspace validator runs, and the permission printed on that line is never read.
  8. fleet-db internal/api/workspace.go:53 → internal/api/authz_wrap.go:26-38 Call two is an admin route. PATCH /api/v1/admin/workspaces/{key} goes through GlobalAuthzWrap(nil), which does not check PermWorkspaceUpdate but does check that some actor exists. Dev mode manufactured one, so it passes. That check is the only thing between the caller and the admin API here.
  9. fleet-db internal/api/issues.go:70 → internal/api/request.go:165-173 Where a handler needs the identity, it takes it from the context. Twenty-one call sites in eight files reach for actorFromContext(r), and every one 401s without an actor — that ID becomes Event.Actor. None of them read a header; the middleware already deleted it.

Now flip one flag. With --authz-enabled left at its default, call one needs a role holding PermRepoCreate — admin or maintainer, in this workspace or globally — and call two goes through RequireGlobal, which reads only the global role and needs PermWorkspaceUpdate, which only admin holds. So loom repo add is a global-admin operation on a fully configured fleet-db. internal/auth/permissions.go:274-782, internal/infra/fleetdb/repo.go:59, 62

The pattern to copy

  1. One permission, named at the registration site. Of the 259 HandleFunc registrations in production code, 257 read wrap(auth.PermXxx, handler). The two that do not are /healthz and /readyz, two of the three default skip paths; the third, /metrics, is registered with mux.Handle instead (cmd/fleet-db/main.go:538-539, 552). grep over the registration lines is the authorization matrix; never compute a permission inside a handler. (That grep is also the fastest way into this package — see Finding Anything for the rest of the route-to-file shortcuts.)
  2. Two wrappers, two scopes. AuthzWrap for /api/v1/{workspace}/… (242 routes) and /api/v2/{workspace}/… (5 more), GlobalAuthzWrap for /api/v1/admin/… (10 routes, 3 registration sites). Choosing between them is a real design decision, and internal/api/workspace_scoped.go:10-27 is the exemplar: GET /{ws}/workspace exists precisely so a workspace-scoped developer can read its own workspace without a global grant.
  3. A privileged lane gets its own permission and its own route. The reason is structural, and the team wrote it down:

Fourth: never read identity from a header in a handler. While the middleware is installed it deletes X-Actor on every path that reaches a downstream handler — both skip loops and the success branch (internal/auth/middleware.go:66, 74, 93) — so a handler that reaches for the header gets an empty string. That is a property of the install, not of the code: the middleware exists only under if cfg.Auth.Enabled (cmd/fleet-db/main.go:483, 508), and two production readers still reach for it — ackCommand takes the header directly (internal/api/control_plane.go:1070), and actorRefFromRequest prefers the context but falls back to it (internal/api/platform.go:2669-2673, 13 call sites in skills.go and platform.go). Under --auth-enabled=false both read whatever the client sent. Copy actorFromContext (internal/api/request.go:165-173), not those two: the context is the only authority.

Trap — "stripped on all code paths"

docs/auth.md:89 says X-Actor "is stripped in all code paths — skip paths, successful auth, and even after failed auth." The last clause is false. There are exactly three r.Header.Del("X-Actor") calls, at middleware.go:66, 74, 93, and line 93 sits inside the err == nil branch. An invalid actor (:85-90), a bad credential (:106-110) and an exhausted source chain (:113-114) all write a 401 and return with the header untouched. No harm follows — nothing downstream runs — but do not write a test that asserts the strip on a failure path, and do not repeat the sentence in a design review. Nor is the fix "no handler ever sees it": the guarantee is "while the middleware is installed, no handler sees a client-supplied value", and two handlers do still read the header (control_plane.go:1070, platform.go:2673).

Trap — "authz off means the admin API is wide open"

It is not open, and it is not closed either. GlobalAuthzWrap(nil) rejects a request with no actor with a 403, but performs no permission check on a request that has one (internal/api/authz_wrap.go:26-38). So on a dev-mode stack the guard stops an anonymous caller and waves through anyone who types a name into a header. Both halves of that sentence are load-bearing: quote only the first half and you will over-trust the deployment, quote only the second and you will file a bug against a deliberate hardening.

Trap — "X-Actor authorizes the caller"

loomcli's own field comment says the actor header is "for audit + (in dev-mode) authorization" (internal/infra/fleetdb/client.go:49-51 loomcli). Read that carefully: the header only ever supplies identity. Authorization is a Redis lookup keyed by that identity — fleet-db:{ws}:acl:roles:{actorID}, falling back to fleet-db:acl:global-roles:{actorID} (internal/auth/acl.go:33-56, internal/storage/keys.go:981-987, 1001-1006). With authz on, X-Actor decides whose role is read, never what that role permits.

Trap — "set a bearer token for production"

Two loomcli comments tell you to (internal/infra/fleetdb/client.go:9-13 and internal/backend/fleet/config.go:20-23 loomcli), and fleethttp.Auth.Apply will happily set the header. fleet-db never constructs BearerTokenSource: main.go:498 is a TODO, and NewBearerTokenSource has no non-test caller at 000793b. A bearer-only request against a production configuration falls through every source and gets a 401 (internal/auth/middleware.go:113-114). X-Fleet-API-Key is a second decoy: loomcli sets it beside X-API-Key (internal/fleethttp/fleethttp.go:40-41), the string appears nowhere in the fleet-db tree, and the server that does read it is loom serve's own fleet-mode registration endpoint (internal/webui/fleet/handlers.go:70-85 loomcli).

A third collision, already on your glossary card: fleet-db's auth.Role is an RBAC tier (admin | maintainer | developer | viewer), while Role is an agent persona with its own workspace-scoped CRUD at /api/v1/{ws}/roles. Both repos flag the clash in code: docs/glossary.md:247-250, internal/storage/keys.go:1289-1292.

Two doors, and the flags reach them differently

fleet-db also serves a line-delimited JSON-RPC surface on a Unix socket, and its authentication is not switchable. When RPC is enabled, the handler is always wrapped in auth.NewAuthConnHandler(..., auth.NewPeerCredSource(), ...) and ConnAuthEnabled: true is a literal in the call (cmd/fleet-db/main.go:1068-1077). Identity comes from kernel peer credentials once per connection, not per request (internal/auth/conn_handler.go:36-61), and a failure closes the socket. Authorization is switchable there — the same possibly-nil authorizer is passed in, and checkPermission returns nil when it is (internal/rpc/methods.go:108-120).

So "the auth flags" are precisely: flags about the HTTP door's authentication, plus one flag about authorization on both doors. The embedded local-mode fleet-db sidesteps the question entirely by passing --rpc-enabled=false (internal/bootstrap/embedded.go:372, 377 loomcli).

Check yourself

From memory, without scrolling: name the two mechanisms this lesson separates, say where each one sits relative to the mux, and say what each one can and cannot see.

Authentication — auth.Middleware, chain middleware, runs before the mux matches. It sees headers and the path, and it does not know which route will match. Output: an Actor in the request context, or a 401. internal/api/server.go:34-41, internal/auth/middleware.go:61-116

Authorization — Authorizer.Require / RequireGlobal, a handler wrapper composed at registration, runs after the mux matched. It sees the matched route's single Permission, the {workspace} path value where there is one, and the actor's role from Redis — and it cannot see the request body. internal/auth/authz.go:37-104, 108-150

They are switched by different flags, and with no actor present the first wrapper skips itself while the second returns 403.

A stack runs with --auth-dev-mode --authz-enabled=false. A request arrives with no headers at all. What does it get?

  • 200, because authorization is disabled on this server
  • 403, because no actor reached the request context
  • 401, because each identity source declined the call
  • 500, because the header source found nothing to read
--auth-enabled was never turned off, so the middleware is installed. APIKeySource and HeaderSource both return ErrNoCredentials, the loop falls out of the bottom, and the middleware answers 401 "authentication required" (internal/auth/middleware.go:113-114). The 403 option is the near miss and worth pinning down: 403 is what an admin route returns for a missing actor — but that wrapper sits inside the handler, and the middleware has already answered 401 long before the mux gets to it.

Which change makes a workspace write handler more likely to reject you, not less?

  • Adding --auth-dev-mode to a stack that had authz enabled
  • Adding --auth-enabled=false to a stack in dev mode
  • Adding --authz-enabled=false to a stack in dev mode
  • Adding --rpc-enabled=false to a stack in dev mode
Turning authentication off is stricter here, not looser: with no middleware there is no Actor, and the 21 call sites of actorFromContext return 401 rather than attribute an event to nobody (internal/api/request.go:165-173, internal/api/issues.go:70-74). Dev mode and --authz-enabled=false both only ever remove checks; the RPC flag does not touch the HTTP door at all.

Reaching back to Lesson 06: with authz at its default, which role can run loom repo add end to end?

  • Only an actor that holds the global admin role
  • Any actor holding the maintainer workspace role
  • Any actor holding the developer workspace role
  • Any actor with a role recorded in that workspace
The command is two calls (internal/infra/fleetdb/repo.go:59, 62). Call one needs PermRepoCreate, which admin and maintainer hold. Call two is PATCH /api/v1/admin/workspaces/{key}, and RequireGlobal consults only the global role and requires PermWorkspaceUpdate — admin-only. Maintainer is the sharp near miss: it clears the first call and fails the second.

The wrapper applied to every /api/v1/admin/… route, and the one that rejects an actorless request even when the authorizer is nil, is .

internal/api/authz_wrap.go:24-41. Three production call sites: apikey.go:50, workspace.go:49, workspace.go:259. Its sibling AuthzWrap guards the other 247 workspace-scoped routes — 242 under /api/v1/{workspace}/ plus 5 under /api/v2/{workspace}/ — and does the opposite on a missing actor.
