Week 4 / Lesson 16 / Testing

What proves what

Every test run in this repo is a claim about reality, and the tiers differ in what they are allowed to claim. This lesson is about picking the cheapest tier that can settle your question — and then writing down, honestly, what the run did and did not establish.

Skill choose the right test tier and state honestly what your run proved Time 35 min Needs 04, 03 Repos loomcli fleet-db

Why this exists

Loom orchestrates AI agents. Almost nothing it does can be proved by inspection, so the team's whole quality story rests on runs — and a run is only as good as the sentence you write about it afterwards. The failure mode this repo is organised against is not a flaky test. It is an honest engineer reporting more than they measured: "tested locally", "verified on a real stack", "the e2e suite passed".

The runbook says so in as many words, twice. Do not overclaim; if a behaviour cannot be reached through the product's own workflow, report it blocked or unverified rather than manufacturing state that looks like evidence.

The one idea

A test tier is not a quality level, it is an evidence class. Moving up the ladder does not make your result "better" — it changes which sentences you are entitled to write. Pick the lowest tier that can settle the question, then say exactly what it settled.

The trace: what a green dogfood run actually says

Lesson 03 taught you to bring this stack up without wrecking a colleague's. This is the other half: what a clean run of it is worth. Follow the evidence, not the containers.

  1. Makefile:258-262 Four services come up under your compose project: redis, fleet-db, loom-local, and a Caddy UI. Everything below is real Loom code running as real processes — that part of "real" is earned.
  2. test/local-mode/docker-compose.yml:56-57 fleet-db starts with --auth-dev-mode and --authz-enabled=false. Authorization is off in this stack. A green run is silent about every permission question, and a permissions regression cannot fail here.
  3. test/local-mode/docker-compose.yml:80 LOOM_BACKEND: localdogfood. This is the realness axis, set in one line. The thing standing in for the model is a shell script on the container's PATH.
  4. test/local-mode/loom-backend-localdogfood:25 The planner's "design" is a string literal. Not generated, not evaluated — typed into the harness by a human. No run of this stack can say anything about planning quality.
  5. test/local-mode/loom-backend-localdogfood:43-55 The coder claims, appends, commits, closes. loom claim, append to local-mode-agent-output.txt, git commit, then loom data close. Every one of those is a genuine product command — the plumbing under them is under test even though the decision to run them is not.
  6. test/local-mode/verify-local-mode.sh:179-194 Thirteen polled assertions, over the HTTP API only. API reachable → tasks exist → planner in review → planner has a design → planner completed session → planner transcript flag → planner transcript entries → coder closed → coder session → coder transcript flag → coder transcript entries → coder diff flag → and last, the one that matters.
  7. test/local-mode/verify-local-mode.sh:161-167 The diff must literally contain the artifact name. This is the assertion that upgrades "the daemon ran" to "the daemon produced a recorded code change". Drop it and a stack that recorded a diff of something else still goes green — the check before it asks only whether diff metadata exists, never what is in it :145-151.

So the honest sentence after a green run is: "Deterministic: real Loom and fleet-db processes, scripted model substitute, authz disabled. Proves the claim → session → transcript → diff loop records correctly. Says nothing about model behaviour or permissions." That is one sentence longer than "verified locally", and it is the entire skill.

Trap — "real" is two different words

You will read "real" in two senses and they do not imply each other. Real backend process means a real loom serve and a real fleet-db behind the specs — that is what test-e2e-real-smoke buys, and the script builds fleet-db from the sibling checkout to get it scripts/start-e2e-server.sh:86-94. Real AI backend means an actual agent CLI, which needs make local-mode-codex-up and mounted host credentials test/local-mode/docker-compose.codex.yml:14, :25. A localdogfood stack is real in the first sense and not the second; test-e2e-real-smoke is real in the first sense only. If auth for the real path is missing, the runbook's instruction is to report the blocker, not to fall back and keep the word. .agent-skills/loom-pr-test/SKILL.md:92

Where a Go test sits on the ladder

The unit tier is deliberately hermetic, and three mechanisms hold it there.

Dependencies are injected, never discovered. One constructor hands you a *cli.Deps with its collaborators mocked and the clock frozen at 2026-01-01, so anything reading time through Deps.Clock is deterministic. The freeze buys nothing outside that path: Logger is the real slog.Default(), and nothing stops a test calling time.Now() itself.

The gate enforces the boundary. check-no-raw-exec.sh flags exec.Command in test files, but a file escapes three ways: its name ends in _e2e_test.go or _integration_test.go, so the find never hands it over; its first five lines carry an integration, e2e, container or playground build tag; or the offending line carries //nolint:norawexec. scripts/check-no-raw-exec.sh:19, :27, :40-43 Shelling out is how a "unit" test quietly becomes something else, so the tier is a gate check rather than a convention — but a porous one. makefile_test.go:29 is an untagged unit test that shells out to make behind a nolint, and internal/driver/flue_integration_test.go carries no build tag at all and is exempt purely by its filename.

Redis is in-process. Eighteen Go test files take the same shape — miniredis.RunT(t), a client from mr.Addr(), cleanup registered on t. internal/kv/scripts_test.go:13-19 It is not a test-only library here, though: eleven production files embed it as the in-process Redis behind loom serve internal/webui/localredis/manager.go:148, so the import on its own tells you nothing about the tier. And testutil.ClearLoomEnv(t) blanks the thirteen desktop variables that would otherwise make a test resolve your real workspace. internal/testutil/testutil.go:13-37

Trap — the green test that proves nothing

TestConcurrentClaims fires ten goroutines at one task through the real Lua claim script internal/kv/scripts.go:46. It looks like a proof of mutual exclusion. It is not: the assertion is successCount < 1 → fail, i.e. at least one winner. The comment above it claims miniredis is single-threaded so the Lua executes atomically, then allows that "multiple can succeed … due to serialization", and settles for at least one. Whatever the reasoning, the assertion that ships does not test exactly-one-wins. That is established two tiers up, by the distributed smoke stack: "two supervisor actors contend for one issue and exactly one wins" on shared Redis with two loom serve processes. internal/kv/scripts_test.go:396-401 · test/distributed/README.md:21 This is the guarantee from Lesson 08 — and the unit test named after it does not test it.

Where a frontend test sits

The Playwright project is the tier selector, and the projects are not interchangeable. chromium and chromium-ci run with only a Vite dev server behind them internal/webui/frontend/playwright.config.ts:163-168; the specs intercept their own API routes. integration* and api* only mean anything when RUN_INTEGRATION_TESTS=1 flips isSelfContained and Playwright starts a real server on ports 8090 and 3100 internal/webui/frontend/playwright.config.ts:15, :26-28, :146-156. The -smoke and -regression variants are the same project narrowed by grep: /@smoke/ and grep: /@regression/ internal/webui/frontend/playwright.config.ts:244, :262.

Vitest defaults to a node environment; any test touching the DOM opts in per file with a @vitest-environment jsdom docblock, which 339 files under src/ do. Coverage thresholds are 60 across all four metrics. internal/webui/frontend/vite.config.ts:219-239

Trap — "the browser suite passed"

make test-e2e runs the chromium project; make test-e2e-ci runs chromium-ci, which is the same suite minus a checked-in quarantine list of specs that currently fail, and with --ignore-snapshots because the committed PNGs were generated on one machine. Makefile:459-469 · internal/webui/frontend/playwright.config.ts:64-74 The two commands give different verdicts on the same code, so naming the project is part of reporting the result. The list may only shrink — repairing a spec means deleting its line.

One real-stack suite enforces the opposite discipline — fail, never skip. test/fleetdb/ui runs a preflight that aborts the whole run rather than skipping, because a suite that quietly passes when no stack was there is a silent fallback.

The Playwright real-stack projects do not hold that line. Under internal/webui/frontend/tests/e2e/, twenty-four of the twenty-six api/ and integration/ specs open with a top-level skip keyed on an environment variable api/issue-lifecycle.api.spec.ts:11, and some skip mid-test on state they did not find api/realtime-updates.api.spec.ts:438 · integration/skills.integration.spec.ts:133, :218. Which is why "the smoke suite passed" needs the skip count attached to it.

The pattern to copy: report in coordinates

The handshake from Lesson 02 is the input side — echo the request back as (depth, realness, provisioning, polarity, target) before you run anything slow. The output side is the same coordinates plus the evidence class, and the runbook lists what a report must contain: the exact command path, the stack URLs and ports, whether the backend was deterministic or a real CLI, the API or browser evidence, any blocked condition, and how to stop anything you left running. .agent-skills/loom-pr-test/SKILL.md:236-244

Two methodology rules ride along with it, both cheap and both learned the hard way. Never let the CLI verify its own writes — loom role show reads through the same client path as loom role set, so a stale cache round-trips silently; cross-check against fleet-db over HTTP. And anchor your success patterns: grep -qE "^Created workspace ACME$", never grep -q Created, which matches the startup line "Created embedded fleet-db". docs/testing/known-issues.md:35-39

Check yourself

From memory: you ran make local-mode-up and then make local-mode-verify, and both were green. Write the one-sentence report — name the evidence class, and name two things the run did not establish.

Evidence class deterministic: real Loom and fleet-db processes in containers, with a scripted shell substitute standing in for the model (LOOM_BACKEND: localdogfood, test/local-mode/docker-compose.yml:80).

It proves the claim → session → transcript → diff loop records correctly, ending at the assertion that the coder's recorded diff contains local-mode-agent-output.txt test/local-mode/verify-local-mode.sh:161-167.

In loomcli, what does the integration build tag select when you run make test-integration?

  • Every spec in the Playwright integration and api projects
  • Nothing extra — no Go file carries that build tag today
  • The tests under test/testenv that need a real fleet-db
  • Each test file that shells out through exec.Command
Zero files in loomcli carry //go:build integration at ce4df56fb, yet Makefile:50-52 still passes TEST_TAGS=integration, so the target runs the same set as make test. Treat "integration" here as a depth word, not a guarantee. The third option is the sharp miss: test/testenv is a real disposable fleet-db stack driven by scripts/test-env.sh, but nothing tags Go tests to select it — you point tests at it with env vars instead. And the word is not empty everywhere: fleet-db has 20 files behind that same tag, and its own make test-integration really does run go test -tags integration — over five named package paths fleet-db Makefile:44-52, which reach 14 of those 20. The tagged tests in internal/rpc, internal/storage and internal/testutil are not in the list.

make gate passed on your branch. Which claim have you earned?

A teammate writes: "Verified on a real stack — the coder agent produced a diff." They ran make local-mode-up then make local-mode-verify. What is wrong with the sentence?

  • The model was a shell script, so the class is deterministic
  • The verifier polls containers, so the API was never exercised
  • The verifier skips its assertions when the stack is unreachable
  • The diff assertion is disabled unless authz has been enabled
The stack is real Loom and real fleet-db, so "real stack" is half-earned — but LOOM_BACKEND: localdogfood test/local-mode/docker-compose.yml:80 makes the agent a shell script that appends a known filename and commits it, so the run is evidence class deterministic and "the coder agent produced" overclaims. The second option is the plausible one to reject carefully: polling the API rather than the containers is exactly what the verifier does, and it is the right method — wait_for loops with a 240-second deadline against HTTP endpoints. test/local-mode/verify-local-mode.sh:30-51, :179-194 The method was fine; the realness label was not.

Count the evidence yourself

  1. In loomcli, run grep -rl "go:build integration" --include='*.go' . | wc -l. Then run the identical command in the fleet-db worktree. Write both numbers down. Which repo's make test-integration means what it says?
  2. Run go test ./internal/kv/ -run 'TestClaimTask_Success$' -v. It passes in under a second with no Redis on your machine. Name the mechanism, then open internal/kv/scripts_test.go:365-401 and state, in one sentence, what TestConcurrentClaims asserts and what it therefore cannot prove.
  3. Read test/local-mode/verify-local-mode.sh:179-194 and list the thirteen assertions. Mark every one that would still pass if the coder wrote its output to a different filename. Now you know why the last line exists.
  4. Reaching back to Lesson 04: find the gate step that would fail if you added exec.Command to a new unit test, then read the three exemption routes at scripts/check-no-raw-exec.sh:19, :27, :40-43. Say which route is the weakest, and what a reviewer therefore has to check that the gate does not.
  5. Optional, and only with the safety rule from Lesson 03: if you bring a stack up to check the trace, run podman ps first, treat every existing stack as someone else's, launch with your own LOCAL_MODE_COMPOSE_PROJECT and an unclaimed port block, and tear down only your own project. Never podman system prune. .agent-skills/loom-pr-test/SKILL.md:94-121, :283
