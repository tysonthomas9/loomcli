Week 3 / Lesson 11 / Execution

Things that are not boundaries

Loom ships four isolation-shaped features. One is an OS boundary; the others are an admission check, a backend flag, and a sentence in a prompt. Telling them apart is the difference between a design that holds and a design built on a guarantee that does not exist.

Skill tell a real security boundary from something that only sounds like one Time 35 min Needs Lesson 10 Repos loomcli fleet-db

Why this lesson exists

sandbox. trust_level. read_only. denied_tools. Read as a group they suggest a system in which untrusted agent code is contained. Read as code, they are four unrelated mechanisms at four different layers, and only one of them is a boundary Loom puts around a process. The design doc opens by saying exactly that. docs/design/execution-isolation.md:1-11

The one idea

The container goes around the program that decides what work exists. It does not go around the process that runs the model and edits your repository. On the driver plane that process is the built-in leaf, exec.CommandContext(ctx, "node", launcherPath) in a host worktree, in every LOOM_DRIVER_SANDBOX mode (internal/driver/task_bridge.go:366); on the daemon plane it is the backend CLI a loom <role> --daemon-mode worker invokes (internal/cli/daemon/supervisor/spawn.go:101-109). Neither is containerized.

Three levels, one sandbox

LevelWhat runs thereContainerizable
L1 — DriverRun bundleThe Flue workflow bundle: the orchestration program that decides what tasks existYes — LOOM_DRIVER_SANDBOX=container
L2 — TaskRun leafThe process that invokes the backend CLI and edits codeNo — the host bridge spawns node directly
L3 — daemon agentThe loom <role> --daemon-mode worker the supervisor spawnsNo — plain host process, backend CLI's own sandbox off

docs/design/execution-isolation.md:13-19

The L1 container is real: rootless podman (docker fallback), --read-only, --security-opt no-new-privileges, mandatory memory/CPU/pids caps, and a host filesystem reachable only through the bundle and launcher identity mounts. internal/driver/sandbox/container.go:159-170, :298-311, :333-347 So when someone says "agents run in a sandbox", ask which level they mean.

You do not have to take the doc's word for the gap. The two executors are the evidence. Executor — the L1 one — carries a launcher seam:

HostBridgeTaskExecutor — the L2 one, the thing that actually runs your model — has no launcher field of any kind. internal/driver/task_bridge.go:47-80 There is no flag, no environment variable, and no serve wiring that puts the L2 leaf in a container. That absence is the isolation model. The one escape is remote, not local: the daytona-task-runner named runner clones the repo into someone else's machine. docs/design/execution-isolation.md:138-139, :171-173

trust_level refuses; it does not confine

untrusted reads like "Loom will contain this". It means "Loom declines to start this here".

The refusal happens before Launch: runBuiltFlueServer resolves a launcher, calls the gate, and returns its result directly — nothing spawned, no fallback. internal/driver/executor.go:748-757 And it is structured, not a bare error: failed, errorClass=sandbox_required, retryable:"false", plus a summary naming both ways out. Copy that shape when you write a gate. internal/driver/sandbox/policy.go:22-27, :80-90

Note what the escape actually is at L1. The gate passes when the driver is trusted or when the launcher implements IsolatingLauncher — and only the container launcher does. internal/driver/sandbox/policy.go:39-47, internal/driver/sandbox/container.go:157

Unknown means untrusted, in both repos

Trust is an exact string compare, so empty, misspelled, or from-a-future-release all fail closed; the policy test pins "" and "sorta-trusted" as refusals so nobody "fixes" it into a substring match. internal/domain/platform.go:57-62, internal/driver/sandbox_policy_test.go:46-48

fleet-db The field lives on the driver row over there, so the same decision had to be restated in the schema. The Postgres migration is its clearest statement anywhere in either repo:

  1. internal/storage/platform.go:2866-2869 Reading a row does not repair it. A missing trust_level deliberately stays empty, because readers already treat unknown as untrusted.
  2. internal/models/platform.go:106-111 Writing one does. Driver.Validate stamps untrusted when the level is empty, so every post-upgrade write carries an explicit level.

The two gates are not the same gate

L2 has trust gates too. They look like the L1 one and are not: neither consults a launcher, because there is no launcher to consult.

Read that error message as documentation. The sibling gate on the request path says the same thing and fails the enqueue before a TaskRun row exists. internal/driver/task_bridge_session.go:119-124 Note the first branch too: the gate fires only for a named runner — a request naming a sibling entrypoint in the bundle.

Trap — "container mode will let my workflow run"

The wrong belief: loom workflow build registered an untrusted version, so turning on LOOM_DRIVER_SANDBOX=container will let it run.

The reality: container mode unblocks the workflow and nothing else. At L1 the gate passes when the launcher isolates; at L2 the gates check trust and stop. So the bundle starts and every named-runner task it requests dies sandbox_required. Only trust unblocks a named runner — an operator approving the version, which writes an approved_version:<id> metadata key that DriverVersionEffectiveTrust reads back as trusted. internal/cli/workflow/workflow_cmd.go:236, internal/driver/approval.go:13-17, :81-84

read_only and the tool lists

These role knobs reach a backend as LOOM_READ_ONLY / LOOM_ALLOWED_TOOLS / LOOM_DENIED_TOOLS. They are backend tool policy, and whether they mean anything depends on which backend resolved. Two predicates decide, over deliberately different sets: SupportsToolControl is claude alone; SupportsHardReadOnly is claude, codex, gemini — those with "a mechanism that makes read_only true regardless of what the model decides to do". internal/cli/backends/backend_safety.go:112-125

Look at the return types. Tool lists fail closed — an error, refuse the run, because there is no soft version of an allowlist. read_only degrades — a warning string, run anyway, on the prompt preamble alone. The asymmetry is deliberate: failing closed on read_only was tried and refused every planner on every soft backend, because seedBuiltInRoles gives the built-in plan role ReadOnly: true on every workspace. internal/cli/backends/backend_safety.go:142-147, internal/cli/serve/workspacemgr/workspace_store.go:479-487

Even on a hard backend, be precise about what you got. Codex's read_only selects --sandbox read-only instead of --dangerously-bypass-approvals-and-sandbox; claude's denies Write,Edit,NotebookEdit,Bash (Bash on purpose — a shell writes through redirection). Real, but it is policy inside a process that still has your whole filesystem. internal/cli/backends/backend_safety.go:56-60, :91-98

Trap — IS_SANDBOX=1

The wrong belief: the code exports IS_SANDBOX=1 onto the agent process, so the agent is in a sandbox. One comment in the tree still says so, and it is wrong.

The reality: it is a shim. claude-code refuses --dangerously-skip-permissions under root unless IS_SANDBOX is set, so Loom sets it to stop the refusal. The Go site says so itself — "loom does NOT create a container around an agent … so on a host run this asserts a sandbox that is not there". internal/cli/backends/backend_claude.go:258-268 The L2 leaf exports the same variable with a comment claiming the runner runs "inside loom's isolated task-run container". No such container exists — its caller spawns node on the host. The variable is evidence of nothing. internal/workflows/builtin/local-task-runner.ts:518-521, :456 The design doc block-quotes an older version of the Go comment, one that did claim a container; that text is gone from the tree, so read the quote as history. docs/design/execution-isolation.md:126-129

Egress: the part that is real, and its exact shape

For a containerized L1 run only, network reach is bounded by LOOM_DRIVER_SANDBOX_EGRESS. An empty value is not "unset, so anything" — it resolves per trust level, fail closed.

ModeWhat the launcher doesEmpty resolves here when
allEngine default network — unrestricted egresstrust is exactly trusted
serve-only--network=none plus a unix-socket relay to serveanything else, empty included
none--network=none, no relay — reaches nothingnever (explicit only)
delegatedEngine default network; enforcement lives outside the launcher, mode recorded truthfullynever (explicit only)

internal/driver/sandbox/egress.go:58-73, :95-105

Only serve-only and none are enforcement. delegated is an honesty mechanism: the launcher applies the default network and records the mode anyway, so a deployment whose NetworkPolicy does the real work keeps a truthful audit trail. Read egress_mode=delegated on a placement record as "somebody else may have bounded this", never as "the launcher bounded it".

And the property that makes serve-only worth anything lives on the host, not in the container: serveSocketRelay forwards every accepted connection to exactly one TCP address — the serve API address captured at launch. Nothing the container sends can redirect it. A run with no LOOM_DRIVER_API_URL degenerates to plain --network=none, never to the engine default. internal/driver/sandbox/egress.go:266-269, :158-166

On macOS the relay leg does not function: host unix sockets do not cross the podman-machine VM boundary — virtiofs shares the inode, not the listener. The --network=none half still applies. Do not chase it as a bug on a Mac. internal/driver/sandbox/egress.go:28-32

Check yourself

From memory, and be specific: LOOM_DRIVER_SANDBOX=container is set, and a trusted builtin workflow requests a local-task-runner task that runs codex on your repo. What is inside the container, and what does the codex process get?

Inside: the workflow bundle, and nothing else — rootless, --read-only, no-new-privileges, capped, and on the engine default network, because the driver is trusted and egress is unset. internal/driver/sandbox/container.go:298-310, internal/driver/sandbox/egress.go:95-105

Outside: everything that matters to your machine. The worker spawns node on the host in a git worktree of your repo (internal/driver/task_bridge.go:366), and local-task-runner is the single entrypoint given the widened env allowlist — so the child inherits ANTHROPIC_API_KEY, OPENAI_API_KEY, GITHUB_TOKEN and the rest, then invokes codex with --dangerously-bypass-approvals-and-sandbox. internal/driver/env.go:82-98, internal/driver/task_bridge_artifacts.go:284-289, internal/workflows/builtin/local-task-runner.ts:456

You set LOOM_DRIVER_SANDBOX=container. Which process now runs inside a container?

  • The workflow bundle that decides what tasks exist
  • The task leaf that runs the model and edits code
  • The daemon agent the supervisor spawns per role
  • Every process the serve run loop spawns for it
Only L1, the orchestration bundle. The second option is the one to be sure about: the L2 leaf is spawned by exec.CommandContext(ctx, "node", launcherPath) in a host worktree, and HostBridgeTaskExecutor has no launcher field that could change that. internal/driver/task_bridge.go:47-80, :366

An untrusted named runner is requested while LOOM_DRIVER_SANDBOX=container is on. What happens?

  • It runs containerized, because the launcher isolates
  • It is refused: the L2 gate never consults a launcher
  • It runs on the host with a soft-enforcement warning
  • It stays queued until an operator raises the limit
Both L2 gates check trust and stop. refuseUntrustedTaskRunnerExecution never looks at a launcher, because the host bridge has none. The first option is exactly the L1 rule — RefuseUntrustedPlacement does pass when the launcher isolates — and assuming it generalises is the expensive mistake. internal/driver/task_bridge_session.go:127-140

A role sets read_only and resolves to the cursor backend. What is actually in force?

  • A prompt preamble only — the agent can still write
  • An OS sandbox policy refusing every write attempt
  • A denied-tools list covering Write, Edit and Bash
  • Nothing — the run is refused before anything runs
Cursor is not in SupportsHardReadOnly, so ValidateSafetyKnobs returns a warning and the run proceeds on the preamble. The last option is the sharp wrong answer: refusing is what tool lists do, and collapsing the two knobs into one policy is the trap-word habit from Lesson 02. internal/cli/backends/backend_safety.go:116-125, :152-165
Before the exercise

Everything below is go test and grep against the checked-out repos. Do not set LOOM_DRIVER_SANDBOX=container against a running stack to try it: podman stacks and their ports are shared machine state, and up --build on a project name someone else created silently recreates their containers.

Prove the gate never spawns, then find the seam that is missing

  1. Run go test ./internal/driver -run TestTrustPlacementPolicy -v. Read internal/driver/sandbox_policy_test.go:97-113 and say in one sentence why it sets NodePath: "/nonexistent/loom-test-node".
  2. Run grep -n "Launcher" internal/driver/task_bridge.go, then the same grep on internal/driver/executor.go. Write down what the diff tells you that no comment in either file states.
  3. Run go test ./internal/driver/sandbox -run TestResolveSandboxEgress -v and name the two subtests that pin the fail-closed default. Then say what egress_mode=delegated on a placement record does not tell you.
  4. Reaching back to Lesson 02: sandbox, trusted, and read_only are all trap words here. Write the one-line disambiguation you would give a teammate who used each of them loosely in a design review.
You succeeded when You can state that a driver_runtime start-failure result would have proved the launcher ran, so sandbox_required proves it did not — and you can point at internal/driver/task_bridge.go:366 as the line where your host shell, your PATH, and — for the bundled local-task-runner — your provider keys reach the model, with LOOM_DRIVER_SANDBOX=container still set.
