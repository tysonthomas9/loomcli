Week 3 / Lesson 08 / Concurrency

Claiming without collisions

This is the problem Loom exists to solve. Many agents, one queue, no coordinator — and no two agents may ever work the same task. Here is exactly how that is guaranteed, across both repos.

Skill reason about the claim race and where its guarantees live Time 40 min Needs 05, 07 Repos loomcli fleet-db

Two assignment problems, deliberately separated

MechanismAn ownership lease in fleet-db.Every runner lists ready tasks, scores them locally, and races everyone else through an atomic claim.
There is no assignment service, on purpose

No central assign-next endpoint hands work out: the product design says Loom should not start with one, and lists building it as out of scope for the MVP and the first cloud implementation docs/product/daemon-agent-runtime-architecture.md:34-37, 451-457. Every runner independently decides what it wants and then races for it. Correctness comes from the race being atomic, not from the race being avoided. If you catch yourself designing a coordinator, you are working against the architecture.

Layer 1: who may run this agent at all

The invariant is (workspace_id, agent_id) → at most one active owner docs/product/daemon-agent-runtime-architecture.md:44, held as an agent ownership lease in fleet-db with a 30-minute TTL internal/cli/daemon/supervisor/supervisor.go:248. The supervisor acquires it at the top of every supervise iteration, before it takes a concurrency slot or runs preflight internal/cli/daemon/supervisor/supervisor.go:294, 306, 313, then heartbeats it every ttl/4 capped at 30 seconds internal/cli/daemon/supervisor/ownership.go:160-166 — at a 30-minute TTL the cap always wins, so in practice it is always 30 seconds.

Acquisition distinguishes three outcomes, not two: acquired, held-by-other, and inconclusive internal/cli/daemon/supervisor/ownership.go:19-28. That third one exists because the verify-before-kill path must branch on it internal/cli/daemon/supervisor/ownership.go:263-275 — "I could not reach the server" is emphatically not "nobody owns this."

Trap — clocks

PID files, flocks, and "is the process still alive?" checks are conveniences. Where the control plane is wired up, only a server-arbitrated lease decides who may run — with two deliberate escapes: no ControlStore or no resolved workspace, and a server that 404s the lease endpoint, both return acquired and let the supervisor proceed unguarded on purpose internal/cli/daemon/supervisor/ownership.go:31-35, 57-61. Where the lease does apply, the code is deliberately paranoid about never comparing a server-returned timestamp against the local clock: ownershipWithinValidity permits fail-open only while the local monotonic and the local wall clock both agree that less than ttl has elapsed since the last confirmed renewal, and either clause expiring ends it. internal/cli/daemon/supervisor/ownership.go:294-322

Layer 2: the atomic step inside a non-atomic claim

Now the interesting half. A runner picks a candidate task and POSTs /issues/{id}/claim internal/backend/fleet/claim_release.go:27; fleet-db routes that to the issue service fleet-db internal/api/claim.go:34, 79. The whole race is settled in that service's first step, and nothing after it is atomic. The step is one small Lua script that takes the issue lock:

Then, in ordinary Go, under the protection of that lock:

  1. issue_service.go:510-515 Take the lock. HELD becomes ErrLockHeld becomes ErrAlreadyClaimed. This is the tie-break — everything below runs under the lock it took.
  2. issue_service.go:517-526 Validate existence. Read the issue after the lock — the comment says "to avoid TOCTOU". If it does not exist, release the lock again and return ErrNotFound.
  3. issue_service.go:527-545 Validate claimability, with two escape hatches first: the same actor re-claiming its own in_progress task returns immediately with no event, and an in_progress task under a different assignee whose lock has expired is a stale takeover that skips the check. Otherwise only open, blocked, deferred, and review pass, and a failure releases the lock fleet-db internal/models/status.go:98-105.
  4. issue_service.go:557-574 Append the claim event, then project it. The projection is what moves the issue between status sets and assignee sets and ZREMs it from the ready queue — a separate step, after the event is already durable.
The lock is the guarantee; the rest is not atomic

Taking the lock and repairing the indexes are separate steps, so there is a window. Between them the issue is still open and still a member of queue:ready, and a competitor's ready query — which reads the ZSET directly and only filters on status when the caller asks it to — will still list it fleet-db internal/storage/ready.go:501-506, 594-600. What the competitor cannot do is take the lock, and that is enough. Projection sits on top as best-effort: a failure is logged and left for the background catch-up rather than failing the claim, so the ready queue can lag a claim that already succeeded fleet-db internal/service/issue_service.go:83-109.

fleet-db does carry the tidier design: a single claim script that takes the lock, validates, mutates, and repairs all five index families in one atomic shot fleet-db internal/storage/claim.go:14-65, mirrored for reading at internal/storage/lua/claim_issue.lua. The server never runs it — grep -rn '\.ClaimIssue(' --include='*.go' . in fleet-db returns only _test.go files, the storagetest helper package, and internal/api/claim.go:79, which calls the service, not the storage. Read it as the guarantee it documents, not as the code that ran.

Notice too that blocked and review are claimable. That is the Lesson 02 vocabulary paying off: blocked-the-status means "a human should look", not "no agent may touch it".

Claimable is not the same as offered

There are two independent gates here, and conflating them will mislead you for months. The claimability check decides what a claim is allowed to take — four statuses. The ready queue decides what an agent is ever shown, and it is far narrower: IsReadyEligible returns false for anything that is not open, for epics, and for a future defer_until fleet-db internal/storage/ready_eligible.go:35-48. The queue itself is maintained to nearly the same rule: the status-transition script ZADDs an issue onto queue:ready only when the new status is open and it is not blocked, not deferred, and not an epic, and ZREMs it whenever the old or the new status is one of open/in_progress/review fleet-db internal/storage/status_transition.go:49-69. Nearly: the script rejects any non-empty defer_until where the Go helper rejects only a future one, and a transition between two inactive statuses — deferred to blocked, say — does not touch the queue at all.

So a daemon picking work never auto-selects a blocked task: it only ever sees open ones. But a targeted claim by id succeeds, because that path goes straight to the claim endpoint and skips the queue entirely. Remember this pair — it is the whole mechanism behind quarantine in Lesson 09, which writes status=blocked precisely to pull a task out of the ready queue while leaving it claimable by hand internal/cli/daemon/supervisor/quarantine.go:22-34, 440-452, 511.

Losing the race is normal

On the loomcli side, a claim conflict is not an error path — it is the expected path. The runner drops that candidate and tries the next best one, up to claimConflictRetryLimit = 16 conflicts before giving up. That retry loop is the decentralised assignment algorithm. internal/cli/daemon/supervisor/claim.go:39

Candidate order comes from SelectBestTask: score descending, then priority ascending, then ID ascending — deterministic, so two runners with identical inputs make identical choices and then let the lock break the tie. internal/cli/task_router.go:147

When an agent has a worktree and no requested task, the ready queue is read up to twice: first scoped to Assignee=<worktree> so an agent prefers work already earmarked for it, then — only if that attempt reached no decision — unscoped internal/cli/daemon/supervisor/claim.go:78-91. A requested task takes its own single-read path claim.go:74-76, 141-167. Resume is checked before any of them claim.go:48-63: an in_progress task is never "ready", so resuming claims by id and bypasses the queue entirely.

Check yourself

From memory: two runners simultaneously pick the same task as their best candidate. Walk through what each one observes, and say where the tie is broken.

Both POST claim. In fleet-db, one AcquireIssueLock returns OK and the other HELD — that is the tie-break, and it happens inside a single atomic Lua script.

The winner proceeds through validation, sets the issue to in_progress, and appends a claim event whose projection repairs the indexes. The loser gets HTTP 409 already_claimed, with the holder attached as meta.existing_owner when the server can read it back fleet-db internal/api/claim.go:83-90; loomcli reads exactly that field internal/cli/daemon/supervisor/claim.go:227-235, drops that candidate, and moves to its next-best task — up to 16 conflicts before it gives up. The loser may still see the task listed as ready until the winner's projection lands; what it cannot do is take the lock.

Two runners claim the same task at the same instant. What actually decides the winner?

  • The atomic lock script: exactly one caller gets OK
  • The ready queue: it lists each task only once
  • The projection: it repairs every index in one pass
  • The router: the higher local score wins the task
The race is settled entirely by AcquireIssueLock, one atomic Lua script returning OK to the first caller, REFRESH to that same caller again, and HELD to everyone else fleet-db internal/storage/locks.go:19-30, 48-56. Everything after it — the status read, the claimability check, the event, the index repair — is ordinary Go running under that lock fleet-db internal/service/issue_service.go:510-574. The ready queue is no tie-break: it can still list a task whose lock is already taken.

A lease acquire returns inconclusive rather than acquired or held-by-other. What does that mean?

  • The server could not be reached, so ownership is simply unknown
  • The lease exists but its remaining validity window has expired
  • Another owner holds it but has not heartbeated it in one cycle
  • The lease was acquired but the fence token failed to increment
"I could not find out" is a distinct third outcome from "no one owns it", and conflating the two is how you get two live owners. The verify-before-kill path branches on exactly this distinction. internal/cli/daemon/supervisor/ownership.go:19-28, 263-275

Which of these statuses can an agent claim?

  • Only open, since any other status implies prior work
  • open and deferred, but never blocked
  • open, deferred, and in_progress
  • open, blocked, deferred, review
All four are claimable. blocked-the-status means a human should look at it, not that agents are barred — the vocabulary lesson pays off here. in_progress is the one the claimability check rejects fleet-db internal/models/status.go:98-105 — though not absolutely: the service lets the same actor re-claim its own in_progress task, and lets a new actor take one over once the old lock has expired fleet-db internal/service/issue_service.go:527-545.

Read the question precisely: it asks what an agent can claim, not what it will be offered. Only open issues reach the ready queue fleet-db internal/storage/ready_eligible.go:35-38, so the other three are reachable only by a claim that names the id.

Read the guarantee, then find its siblings

  1. Read issueService.ClaimIssue end to end in the fleet-db worktree — the claim as it actually runs. Then read internal/storage/lua/claim_issue.lua (80 lines) beside it: the same guarantee written as one atomic script, which the server does not call.
  2. Note every place the service releases the lock before returning an error — there are four. What would break if one of those releases were missing?
  3. List the other Lua scripts in internal/storage/lua/. Pick two whose names suggest they guard a similar race and confirm your guess by reading their headers. What is the common shape? (They are mirrors too: of the 47 files there, 20 say so outright — grep -lie 'canonical' -e 'keep in sync' internal/storage/lua/*.lua.)
  4. Back in loomcli, open claim.go and find the test that pins the conflict cap. Reason about what happens on a very busy workspace when a runner exhausts all 16 — does it fail the run, or go idle and try again next cycle?
