The words that lie

By the end of this lesson you can use this codebase's overloaded terms precisely — and, more usefully, notice when a doc, a ticket, or a colleague is using one of them loosely.

Skill disambiguate a trap word before acting on it Time 30 min Needs Lesson 01 Repos loomcli

Why this is lesson two and not lesson twenty

Most onboarding treats vocabulary as a glossary you skim once. Here it is the load-bearing lesson, for a specific structural reason: this codebase reuses ordinary English words as precise domain terms. A wrong assumption about a type produces a compile error. A wrong assumption about a word produces a confident, fluent, wrong sentence — in a design doc, in a ticket, in a PR description — that nobody catches, because it reads perfectly well.

The repo knows this about itself. AGENTS.md opens by telling you to read the glossary first, and lists the words it considers dangerous: loom, flue, fleet, aether, codex, daytona, atlas, claude. That instruction is not boilerplate — it is a scar. AGENTS.md:5-10

The one idea

When you meet one of these words, you are not reading a description — you are reading a claim about which of several mechanisms is involved. Resolve which one before you act, and never resolve it by guessing from context.

How this team writes definitions

Notice the format used in CONTEXT.md. Every term is defined and then followed by the words you must not use for it:

That _Avoid_ line is doing real work. It is not style guidance — it is a list of the wrong mental models people actually brought to this concept, written down so the next person does not bring them too. All 21 terms in CONTEXT.md carry one — grep -c '^_Avoid_' CONTEXT.md returns 21 — and no rule anywhere says they must, so the convention holds by consistency alone. Match it when you add a term. CONTEXT.md:7-91

Read the _Avoid_ lines as a fossil record of past confusion. "Avoid: repo allowlist" tells you that someone once assumed Repository Set was a permission boundary — and the definition explicitly says it is not one.

The four worst offenders

1. skill — one word, two unrelated mechanisms

A skill is a document entity: a SKILL.md body plus optional text files, stored in the workspace and loaded into an agent's worktree so the agent can use it while working.

A role's config also has a skills: field. That field is not a list of skills. It is a task-routing filter whose tag strings are matched against issue labels to score which tasks the role pulls.

Trap

Same word, no shared mechanism whatsoever. Adding a document named review.md does not make a role with skills: [review] load it, and does not change task routing. Say skill for the document and role skills (or routing tags) for the filter — the glossary makes that naming an instruction, not a suggestion. docs/loom-glossary.md:21-27

The related term is skill scope: workspace-scoped skills load for every loom-managed agent in the workspace; role-scoped skills load only for that role's agents and shadow a same-named workspace skill. Being in scope is what makes a skill load — there is no separate attach list. If you go looking for the place where skills get attached to an agent, you will not find it, because scope is the whole mechanism. docs/loom-glossary.md:28-31

2. blocked — deliberately two things

This is the one that most rewards care, because the ambiguity is intentional and was defended:

SenseWhat it isHow you recognise it
Status The literal blocked issue status. A worker parked the task and declared a blocker, so a human must act. On the wire, in PatchIssueRequest, and in fleet-db. Stands alone: "this issue is blocked".
Dependency An issue that cannot start because issues it depends on are still open. Derived from blocked_by edges; rendered by BlockedBadge. Always names what is blocking: "Blocked by 3 issues".

Nothing translates between them. The disambiguator is grammatical, and the team chose that over renaming: the status sense was displayed as "Stuck" for a while, and that was deliberately reversed. So do not helpfully introduce a third word in your PR — that argument has already been had. docs/loom-glossary.md:124-138

3. stuck — a third thing that borrows the word

task.stuck (internal/events, TaskStuckData) is a daemon event for a task that failed repeatedly across consecutive auto-mode invocations and was skipped so the loop could make progress elsewhere.

The distinction worth memorising

The loop gave up; the agent declared nothing. That is what separates stuck from blocked-the-status. It is not an issue status, it does not set one, and AgentState "stuck" in the web UI is this sense — not either sense of blocked. docs/loom-glossary.md:145-149

4. stage vs phase — derived vs stored

These sound like synonyms and are opposites in the way that matters:

  • Stage — Journey vocabulary, derived rather than stored. Nothing stores a stage. It is computed from an issue's event history: a stage is a contiguous run of that history with the same status and the same owner. Because the window is bounded, a Journey shows the stages that window can support — not necessarily the issue's whole life.
    Note: the repo glossary still calls this "UI-local", but that has drifted — a server-side journey model now computes the same spans (internal/webui/service/journey.go:292). The load-bearing half — nothing stores a stage — still holds.
  • Phase — a runtime concept with storage behind it: the log of one stretch of agent work, planning or implementation, written to tasks/<id>/<phase>.log and surfaced as its own tab.

The compression: a phase is something an agent ran; a stage is something the issue was. docs/loom-glossary.md:156-166

The dangerous ones: words that sound like guarantees

Three things that are not a security boundary

sandbox — almost always the L1 workflow-bundle container. It contains the DriverRun bundle only. The TaskRun leaf that runs the LLM and edits your code is not containerized on any local path.

trust level (trusted/untrusted) — primarily an admission decision: Loom refuses to launch an untrusted bundle outside an isolating launcher. It does not confine the agent process that edits your code. One narrow exception: for a containerized DriverRun with no explicit egress setting, trust level selects the network mode — trusted resolves to all, anything else to serve-only, failing closed. internal/driver/sandbox/egress.go:95-105

read_only / allowed_tools / denied_tools — backend tool and approval policy. Real restrictions where the backend has a mechanism, and a prompt preamble where it does not. Never an OS boundary.

docs/loom-glossary.md:102-121

This is the highest-stakes group in the glossary. Each of these words carries an industry meaning that implies containment, and here none of them do. If you design a feature on the assumption that read_only stops an agent from writing, you will ship something that does not do what its own config says.

The practice: the terminology handshake

Knowing the definitions is not the skill. The skill is a habit AGENTS.md makes mandatory: before running anything slow or irreversible, echo the request back as coordinates — (depth, realness, provisioning, polarity, target) — disambiguate any trap word instead of guessing, and state the evidence class of what you ran:

Evidence classMeans
deterministicOrchestration only.
realA real local backend.
liveReaches a real external or paid service. Costs money, may mutate external state.

AGENTS.md:29-33

And if a real or live path is blocked, you report blocked/unverified. You never fabricate state as evidence. The trap words in this axis are local, live, real, verify, and gate. AGENTS.md:22, 33-34

Check yourself

From memory: give the one-line compression that separates a stage from a phase, and say which one has storage behind it.

A phase is something an agent ran; a stage is something the issue was.

The phase has storage — tasks/<id>/<phase>.log. The stage is derived on the fly from a bounded window of the issue's event history and is stored nowhere. docs/loom-glossary.md:156-166

A ticket says "the agent is stuck on FLEET-42". Which reading does the codebase's vocabulary actually support?

  • The issue carries the literal blocked status and needs a human
  • The issue cannot start because its dependencies remain open
  • The worker declared a blocker and parked the task for review
  • The daemon skipped the task after repeated consecutive failures
stuck is the daemon's word: the loop gave up so it could progress elsewhere. The agent declared nothing. The first and third options both describe blocked-the-status, and the second describes blocked-the-dependency — three plausible readings the word does not mean. docs/loom-glossary.md:145-149

A role's config contains skills: [review]. What does that field do?

  • Matches its tag strings against issue labels to score task routing
  • Loads the workspace skill document named review into the worktree
  • Grants the role permission to run review-scoped tools and commands
  • Attaches the review skill so the role shadows the workspace version
It is a routing filter, sharing nothing with the skill document mechanism but the word. The fourth option is the sharpest near-miss: shadowing is real, but it comes from skill scope, not from this field. docs/loom-glossary.md:21-31

Which of these bounds what an already-running agent process can reach on the host?

  • Setting the driver trust level for that run to untrusted
  • Setting read_only on the role's backend tool policy
  • None of these — each is an admission or policy decision only
  • Running the agent under the L1 workflow-bundle container sandbox
Trust level is admission, read_only is backend policy (sometimes only a prompt preamble), and the sandbox contains the DriverRun bundle — not the TaskRun leaf that edits code. Note the question says agent process: trust level does bound the network of a containerized DriverRun by selecting its egress mode, but that is a different thing from the agent, and it is the only place trust does any bounding at all. docs/loom-glossary.md:102-121; internal/driver/sandbox/egress.go:95-105

Hunt a loose usage, then run a handshake

  1. Pick one trap word — skill, blocked, or sandbox — and grep for it across docs/ in loomcli.
  2. Find one occurrence where you cannot tell which sense is meant from the sentence alone. Write down the path:line and both readings it could carry.
  3. Now practise the handshake on a task you might actually be given: "verify the claim loop works locally." Write out the coordinates (depth, realness, provisioning, polarity, target) you would echo back, and name which trap words in that sentence you would refuse to guess at.
  4. Reaching back to Lesson 01: for the sense of blocked that lives in fleet-db, which repo would you expect to hold its definition — and why does that follow from "loomcli orchestrates, fleet-db remembers"?
You succeeded when You can state both readings of your ambiguous line without looking anything up, and your handshake names at least two words in "verify the claim loop works locally" as needing disambiguation. (locally and verify are both on the trap list; claim is worth questioning too.)
