Week 6 / Lesson 31 / Landing the plane

Your first task

One real task, from the ready queue to an open pull request, using nothing you have not already been taught. Then: where to go when this course stops.

Skill take a task from claim to opened PR without help Time 60 min Needs 02, 03, 16 Repos loomcli fleet-db

Why this exists

You now know where things are. That is not the same as knowing the order to do them in, and the order is what a first task actually tests. Everything below has appeared in an earlier lesson; this one is the sequence, written down once, with the file that is the authority for each step.

The reason the sequence matters here more than in most codebases is that four of the steps are enforced by something other than your judgement. The base branch is a fact about the remote. The gate is a Makefile. The PR evidence schema is a contract file in the other repo, with a shell script holding fleet-db's CI to the same seven headings. And the local stack is shared machine state that other people are using while you work.

The one idea

Nothing in this lesson is new knowledge. The capstone is the order: dictionary, task, isolate, change, gate, evidence, PR, push. Skipping a step does not fail fast — it fails at review, or in somebody else's stack.

The run sheet

Fourteen hops. Two of them cross into fleet-db: one is a contract document, the other is a contract document plus the shell script that enforces it — the process contract for this work lives in the other repo even when the change does not.

  1. loomcli AGENTS.md:5-10 Read the dictionary before the ticket. The first instruction in the repo's operating manual is to read docs/loom-glossary.md (176 lines) — because loom, flue, fleet, aether, codex, daytona, atlas and claude all mean something specific here (AGENTS.md:6-8); skill is one more, from the glossary's own entry (docs/loom-glossary.md:21-27). If the issue text uses a word from the trap list, resolve it now.
  2. AGENTS.md:163-170 → internal/cli/data/ready.go:18-40 Find work, read work. loom data ready --limit 10, then loom data show <id>. The ready leaf builds a backend.ReadyOpts, calls ib.Ready, and prints — the thin-leaf shape from Lesson 06. Note this command is not read-only in local mode; see the safety callout below.
  3. fleet-db docs/agents/contracts/task-contract.md:3-10, 18-20 Decide whether the task is workable. Every implementation task must state six things: goal and explicit scope boundaries, files expected to change, invariants, required validation commands, rollback plan, risks and assumptions. The same file warns that open does not mean ready — "ready for pickup" is a derived ready-queue property. The contract requires all six (task-contract.md:3); the more of them a task leaves unstated, the more the right move is a comment asking for them rather than a commit.
  4. loomcli Makefile:559-565 Isolate the checkout — with fleet-db beside it. Make a worktree per task, and if the task touches both repos, put both worktrees in one parent directory as siblings. That is not taste: Makefile:559 wildcards ../fleet-db and ../../fleet-db relative to your checkout for the repo directory, and Makefile:560 wildcards those same two places again for a built fleet-db binary inside them — only that second hit exports FLEET_DB_BIN. The compose stack is stricter: context: ../../../fleet-db (test/local-mode/docker-compose.yml:40) resolves relative to the compose file, so it accepts the sibling layout and nothing else.
  5. .github/workflows/ci.yml:3-9 Confirm the base branch with a human. CI runs on pushes to main and v5, and on pull requests to any base, so the workflow will not tell you which one is right. git rev-list --left-right --count origin/main...origin/v5 prints 1   1786 at this pin. Branch policy is a human fact — ask before you branch, not after you rebase.
  6. Makefile:683-692 → scripts/hooks/pre-push:4-11 Find out where the pre-push gate would land — do not install it from a shared tree. make hooks copies scripts/hooks/pre-push into git rev-parse --git-path hooks (Makefile:571, 686-687). Run that command inside a worktree and it prints the parent clone's .git/hooks — one directory shared by every worktree of that clone and everyone working in one, so make hooks changes git push behaviour for all of them at once. The copy also happens before the pre-commit/golangci-lint PATH checks (Makefile:689-690), so a run that errors out still leaves the hook behind. Installing it is a decision for a clone you own. Read it instead — eleven lines: unset everything git rev-parse --local-env-vars names, so a nested git command in a temp repo cannot mutate this checkout (pre-push:4-8), then make check (pre-push:10-11).
  7. internal/cli/data/claim.go:14-29 Claim it. loom data claim <id> calls ib.ClaimIssue(ctx, args[0], 0) and prints. The --actor flag is "captured for command-line parity" and never read (claim.go:9-12, 32) — the effective actor comes from the backend's configured identity, so you cannot claim as somebody else by flag. Lesson 08 is where the race actually lives.
  8. internal/cli/repo/repo_cmd.go, .golangci.yml Write the change by copying the nearest exemplar. Not by inventing a shape. Lesson 06 names the reference command; Lesson 04 makes the point that the 687-line .golangci.yml is the style guide nobody will hand you.
  9. AGENTS.md:29-35 Handshake before anything slow or irreversible. Echo the request back as (depth, realness, provisioning, polarity, target), disambiguate the trap word instead of guessing, and state the evidence class of what you are about to run. This is the practice from Lesson 02, and it is cheapest immediately before the expensive thing.
  10. Makefile:644-665, 668, 586-625 Run the gate. make check runs check-go and check-frontend in parallel and prints each log only on failure; make gate is a backward-compatible alias for it (:668). check-go is thirteen numbered steps: step 11 regenerates and diffs the API types, steps 12 and 13 are go test -race and a 60% coverage floor. Touched no frontend code? Run make check-go — and say which one you ran.
  11. .agent-skills/loom-pr-test/SKILL.md:94-123 Runtime evidence, only if the change is user-visible. Your own LOCAL_MODE_COMPOSE_PROJECT, your own LOCAL_MODE_FLEETDB_PORT / _API_PORT / _UI_PORT, verified through the matching verifier (:110-113) and torn down by that project name and nothing else (:117-121).   12. .agent-skills/loom-pr-test/SKILL.md:232-244 Write the report before you write the PR. The runbook lists what a report must always contain — exact command path, stack URLs and ports, whether the backend was deterministic or a real CLI, browser evidence when UI behaviour matters, any blocked condition — and its last line opens with the three words that are the whole ethic of this repo: "Do not overclaim." (:244)
  13. fleet-db docs/agents/contracts/pr-contract.md:3-11 → scripts/harness/review_gate.sh:15, 82-90 The PR evidence has a schema. Seven items, and on the fleet-db side a shell script greps for them as literal Markdown headings and fails the build when one is missing or empty — but what it greps is artifacts/harness/review-evidence.md (review_gate.sh:15), a file CI regenerates from scratch immediately beforehand (harness.yml:33-34 → generate_review_evidence.sh:46-94). Nothing machine-reads the prose you write. Neither repo has a PULL_REQUEST_TEMPLATE — .github/ holds only workflows/ in loomcli and workflows/ plus badges/ in fleet-db — so the contract file is the template, and reviewers are what enforce it.
  14. loomcli AGENTS.md:172-195 Land the plane. File follow-up issues, run the gates, update issue status, push, clean up, verify, hand off. I diffed this block against fleet-db AGENTS.md:55-78: byte-identical, all 24 lines. It is the one process document both repos agree on exactly.

The worktree, and why it has a sibling

Two lines of the Makefile decide whether half the repo's tooling can find fleet-db at all:

Read it as a rule about directory layout, and notice that the two wildcards look for different things. Line 559 accepts the fleet-db repo one level up or two levels up and sets FLEET_DB_REPO; line 560 looks in those same two places for a built fleet-db binary, and only that hit exports FLEET_DB_BIN. Anywhere else and neither resolves, so the tests and stacks that need a real fleet-db binary do not find one. The course's own pinned trees satisfy the first branch of the repo wildcard — .worktrees/onboarding/loomcli and .worktrees/onboarding/fleet-db, siblings under one task directory — but not the binary wildcard: nothing is built in them, so at this pin FLEET_DB_BIN stays empty and TestE2E_IssueBackendConformance_AllModes skips (internal/cli/issue_backend_conformance_e2e_test.go:127-134). Copy the sibling shape for your own task, then build fleet-db inside it or set FLEET_DB_BIN yourself.

The unhelpful shape is the one .gitignore:57-58 quietly invites: <loomcli>/worktrees/mytask. That path ignores cleanly, and from inside it ../fleet-db is <loomcli>/worktrees/fleet-db and ../../fleet-db is <loomcli>/fleet-db — neither of which exists. It works until the first test that needs the other repo.

Shared machine — this is not a formality

Other people's stacks are running while you work, and the podman compose projects are machine state, not session state. up --build on an existing project name recreates somebody else's containers. So: run podman ps first, treat every stack you did not start as owned, always pass your own LOCAL_MODE_COMPOSE_PROJECT and your own unclaimed port block, and tear down only that project by name (.agent-skills/loom-pr-test/SKILL.md:94-123, 256-260). Never make local-mode-down bare: with no LOCAL_MODE_COMPOSE_PROJECT it defaults to loomcli-local-mode (Makefile:8) and stops whoever owns that stack. The runbook still shows the bare form as its default cleanup (SKILL.md:250-254) — treat that as a runbook bug and always pass your own project name.

Two more that catch people on their first day of real work. fleet-db's make gate starts containers — it calls test-e2e, which is go test -tags e2e against real containers and is documented as requiring podman or docker (fleet-db Makefile:171-179, 59-62). And loom data ready is not a read-only command in local mode: it forks an embedded fleet-db, which MkdirAlls a fleet-db/ directory under your data dir and writes a Redis snapshot into it (internal/bootstrap/embedded.go:324-327, 339). The runbook's rule is to keep your real ~/.loom safe and use a throwaway LOOM_CONFIG_DIR (SKILL.md:23).

The evidence, and what actually checks it

fleet-db's PR contract is seven items long. It is also, uniquely in these two repos, machine-checked: make harness-review-gate runs on every fleet-db pull request with STRICT_REVIEW_GATE=1 (fleet-db .github/workflows/harness.yml:33-39), and the script behind it greps the generated evidence file — not your PR body — for exact headings.

Those seven headings map one-to-one onto the seven items of docs/agents/contracts/pr-contract.md:5-11, in the same order — but two are worded differently, and review_gate.sh:93 matches with grep -Fqx, literal and whole-line. Copy headings from the script, not the contract: it wants ## Commands run for validation (the contract says "Exact commands run for validation") and ## Autofix operations performed by agents (the contract says "Any autofix operations performed by agents"). loomcli has no equivalent script, and its commit bodies do not use these headings — none of the last 200 do (git log -200 --format=%B, grepped for each of the seven). What they share is the substance: 5eb3e5843 runs Problem / Change / Tests / known remaining surfaces, ce4df56fb a Verification block naming exactly what was run. Treat the seven items as the checklist your prose has to answer in both repos, and fill them in like this:

Contract item (pr-contract.md)Where your answer comes from in loomcli
Summary of behaviour change (:5)The issue you claimed, plus the diff. Symptom, mechanism, fix — one paragraph.
Exact commands run for validation (:6)Literally what you typed: make check or make check-go (Makefile:644-665, 586-625), plus any single-package go test.
Test results and affected coverage areas (:7)check-go step 13 enforces a 60% floor (Makefile:623-624). Name the packages you moved, not the number alone.
Files changed and rationale (:8)git diff --stat against your base, one clause per file. Files you touched only to satisfy the linter count.
Risk assessment (:9)Which seam you touched. Lesson 07 for the two clients; Lesson 28 for what fails loudly versus silently across the repos.
Rollback strategy (:10)Is reverting the commit enough, or does a fleet-db deploy have to move first? If ordering matters, say the order.
Autofix operations by agents (:11)The pre-commit hooks rewrite files: trailing-whitespace and end-of-file-fixer (.pre-commit-config.yaml:28-29). If they touched your diff, that is an autofix.
Trap — "the review gate passed, so my evidence is good"

The gate checks shape, not truth. It asserts that seven headings exist, that each has at least one alphanumeric character under it, and that the file contains no TODO/TBD/FIXME/PLACEHOLDER (fleet-db scripts/harness/review_gate.sh:92-107). It cannot tell whether "Commands run for validation" lists a command you actually ran. The generator even fills the summary and autofix sections with defaults when the environment does not override them (scripts/harness/generate_review_evidence.sh:13-14) — and harness.yml:33-34 sets neither variable, so in CI both sections are canned. Those defaults contain no placeholder word, so they sail through. Honest evidence is a thing you write for a reviewer, not a thing the gate extracts.

Trap — "the conformance suite is green"

The closest thing to a cross-repo contract test in loomcli is TestE2E_IssueBackendConformance_AllModes, four subtests — fleetdb-local, fleetdb-cloud, fleet-direct, api-server — behind the issuebackend_e2e build tag (internal/cli/issue_backend_conformance_e2e_test.go:1-2, 30, 34, 57, 76, 100). If it cannot find a fleet-db binary it calls t.Skip with the message "fleet-db binary unavailable; set FLEET_DB_BIN or install fleet-db on PATH" (:127-134) — and a run that skips everything still prints ok. This is the failure mode Lesson 16 is built around: the exit status is not the evidence class. Read the skip lines.

You are about to cut a branch for your first loomcli change. What do you establish first?

  • How far origin/main and origin/v5 have diverged, then ask
  • Which branch the repo config lists as its default branch
  • Which branch the most recently merged pull request targeted
  • Whether the pre-push hook is installed in this new worktree
git rev-list --left-right --count origin/main...origin/v5 prints 1   1786 at this pin, so the two branches are not interchangeable — and .github/workflows/ci.yml:3-9 runs CI on pushes to both and on pull requests to any base, so the workflow file will not decide it for you. Measuring the divergence tells you the question is live; only a human can answer it. The last-merged-PR option is the sharp near-miss: it is evidence, not policy, and one cherry-pick makes it lie.

make check passed and you started no stack. What may the PR body claim?

  • That the change is proven against a real local backend
  • That the change passed the repo gate, and nothing more
  • That the change was verified end to end in local mode
  • That the change is safe to merge without more review
make check is check-go plus check-frontend — build, lint, unit tests with the race detector, coverage floors (Makefile:644-665, 586-625). That is the deterministic evidence class from Lesson 16: no real backend was reached, so the first and third options are the overclaim the runbook forbids in three words at SKILL.md:244.

A colleague reports that go test -tags issuebackend_e2e ./internal/cli printed ok. What has that established?

  • Nothing when the fleet-db binary is absent and it skips
  • That all four backend modes agree on the shared suite
  • That the fleet and api backends return identical errors
  • That the embedded fleet-db subprocess started and stopped
The helper calls t.Skip when no fleet-db binary can be diagnosed (internal/cli/issue_backend_conformance_e2e_test.go:127-134), and a fully skipped package still exits zero and prints ok. The second option is what a green run would mean, which is exactly why it is the tempting one — ask for the skip lines before you believe it.

fleet-db's strict review gate reads your evidence from and fails the build if any of the seven required headings is missing or empty.

The path is set at fleet-db scripts/harness/review_gate.sh:15 and written by scripts/harness/generate_review_evidence.sh:5-6. In CI the artifact is uploaded alongside the eval results (.github/workflows/harness.yml:41-49).

Dry-run the whole run sheet, touching nothing

Read-only, and stays that way. Do not run make local-mode-up or local-mode-down, do not start a server on a fixed port, do not run loom data ready (hop 2 — it forks a fleet-db and writes under your data dir), and write your notes outside both repos. If you ever do bring a stack up for real work: podman ps first, your own LOCAL_MODE_COMPOSE_PROJECT and your own unclaimed port block, and tear down only the project you created.

Who to ask

The course's own resource list is blunt about where the unwritten answers are (docs/onboarding/RESOURCES.md:115-127): code review on your own PRs is the highest-bandwidth feedback loop available and the only one that corrects judgement rather than facts — so open PRs early and small. After that, existing issues: loom data show <id> on a closed task teaches the working norms faster than any document, because you see how it was scoped, argued and closed. And practise the terminology handshake out loud with a colleague — RESOURCES.md:125-127 calls that the fastest way to internalise the trap words. The protocol itself is one-sided (AGENTS.md:29-35): you state the coordinates before the expensive thing, audience or not.

There is one gap you are now the right person to close. RESOURCES.md:137-139 records that no team communication channels are written down anywhere in this workspace — no channels, no standups, no review rotation. For an internal codebase those are the real community. Ask on your first day back, and add them to RESOURCES.md. That is a legitimate first PR against this course.

Outside the building

Your skills will be tested where nobody has read this course. For the general technologies under this system, the durable places to go deep:

  • Redis and event sourcing. The official Redis documentation for Streams, Lua scripting and Functions is the primary source for the mechanics that Lesson 18 and Lesson 20 depend on. For the pattern rather than the tool, Martin Fowler's Event Sourcing article (martinfowler.com/eaaDev/EventSourcing.html) and Greg Young's talks are still the reference statements, and the DDD/CQRS/ES community Slack is where the awkward questions get argued — projection rebuild cost, snapshotting, and what to do when the log outlives its schema.
  • Agent orchestration. Anthropic's engineering writing on building effective agents is the closest thing to a shared vocabulary in this space, and the Claude Agent SDK documentation is the concrete counterpart. Beyond that the field mostly publishes in conference talks and preprints rather than books; treat anything older than about a year as history.
