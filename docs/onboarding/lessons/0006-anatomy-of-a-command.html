Week 2 / Lesson 06 / The spine

Anatomy of a command

One command, all the way down — from a shell argument to an HTTP write and back. This trace is the spine of the whole course; every later lesson attaches to a hop on it.

Skill follow any CLI command through every layer Time 40 min Needs 01, 05 Repos loomcli
Why one trace

You cannot read 180,000 lines. You can read one path through them. Everything in this codebase is a variation on the path below, so learning it once buys you the ability to predict where anything else lives. We will come back to this trace in later weeks and go deeper at particular hops.

Our specimen, chosen because it touches every layer:

loom repo add backend git@github.com:acme/backend.git --groups infra

The trace

  1. cmd/loom/main.go:13-38 → internal/cli/repo/repo_cmd.go:71-82 Package init()s run. Go initialises every blank-imported package. repo's init() binds its flags, attaches its five verb subcommands to repoCmd, and calls cli.RegisterCommand(repoCmd). Nothing is attached to the root command yet — this only appends to a slice.
  2. internal/cli/root.go:155, 288-290 Execute flushes the pending registrations into rootCmd. Because the slice holds pointers, init() ordering between files does not matter — one file can register workspaceCmd while another later adds subcommands to the same pointer (internal/cli/workspace/workspace_cmd.go:102-106, workspacev2_cmd.go:91-95).
  3. internal/cli/root.go:182, 224-259 Tracing and the root context. OTel turns on only when LOOM_TRACE=1 or an OTLP endpoint is set. The root span's context is published globally via cmdstore.SetRootContext(ctx) — necessary because the store helpers build their own context and ignore cmd.Context().
  4. internal/cli/repo/repo_cmd.go:46 Arity validation — earlier than you expect. Args: cobra.ExactArgs(2). cobra checks arity before it walks up the tree looking for a PersistentPreRunE (ValidateArgs at command.go:968, the hook at command.go:985-986 of cobra@v1.10.2). So loom repo add onlyone fails with usage text before the logger exists and before any flag is mirrored into the environment — no setup runs at all.
  5. internal/cli/root.go:112-145 PersistentPreRunE. In order: init the logger; mirror --server→LOOM_SERVER_URL and --workspace→LOOM_WORKSPACE; resolve the backend; then rebuild the cached dependencies so they reflect the flags just mirrored. That ordering is load-bearing — see the trap below.
  6. internal/cli/repo/repo_cmd.go:84 → cmdstore/cmdstore.go:124 The wrapper pattern. RunE does not open a store. It immediately delegates to cmdstore.WithActiveWorkspace(func(ctx, h, ws) error {…}). This is the convention for any command that touches state.
  7. internal/bootstrap/openstore.go:85, 122-123 → mode.go:54 → embedded.go:305, 339 Mode detection. DetectMode(): LOOM_FLEET_DB_URL set → cloud (plain HTTP client); unset → local, which reuses or spawns an embedded fleet-db subprocess backed by a miniredis snapshot at <LoomDir>/fleet-db/redis-snapshot.json. This is where Lesson 01's two legal paths become one line of code.
  8. internal/bootstrap/mode.go:76-91 Workspace resolution. Only LOOM_WORKSPACE is consulted — never state.json — and the key is then validated against the store, so a stale value fails loudly with active workspace %q not found in fleet-db.
  9. internal/cli/repo/repo_cmd.go:96-107 → internal/infra/fleetdb/repo.go:42-69 The write — which is two HTTP calls. POST /api/v1/{ws}/repos, then PATCH /api/v1/admin/workspaces/{ws} with add_repos. If the PATCH fails, the repo row is deleted again.
  10. internal/infra/fleetdb/client.go:445-513 Error mapping. classifyHTTPError turns HTTP status plus an error code into domain sentinels: 404 → domain.ErrNotFound, 409 → ErrAlreadyExists (or ErrAlreadyClaimed / ErrInvalidTransition by code), 400/422 → ErrInvalid, other 4xx → ErrConflict. Callers compare with errors.Is, never with status codes.
  11. internal/bootstrap/openstore.go:57-70 Unwinding. WithStore's deferred h.Close() runs. It always closes the client; it stops the embedded fleet-db subprocess only if this command was the one that spawned it. openLocalStore tries reuse first (openstore.go:122-124), and the reuse path returns a handle with no embedded field (openstore.go:145-159), so Close's if h.embedded != nil guard skips the stop and the subprocess outlives the command.

Three things worth stopping on

The wrapper is the convention

Commands that touch state for the length of one call do not open stores, resolve workspaces, or handle signals. They hand a closure to cmdstore.WithActiveWorkspace, which builds a SIGINT/SIGTERM-cancellable context, opens the store, resolves the active workspace, and defers cleanup (internal/cli/cmdstore/cmdstore.go:111-132). The exceptions are the commands that hold the handle past a single closure — serve and daemon for the life of the process, epic run for the life of its own signal context. Those call cmdstore.OpenStore directly and own the Close themselves. internal/cli/serve/serve.go:223-227, internal/cli/daemon/daemon_cmd.go:322, internal/cli/epic/run.go:112-119

Keeping local-vs-cloud selection inside bootstrap is exactly what the control-plane path guard from Lesson 04 enforces: it fails any non-test file outside openstore.go that imports internal/infra/fleetdb or calls fleetdb.New(. scripts/check-control-plane-paths.sh:58-71, 76-98

So "which mode am I in?" is never a question a command asks. If you find yourself wanting to know, you are probably about to violate the guard.

Multi-step commands undo their own mess

runRepoAdd clones a checkout, creates the store record, and if remembering the local path fails it deletes the record and removes the clone. The two-call write at hop 9 does the same thing one layer down. There is no transaction manager here; compensating rollback written by hand is the house style, and reviewers will expect it. internal/cli/repo/repo_cmd.go:86-112

The error you return becomes an exit code

Execute returns the error to main, which prints it to stderr and exits with cli.CommandExitCode(err) — the code carried by a CLIExitCode() error if the error implements it, otherwise 1. So an error type is part of your command's public interface. cmd/loom/main.go:53-57 internal/cli/exit.go:36-45

Trap — the ordering inside hop 5

PersistentPreRunE mirrors flags into environment variables and then rebuilds the cached dependencies. If you add setup that reads configuration, putting it before the mirror step means you read the state the flags were meant to override — and it will work fine in every test that does not pass the flag. Add new resolution after the rebuild, not before.

Check yourself

From memory: a command needs to read and write workspace state. Name the wrapper it must use, and the three things that wrapper does for it.

cmdstore.WithActiveWorkspace(func(ctx, h, ws) error {…}).

It builds a signal-cancellable context from the published root context; opens the store (which is where local-vs-cloud mode is detected and, in local mode, the embedded fleet-db is reused or spawned); resolves and validates the active workspace key; and defers Close(), which stops the embedded fleet-db only if this command was the one that spawned it. internal/cli/cmdstore/cmdstore.go:111-132 internal/bootstrap/openstore.go:64-68, 145-159

Your command gets a 409 from fleet-db. What should the calling code branch on?

  • The HTTP status code returned on the response from the client
  • A domain sentinel error compared using errors.Is
  • The error string returned by the fleet-db client wrapper
  • The error code field parsed directly from the response body
classifyHTTPError exists precisely so callers never see status codes: it maps 409 onto ErrAlreadyExists, ErrAlreadyClaimed, or ErrInvalidTransition depending on the body's code. Branching on the status re-implements that mapping badly. internal/infra/fleetdb/client.go:445-513

You set LOOM_WORKSPACE=GONE for a workspace that no longer exists. What happens?

  • Loom falls back to the last workspace recorded in state.json
  • The command runs and fails later with a confusing not-found error
  • Resolution fails immediately: active workspace not found in fleet-db
  • Loom creates the workspace on demand and continues with the command
The key is validated against the store during resolution, so a stale value fails fast and by name. The first option is the trap worth remembering: state.json is a cache and is deliberately never consulted here. internal/bootstrap/mode.go:76-91

In local mode, when does a command's deferred h.Close() stop the embedded fleet-db subprocess?

  • Only when that command was the one that spawned it
  • Always, because every handle owns the process it uses
  • Never, since the daemon alone supervises that process
  • Only when the runtime file records no other reader
Ownership decides it. openLocalStore tries to reuse a healthy running runtime before spawning one (openstore.go:122-124); the reuse path returns &StoreHandle{…} with embedded left nil (openstore.go:145-159), and Close only calls embedded.Stop() when that field is non-nil (openstore.go:64-68). So a command that reused a runtime closes its client and leaves the subprocess running — which is exactly why loom serve can hold one open across many other commands (internal/cli/serve/serve.go:223-227, 292-296).

Walk it yourself, then diff a second command against it

  1. Open internal/cli/repo/repo_cmd.go and land on hops 1, 4, 6 and 9 — the four that land in this one file. Do not read the whole file; practise landing on the lines the trace names.
  2. Now pick a different store-touching command — loom role set is a good one — and find its equivalent of each hop. Which hops are identical? Which differ, and why?
  3. Find a command that does not use cmdstore.WithActiveWorkspace. What is different about what it does? (Hint: not every command touches workspace state.)
  4. Reaching back to Lesson 05: hop 9 writes the repo to fleet-db, and the rememberRepoLocalPath call folded into the same hop (internal/cli/repo/repo_cmd.go:108-113) caches a local checkout path. Name the tier each of those lands in, and say which one you could delete without losing anything.
You succeeded when You can point at the exact line in your second command where the store write happens, and state — without rerunning the trace — what would happen to the embedded fleet-db if that command returned an error halfway through.
