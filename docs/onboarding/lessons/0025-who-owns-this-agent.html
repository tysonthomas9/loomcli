Week 6 / Lesson 25 / Control plane

Who owns this agent

Ownership has three answers, not two. The third one — I could not find out — is the one that decides whether you kill a running agent or let it finish, and it is the only one you have to design for.

Skill determine who owns a given agent right now — including when the answer is inconclusive Time 35 min Needs 07, 08, 17 Repos loomcli fleet-db

Why this exists

An agent is a named assignment that uses a role; a worker agent runs as a process in a worktree, started by a supervisor inside a loom daemon. Nothing stops you from starting a second daemon — a stale one from another terminal, a desktop-managed one, a container that was never reaped — and nothing stops that second daemon from reading the same config and deciding it too should run planner. Two processes in the same worktree, both committing, both pushing.

Lesson 08 named the invariant that prevents it: (workspace_id, agent_id) → at most one active owner, held as an agent ownership lease in fleet-db. This lesson is that lease at full depth, because the interesting part is not the happy path. It is what a supervisor does the moment it stops being sure.

The one idea

Ownership is the result of an operation, never the value of a field. You learn who owns an agent by asking fleet-db to arbitrate — an acquire, or a heartbeat — and if that call does not complete you have learned nothing. "Could not reach the server" and "nobody owns it" are different facts, and the entire kill/keep decision hangs on not confusing them.

You met the same principle one lesson family over. In Lesson 17, serve proves a TaskRun lease by issuing a real fenced no-op heartbeat rather than comparing fields it already has in hand (internal/webui/handlers/taskrunapi/module.go:244-259). Same instinct, different object.

Nothing in fleet-db's acquire path produces a 404 — the storage call either writes or answers CLAIMED (fleet-db internal/storage/control_plane.go:694-713), and writeStorageError issues 404 only for ErrStorageNotFound (internal/api/control_plane.go:1237-1238) — so a 404 here means the endpoint is not there: an older fleet-db, or something in front of it that does not route /agent-ownership-leases. The supervisor reads that as "this backend does not support ownership leases", clears its lease state, and runs unguarded. That is a deliberate back-compat fail-open, and a test pins it: TestAcquireAgentOwnershipContinuesWhenBackendDoesNotSupportOwnershipLeases feeds Acquire a wrapped domain.ErrNotFound and asserts the outcome is ownershipAcquired with the lease state cleared (ownership_test.go:15-40, 46-48). It has a twin at the top of the function: with no control store or no workspace, the answer is also ownershipAcquired, "so non-control-plane supervision keeps today's behavior exactly" (ownership.go:31-35). When you ask "who owns this agent" and the answer is "nobody", check first that ownership is switched on at all.

The arbiter is a dozen lines of Lua

fleet-db The acquire endpoint runs one script. Everything the guard needs is read and written inside it, so two daemons acquiring at the same instant cannot both win:

Three properties fall out of those lines, and all three matter to you:

  • Expiry is a field comparison, not a Redis TTL. The script compares expires_at_unix against a server-supplied "now" (ARGV[2], stamped at internal/storage/control_plane.go:683). The hash key itself is never given an EXPIRE — the only writes the acquire and renew scripts issue are INCR/SADD/HSET (redis.go:213-224, :252-256), and nothing writes expired back into the hash — so an expired lease is still a row you can read.
  • Same-owner re-acquire preserves the token (redis.go:210, :215-222) — though the fence still advances, because the INCR at redis.go:213 sits below the only early return. Preserving the token is what makes "re-acquire to find out" a safe probe rather than a destructive one.
  • Different owner plus live lease is the only refusal. Everything else — no row, expired, released, or the same owner re-acquiring — overwrites and bumps the fencing token (internal/storage/control_plane.go:665-671).
There is a copy of this script at internal/storage/lua/acquire_ownership_lease.lua, and its header says the Go constant is canonical (lines 6-7). Believe it: nothing in fleet-db go:embeds the lua/ directory, so only the string in redis.go is ever executed. The two are byte-identical today. The comment on claimIssueLua (internal/storage/claim.go:12-13) points the other way and names a file — lua/claim.lua — that does not exist under that name.

The trace: a heartbeat fails

This is the path the lesson is really about. The supervisor is running an agent and holds a lease. One heartbeat round trip comes back with an error. Nothing here is allowed to conclude anything from a timestamp.

  1. internal/cli/daemon/supervisor/supervisor.go:294-304 Where the lease sits in the loop. Every iteration of superviseAgent acquires ownership before taking a concurrency slot or doing pre-flight setup. Anything other than ownershipAcquired means sleep 5 s and try again (ownership.go:354-372). On success it starts the heartbeat goroutine and builds a releaseOwnership closure that is called on every normal exit path.
  2. ownership.go:189-210 The heartbeat itself. doOwnershipHeartbeat captures sentAt := time.Now() before the request, then on success stores the server's LastHeartbeat for display and sentAt as OwnershipRenewedAt. The comments on lines 205 and 207 label which field is which — "display/telemetry only" against "local-clock anchor". That split is load-bearing at hop 8.
  3. fleet-db internal/api/control_plane.go:968-980 → internal/storage/redis.go:239-258 The server's verdict. The handler requires an X-Agent-Ownership-Lease-Token header and calls RenewAgentOwnershipLease. The Lua returns one of four strings, and the Go layer turns them into typed errors: NOT_FOUND, NOT_OWNER, INVALID (exists, token matches, not live), or OK (internal/storage/control_plane.go:778-791).
  4. internal/infra/fleetdb/client.go:283-292, 452-512 Status becomes sentinel. The store stack's classifyHTTPError maps the response onto a domain.Err* — the Lesson 07 currency, not *backend.BackendError. 404 → ErrNotFound, 403 → ErrConflict, 410 → ErrGone. A 5xx or a transport failure gets no sentinel at all.
  5. ownership.go:325-334 Typed or untyped — the first fork. isTypedDomainError asks one question: did the server classify this, or did the wire fail? It matches five sentinels and nothing else.
  6. ownership.go:218-241 Verify before kill. Untyped ⇒ one immediate heartbeat retry, because "one immediate retry IS the false-alarm verification, and it is server-side proof (no client clock involved)" (ownership.go:222-224). Retry succeeds ⇒ carry on, and the renewal anchor advances naturally. Retry fails untyped again ⇒ bounded fail-open (hop 8). Typed ⇒ skip the retry and go straight to re-acquire arbitration.
  7. ownership.go:247-276 Arbitration — and the branch that is the lesson. First a dead-process guard read from supervisor state rather than kill(pid, 0) (lines 250-257 explain why signal-0 is worse). Then one tri-state re-acquire: ownershipAcquired ⇒ keep running with a new fence; ownershipHeldByOther ⇒ killAgentForOwnership(..., "verifiably_lost", ...); ownershipAcquireInconclusive ⇒ hop 8.
  8. ownership.go:282-292, 294-323 Bounded fail-open. Keep running only while the last confirmed renewal proves the lease is still live server-side. Past that bound, kill with reason ownership_unverifiable.

Notice that the three typed heartbeat failures all converge on the same place. That is deliberate: the code does not try to infer ownership from which typed error it got. It asks again, with an operation whose answer is authoritative.

The fail-open window, and why it never reads ExpiresAt

Here is the predicate the inconclusive branch rides on. The comment is longer than the function, and it should be:

Unpack the argument, because it is the reusable part. The anchor renewedAt is a local timestamp taken just before a request that the server later confirmed. The server set the lease to expire at its own processing time plus the TTL, and its processing came after our send. Therefore "less than TTL has elapsed on my clock since I sent" implies "the lease was still live on the server" — with no comparison between two machines' clocks anywhere. ownershipRemainingValidity then computes it twice, once monotonic and once wall (Round(0) strips the monotonic reading), and takes the smaller (ownership.go:294-308).

Trap — "held by another daemon" does not arrive as you expect

The classifier at ownership.go:53 recognises ErrAlreadyExists and ErrConflict as held-by-other. But a real refusal from fleet-db is a 409 carrying "code":"already_claimed" (fleet-db internal/api/control_plane.go:1241-1242), and classifyHTTPError gives that its own sentinel, domain.ErrAlreadyClaimed (internal/infra/fleetdb/client.go:461-462), which is an independent errors.New that wraps neither of the other two (internal/domain/errors.go:20, 28, 32). So a genuine CLAIMED lands in the inconclusive arm, and arbitration rides out the validity window instead of killing at once.

Why nobody notices: the fake used by the tri-state test returns ErrAlreadyExists for held-by-other (ownership_verify_test.go:487-488), and so does memstore (internal/infra/memstore/terminal_artifact.go:571-573). Compare the house pattern one directory over, which matches all three sentinels together: internal/webui/handlers/driverapi/module.go:822. At the top of the supervise loop the mistake is invisible — both outcomes just sleep and retry (supervisor.go:294-299). It only bites on the verify-before-kill path.

Every citation in that trap was opened and checked, but the conclusion is a reading of code in the two pinned trees — not an observed runtime failure. Treat it as a worked example of how to reason across the seam, and reproduce the reading yourself in step 3 of the exercise before you repeat it to anyone.

So how do you actually answer the question?

No loom command answers this for an arbitrary agent. loom daemon status comes closest — it prints Ownership: fence N per agent, and the JSON carries ownership_lease_id, ownership_fencing_token and ownership_last_heartbeat (internal/cli/daemon/daemon_display.go:34-36, daemon_cmd.go:47-49) — but that is one daemon reporting the lease it holds, read out of its own state file (daemon_state.go:146-148, via ReadStateFile at daemon_cmd.go:501). It never asks fleet-db, so it cannot tell you that some other daemon owns the agent. Grep for consumers of AgentOwnershipLeases() and you get the supervisor, the tracing wrapper, and the two store implementations — nothing operator-facing. (That grep is the standard move; if it did not come to you first, re-read the decision tree in the navigation reference.) You answer the question by reading fleet-db, and there is a right way and a wrong way.

Trap — GET returns a status you must not trust

GetAgentOwnershipLease is an HGETALL and an unmarshal. Nothing normalises the stored status, so a lease whose expires_at passed an hour ago still reads "status":"active":

func (s *RedisStorage) GetAgentOwnershipLease(ctx context.Context, ws, agentID string) (*models.AgentOwnershipLease, error) {
	data, err := s.client.HGetAll(ctx, AgentOwnershipLeaseKey(ws, agentID)).Result()
	if err != nil {
		return nil, err
	}
	return unmarshalAgentOwnershipLease(data)
}

fleet-db internal/storage/control_plane.go:716-722. List does normalise — it runs every row through agentOwnershipLeaseEffectiveStatus, which downgrades active to expired when ExpiresAt is not in the future (:747 and :1942-1947). Grep for that helper and you get exactly three hits, none of them in Get.

Which gives the procedure. In order of decreasing trust:

  1. List, filtered. GET /api/v1/{ws}/agent-ownership-leases?status=active — the filter is applied to the effective status (fleet-db internal/storage/control_plane.go:1936), and the rows come back with status already corrected. Every row is a live owner; the owner_id and node_id tell you which supervisor.
  2. Get, then do the expiry check yourself. If you fetch one agent's lease directly, compare expires_at against now before believing status. That is precisely what the daemon's IPC validator does for the session lease — status check and expiry check as two separate guards (internal/cli/daemon/daemon_ipc.go:473-484).
  3. Attempt an acquire. The only fully authoritative answer, because it is the arbiter itself. Reserve it for the runtime: it is a write, it bumps the fencing token, and a stranger's acquire is how an agent gets killed.
Before you point any of that at a running stack

These stacks are shared machine state. Pick your own compose project and your own unclaimed port block; never up, down or --build a stack you did not create, and never touch someone else's podman or agent-browser session. Reading is fine; the acquire in step 3 is a write against whatever workspace you aimed it at. Nothing in this lesson's exercise starts a stack.

Trap — the PID is inside the owner's name

resolveNodeID returns loom-supervisor-<hostname>-<pid> (internal/cli/daemon/supervisor/control_plane.go:145-153), and that string is the lease's owner_id (ownership.go:44-51). So a restarted daemon is a different owner — same host, same workspace, same agent, new PID. The lease is released on the normal unwind paths (supervisor.go:301-304, 307, 316, 330), but a SIGKILLed daemon releases nothing, and the next daemon's acquire is refused until the old lease expires. With defaultLeaseTTL = 30 * time.Minute (supervisor.go:248) that is a long time to watch an agent refuse to start for no visible reason.

The log line is your tell, and it is the one the previous trap predicts: a refusal that reached the ErrAlreadyExists/ErrConflict arm logs agent ownership held by another daemon at Info (ownership.go:54); one that fell past it logs agent ownership acquire failed at Warn (ownership.go:62). Same cause, different line.

And loom workspace ops diagnose will not tell you: its duplicate_daemon_ownership warning compares two daemon PID files and never reads a lease (internal/cli/workspace/ops_cmd.go:683-692). That is Lesson 08's rule again — PID files are a convenience, the lease is the authority — showing up as a gap between two tools that sound like they answer the same question.

Check yourself

From memory: a supervisor's ownership heartbeat returns an error. Walk the whole decision to one of three ends — keep running, re-acquire, kill — and say what makes each step safe without comparing two machines' clocks.

1. Typed or untyped? isTypedDomainError matches ErrGone, ErrNotFound, ErrAlreadyExists, ErrConflict, ErrInvalid — a sentinel means the server classified it; anything else means the wire failed. ownership.go:325-334

2. Untyped ⇒ retry once. The retry goes through the same heartbeat plumbing, so a success is a genuine renewal and the anchor advances. Still untyped ⇒ step 4. ownership.go:221-237

3. Typed ⇒ one tri-state re-acquire. Dead-process guard first, from supervisor state rather than signal-0. Acquired ⇒ continue with a new fence. Held-by-other ⇒ kill, reason verifiably_lost. Inconclusive ⇒ step 4. ownership.go:247-276

4. Bounded fail-open. Continue only while both the monotonic and the wall clause say less than the TTL has elapsed since the last confirmed renewal — a local anchor taken before a request the server acknowledged, never the server's ExpiresAt. Past it, kill with reason ownership_unverifiable. ownership.go:282-292, 294-323

In re-acquire arbitration, what separates ownershipHeldByOther from ownershipAcquireInconclusive?

  • held-by-other kills now; inconclusive rides out the validity window
  • held-by-other rides out the window; inconclusive kills immediately
  • both kill at once, but only inconclusive records a LastError reason
  • both ride out the window; only held-by-other emits a warning line
Verifiable loss is the only thing that justifies killing a running agent immediately (ownership.go:270-272). Inconclusive means the server's verdict is unknown, so the supervisor keeps running until the last confirmed renewal can no longer prove the lease is live, then fails closed with reason ownership_unverifiable (ownership.go:282-292). Both do set LastError — the reason string is what differs (ownership.go:338-352).

fleet-db refuses an acquire because another daemon holds a live lease. Which sentinel reaches acquireAgentOwnership?

  • domain.ErrConflict, the generic leftover-4xx sentinel
  • domain.ErrAlreadyExists, the uncoded-409 default sentinel
  • domain.ErrAlreadyClaimed, the coded-409 claim sentinel
  • domain.ErrNotOwner, the 403-forbidden owner sentinel
The Lua returns CLAIMED, storage turns that into ErrAlreadyClaimed, the API writes 409 with code: already_claimed, and classifyHTTPError's coded arm maps it to domain.ErrAlreadyClaimed (client.go:461-462). ErrAlreadyExists is the sharp near-miss: a 409 with no recognised code really does fall through to it (client.go:476) — which is exactly the sentinel ownership.go:53 is written against.

You want to know whether agent planner is owned right now. Which read can you trust on its own?

  • GET the lease row and trust the status field it returns
  • LIST the leases and trust the status filter it applies
  • GET the node row and trust the last_heartbeat it returns
  • Read the two daemon PID files that ops diagnose compares
List rewrites each row's status through agentOwnershipLeaseEffectiveStatus before filtering (fleet-db internal/storage/control_plane.go:747, 1936). Get does not (:716-722), so its active can be arbitrarily stale. The node row answers a different question — is that supervisor process alive — and the PID files are the convenience the lease exists to replace.

Your heartbeat token still matches the stored lease, but the lease is no longer live. fleet-db answers HTTP with code lease_expired, and loomcli turns that into domain.ErrGone.

The Lua's INVALID result — exists, token matches, not live — is isolated precisely so it can become 410 rather than a generic conflict, because 410 tells the client that re-acquiring is safe. fleet-db internal/storage/control_plane.go:785-788; internal/api/control_plane.go:1247-1250; loomcli internal/infra/fleetdb/client.go:495-498
