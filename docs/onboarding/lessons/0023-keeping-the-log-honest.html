Keeping the log honest

Three background subsystems decide how much of the log survives in Redis — two of them delete, one only copies — and they are not interchangeable. By the end you can answer "how much history does this deployment actually have?" from its config alone — and you will never write a trim that can walk past the archive fence.

Skill state a deployment's real history horizon, and fence any trim you write Time 40 min Needs 05, 02 Repos fleet-db loomcli

Why this exists

The event log is the truth, and the event log lives in RAM. Those two facts are in permanent tension, and everything in this lesson is the settlement between them. A workspace that has been busy for a year cannot keep every event in a Redis STREAM forever, so three separate subsystems exist to make it smaller — and each one answers a different question about the same bytes.

fleet-db writes the settlement down, which is unusual and worth reading before anything else. This paragraph is what a client is entitled to assume:

Note what that sentence is not. It is not "we keep 100 events". It is a floor, on one backend, under one configuration, for one of the two read paths. Change the backend or turn on a flag and the number changes — in both directions. Your job in this lesson is to be able to compute the real number rather than quote the doc.

That guarantee is regression-tested through HTTP rather than through the compactor's internals, and the test lives outside internal/ on purpose: test/durability/doc.go:5-9 explains that harness/policy.yaml forbids internal/api from importing internal/storage, and that misnaming a file to slip past the layering rule would be worse than moving the test.
The archive fence

The archive fence is one function value — models.ArchiveFenceFunc, a closure returning the last event ID confirmed written to cold storage for a workspace. Nothing may trim past it, and when it cannot be resolved the sweepers skip trimming entirely rather than guess. Trimming past the fence is not gated by a config flag; it is gated by proof that a durable copy exists. Whether a sweeper runs at all is still a flag — and on the default, fence-less path the compactor deletes below a 100-event floor with no durable copy anywhere (cmd/fleet-db/main.go:864, internal/compaction/compactor.go:192-197). internal/models/event.go:217-220

Three subsystems, three questions

Read the table by the second column. Each sweeper is triggered by a different property of the data, so they fire at different times, on different keys, with different consequences. Calling any of them "cleanup" will cost you an afternoon.

The last row is the one people get wrong in review. Of these three, the only one running on a stock fleet-db is the one that deletes; the one that makes a durable copy is off. That is a decision, not an oversight — but it means the default deployment's history horizon is exactly the compaction floor and nothing more. (A fourth sweeper outside this table — pub/sub topic retention — is also on by default and also deletes: internal/config/config.go:272, internal/storage/redis_pubsub.go:323. See the trap below.)

Why the archive is off: an earlier revision of commit d5945f8 enabled the SQLite archive by default, and review found two P0 defects it would have activated. Archive rows are keyed by event_id alone (internal/archive/migrate/migrations/sqlite/001_initial.up.sql:3), which collides across workspaces because Redis assigns stream IDs per stream — and INSERT OR IGNORE (internal/archive/sqlite/sqlite.go:107) then silently drops the loser while the worker advances the cursor the compactor trusts. The second: ordinary workspace deletion purges the Redis ID counter while leaving the archive intact, so a recreated workspace reissues IDs the archive still holds events for. That commit message is the best prose in the repo on what compaction may and may not destroy; read it before you propose turning the archive on.
Trap — "archive" names two unrelated things, and "retention" three

This is Lesson 02's problem again, inside one repo:

  • archive.EventArchive (internal/archive/archive.go:15) is SQL cold storage. It feeds the fence and the point-in-time reads.
  • retention.ArchiveStore (internal/retention/archive.go:39) writes JSONL files and manifests to a directory. Only the retention sweep writes to it (internal/retention/manager.go:285); the restore-drill validator reads and verifies the same manifests (internal/retention/restore.go:42, 72, 83), and is constructed only in tests today. The two share no interface, no storage and no cursor.
  • retention.RetentionPolicy (internal/retention/policy.go:15) is about events: HotEventsTTL, ArchiveBeforeTrim, VerifyBeforeDelete, SnapshotBeforeTrim.
  • storage.RetentionPolicy (internal/storage/storage.go:661) is {MaxAge, MaxLen} and applies to pub/sub topics, not to events. It is on by default (internal/config/config.go:272) — a completely different sweeper from the one that is off.
  • SnapshotRetention (internal/compaction/compactor.go:24-25) is neither: it is how many snapshots to keep per issue (3).

Disambiguate the way this repo's own glossary does — by naming the package. Say "the event archive" or "the retention archive"; "the archive" alone is not a statement. docs/glossary.md:194-204. None of these five are in the course's trap-word card yet, because that card covers loomcli's vocabulary — so add them to your own copy.

Why one workspace cursor can fence a per-issue stream

The fence is a workspace-level cursor: the archive worker tails the global stream fleet-db:{ws}:events and saves its position there (internal/archive/worker.go:135 → Subscribe at internal/storage/redis_eventstore.go:157-160). The compactor then uses that ID to trim a different stream, fleet-db:{ws}:events:issue:{id}. That is only sound because of one line of Lua:

The server assigns the ID once, on the global stream, and the per-issue copy is written with that same ID. So "this ID is archived" is a claim that transfers across stream families, and comparing the two is meaningful. Compare them with EventID.Before, never as strings — the format is <ms>-<seq> and the comparison is numeric, so "999-0" < "1000-0" is true in code and false in strings.Compare. internal/models/event.go:225-247

There are five things called "cursor" in this repo (docs/glossary.md:178-182), and two of them appear in this lesson: the projector cursor (fleet-db:{ws}:projector:cursor) and the workspace archive cursor that is the fence (LoadCursor, internal/archive/archive.go:39-41). Do not confuse the second with the per-issue archive high-water mark LatestArchivedID (internal/archive/archive.go:31-33), which the hybrid read splits on — the glossary does not count it among the five, and it is not a cursor. The Last-Event-ID you met in Lesson 13 is a use of an EventID, not a sixth (docs/glossary.md:166-167).

The trace: your local stack eats its own history

Nine hops, starting on your laptop. The specimen is an issue that has just received its 101st event in a loom local-mode stack.

  1. loomcli internal/bootstrap/embedded.go:366-383 The spawn decides nothing. Local mode starts the fleet-db subprocess with exactly four flags — --redis-durability-profile=managed, --auth-dev-mode, --authz-enabled=false, --rpc-enabled=false — plus env vars for the HTTP address, the Redis address and pool sizing. Not one of them mentions compaction, archive or retention. The subprocess does inherit your whole shell environment (embedded.go:379) and env beats defaults (fleet-db internal/config/config.go:281), so the shipped defaults apply unless you have a FLEET_COMPACTION_*, FLEET_ARCHIVE_*, FLEET_RETENTION_* or FLEET_BACKEND exported (config.go:1392, 1441, 1499, 1105). This is the hop from Lesson 06, seen from the other side.
  2. fleet-db internal/config/config.go:232-263 Default() settles it. Compaction.Enabled: true, threshold 100, sweep 5 m; Retention.Enabled: false; Archive.Enabled: false. Your laptop is running a compactor with no fence.
  3. cmd/fleet-db/main.go:864-872 Wiring, and the one conditional that matters. The compactor is built only when the backend is not Postgres. The fence option is appended only if cfg.Archive.Enabled and an archive backend actually initialised. No archive, no fence — and archiveFence == nil is a different code path from "the fence returned nothing".
  4. internal/storage/redis_eventstore.go:65-79 The 101st event lands. One Lua call, two XADDs, one ID. The per-issue stream is now 101 entries long. Nothing has been deleted yet; compaction is a sweep, not a write hook.
  5. internal/compaction/compactor.go:404-426 The sweep finds it. findOversizedStreams SCANs events:issue:*, pipelines XLEN over the hits, and returns every ID whose length is >= StreamThreshold. 101 ≥ 100, so this issue is a candidate. StartAll runs a sweep immediately at boot, before the first tick (compactor.go:338-343) — which is why a one-shot loom command can compact.
  6. internal/compaction/compactor.go:254-273 The fence is resolved once per workspace per sweep, not once per issue, and the (fence, fenceValid) pair is passed down explicitly. If the closure errors, fenceValid stays false and every trim in this sweep is skipped — snapshots still happen. On your laptop the closure is nil, so both values are zero.
  7. internal/compaction/compactor.go:126-180 Write, verify, then delete. Read the issue hash (empty hash ⇒ skip entirely); read the stream tip with XREVRANGE + - COUNT 1; return early if a snapshot already exists at that exact tip; marshal the hash to JSON and Save; then read the snapshot back and compare LastEventID before any trim runs. Copy this order into anything destructive you write.
  8. internal/compaction/compactor.go:192-203 The branch this whole lesson is about. No fence configured ⇒ TrimStreamMaxLen(…, 100). Fence configured ⇒ computeTrimPoint, then XTRIM MINID. Two different Redis commands with two different survivor counts. See the figure below.
  9. internal/service/issueevents.go:104 What the client gets back. GetHistory calls s.store.GetIssueEvents and nothing else. Whatever survived step 8 in Redis is the timeline — /history has no second source.

TrimStreamMaxLen is XTRIM MAXLEN ~, which keeps at least that many entries and is a no-op for maxLen <= 0. TrimStream is XTRIM MINID, which removes everything strictly below the given ID and keeps the fence entry itself. internal/storage/redis_compactor_store.go:46-66

The counter-intuitive consequence

Turning the archive on makes GET /issues/{id}/history return less, not more. With the fence configured and the archive worker caught up, the fence is at or beyond the issue's stream tip, so computeTrimPoint returns the tip (compactor.go:235-241) and XTRIM MINID tip leaves the stream holding one entry, until the next append. The floor only exists on the archiveFence == nil branch. The archived events are safe — they just are not reachable through that endpoint.

Nothing pins that survivor count. TestCompactIssueFenceAboveTip asserts only trimmed > 0 and its comment calls the case "same as no fence" (internal/compaction/compactor_test.go:1491-1494) — which is true of the trim direction and false of the survivor count. If you ever ship the archive on by default, that is the assertion to tighten first.

The pattern to copy: how a fenced trim is written

There are exactly two consumers of ArchiveFenceFunc in the tree, and they were written to the same shape on purpose. Learn the shape once:

Four guards, in this order, and the retention manager's constrainTrim repeats them line for line with one addition — it also treats the Redis maximum sentinel "+" as "constrain me" (internal/retention/manager.go:325-347). The rules the shape encodes:

  1. Resolve the invariant once, then pass it down. The fence is fetched per workspace per sweep and threaded through CompactIssue / ArchiveAndTrim / computeTrimPoint / constrainTrim as an explicit (fence, fenceValid) pair. Never re-fetch it in a loop.
  2. Distinguish "no fence" from "fence unknown" from "fence empty". Three states, three branches. Collapsing them into one nil check is how you turn a config question into data loss.
  3. Fail closed. Unknown ⇒ return the skip sentinel, never the tip. TrimStreamMaxLen(maxLen <= 0) is a no-op rather than "trim everything" (internal/storage/redis_compactor_store.go:57-60). The pub/sub trimmer does the same with an empty floor (internal/storage/redis_pubsub.go:313-315).
  4. Never call XTrim* from a policy layer. Retention depends on a two-method StreamTrimmer interface it declares itself, with a comment saying exactly this (internal/retention/manager.go:41-46).
Trap — the unfenced trim you can write by accident

storage.EventStore — the interface almost every service already holds — exposes TrimStream(ctx, workspace, issueID, minID) (internal/storage/storage.go:648-650), implemented as a bare XTRIM MINID at internal/storage/redis_eventstore.go:390-398. It has no production caller: both real trims go through RedisCompactorStore. So the fence is not a wall around Redis; it is a convention observed by two call sites, and an unfenced XTRIM is one method call away on a dependency your service already holds.

And Lesson 04's gate will not save you: harness/policy.yaml defines rules for key construction, import layers, Lua arity, handler coverage and doc drift, and nothing about trimming. Verify that yourself in the exercise — it is the difference between a rule the machine enforces and a rule you have to hold.

Trap — "enabling the archive extends the timeline"

It does not. GET /issues/{id}/history reads s.store.GetIssueEvents and stops (internal/service/issueevents.go:104). Only the point-in-time endpoint GET /api/v1/{ws}/issues/{id}/at/{timestamp} goes through a reconstructor, and only that reconstructor is swapped for ArchiveReconstructor when an archive backend exists (cmd/fleet-db/main.go:725-729, internal/api/history.go:48-49). Its mergedEvents reads all archived events for the issue, then the Redis tail strictly after the per-issue high-water mark, and concatenates without dedup because the split is exclusive (internal/history/archive_reconstructor.go:79-111).

The doc states this correctly at docs/architecture.md:1365-1369. A code comment in the compactor does not: internal/compaction/compactor.go:34-35 says per-issue streams' "timeline endpoint does stitch the archive back on." That comment is a fossil: the merging /history it describes was written on the dropped revision of d5945f8 and never shipped. Believe the handler, not the comment.

Answering the question

Four config reads, then one question about the caller. In order, because each answer makes the later ones irrelevant:

  1. --backend / FLEET_BACKEND. Postgres skips compaction, retention and the archive worker outright (cmd/fleet-db/main.go:864, 966-999, 1002) and keeps the full log. Stop here if it says postgres; default is redis (internal/config/config.go:185).
  2. Compaction enabled, and its threshold. On by default at 100. This is your floor only while no fence exists.
  3. Archive enabled, and an archive backend that initialised. Both, or the fence is nil — and with --archive-enabled but no --archive-backend you get a startup WARN and no fence (cmd/fleet-db/main.go:997-998). If the fence exists, the floor is gone and the horizon becomes "whatever the archive worker has not yet confirmed".
  4. Retention enabled. If yes, an age cutoff also applies — to the global stream as well — but only for the workspace literally named DEFAULT.

Then: which endpoint is the caller using? /history sees only what is in Redis. /at/{timestamp} can be seeded by a snapshot when the issue.create event has been trimmed away (internal/history/reconstructor.go:87-107) — and only three snapshots survive per issue (internal/compaction/compactor.go:24-25, internal/storage/redis_snapshot_store.go:141-151).

All four config reads live in one function, config.Default(), and one file, cmd/fleet-db/main.go. When you need the loomcli half of the answer instead — which command opened which store, in which mode — the decision tree on the Finding Anything card gets you there faster than grep.

A consequence worth predicting rather than discovering: a workspace created after startup gets a projector, because workspace creation notifies the projector manager (internal/api/workspace.go:123-124, cmd/fleet-db/main.go:573), but it gets no archive worker — the archive manager is handed a startup snapshot of workspace keys (cmd/fleet-db/main.go:751-769, 972) and is not wired as a notifier. With the archive on, that workspace's LoadCursor returns "" with no error (internal/archive/sqlite/sqlite.go:304-315), so fenceValid is true, the fence is empty, and every trim is skipped forever. Redis grows; nothing is lost. Fail-closed, working exactly as designed.

Check yourself

From memory: you are handed a fleet-db deployment you have never seen and asked how far back an issue's timeline goes. State the four things you check, in order, and what each one changes about the answer.

1. The backend. postgres ⇒ the full event log, kept indefinitely; compaction, retention and the archive worker are all skipped. cmd/fleet-db/main.go:864, 966-999, 1002

2. Compaction, and its threshold. On by default, threshold 100. That is the floor — XTRIM MAXLEN ~ keeps at least that many. internal/config/config.go:232-237, internal/compaction/compactor.go:193-197

3. Archive enabled and a backend that initialised. Both, or there is no fence. With a fence the floor disappears and the trim goes to min(fence, tip). cmd/fleet-db/main.go:866-872, internal/compaction/compactor.go:198-203

4. Retention enabled. Adds a 30-day age cutoff with no floor, over per-issue and global streams — but only for the workspace DEFAULT. cmd/fleet-db/main.go:308, 1002, 1037, internal/retention/manager.go:186-191

Then ask which endpoint the caller uses: /history reads Redis only; /at/{timestamp} can be seeded from a snapshot or, with the archive on, from archived events.

The archive fence closure returns an error during a sweep. What happens to that workspace for the rest of the sweep?

  • Snapshots still run; every trim in the sweep is skipped
  • Snapshots are skipped; every trim runs to the stream tip
  • Snapshots still run; every trim falls back to the floor
  • Snapshots are skipped; the whole sweep aborts with an error
The fence is resolved once per workspace; on error fenceValid stays false and computeTrimPoint returns the skip sentinel, while the snapshot-and-verify steps run unchanged (internal/compaction/compactor.go:263-273, 225-229). The third option is the sharp near-miss: the StreamThreshold floor lives on the archiveFence == nil branch only, so a configured fence never falls back to it. Asserted at compactor_test.go:1541-1553.

You set FLEET_ARCHIVE_ENABLED=true with a working SQLite backend. What changes for GET /issues/{id}/history?

  • It reads the archive first, then appends the Redis tail
  • It reads the newest snapshot, then replays the Redis tail
  • Nothing: it reads the Redis per-issue stream and only that
  • It reads the archive only if the create event was trimmed
GetHistory calls s.store.GetIssueEvents and has no other source (internal/service/issueevents.go:104). The first two options describe real code — ArchiveReconstructor.mergedEvents and the snapshot-seeded replay — but both are wired behind /at/{timestamp}, not the timeline (internal/api/history.go:48-49). In practice the endpoint returns fewer events afterwards, because the fence replaces the 100-event floor.

Reaching back to Lesson 06: a plain loom command spawns the embedded fleet-db. Which history subsystems are live inside it?

  • Compaction off, archive off, retention off — nothing sweeps here
  • Compaction on, archive off, retention off — the shipped defaults
  • Compaction on, archive on, retention off — a fence is wired
  • Compaction on, archive off, retention on — an hourly age sweep
The spawn passes four flags and a handful of env vars, none of them about history (loomcli internal/bootstrap/embedded.go:373-383), so config.Default() decides (fleet-db internal/config/config.go:232-263). And because StartAll sweeps immediately before its first tick (compactor.go:338-343), a short-lived CLI process is long enough to trim.

Exactly two production subsystems consume models.ArchiveFenceFunc: the compactor, and the manager.

Both are constructed with a WithArchiveFence option from the same closure over archiveBackend.LoadCursor (cmd/fleet-db/main.go:867-870, 1016-1019), and both apply it with the same four-guard shape (internal/compaction/compactor.go:221-242, internal/retention/manager.go:325-347).

Compute the horizon, then prove the floor

Before you start

Every step here is read-only: greps, file reads, and go test of a single package against an in-process miniredis. Do not run make local-mode-up or down, start a server on a fixed port, or touch a podman or agent-browser stack for this lesson. If you ever do bring a stack up on this machine: pick your own compose project and your own unclaimed port block, and never touch a stack you did not create.

  1. In fleet-db, enumerate the fence's consumers: grep -rn --include="*.go" "ArchiveFenceFunc" . | grep -v _test.go. Name the two subsystems and the one file that defines the type.
  2. Now enumerate every trim: grep -rn --include="*.go" "XTrim" . | grep -v _test.go. Six hits: five calls and one comment. Classify each call as fenced, floored, fenced by something else, or reachable but unused — and for the last one, name the interface that puts it within reach of an ordinary service.
  3. Prove the floor: go test ./test/durability/ -run TestCompactionFloor -v. Read the two t.Logf lines, then open compaction_floor_test.go:52-64 and say what each of those four t.Fatals defends against — every one of them refuses to run rather than pass vacuously if a shipped default changes.
  4. Prove fail-closed: go test ./internal/compaction/ -run 'TestCompactIssueFence' -v. Four tests pass. Say which two demonstrate that an unresolvable fence skips the trim, and what each one passes as the fenceValid argument.
  5. Check the gate's blind spot (interleaves Lesson 04): grep -n "trim\|XTrim" harness/policy.yaml. Then read the rules: block from line 58 and write one sentence saying which machine-checked rule would fire if you built a Redis key by hand inside a new trim helper, and which would not fire on the trim itself.
  6. Back in loomcli, read internal/bootstrap/embedded.go:366-383, confirm with env | grep ^FLEET_ that nothing in your own shell overrides the defaults the subprocess inherits, then state, with the fleet-db line that decides it, which of the three subsystems is running in your own local stack right now — and therefore how far back /history goes for an issue you have touched 400 times.
You succeeded when Step 1 prints 6 lines across 3 files and you can name compaction and retention; step 2's six hits resolve to five real calls plus one comment; step 3 prints per-issue stream trimmed to the floor: 150 -> 100 events (threshold 100) followed by history over HTTP after compaction: 100 entries, total_events=100; step 4 shows ok github.com/tysonthomas9/fleet-db/internal/compaction with four PASS lines; step 5's grep returns nothing; and, with no FLEET_ variables exported, your answer to step 6 is "compaction only — at least the last 100 events, and no durable copy outside the miniredis snapshot."
