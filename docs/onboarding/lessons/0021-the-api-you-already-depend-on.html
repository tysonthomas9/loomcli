Week 5 / Lesson 21 / fleet-db

The API you already depend on

Every path string in loomcli is a bet on a route table you did not write. Here is how to find the line that route is registered on, and how to read what it actually answers — before you call it.

Skill find the fleet-db route behind any loomcli call and read its real contract Time 30 min Needs 06, 07 Repos loomcli fleet-db

Why this exists

Lesson 07 gave you the client half of this boundary: two stacks, two error models, one server. It stopped at the wire. This is the other side of the same wire.

Look at what a store call actually is:

Nothing type-checks that. It is a string, concatenated at runtime, asserting three things at once: that a Go http.ServeMux in another repository has that exact pattern registered; that it answers with a body rather than a 204; and that the body decodes into repoWire, the local struct whose comment claims it "mirrors fleet-db's models.Repo JSON shape" (internal/infra/fleetdb/repo.go:15-26). Get any of the three wrong and you find out in production, or in an integration test if you are lucky.

The good news is that all three are cheap to check, because fleet-db's edge is one flat, greppable table.

The one idea

api/openapi.yaml is the index. The handler is the contract. A harness check machine-verifies that every registered route appears in the spec — bar one hard-coded exemption — so the spec is a reliable map of what exists. Nothing ties a route's documented responses to what its handler writes, so its status codes and body shapes are prose except where someone pinned one by hand. For what actually comes back, read the handler.

The route table is one grep fleet-db

Every route in fleet-db is registered in one of the top-level files of internal/api/, one file per route group, each exposing one or two RegisterXxxRoutes functions — workspace.go exports RegisterWorkspaceRoutes at :43 and RegisterIntegrityRoutes at :253, and issues.go, skills.go, revert.go, history.go and v2_routes.go each export a pair too. The registration line carries everything you need to identify a route: method, pattern, permission, handler.

That shape repeats 260 times, and the whole surface sorts into four groups: 242 workspace-scoped routes under /api/v1/{workspace}/…, where the path parameter is the Workspace key; 10 admin routes under /api/v1/admin/…; 5 under /api/v2/; and three infrastructure routes registered outside internal/api/ — GET /healthz and GET /readyz (cmd/fleet-db/main.go:538-539) and GET /metrics (main.go:552). There is no router package, no annotation, no code generation — the literal string in the source is the route.

Count it yourself in the exercise. The number matters less than the fact that it is countable: an edge you can enumerate with grep is an edge you can audit.

They describe different servers. loomcli's is titled Loom CLI API, has 129 paths, and covers the web UI and daemon surface under /api/workspaces/… — it contains zero /api/v1/ paths. fleet-db's is titled fleet-db, 12,235 lines, 183 paths, 259 operations. The trace: one write, across the boundary

Lesson 06 ended hop 9 at "the write — which is two HTTP calls". This is that hop, opened up.

  1. internal/infra/fleetdb/repo.go:42-69 The call. repoStore.Create builds an anonymous request struct, then POST /api/v1/{ws}/repos. On success it makes a second call, PATCH /api/v1/admin/workspaces/{ws}, and if that fails it DELETEs the repo it just made (repo.go:62-67) — the hand-written compensating rollback from Lesson 06.
  2. fleet-db internal/api/repos.go:64 ← the grep lands here The registration. wrap(auth.PermRepoCreate, h.create). Two facts for free: the permission this route demands, and the handler that serves it. Note that the second call in hop 1 goes to a different family — /api/v1/admin/… routes are registered with GlobalAuthzWrap instead (internal/api/workspace.go:53), and the workspace admin routes spell their path parameter {key}, not {workspace}. The admin family is not uniform — the four apikey routes spell theirs {id} (internal/api/apikey.go:51-54) — so grep the literal you actually built.
  3. cmd/fleet-db/main.go:650 The wiring. api.RegisterRepoRoutes(srv.Mux(), repoSvc, logger, wsValidator, authorizer). A Register function nobody calls compiles fine and serves nothing, so this line is the proof that the route exists at runtime — provided the call is not inside a conditional. Some are: the apikey group is registered only when cfg.Auth.Enabled (main.go:568-570). The fourth argument is the workspace validator built at main.go:580.
  4. internal/api/authz_wrap.go:12-19 Order of the wrappers. AuthzWrap returns mw(authz.Require(perm, next)), so the workspace validator runs first, then the permission check, then your handler. Anything those two write, your handler never sees.
  5. internal/api/workspace_middleware.go:46-91 Three statuses before the handler. A malformed workspace key is 400 invalid_parameter (:76-79); a key that does not exist is 404 from NotFound("workspace", key) (:81-86); a lookup that fails for any other reason is 500 internal_error (:87-89). All three are produced by a wrapper, so none appears anywhere in repos.go. A request carrying X-Fleet-Repo or ?repo= takes the resolver branch instead (:46-73) and answers through writeResolverError (:100-108).
  6. internal/api/repos.go:71-114 The handler, and the house skeleton. Path values → decodeJSON (400 invalid_json, or 413 body_too_large past the 1 MB cap at internal/api/json.go:7) → repo.Validate() (400 validation_failed) → the service call → on success WriteJSON(w, http.StatusCreated, repo). The other four handlers in this file are variations on those steps.
  7. internal/api/errors.go:139-271 → response.go:87-93 One table turns sentinels into statuses. writeServiceError calls MapServiceError, the switch every route on the shared error path goes through — the control-plane and await routes carry their own (writeStorageError, internal/api/control_plane.go:1235-1254). A duplicate repo returns service.ErrAlreadyExists (internal/service/repo_service.go:74-75), which becomes 409 already_exists (errors.go:214-215). For every sentinel the switch matches, the message is the sentinel's own Error() string, deliberately stripped of wrapping context so internal detail cannot leak (errors.go:132-138); four typed errors are peeled off by errors.As before the switch and carry their own message and Meta (errors.go:146-161).
  8. internal/api/response.go:60-77 The error envelope. WriteError wraps the APIError under an "error" key, always. The shape on the wire is {"error":{"code":…,"message":…,"meta":…}}. The package declares 30 ErrorCode constants — 24 at errors.go:15-52, six for the await routes at await.go:24-35 — and the workspace validator forwards six more verbatim, the UPPER_SNAKE resolution codes (internal/resolution/errors.go:8-15, via workspace_middleware.go:108).
  9. loomcli internal/infra/fleetdb/client.go:422-428, 445-513 Back across the wire. Any status ≥ 400 goes to classifyHTTPError, which reads error.code out of that envelope (client.go:549-559) and turns status + code into a domain.Err* sentinel: 404 → ErrNotFound, 409 with no recognised code → ErrAlreadyExists, 400/422 → ErrInvalid. Anything 4xx it has no arm for — 413, for one — falls through to ErrConflict (client.go:509-511).

Nine hops, nothing inferred. That is the whole method: grep the literal, confirm the wiring, read the handler down to its writes, then read the mapping table at each end of the wire.

Reading the contract: three questions

1. Which statuses can this route return?

Not "which does the spec list" — which can the code write. For POST /api/v1/{workspace}/repos, the full ledger on the plain path — a request carrying X-Fleet-Repo or ?repo= adds the resolver branch's own statuses and codes — and what each one becomes by the time your calling code sees it:

The spec entry for this route documents three of those: 201, 400, 409 (api/openapi.yaml:4931-4941). It is not lying — it documents what the handler writes deliberately. It simply does not know about the wrappers. Whatever the auth chain answers before any of this is a separate question, and the subject of Lesson 22.

2. What does an error body look like?

Always the same object, from every route that goes through WriteError. Which makes the spec's schema for it a problem:

The wire shape is not a string. It is ErrorResponse{Error *APIError} (internal/api/errors.go:57-79), and the hard-coded 500 fallback in WriteJSON spells the bytes out: {"error":{"code":"internal_error","message":"internal server error"}} (internal/api/response.go:66). Both loomcli client stacks agree with the code and not with the spec — they parse error.code as a nested field (internal/infra/fleetdb/client.go:549-559, internal/backend/fleet/fleet.go:194-209). That one schema is referenced 21 times in the spec.

Fixing it would make a contained first fleet-db PR. Nothing in fleet-db generates code from the spec — the file's only consumers in the repo are three tests in internal/api/ and the coverage check — so the blast radius is whatever reads it outside these two repos. Read internal/api/errors.go:57-69 for the real fields; details and meta belong in the shape too.

3. Is it paginated, and what is the default?

The spec marks this explicitly, but on only 20 of its 259 operations, with three values: x-pagination: none (16), limit-only (2), and cursor (2 — the v1 and v2 mutation-event endpoints you crossed in Lesson 13, at api/openapi.yaml:1873 and :2197). Where the marker is absent, read the handler.

loomcli mostly treats the spec this way. It names fleet-db's api/openapi.yaml in four comments outside tests, and three are about query parameters — "fleet-db's listIssues endpoint expects type, not issue_type" (internal/backend/fleet/params.go:166-169), the count endpoint's filters (params.go:252-255), and the params listAgentSessions does not yet accept (internal/infra/fleetdb/control_plane.go:148-151). The fourth cites it for a response shape: fleetMutationEvent mirrors components.schemas.Event (internal/backend/fleet/convert.go:490-494).

GET /api/v1/{workspace}/issues is the one to know, because everything lists issues. It has no marker, and it silently truncates:

So the storage layer's "give me everything" mode cannot be requested over HTTP at all. And the response envelope will not tell you it happened: ListResponse carries issues and count, where count is the length of this page (internal/api/json.go:31-34, issues.go:252-255). The spec's IssueListResponse schema does show total, offset and limit — described as planned or echoed-back, and absent from the schema's required: [issues, count] (api/openapi.yaml:8125-8152).

Trap — "no limit parameter means no limit"

loomcli's issue backend post-filters client-side when it asks for more than one label or more than one source repo. To do that it needs the unfiltered set, so it deliberately clears the limit: if needsListClientFilter(opts) { server.Limit = 0 } (internal/backend/fleet/params.go:145-157), and addListCoreFilters only emits limit when it is positive (params.go:176-178). Sending no limit reads as "everything" in loomcli and as "50" in fleet-db. The multi-label filter therefore runs over the first 50 rows, and returns a short answer that looks like a complete one.

Trap — trusting the spec's response codes

PATCH /api/v1/{workspace}/repos/{name} is documented as 204:

    patch:
      tags: [Repos]
      summary: Update a Repo
      operationId: updateRepo
      # … requestBody elided …
      responses:
        "204":
          description: Repo updated
        "404":
          $ref: "#/components/responses/NotFound"

The handler re-reads the record and returns it with 200:

	repo, err := h.svc.GetRepo(r.Context(), workspace, name)
	if err != nil {
		writeServiceError(w, r, err, "read updated repo failed")
		return
	}
	WriteJSON(w, http.StatusOK, repo)

api/openapi.yaml:4972-4986 against internal/api/repos.go:174-179. loomcli depends on the code, not the document: repoStore.Update decodes a body (internal/infra/fleetdb/repo.go:107-111), and the client returns early on a real 204 without decoding anything (client.go:429-431) — so a server that honoured its own spec would hand every caller a zero-valued repo and no error.

Why the spec drifts in exactly this way

Because of what is gated and what is not. Four mechanisms, and each covers precisely one thing:

  • Route existence — gated, hard. scripts/harness/cmd/check_openapi_coverage/main.go regex-scans every HandleFunc(/Handle( in internal/api and cmd/fleet-db, normalises {param} names away (main.go:217-221, which is why {key} and {workspace} both match), and exits 1 on any undocumented route:. The scan is non-recursive and skips _test.go (main.go:112-113, :124), so what it gates is the top-level files of those two directories — and it carries one hard-coded exemption, GET /metrics (main.go:26-28), which is registered at cmd/fleet-db/main.go:552 and documented nowhere.
  • Stale spec entries — a warning, not a failure. A documented path with no code route prints to stderr and the check still passes (main.go:82-88). The spec is a superset by design.
  • Request fields — gated, for two schemas. TestOpenAPIRequestSchemasMatchTheirStructs reflects over CreateIssueRequest and UpdateIssueRequest only. Every JSON body in the package is strictly decoded — decodeJSONBytes calls DisallowUnknownFields for all of them (internal/api/request.go:130-132), so one unknown field rejects the entire body anywhere — but only these two schemas are pinned to their struct. Its own comment says why response schemas are out of scope: "A response schema may legitimately expose a narrower or wider view" (internal/api/openapi_request_parity_test.go:45-53).
  • Documented responses — gated only where someone pinned them by hand. A few tests assert one fact each: that the issue-metadata DELETE entry documents a 400 (internal/api/openapi_test.go:352-371), and that the Issue, Role and TaskRun schemas carry particular properties and enums (openapi_test.go:14, :51, :105, :378). Nothing compares a route's documented responses against the handler that answers it.

So a route nobody thought to pin drifts freely. Neither of the two drifts above is pinned, and both are on green builds right now.

The pattern to copy when you add a route

  1. One RegisterXxxRoutes per route group, the permission named on the registration line. Never compute a permission inside a handler — the point of the convention is that grep 'HandleFunc(' internal/api is a readable authorization matrix.
  2. Declare the narrow interface your handlers need, at the top of your file — RepoService at internal/api/repos.go:15-23 lists five methods and names its real implementation in a comment. internal/api may import only service, models, logging, config and resolution (harness/policy.yaml:4-10) — never internal/storage. The concrete store is passed in from main.go.
  3. Return errors as sentinels from the service and map them once. If your handler is choosing a status code from a service error inline, you are duplicating MapServiceError.
  4. Add the path entry with a unique operationId, and set x-pagination if it lists anything. The coverage check forces the path entry and TestOpenAPIHasNoDuplicateOperationIDs forces the id to be unique (internal/api/openapi_uniqueness_test.go:55-86); nothing forces x-pagination, which is why the marker is on 20 operations and not 259.
  5. Write down the response codes you chose — in the spec entry, and in a test if a client depends on them. As you have just seen, that is the only place the choice is recorded.

Check yourself

From memory: you are looking at a loomcli line that calls a path under /api/v1/. Name the four things you open, in order, to learn what that endpoint returns — and say which one you must not trust for the answer.

1. The registration line — grep the templated literal in fleet-db internal/api/. Gives you the file, the permission, and the handler name.

2. cmd/fleet-db/main.go — the Register…Routes call, which proves the group is wired and shows which validator and authorizer wrap it.

3. The handler body, down to its WriteJSON / WriteNoContent calls, plus the wrappers that can answer before it (internal/api/workspace_middleware.go:76-91).

4. MapServiceError (internal/api/errors.go:139-271) for every status a service sentinel can produce.

api/openapi.yaml is trustworthy for which routes exist and what query parameters they take — its route list is machine-checked. Do not trust it for response codes or body shapes; no check compares those against the handler.

What does PATCH /api/v1/{workspace}/repos/{name} actually return on success?

  • 204 and no body at all, exactly as the spec entry says
  • 200 and the re-read repo, though the spec says 204
  • 200 and the patch echoed back, as the spec's schema says
  • 204 and the repo in an X-Repo header, not in the body
The handler updates, re-reads, and writes WriteJSON(w, http.StatusOK, repo) (internal/api/repos.go:174-179); the spec documents "204": Repo updated (api/openapi.yaml:4982-4984). The first option is the one to feel the sting of — it is what the document says, and it is wrong. Note what depends on this: repoStore.Update decodes a body, and the client short-circuits on a real 204 without decoding (internal/infra/fleetdb/client.go:429-431).

Where do you learn what an error body from fleet-db looks like?

  • api/openapi.yaml, whose ErrorResponse schema is the contract
  • internal/service/errors.go, where the sentinel errors live
  • internal/api/response.go, whose WriteError sets the status
  • internal/api/errors.go, where APIError and its codes live
The spec's ErrorResponse types error as a string (api/openapi.yaml:8515-8520) and is referenced 21 times; the wire shape is an object with code, message, optional details and meta (internal/api/errors.go:57-79). internal/service/errors.go declares the sentinels but says nothing about status codes — that mapping is MapServiceError. response.go only wraps and writes what it is handed.

Reaching back to Lesson 07: GET /api/v1/{ws}/issues with no limit parameter returns…

  • every matching issue, since an absent limit means no cap
  • at most 200 issues, the hard cap the API layer enforces
  • at most 50 issues, the default the API layer substitutes
  • every matching issue, since storage treats a 0 as "all"
parseListOptions sets opts.Limit = defaultLimit before it looks at the query, and clamps anything above maxLimit (internal/api/issues.go:17-19, 652-665). The last option is true one layer down and unreachable from here: storage does treat 0 as a full scan (internal/storage/issue.go:385-389), but the handler never passes a 0. This is why loomcli's multi-label list — which clears the limit precisely to get everything (internal/backend/fleet/params.go:153-155) — filters over 50 rows.

Every sentinel that reaches writeServiceError becomes an HTTP status in one switch, in the file — the same file that declares 24 of the API's 30 ErrorCode constants.

MapServiceError at internal/api/errors.go:139-271, reached through writeServiceError (internal/api/response.go:87-93). Its RPC twin is (*methods).mapServiceError (internal/rpc/methods.go:192), and a harness check compares both against internal/service/errors.go (scripts/harness/cmd/check_service_error_coverage/main.go:47-50) — unless the sentinel is on the 11-entry RPC waiver list (:23-35).

Read a contract you have already been calling

Before you start

Every step here is a read: greps, file reads, one single-package go test, one go run of a harness script. Do not start a stack for this lesson. This is a shared machine. If you later want to curl a live fleet-db, use a stack you started, with your own compose project name and an unclaimed port block — never up, down or --build a compose project you did not create.

  1. In loomcli, open internal/infra/fleetdb/repo.go:114-121 (repoStore.Delete). Write down both paths it calls, in order.
  2. In fleet-db, find the first one: grep -rn '"DELETE /api/v1/{workspace}/repos/{name}"' internal/api/. Note the file, the line, the permission and the handler method. Then prove it is live: grep -n 'RegisterRepoRoutes' cmd/fleet-db/main.go.
  3. Read that handler, then write the full status ledger for it — every status the handler can write, plus the three the workspace validator can write first on the plain path (internal/api/workspace_middleware.go:76-91). Compare it against the spec entry at api/openapi.yaml:4987-4995. Which of your statuses are missing there?
  4. Do the same for the PATCH on the same path and find the disagreement in the other direction, where the document claims something the code does not do.
  5. Run both gates: go test ./internal/api/ -run 'TestOpenAPI' and go run ./scripts/harness/cmd/check_openapi_coverage/. Both pass. In one sentence each, say why neither one catches step 3 or step 4.
  6. Reaching back to Lesson 07: which of the two client stacks does repoStore belong to, which error model does it produce, and which sentinel does the 404 from step 3 arrive as? Then answer the same three questions for GET /api/v1/{ws}/issues/ready, which is served by the other stack.
  7. Count the table: ls internal/api/*.go cmd/fleet-db/*.go | grep -v _test.go | xargs grep -hoE '(HandleFunc|Handle)\("[A-Z]+ /[^"]+"' | sort -u | wc -l
You succeeded when Your grep in step 2 lands on internal/api/repos.go:68 (PermRepoDelete, h.delete) and on cmd/fleet-db/main.go:650; your step-3 ledger has seven entries against the spec's two, including two different 400s — one from the validator for a bad workspace key, one from the handler for a bad repo name — neither of which the spec entry lists; step 4 gives you 200 in the code against 204 in the document; both commands in step 5 pass; and step 7 prints 260. Drop the grep -v _test.go and you get 267 instead — the test files register routes of their own, which is exactly why the coverage check skips them (check_openapi_coverage/main.go:124).
Read next, in full

fleet-db internal/api/errors.go. It is most of the client-visible error contract of the route table in one file: 24 of the API's 30 ErrorCode constants, with comments explaining why the awkward ones exist; the APIError shape; and MapServiceError — the switch that decides what a service failure looks like from outside on every route that goes through writeServiceError. Read it beside loomcli's two receivers, internal/infra/fleetdb/client.go:445-513 and internal/backend/fleet/errors.go:15-82; the second one hard-codes fleet-db's code strings as literals, which tells you exactly how much this file is load-bearing. If you want a second, shorter read, internal/api/repos.go is 194 lines and contains one complete route group end to end.
