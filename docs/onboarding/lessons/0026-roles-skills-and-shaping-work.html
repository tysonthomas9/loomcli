Week 6 / Lesson 26 / Control plane

Roles, skills, and shaping work

A role is a scoring function over one shared ready queue. Learn which of its fields reject a task and which merely prefer one, and you can answer the question people actually ask you: why did that agent pick that task?

Skill configure a role so the right agent claims the right task — and predict what it will refuse Time 30 min Needs Lesson 05, Lesson 08 Repos loomcli fleet-db

Why this exists

A workspace has one ready queue and many agents pulling from it. No dispatcher pushes work at a runner: every runner reads the same list, ranks it locally, and races for the top item — which is the claim protocol you already know from Lesson 08. The daemon tries two directed cases ahead of the shared queue — a task explicitly requested for this agent, and one already assigned to its worktree (internal/cli/daemon/supervisor/claim.go:70-86) — and falls back to the queue for everything else.

So "shaping work" is not routing in the network sense. It is choosing a ranking function that each runner applies to the shared list. That function is a role, and it is one function — MatchTask at internal/cli/task_router.go:74-142. Everything a role can say about which task it wants is expressed there, and nowhere else.

The one idea

Role fields do not partition the queue — they rank it. Exactly five conditions reject a task outright. Everything else is a preference, and a preference loses to an empty queue: a role with skills that match nothing will still claim an unrelated task rather than idle.

Skills are a preference, not a filter

Past the five gates the score starts at 100 and accumulates. The skill branch is the whole reason people misread this file:

Score 10, not 0. And SelectBestTask keeps every candidate with m.Score > 0 (internal/cli/task_router.go:149-153), so a task no skill matched is still claimable — it just sorts below every task that did.

countSkillMatches itself is set membership over raw strings: labels go into a map[string]bool and each skill tag is looked up verbatim (internal/cli/task_router.go:282-297). No lowercasing, no trimming, no prefix or glob matching. Go does not match the label go, and backend does not match backend-api.

These are the role skills of Lesson 02, not the skill document entity. One is a string compared against an issue label; the other is a SKILL.md loaded into a worktree. Nothing connects them.

The accumulating half is 100 + 50×matches + 30 if the repo matches + (20 − 4×priority), with the priority term clamped to [0, 20] (internal/cli/task_router.go:117-135). Read the constants against each other and the design falls out: one skill match is worth 50, a repo match 30, and the priority term — capped at 20 — swings only 16 across the legal P0-to-P4 range, 20 at P0 down to 4 at P4 (fleet-db internal/models/priority.go:17-20). A skill match outranks every priority difference there is. The tests pin the arithmetic — a P2 task with one match scores 162, with two matches 212 (internal/cli/task_router_test.go:241, 260).

Note the ordering of the two soft outcomes. The skill check returns before the repo check, so "right repo, wrong skills" scores 10 and "right skills, wrong repo" scores 5. The lower-value thing sorts higher.

In the daemon's own claim path the score-5 branch rarely fires, because the ready query was already narrowed: buildClaimOpts puts the agent's resolved repos in ReadyOpts.SourceRepos (internal/cli/daemon/supervisor/claim.go:108-110) and FleetBackend.Ready applies that as a hard client-side filter before scoring (internal/backend/fleet/fleet.go:394 → internal/backend/fleet/deferred.go:124-126). Same field, two mechanisms.

The role half is merged with the agent half by MergeRoleConstraints, which is deliberately blunt: an agent's PathPatterns and Backend replace the role's, and SourceRepos is always agent-level, never role-level (internal/cli/task_router.go:45-69). There is no field where the two are unioned.

Role and agent definitions are both fleet-db entities (glossary, Core objects); the yaml: tags on config.RoleConfig and config.AgentEntry (internal/cli/config/project.go:68-123) are vestigial — that package imports no YAML library at all. If you need to find which layer reads a given field, the navigation reference's decision tree is faster than a grep.

Trap — a task_filter value nothing parses

fleet-db's own model documents the field as a filter expression — “a filter string (e.g., "type=bug,label=urgent"). The format is consumed by the agent runtime; storage treats it as opaque.” (fleet-db internal/models/role.go:182-185)

No such format exists. The only consumer is applyTaskFilter, whose switch knows three values and whose default: arm is byte-for-byte the has_design arm (internal/cli/task_router.go:257-266). Nothing validates the field on the way in — not the CLI, not the PATCH handler (fleet-db internal/api/roles.go:206-238). So loom role set reviewer task_filter "type=bug" succeeds, is stored verbatim, and silently means has_design. A role that appears to be scoped to bugs is scoped to everything with a design — and plain loom role show will not even tell you the value is there, because it prints no task_filter line (internal/cli/role/role_cmd.go:214-255); only --json (:211-213) echoes it back.

Trap — max_priority reads backwards

Priorities are numbers where smaller is more urgent: P0 is critical, P4 is backlog, P2 is the default (fleet-db internal/models/priority.go:5-15). max_priority caps the number (internal/cli/task_router.go:96-98), so max_priority: 1 does not mean "at most one priority level" and does not mean "low priority work only" — it means P0 and P1 only, and nothing else, ever. Set it to 0 on a role and that role idles unless somebody files a critical bug. fleet-db's own field comment ("caps the highest priority issue this role may claim", fleet-db internal/models/role.go:219-221) reads as the opposite of what it does.

A role field that goes nowhere

fleet-db's Role carries labels and exclude_labels with a fully specified semantics — AND over required labels, OR over excluded ones, exclusion evaluated first (internal/models/role.go:200-211). They are accepted by the API, persisted, and projected. They are read by no query or claim path in either pinned tree, and loomcli does not even carry them: the client's roleWire has no such fields (loomcli internal/infra/fleetdb/role.go:21-45), and the string exclude_labels appears zero times in the whole loomcli repo. Setting them does nothing. Do not build a routing story on them without wiring them first.

What "no matching role" looks like

Two silent no-ops are worth knowing before you debug an idle agent.

First, an agent whose role is neither built-in nor carries a task_filter is never pre-claimed at all: shouldClaimTaskForRole returns BuiltInRoles[role] || RoleConfig.TaskFilter != "", and claimTask returns early when it is false (internal/cli/daemon/supervisor/claim.go:44-46, 294-296). Skills alone do not qualify a role for the claim path.

Second, in the agent's own in-process poll loop, BuildRouterTaskCheck returns nil — meaning "no routing, use the generic availability check" — when skills, max priority, task filter, repo label and source repos are all empty (internal/cli/task_router.go:324-326). An entirely unconfigured role does not score anything.

On a running stack the tool for all of this is loom daemon queue <agent>, which loads the agent's role from fleet-db, scores the real ready queue, prints the top five with their Reason strings and tallies the rejections by reason (internal/cli/daemon/daemon_queue.go:17-33, 121-145, 147-184). It needs no daemon and no socket.

Shared machine

loom daemon queue reads fleet-db, which in local mode means starting or reusing an embedded runtime under a config directory other people's agents may be using. Nothing in this lesson's exercise requires it, and you should not reach for it here. When you do run a stack later: pick your own compose project and your own port block, and never up, down or --build a stack you did not create.

A role sets skills: [go, daemon]. The only ready task is labelled frontend. What happens?

  • Skips it: a role with skills claims only tasks whose labels match
  • Claims it once the no-work backoff lapses and nothing better lands
  • Claims it: the task scores 10, and 10 still counts as a candidate
  • Skips it, logging a routing warning that names the unmatched labels
The skill branch returns Score: 10, not 0 (internal/cli/task_router.go:107-109), and SelectBestTask keeps every candidate with Score > 0 (:149-153). Skills bias the ranking; they never remove a task from consideration. "Skips it" is the belief the field's name invites, and it is the one that produces surprised agents.

You run loom role set reviewer task_filter "type=bug". Which tasks does the role now take?

  • type=bug — fleet-db parses it before returning a ready queue
  • any — an unrecognised filter value disables filtering entirely
  • needs_plan — the default the router applies when parsing fails
  • has_design — unknown filter values fall through to that branch
The switch knows three values and its default: arm duplicates the has_design arm (internal/cli/task_router.go:257-266). The command succeeds because nothing validates the field: not the CLI, and not fleet-db's PATCH handler, which checks effort, kind, executor, input policy, run duration and prompt — no routing field among them (fleet-db internal/api/roles.go:206-238).

Score two ready tasks with MatchTask, for a role that sets both skills and source repos. One matches the repo but no skill; the other matches a skill but not the repo. Which ranks higher?

  • The skill match, at 50 — a skill bonus outranks any repo mismatch
  • The repo match, at 10 — the skill check returns before the repo one
  • Neither — both score zero and never enter the candidate list at all
  • The skill match, at 30 — repo affinity is only a tie-breaking bonus
Order of evaluation decides it. The skill branch returns Score: 10 before the repo branch is ever reached (internal/cli/task_router.go:107-109), and the repo branch returns a flat Score: 5 that discards the +50 already accumulated (:117-124). So the lower-value task sorts higher — and both are still claimable.
