Realtime, one frame at a time

Five SSE streams, one writer, and one question you must be able to answer from the code alone: is this stream resumable? The answer is never "it writes event IDs, so yes".

Skill reason precisely about SSE frames and stream resumability Time 30 min Needs Lesson 12 Repos loomcli fleet-db

Why this exists

A browser tab watching a kanban board needs to hear about a change made by somebody else, in another process, seconds after it happens — without polling and without a reload. Server-Sent Events is a deliberately tiny protocol for that: a long-lived text/event-stream response, cut into frames separated by blank lines. Because it is tiny, it is easy to write by hand, and five different streams in this repo did exactly that.

The result was drift. The ADR that ended it is one paragraph long and worth reading in full:

That consolidation is commit ce4df56fb — the commit this whole course is pinned to. Note the split it draws, because it is the map of this lesson: the writer owns bytes; the handler owns meaning. Whether a stream can be resumed is a question about meaning, so the writer cannot answer it and never tries.

An earlier attempt (PR #182) shared the writer but left its fields public and kept discarding write errors, so bypass stayed possible. The ADR lists it under Considered Options as "reference only" — docs/adr/0001-sse-framing-single-writer-seam.md:27-30.
The cursor contract

A stream is resumable only when the server honors the client's Last-Event-ID on reconnect — reads it, and uses it to decide where to start. Writing id: lines is necessary and not sufficient. An ID the server never consults does not make a stream resumable; it only makes it look resumable.

Five frame kinds, five methods

CONTEXT.md names the vocabulary, and every Writer method belongs to exactly one term — though Resumable Event has two of them: WriteEvent takes an int64, formats it, and hands off to the string form WriteEventID (internal/webui/server/realtime/writer.go:32, 38). The bytes in the last column are copied from the golden test, which asserts them literally.

Those exact strings are pinned at internal/webui/server/realtime/writer_test.go:16-50. The method set is five lines of API surface:

Both fields are lower-case, so no caller outside the package can reach the socket. Everything funnels into one private encoder, which rejects CR/LF/NUL in IDs and CR/LF in event names, normalises \r\n and \r to \n, emits one data: line per segment, writes the frame in a single Write, returns the write error, and only then flushes. internal/webui/server/realtime/writer.go:52-95

The seam has a tripwire, not a proof — the ADR's own words. An AST test parses every non-test .go file under internal/ and cmd/ — except writer.go itself — and fails on any string literal with a line starting id:, event:, data: or retry:. A comment marker trips it only when the same literal also carries a newline, so a bare ": heartbeat" walks past (writer_seam_test.go:69); and it reads string literals only, so a prefix assembled at runtime is invisible to it — which is what the exercise asks you to work out. internal/webui/server/realtime/writer_seam_test.go:15, 24-30, 61-73

The trace: one mutation, and the ID it carries

  1. internal/webui/subscription/module.go:45-52 The route. GET /api/workspaces/{ws}/events is served by realtime.NewHandler, wired with the hub, the catch-up function, the workspace-from-context function, the SSE token store, and the activation callback.
  2. internal/webui/server/realtime/handler.go:74-88 Commit to the stream. Four headers (text/event-stream, no-cache, keep-alive, X-Accel-Buffering: no), then NewWriter(w) — a 500 if the ResponseWriter is not a Flusher — then SetWriteDeadline(time.Time{}) so the server-wide write timeout does not kill a long-lived stream.
  3. handler.go:90 → hub.go:360-379 Read the cursor. This is the hop that makes the stream resumable. ParseLastSince merges the Last-Event-ID header and the ?since= query: whichever is present wins; if both are present and both parse as int64, the larger header wins; otherwise the query wins. Opaque cursors are preserved as-is.
  4. handler.go:134, 179-194 → subscription/multi.go:277-293 Catch up before anything else. sendCatchUp returns immediately if since is empty, the workspace is empty, or no catch-up callback is wired (handler.go:180); otherwise it asks the workspace's subscriber for the mutations after that cursor and writes each one that passes the connection's ?source_repos= filter (handler.go:186) as a resumable event.
  5. subscription/backend_subscriber.go:108-122 → fleet-db internal/api/mutations.go:83-97 The cursor's real home. Catch-up is not served from an in-process ring buffer: GetMutationDataSince calls back out to the workspace's issue backend under a timeout — a fresh read, over the wire. On the fleet-db side that read decodes the opaque token (400 invalid since parameter if it is not one), serves the workspace's events after it, and returns the next cursor (mutations.go:24-29); its long-poll timeout is capped at mutationsMaxTimeout = 10000 (mutations.go:19).
  6. handler.go:141, 149 Then, and only then, the handshake tail. WriteRetry(RetryMs) — 5000 ms, from hub.go:17-24 — followed by a non-resumable connected event written with WriteEventNoID. The order catch-up → retry → connected is a contract; see the trap below.
  7. handler.go:201-235, 237-244 The loop. Three cases: a payload from the client's channel, written by writeSSEEvent as event: mutation with an ID; a 30-second tick that writes : heartbeat; and request-context cancellation, the normal close path. Any write error ends the stream — the error is no longer swallowed.
  8. handler.go:246-267 Which ID? eventIDForMutation uses the payload's opaque fleet-db Cursor when it has one — set on the payload at realtime/backend_adapter.go:19-21 — and otherwise falls back to a monotonic millisecond-scale counter, which is exactly what the numeric catch-up path expects to be handed back.
  9. internal/webui/frontend/src/api/common/sse.ts:382-386, 172-179 The browser closes the loop. The mutation listener stores event.lastEventId verbatim ("Fleet-db emits opaque durable cursors here, so preserve the value as-is"), and the next connect() passes it as the since parameter of the URL. The cursor rides the query string, because the client builds a fresh EventSource on every reconnect.
Why manual reconnect at all? The ?token= is single-use, so native EventSource auto-reconnect would replay a burnt token forever. handleError closes the source and re-runs the whole connect with a fresh token on exponential backoff — internal/webui/frontend/src/api/common/sse.ts:328-340, 342-370.

Now answer the question: is this stream resumable?

The bottom row is the most instructive. Its IDs are a process-global counter and its resume position is a file byte offset; the two are unrelated, so even if someone routed the header into startOffset the numbers would mean nothing to each other. And nothing routes it: internal/webui/log/module.go:26-34 registers two or three non-streaming log routes — the agent-log route is conditional on agentSvc (module.go:28) — and no stream at all; a repo-wide grep finds no caller of LogStreamer outside its own package.

Trap — "it has IDs, so the client can resume"

The PR review stream writes a well-formed id: on every message frame (internal/webui/handlers/prreview/stream.go:206). A browser will dutifully remember it and send it back. Nothing on the server reads it: prepareReviewerStream resolves a workspace, a pull request and an agent, and nothing else (stream.go:81-98), and the de-duplication set is created fresh inside runReviewerStream (stream.go:100-101). After a drop the client is re-sent the whole conversation from the beginning. That is a fine design for a stream whose payload is a full snapshot — it is not resumability, and calling it that will send someone hunting for a replay bug that does not exist.

Trap — reordering the handshake

It is tempting to greet the client first: connected, then retry, then the backlog. Do not. Catch-up events go out before the retry directive and the connected event (internal/webui/server/realtime/handler.go:134, 141, 149), and connected is written with WriteEventNoID so it cannot move the reconnect cursor past events the client has not seen. The comment on that line says exactly this, the golden test pins the ID-less bytes (writer_test.go:31-36), and two live tests split the ordering between them: catch-up before connected (internal/webui/app/sse_live_test.go:471-503) and retry before connected (sse_live_test.go:685-687). Neither pins all three hops — the catch-up test's reader drops retry: lines before it ever sees them (sse_live_test.go:148-151).

The pattern to copy when you add a stream

  1. Do every fallible thing before the headers. The driver watch resolves auth, the parent run, the epic, the cursor, the backend and the snapshot inside prepareWatch, so a failure is a structured JSON error instead of a dead text/event-stream. internal/webui/handlers/driverapi/watch.go:82-131
  2. realtime.NewWriter(w), four headers, SetWriteDeadline(time.Time{}). Skip the deadline and the server-wide write timeout kills your stream mid-life.
  3. Decide the cursor contract explicitly and write it in the doc comment. The watch handler's comment states the frame names, what the ID is, and that Last-Event-ID (or ?afterSeq=) is an exclusive seq cursor. watch.go:43-55
  4. Pick a cadence per stream. There is no shared heartbeat constant by design: the workspace stream beats every 30 s (hub.go:17-24), the driver watch every 15 s (watch.go:24-27). CONTEXT.md:89-91 says cadence belongs to the individual stream.
  5. Never format a frame yourself — not in a helper, not in a log line. The seam test walks all of internal/ and cmd/.

Check yourself

From memory: you are handed an unfamiliar SSE handler. State the two questions that decide whether the stream is resumable, and name the file that answers each one for the workspace …/events stream.

1. Does it write event IDs, and what are they? For …/events: writeSSEEvent → eventIDForMutation, which prefers the opaque fleet-db Cursor and falls back to a millisecond-scale counter. internal/webui/server/realtime/handler.go:237-267

2. Does the server read Last-Event-ID and start from it? For …/events: ParseLastSince merges header and ?since=, and sendCatchUp replays from it before the retry and connected frames. handler.go:90, 134, 179-194; hub.go:360-379

Only both together mean resumable. Question 1 alone is satisfied by the PR review stream, which is not resumable.

A stream writes id: on every event frame, but no file in the handler's package mentions Last-Event-ID. What is it?

  • Resumable, since the browser resends the ID it last saw
  • Resumable, provided the client also passes a query cursor
  • Not resumable — nothing on the server consults that ID
  • Not resumable, because event IDs must be numeric to work
Honoring the ID is the whole contract (CONTEXT.md:77-79). The first option is the sharp wrong answer: the browser really does resend it, which is precisely why an unread ID is so convincing. IDs are opaque strings by design, so the last option is false too — fleet-db cursors are not numeric. internal/webui/server/realtime/writer.go:36-40

Why is the connected event written with WriteEventNoID rather than with an ID?

  • Because a handshake frame has no payload worth identifying later
  • Because an ID there would move the cursor past unreplayed events
  • Because the hub has not yet assigned this client its stream cursor
  • Because clients ignore identifiers on frames they did not subscribe
It is a Non-resumable Event on purpose: it arrives after catch-up and after retry, and any ID on it would become the client's new reconnect position (internal/webui/server/realtime/handler.go:148-149). The first option sounds right and is not the reason — the frame does carry a payload, {"clientId":N}.

Reaching back to Lesson 05: when a browser reconnects with a cursor, where do the replayed mutations come from?

  • From the issue backend, re-read over the wire after the cursor
  • From the hub's 1024-entry broadcast retry queue in memory
  • From the per-client 64-slot send buffer kept after the drop
  • From a replay file the subscriber writes for each workspace
GetMutationDataSince calls back out to the workspace's issue backend under a timeout — catch-up is a fresh read, not a memory replay (internal/webui/subscription/backend_subscriber.go:101-122). The retry queue is real but is an outbound buffer for a full broadcast channel (hub.go:266-282), and a dropped client's channel is closed, not retained (hub.go:180-189).
