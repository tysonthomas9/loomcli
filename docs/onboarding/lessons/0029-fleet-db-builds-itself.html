Week 6 / Lesson 29 / Cross-repo

fleet-db builds itself

Three quarters of this repo's commits were written by an agent, so its architecture could not stay in prose. It lives in a 165-line policy file, and that file — not a reviewer — is what will reject your first change.

Skill read harness/policy.yaml and predict what fleet-db's gate rejects Time 35 min Needs Lesson 04, Lesson 18 Repos loomcli fleet-db

Why this exists

Count the authorship of fleet-db at the commit this course is pinned to: 709 of 932 commits carry a Co-Authored-By: Claude trailer. The repo's own guide says so in its first sentence — "an agent-first repository that uses Loom for role execution and FleetDB as the canonical task source" (AGENTS.md:4) — and loom.yaml names the five roles and the two standing worktree agents that do the work (loom.yaml:13-47).

That fact drives everything else in this lesson. A convention that lives in a markdown file is a convention a fresh agent context may or may not have read. A convention that exits non-zero is one nobody can miss. So fleet-db took the move you already saw in Lesson 04 — make the rule mechanical — and pushed it one step further. Where loomcli's Go gate calls nine hand-written guard scripts, each with its thresholds wired into the Makefile one line at a time (loomcli Makefile:596-610, 624), fleet-db has one machine-readable policy file plus programs that read it.

The one idea

harness/policy.yaml is fleet-db's constitution: 14 named rules and an import DAG, in 165 lines. The scripts/harness/check_*.sh wrappers are the courts that apply it, and harness/evals/ is the test suite for the courts. Read the constitution before you write code, not after your first failed gate.

And a warning about the word itself, from Lesson 02: gate is one of the five trap words (loomcli AGENTS.md:22; glossary). In loomcli, make gate is a one-line alias. In fleet-db it is a six-step target that runs containers. Same word, different blast radius.

The two gates, side by side

What a repo chooses to enforce is a statement of what it is afraid of. Read this table that way.

What the custom checks measure Size and shape: file LOC, package file count, import fanout, legal control-plane paths Invariants: import layers, key centralisation, Lua↔Go sync, action↔handler coverage

The shape of the difference: loomcli is afraid of getting too big to navigate — its ceilings are 1,000 lines per source file and 2,500 per _test.go, 25 non-test files per internal/ package, and 18 module-internal imports per package (loomcli Makefile:598-602, scripts/check-loc.sh:71-76). fleet-db is afraid of an invariant being broken invisibly — a Redis key spelled by hand in the wrong package, an event action with no projector handler, a Lua script whose KEYS indices drifted from its Go caller. Those failures do not look like failures until production. Neither repo enforces the other's list, and both are right.

fleet-db has no LOC ceiling, no package-size limit and no import-fanout limit — which is why cmd/fleet-db/main.go's run() is a single 1,011-line function (cmd/fleet-db/main.go:119-1129) and passes the gate. The one rule that could have caught it, cmd_bloat, skips any function named run in a */main.go — hardcoded in the checker, not written in the policy (scripts/harness/cmd/check_cmd_bloat/main.go:67-69).

The trace: one policy line to a blocked push

You edit internal/recovery/service.go, add an import, and push.

  1. Makefile:667-668 The habit you built in Lesson 04. In loomcli, gate: check — one line, and check runs Go and frontend gates concurrently. Nothing below this hop is true in that repo.
  2. fleet-db scripts/hooks/pre-push:12-16 The push hook. It runs make gate and aborts the push on failure. One escape hatch, checked first: SKIP_GATE set to anything skips the whole gate and prints a warning to stderr (:7-10).
  3. Makefile:171-179 gate is six sequential sub-makes. gate-static, gate-tests, coverage-merge, coverage-pkg, test-e2e, harness-eval. No aliasing, no shortcut.
  4. Makefile:182-186 gate-static seeds the build cache, then forks. go build ./... once, then make -j5 across vet, lint-keys, lint-deadcode, lint and harness-lint.
  5. scripts/harness/run_checks_parallel.sh:22-38, 40 Compile the checkers once. Every directory under scripts/harness/cmd/ — thirteen of them, twelve checkers and one autofixer — is built in parallel into a mktemp -d and the path is exported as HARNESS_BIN_DIR.
  6. run_checks_parallel.sh:43-59, 68-74 Sixteen checks fan out. Each runs as a background job from the repo root with its stdout and stderr captured to its own file. Only a failing check's output is ever printed.
  7. scripts/harness/check_import_layers.sh:10-13 The wrapper is the stable interface. If HARNESS_BIN_DIR holds a prebuilt binary it execs it; otherwise it go runs the source. That two-tier shape is the documented contract — "shell wrappers … are the stable interface used by Make and evals" (harness/README.md:18) — so you can run any single check by hand.
  8. scripts/harness/cmd/check_import_layers/main.go:37-55 Read go.mod, then the policy. The module path comes from go.mod; the layer list from $HARNESS_POLICY_FILE, defaulting to harness/policy.yaml (:42-45). A broken policy exits 2, a violation exits 1 — config error and rule breach are different failures.
  9. main.go:85-113, 115-124 Parse every file's imports. parser.ParseFile(…, parser.ImportsOnly) on each .go file; each module-local import is mapped to a layer and tested against that file's allow set. Any violation prints and exits 1.
  10. run_checks_parallel.sh:78-89 The collector. It prints the failed check's captured output, lists the failed names, and exits 1 — harness-lint fails, gate-static fails, gate fails, the push never happens.
  11. Makefile:178 → scripts/harness/run_evals.sh:14, 267-270 And then the gate checks the checkers. Even with all sixteen green, gate's last step runs 32 eval specs. The default minimum score is 100, and one failed blocker scenario fails the suite regardless of score.

The pattern to copy: a rule is five files

Adding an architectural rule here is not "write a script". It is a fixed five-part shape, and the shape is what makes the rule survive:

  1. A block under rules: in harness/policy.yaml — the tunable parts, so a fork of the harness can change them without touching Go.
  2. scripts/harness/cmd/check_x/main.go — the implementation. Exit 1 for a violation, exit 2 for a broken configuration.
  3. scripts/harness/check_x.sh — the wrapper: prebuilt binary if available, else go run.
  4. A line in the checks=() array (run_checks_parallel.sh:43-59) so make harness-lint runs it.
  5. A pair of eval specs in harness/evals/ — one asserting the check passes on this repo, one asserting it fails on a deliberately broken fixture.

Step 5 is the one that does not exist in loomcli, and it is the interesting one. eval_002_self_import_layers.yaml runs the real check against the real repo and requires exit zero. eval_002_layer_violation.yaml copies a three-file fixture repo into a tempdir, git inits it, points HARNESS_POLICY_FILE back at the real policy (run_evals.sh:126-138) and requires non-zero. The fixture is the whole violation:

A check that has never been observed to fail is not a check. This is that idea made routine — and it is close kin to the evidence-class discipline from Lesson 16: the eval names, in the spec, exactly what it proves.

The checker itself is usually small and blunt. This is all of the action_handler_coverage logic — the rule from Lesson 18 that every event action must land in internal/projection/handlers.go, enforced in both directions:

Two hardcoded paths (internal/models/event.go and internal/projection/handlers.go, main.go:18-19), two regexes, two loops. Today both sides hold 43 entries — internal/models/event.go:18-92 and internal/projection/handlers.go:16-63 — and the check exists to keep that equality true after somebody adds the 44th.

Where the map lies to you

"Which checks run" is not answerable from any one file, and both directions of the mismatch are live today. check_module_path has a policy rule (policy.yaml:78-80), a Go binary, a wrapper and three eval specs — but it is not in the checks=() array, so make harness-lint never runs it; the only one of the three that points it at this repo rather than a fixture is eval_005_self_module_path.yaml, a blocker eval. Going the other way, check_service_error_coverage, check_rpc_method_coverage and check_projector_handler_noop run in harness-lint (run_checks_parallel.sh:57-59) with no policy rule and no eval of their own — nothing has ever watched them fail. They reach the eval suite only through eval_102_repo_harness_lint.yaml, which re-runs make harness-lint and expects zero. Of the three, only check_projector_handler_noop has an escape hatch: the inline harness:noop-ok pragma.

Three traps

Trap — make harness-gate does not exist

Four checked-in places tell you to run it: AGENTS.md:49, docs/agents/index.md:33 ("harness.yml enforces harness-gate"), harness/README.md:40, and the review-evidence generator. The Makefile has no such target — CI runs make gate (.github/workflows/harness.yml:28) and so does the push hook. This was already found and half-fixed: commit 80b62e7, "post_task_gate.sh called make harness-gate which doesn't exist in the Makefile — the correct target is make gate. Fixed the script." The script was fixed; the four documents were not. Worse, the untouched generator writes the dead command into the artifact the review gate then blesses:

In CI — or with STRICT_REVIEW_GATE=1 — the review gate reads that file and requires seven exact H2 headings, each with a non-empty body, and no TODO|TBD|FIXME|PLACEHOLDER anywhere (scripts/harness/review_gate.sh:82-107); on a developer machine it never opens the evidence file at all (:5-12, 24-27, 77). It never asks whether the commands are real. Machine checks verify shape, not truth — which is the argument the next lesson is built on, arriving here as a working example.

Trap — the layer DAG only constrains packages it names

The natural reading of layers: is "this is the dependency graph." It is not. It is an allowlist over listed packages, and a file in an unlisted package is skipped before any import is examined:

internal/ holds 23 packages; the policy names 12 of them. So archive, auth, cursor, graph, history, migrate, recovery, resilience, retention, routing and testutil are unconstrained in both directions — nothing checks what they import, and nothing checks who imports them. Concretely: internal/recovery/service.go:16 imports internal/projection, and internal/retention imports internal/recovery, while its sibling sweeper internal/compaction — which is listed — may import only storage and models (policy.yaml:38-41). cmd/ is unlisted too, which is why main.go can import everything. Before you cite the layer block as proof that an edge is illegal, check that both ends are named in it.

Trap — the prompt's coverage number is not the gate's

The implementer role prompt says "The project enforces 90% statement coverage" and "Coverage must stay at or above 90%" (prompts/fleet-task.md:27, 67). The Makefile enforces COVERAGE_TOTAL_MIN ?= 75.0 aggregate and COVERAGE_PKG_MIN ?= 50 per package (Makefile:10-11, checked at :76 and :84). Same prompt, same file, one line apart from the sentence that is true: "make gate must pass. This is the single definition of 'done'" (prompts/fleet-task.md:68). When a prompt and the Makefile disagree, the Makefile is what runs.

One more, found by reading rather than running: make hooks copies four files — pre-commit pre-push post-checkout post-merge (Makefile:245-253) — but scripts/hooks/ contains only pre-push and test_hooks.sh. Three of the four cps cannot succeed, so the recipe exits non-zero after installing the one hook that matters. Do not run it to check: it writes into .git/hooks, which is shared by every worktree.
Before you run anything in fleet-db

Do not run make gate, make test-e2e or make test-integration for this lesson. The gate's fifth step is make test-e2e (Makefile:177), and both test-integration and gate-tests run podman rm -f $(podman ps -a --filter name=reaper -q) (Makefile:49, 210) — a name filter over every reaper container on the machine, not just this run's. That will delete containers belonging to a colleague's testcontainers run. Same rule as Lesson 03: pick your own compose project and your own port block, and never touch a stack, container or browser session you did not create. Everything in the exercise below is a read, a grep, or a check script that only reads files.

AGENTS.md tells you to run make harness-gate in fleet-db. What happens?

  • It runs the harness lint checks and skips the test suites
  • It fails, because there is no such target in the Makefile
  • It runs the whole gate, being an alias for make gate
  • It runs the eval suite only, which is what CI uses
There is no harness-gate target; CI and the push hook both run make gate (.github/workflows/harness.yml:28, scripts/hooks/pre-push:13). The third option is the sharp near-miss because that is the shape in loomcli, where gate really is an alias (Makefile:667-668) — carrying that expectation across the repo boundary is exactly how this trap catches you.

internal/retention is not named in harness/policy.yaml's layers:. What does the import-layer check enforce for it?

  • Nothing, because a package the policy does not name is skipped
  • Only the default allow list of models, logging, and config
  • Exactly the rules that its nearest listed parent package has
  • Only that it must not import any other unlisted package
layerForFile returns nil for an unmatched path and the file is skipped before its imports are read (cmd/check_import_layers/main.go:89-92); an import that resolves to no layer is skipped too (:104-107). There is no default and no inheritance — prefix matching is longest-first over the listed names only (:327-329, 353-362).

Reaching back to Lesson 04: what does fleet-db's make gate include that loomcli's make gate does not?

  • End-to-end tests, plus a self-test of its own checks
  • A frontend typecheck, plus a frontend architecture lint
  • A race-detector test run, plus a line-count ceiling
  • A staleness check on generated code, plus a coverage floor
test-e2e and harness-eval are steps 5 and 6 (Makefile:177-178); in loomcli e2e lives in the separate gate-e2e target (Makefile:670-674) and nothing tests the guards. Each of the last two options pairs something both gates run — a race-detector test (fleet-db Makefile:41, loomcli Makefile:622) and a coverage floor — with something only loomcli has: a line-count ceiling (Makefile:598) and a generated-code staleness check (Makefile:610). Neither pair is an addition fleet-db makes.

A checker reads its tunable configuration from $HARNESS_POLICY_FILE, defaulting to — and exits 2, not 1, when that file cannot be parsed.

Every policy-driven checker does this; see cmd/check_import_layers/main.go:42-50 and cmd/check_cmd_bloat/main.go:22-31. Exit 2 means "I could not evaluate the rule", which is a different bug from exit 1, "you broke the rule".

Read the constitution, then make it answer questions

Read-only throughout. No make gate, no test-e2e, no containers, no servers on fixed ports. If you later run a stack for something else, pick your own compose project and unclaimed port block, and never touch one you did not create.

  1. Read harness/policy.yaml end to end — 165 lines, ten minutes. For each of the 14 rules, write one sentence: what would a change of mine have to do to trip this? If you cannot answer for a rule, open its scripts/harness/check_*.sh and then its cmd/check_*/main.go — the same landing-on-a-line habit Finding Anything drills for loomcli, applied to a repo whose map you do not have yet.
  2. Run the four checks that need no compiler and no containers, from the fleet-db repo root: ./scripts/harness/check_repo_identity.sh, check_status_doc_sync.sh, check_docs_links.sh, check_lua_go_sync.sh.
  3. Run one policy-driven Go checker: ./scripts/harness/check_action_handler_coverage.sh (about a second). Then count both sides it compares, by hand: grep -cE '^[[:space:]]*Action[A-Za-z0-9_]+[[:space:]]+Action[[:space:]]*=' internal/models/event.go and grep -cE 'models\.Action[A-Za-z0-9_]+[[:space:]]*:' internal/projection/handlers.go. Reaching back to Lesson 18: which two handler functions are registered for more than one action apiece, and why that does not break the count?
  4. Find the doc/code conflict yourself: grep -rn "harness-gate" --include="*.md" --include="*.sh" --include="Makefile" . | grep -v fixtures. Then grep -n "^gate" Makefile. Decide which of the four hits is the dangerous one and say why in a sentence.

Write one sentence per repo defining the word gate there — this is the terminology handshake from Lesson 02, applied to a word you now know is overloaded across the repo boundary.
  6. Confirm the premise of the lesson: git log --grep="Co-Authored-By: Claude" --format=%H | wc -l and git rev-list --count HEAD.
