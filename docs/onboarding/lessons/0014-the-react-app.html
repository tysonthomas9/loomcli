Week 4 / Lesson 14 / Frontend

The React app

A quarter of a million lines of TypeScript you are about to have to change. You do not need to be fluent in modern React to change it safely — you need four rules. Three of them a linter or a build gate fails you on the moment you break them; the fourth only a reviewer catches.

Skill find and safely modify any part of the frontend Time 35 min Needs Lesson 12 Repos loomcli

internal/webui/frontend/src holds 1,033 TypeScript files and 251,753 lines. Nobody here has read all of it. What makes it navigable is that the directory layout is not a style preference — it is a dependency graph a linter will not let you violate. Paths below are relative to internal/webui/frontend/ unless they begin with internal/.

The one idea

Every question you will have here — where a file goes, why some indirection exists, why an import will not compile — is answered by the layer DAG in the header comment of eslint.config.js. Read it once and the rest of the codebase stops looking arbitrary. internal/webui/frontend/eslint.config.js:1-47

How the SPA reaches a browser

Start here, because this is what people get wrong first. The frontend is not compiled into the Go binary. There is no //go:embed of the built bundle anywhere under internal/webui. The server serves a directory, and only if you name one:

So loom serve with LOOM_FRONTEND_DIR unset registers no / route and serves zero frontend — it is a JSON/SSE/WebSocket API and nothing else. It says which mode it is in on startup: api-only mode — frontend served externally, or serving bundled frontend. internal/webui/app/server_app.go:99-103 The flag is --frontend-dir, defaulting to $LOOM_FRONTEND_DIR. internal/cli/serve/serve.go:162 Because that default is an inherited variable, "bare" is a claim about your shell, not about the command line: loom local exports LOOM_FRONTEND_DIR into the loom serve child it spawns, and a desktop-launched shell inherits it. internal/cli/local/runtime.go:456-459 Run env | grep LOOM_FRONTEND_DIR before you trust either startup line. When a directory is named, requests matching no file fall back to index.html — that fallback is what lets /ws/<id>/kanban survive a hard refresh. internal/webui/app/frontend.go:18-37

Trap — loom serve --help lies by omission

The command's long description says "The frontend is served externally (reverse proxy, CDN, Vite preview, etc.)" and then lists sixteen environment variables — LOOM_FRONTEND_DIR is not among them. Read only the help text and you would conclude in-process serving does not exist. It does; the flag registration a few dozen lines further down reads that exact variable. internal/cli/serve/serve.go:104-128 vs :162

Day to day you use neither path: make dev runs scripts/dev.sh, bringing up Vite on :3000 proxying /api to the Go server. The Makefile says it flatly — "Post-Phase-5 there is no Loom-served UI; use make dev (Vite on :3000)." Makefile:719-732

The directory contract

Ten layers and an explicit list of permitted edges — not a strict stack. eslint-plugin-boundaries is configured with default: "disallow" and no allowlist, so any edge not explicitly listed is a lint error. eslint.config.js:182-186

Above those in the table sit contexts, then views (one page component per route), then app — App.tsx, main.tsx, router.tsx — which may import from everything. Row order is rough altitude, not a rule the linter enforces: components may import contexts from above it, and contexts and hooks may import each other. Read the allow blocks, never the row order. eslint.config.js:235-283 In terms you already have:

The escape hatch, and why it is safe

Type-only imports are legal across every edge, because TypeScript erases them and no runtime coupling appears. That is why @typescript-eslint/consistent-type-imports is an error, not a warning: the hatch is only trustworthy if you cannot smuggle a value import through it. eslint.config.js:143-150, 344-355

The trace: one wire frame to one repainted card

An agent elsewhere changes an issue's status; an operator has the Kanban board open. Every hop:

  1. src/router.tsx:201-210 → src/components/WorkspaceLayout/WorkspaceLayout.tsx:92-93 The URL is the state machine. /ws/:workspaceId renders WorkspaceLayout → App → the pages; there is no "current view" variable. The layout mounts <WorkspaceProvider><StoreProvider>, scoping everything below to one workspace.
  2. src/hooks/common/useStoreContext.tsx:225-234, 243-253 Stores are built once, then wired. useState(() => createIssueStore({…})) — the lazy initialiser runs on first render only, so the store's identity survives every later one. The provider nests StoreContext.Provider → EventProvider → StoreWiring → children.
  3. src/api/common/sse.ts:143 → :15-33 A JWT is exchanged for an opaque SSE token via GET /api/workspaces/{ws}/events/token, because EventSource cannot send an Authorization header and a JWT in a query string would land in access logs. A 404 is not an error: it means { kind: "disabled" }, the normal local-dev path.
  4. src/api/common/sse.ts:182-190 One EventSource opens on /api/workspaces/{ws}/events?since=…&token=…, with listeners for two named events: mutation and connected. Exactly one mutation stream per workspace, for the whole app — not the app's only EventSource, though: useWorkflowRunStreams opens one per active workflow run, capped at eight. src/hooks/workflows/useWorkflowRunStreams.ts:42, 207
  5. src/api/common/sse.ts:372-388 A frame arrives. handleMutation JSON.parses it, records event.lastEventId as the reconnect cursor, and calls onMutation. Malformed JSON is warned about and dropped, never thrown.
  6. src/hooks/common/useEventProvider.tsx:184-212 Fan-out, with no React state touched. The provider walks a ref-held subscriber map and calls matching callbacks directly — nothing re-renders here, which is why the app absorbs a fast stream.
  7. src/hooks/common/useStoreContext.tsx:125 → src/stores/issueStore.ts:426-441 issueStore is one of those subscribers. StoreWiring's effect calls issueStore.getState().connectToEvents(subscribe), registering a callback that funnels every mutation into applyMutation.
  8. src/stores/issueStore.ts:443-470 → :127-161 → src/stores/issueStoreHelpers.ts:340 Three gates, then a pure reducer. Optimistic (a local write is in flight → buffer it), workspace (wrong workspace → drop), source-repo (filtered out → drop). Then the reducer — processMutation, which issueStore.ts:41 imports under the alias applyMutationPure — takes the current map and returns a new one plus flags; the wrapper does the set(). The reducer is testable with no store and no renderer.
  9. src/App.tsx:247-248 React finds out. useStore(issueStore, (s) => s.issuesMap) is a subscription with a selector: App re-renders only when that one field's identity changes. It did, because the reducer returned a fresh Map.
  10. src/App.tsx:1464-1471 → src/views/KanbanPage.tsx:16-35 → src/components/IssueCard/IssueCard.tsx:150 Shell publishes, page consumes, one card repaints. App owns and filters the data and hands it down via <WorkspaceViewProvider data actions>; KanbanPage calls useWorkspaceViewData() and renders — pages almost never fetch. IssueCard is memo(...), so only the card whose Issue identity changed re-renders.

One bad subscriber cannot poison the others, and the stream is a broadcast bus, not a state container — in Go terms, one goroutine reading a channel and calling registered handlers, not a channel per consumer.

Zustand, in one paragraph

A store is built by a factory that returns a plain object. The interesting part is what is deliberately not in the state:

Anything React must repaint for goes in the store state (issuesMap, isLoading, error, pendingIds). Bookkeeping — abort controllers, timers, optimistic snapshots, the active workspace id — lives in the closure, where changing it triggers nothing. That split is the most-copied pattern in src/stores. And because it is a factory, not a package-level global, the store is unit-testable with no renderer and every provider gets its own instance. The running app does not exercise that on a workspace switch: WorkspaceLayout never unmounts across /ws/A → /ws/B, so the lazy initialiser does not re-run and the one instance is retargeted by reassigning activeWorkspaceId — which is exactly why applyMutation needs a workspace gate. src/hooks/common/useStoreContext.tsx:224, src/stores/issueStore.ts:204, 451-458 Read it as a Go constructor returning a struct.

The four rules a reviewer will hold you to

1. Only src/api touches the network

Enforced by an AST linter, not by convention:

It parses each file with the TypeScript compiler and flags any call resolving to fetch, window.fetch or globalThis.fetch, unwrapping parentheses and as casts on the way — so (fetch as any)(…) does not hide. Its sibling check-no-hardcoded-urls.mjs bans literal /api/ strings outside the same directory. The check is narrower than the rule, though: only fetch is banned, so two long-lived sockets live outside src/api — a new WebSocket in the terminal component and a per-run new EventSource in a workflow hook. Grepping for fetch does not find every socket in this app. src/components/TerminalView/instances/terminalConnection.ts:180, src/hooks/workflows/useWorkflowRunStreams.ts:207 Inside src/api, copy this shape:

api is createClient<paths>({ baseUrl: API_BASE_URL }) src/api/common/client.ts:272, where paths is the generated OpenAPI type — so the URL string, the path params and the response body are all checked at compile time.

2. Cross-component imports go through the barrel

A component directory is a module with exactly one public surface. A second AST linter decides what counts:

So @/components/KanbanBoard and @/components/KanbanBoard/index are legal; @/components/KanbanBoard/columnConfigs is not, and the message names the path to use instead. Five grandfathered pairs sit in that script's ALLOWLIST scripts/check-component-boundaries.mjs:14-35 — do not add a sixth. Most components are re-exported from src/components/index.ts, which is why most files import { ErrorBoundary, SwimLaneBoard } from plain @/components. The barrel is not exhaustive: 28 of the 95 directories under src/components are absent, four of them by an explicit comment so a lazy-loaded chunk stays split. Import those by directory, the way KanbanPage imports @/components/IssueViewGuard. src/components/index.ts:42-46, src/views/KanbanPage.tsx:4

4. Never call localStorage directly

Browser storage should be workspace-scoped: use wsGet / wsSet / wsRemove, which build a loom:{wsId}:{key} key and swallow quota and private-browsing errors instead of throwing mid-render. src/utils/scopedStorage.ts:7-37 It is one more rung on the ladder from Lesson 05 — per-browser, per-workspace, and always safe to delete.

This is the one rule of the four with no machine behind it: nothing in eslint.config.js or scripts/ so much as mentions localStorage. It shows — theme, split ratio, terminal font and recent assignees all still read and write unscoped global keys. src/hooks/ui/useTheme.ts:25, src/hooks/ui/useSplitRatio.ts:20, src/hooks/terminal/useTerminalFont.ts:47, src/hooks/issues/useRecentAssignees.ts:29 Only a reviewer catches this one, and those callers are debt, not precedent.

Trap — the indirection is not accidental

You will find src/hooks/api.ts, whose body is export * from "@/api" plus a few named re-exports, and assume someone was being clever. Its header explains: components may not import @/api at all, so they reach it through the hooks layer; 38 component→api call sites had to move, and a useCreateIssue-style wrapper per api function would have been ceremony with no runtime benefit. Before you "simplify" an odd re-export here, check whether it is a DAG edge in disguise. src/hooks/api.ts:4-8, 20

Trap — vitest runs in node, not a browser

The natural assumption is that a React test suite hands you a DOM. It does not: vite.config.ts:221 sets environment: "node". A test touching document must opt in with a docblock at the top of the file —

/**
 * @vitest-environment jsdom
 */

— which 338 of the 401 test files under src carry, plus src/test-utils/a11y-helpers.ts, which needs it for the same reason. Forget it and you get an opaque document is not defined pointing nowhere near the cause. A quieter sibling: npm run typecheck does not check tests. tsconfig.json's exclude lists **/*.test.ts, **/*.test.tsx, **/*.spec.ts, **/*.spec.tsx, tests and playwright.config.ts, so "typecheck passed" is a claim about production code only. tsconfig.json:33

Check yourself

From memory: you must add a button to an existing component that calls a new backend endpoint and shows the result. Name every directory you will touch, in dependency order, and say why the component itself cannot hold the fetch.

api/openapi.yaml → regenerate both sides (make gen-go-api, npm run generate:types) → src/api/<domain>/ for the facade using api.GET → src/hooks/ for the hook (or src/hooks/api.ts's re-export) → src/components/<Name>/ for the button, exported through that directory's index.ts.

Two independent, separately enforced reasons: eslint-plugin-boundaries forbids the components → api runtime edge (eslint.config.js:247-264), and check-no-raw-fetch.mjs flags the call itself anywhere outside src/api/, with an empty allowlist.

You run loom serve with no flags, in a shell where LOOM_FRONTEND_DIR is unset, and open http://localhost:8080/ in a browser. What do you get?

  • The SPA, served from the copy embedded in the Go binary at build time
  • The SPA, but only after the server has built the dist directory once
  • Nothing — no route is registered for / unless a directory is named
  • A redirect to the Vite dev server, which the API proxies through to
registerFrontendRoutes returns early when FrontendDir is empty, so / is never registered and the process logs api-only mode — frontend served externally. The first option is the one worth killing: there is no //go:embed of the bundle anywhere under internal/webui on this branch, so "it's embedded" is simply false here. internal/webui/app/frontend.go:11-16

A component needs the current issue list. Where does it get it?

  • By importing the store from @/stores and calling getState()
  • From props or context, passed down by a hook or shell
  • By calling getKanbanIssues from the @/api/issues barrel
  • From a module singleton exported by src/stores/index.ts
Components may import components, contexts, hooks, utils, styles and types — no api, no stores. The shell computes and publishes through WorkspaceViewContext; a hook may reach a store on a component's behalf. The fourth option is the sharpest miss, because such singletons genuinely exist (editorStore, backendsStore, skillsStore) — but a component importing one still crosses a forbidden edge. eslint.config.js:247-264

How many EventSource connections carry a workspace's mutation stream?

  • One, owned by the provider and shared by all subscribers
  • One per store that has registered a mutation subscriber
  • One per mounted page component that renders live data
  • One per source repo currently selected in the filter
EventProvider constructs a single WorkspaceSSEClient per workspaceId and fans mutations out to a subscriber map by direct callback. Subscribers are map entries, not connections — which is why adding a live view costs nothing at the transport layer. The workspace can hold other streams — useWorkflowRunStreams opens up to eight, one per active workflow run — but none of them carries mutations. src/hooks/common/useEventProvider.tsx:184-212

Break each rule on purpose, then read the failure

Safety first: work on a scratch branch and revert between steps. If a step tempts you to start a dev server, check lsof -nP -iTCP:3000 -sTCP:LISTEN first — Vite uses strictPort: true on 3000 (vite.config.ts:178-180) and that port is shared host state.

  1. From the repo root: cd internal/webui/frontend && npm install, then npm run check:arch once, clean, so you know what passing looks like.
  2. Add const r = await fetch("/api/health"); inside any component under src/components/ and re-run npm run check:arch. Note which of its four sub-checks fired and what the message tells you to use instead. Revert.
  3. Add import { DEFAULT_COLUMNS } from "@/components/KanbanBoard/columnConfigs"; to a component in a different directory and re-run. Then change it to @/components/KanbanBoard and re-run. Revert.
  4. Add import { getKanbanIssues } from "@/api/issues"; — a value import — to a component and run npm run lint. Change it to import type { GraphFilter } from "@/api/issues"; and run again. Say in one sentence why the second is allowed. Revert.
  5. Delete the @vitest-environment jsdom docblock from the top of src/contexts/__tests__/WorkspaceViewContext.test.tsx, run npx vitest run on that one file, write down the exact error, and restore it.
  6. Reaching back to Lesson 12: run loom serve --help and confirm LOOM_FRONTEND_DIR is absent from its environment-variable list. Then find the line in internal/cli/serve/serve.go that reads it anyway.
You succeeded when For each of steps 2-4 you can name the script or ESLint rule that caught it and quote its message; npm run check:arch and npm run lint both pass again on your branch; and you can say which of the two startup log lines (api-only mode — frontend served externally / serving bundled frontend) your loom serve emits, and why that turns on LOOM_FRONTEND_DIR rather than on the command line.
