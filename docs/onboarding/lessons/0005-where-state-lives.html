Week 1 / Lesson 05 / Object model

Where state lives

By the end of this lesson you can name every core object in Loom, say which of three storage tiers holds it, and know which of those tiers you are allowed to delete.

Skill place any piece of state in the right tier Time 35 min Needs 01, 02 Repos loomcli

Start by unlearning something

Every tool like this has a config file. This one does not.

Workspaces, repos, roles, agent definitions, daemon profiles — all of it lives in fleet-db. There is no loom YAML to edit. This matters on day one because the code will actively mislead you: the config structs still carry YAML tags.

Those tags are a fossil. Nothing parses a loom YAML file. Where the config actually comes from:

Trap

You will at some point go looking for the YAML file those tags imply, or worse, add a field with a yaml: tag and expect it to be loadable. The tags survive from a pre-fleet-db era. The only YAML decoding in non-test code under internal/ and cmd/ is SKILL.md frontmatter (internal/cli/skill/github_install.go:941, 945); repo-wide you also hit scripts/openapi-to-30/main.go:36, a build script that rewrites the OpenAPI spec. Nothing anywhere decodes loom's own configuration from YAML. Check for yourself: grep -rn "yaml\.Unmarshal" --include="*.go" internal cmd.

Three tiers, one truth

TierHoldsIf you delete it
fleet-db Shared truth: everything in internal/domain, plus issues. You have lost real data. This is the authoritative tier.
Node-local "Where is it on this machine": ~/.loom/state.json (internal/bootstrap/statecache.go:19-32), stacks.json (internal/stackstore/stackstore.go:86), desktop local-settings.json (internal/localsettings/settings.go:24). Regenerates. A missing state.json is recoverable and never load-bearing (internal/bootstrap/statecache.go:30-32).
Worktree-local Materialized artifacts: the skill projection under .agents/skills, which Loom owns outright (internal/skillmat/materialize.go:35, 38-39), and the Loom-managed hook entries inside .claude/settings.json / .codex/hooks.json, which Loom merges into rather than owns (internal/hookcfg/hookcfg.go:38-46). The projection regenerates on the next run. The hook files do not: Loom rewrites only commands beginning "loom " and preserves everything else (internal/hookcfg/hookcfg.go:75-76, 266-297).
The one idea

Only fleet-db is authoritative. The other two tiers are caches you are allowed to throw away. When you are debugging weird state, that is the order to suspect things in. Clear them only in a checkout of your own, and per-entry rather than per-file: .claude/settings.json is tracked by git here (git ls-files .claude/settings.json) and holds entries Loom neither wrote nor restores.

This is also why ~/.loom/state.json is a cache and not config: runtime commands deliberately do not treat it as an implicit default, so they cannot silently cross workspace boundaries (internal/cli/cmdstore/cmdstore.go:82-85). Set LOOM_WORKSPACE or pass --workspace.

The object graph

Issues live on a different axis

Notice what is not in that tree: issues. They are not domain types at all. They come from fleet-db's issue tracker and carry their own vocabulary.

And the single most useful fact about them:

Epics are not a separate object

An epic is just an issue whose IssueType is "epic". A task is just the ordinary work item. Nothing stores an epic as its own record: grep -rn "type Epic" internal returns nine hits, but every one is a projection or a call argument derived from ordinary issues (internal/types/types.go:157, internal/driver/epic_snapshot.go:41, internal/cli/epic/epic_stack.go:131). The parent-child dependency edge is what makes an epic contain tasks — one of the five dependency types fleet-db will store (internal/backend/fleet/fleet_mutations.go:28-34). And per that comment: agents never work on epics directly.

The other thing linking the two axes is labels. A role's Skills[] routing tags are matched against an issue's labels to score which tasks that role pulls (internal/domain/skill.go:282-284, internal/cli/task_router.go:106-113) — which is the mechanism behind the skill vs role skills distinction from Lesson 02. One is a document loaded into a worktree; the other is a string compared against a label.

"Agent" means three different things

You met one overloaded word in Lesson 02. Here is the one that will bite you in code review:

TypeIsDefined
domain.AgentA long-lived assignment of a Role to repos. Also called an "agentdef".domain/agent.go:493-499
domain.AgentSessionOne run of that assignment.domain/control_plane.go:81-102
entity.AgentA legacy issue-shaped record with roles named polecat/witness/mayor. Not used by anything live.internal/entity/agent.go:42-66 (role constants at 12-19)

Say which one you mean, every time. And if you find yourself in internal/entity wondering why nothing calls it — that is expected. Its doc comment claims to be the single source of truth for all downstream packages (internal/entity/doc.go:7-9), but grep -rl 'internal/entity"' --include='*.go' . | grep -v '^./internal/entity/' returns 12 files against 51 for internal/types — tests included; drop those and it is 7 against 23. And the converters that build entity values are not in entity at all: nine of them have no non-test caller, three in internal/backend/fleet/entity_convert.go:112, 125, 308 and six in internal/backend/mapping/. Do not "wire up entity" as a side quest.

Check yourself

From memory: name the three storage tiers, one example of what each holds, and which ones you may safely delete.

fleet-db — shared truth: workspaces, repos, roles, agents, skills, daemon profiles, issues. Never safe to delete; it is the only authoritative tier.

Node-local — where things are on this machine: ~/.loom/state.json, stacks.json, desktop local-settings.json. Safe; regenerates.

Worktree-local — materialized artifacts: .agents/skills, which Loom owns and regenerates, plus the "loom "-prefixed hook entries inside .claude/settings.json / .codex/hooks.json. Those entries are all Loom rewrites; the rest of both files is not its to restore.

You want to change the fields on a role. Which file do you edit to change what is stored?

  • A workspace YAML file that the daemon config loader parses
  • The RoleConfig struct tags in internal/cli/config
  • The role record cached under the node-local ~/.loom directory
  • The domain type, since roles are stored in fleet-db not on disk
Roles live in fleet-db. The YAML tags on RoleConfig are a fossil from a pre-fleet-db era and no loom YAML is parsed anywhere — which makes option two the trap this lesson exists to defuse. internal/cli/config/project.go:236-246

How does Loom represent an epic?

  • A dedicated Epic domain type stored alongside Role and Agent
  • An ordinary issue whose IssueType field equals "epic"
  • An issue carrying the reserved label "epic" among its label set
  • A workspace-scoped grouping object that owns a list of task IDs
There is no Epic type, table, or service — just IssueType == "epic", with parent-child dependency edges doing the containing. The label option is the sharp near-miss: labels are real and load-bearing here, but for routing, not for epic-ness. internal/cli/taskfilter.go:14-17

A colleague's PR description says "the agent finished at 14:03". Which type are they almost certainly talking about?

  • domain.Agent, the assignment of a role to repos
  • entity.Agent, the canonical issue-shaped agent record
  • domain.AgentSession, a single run of an assignment
  • All three are the same object viewed at different layers
Only a run finishes at a time. The assignment is long-lived, and entity.Agent is legacy with no live users. This is exactly the ambiguity to flag in review rather than assume away.

Draw it, then find where it is wrong

  1. Close this lesson. On paper, draw the object graph from memory: Workspace at the root, and as many of its children as you can place. Then reopen and compare — the gaps are your study list.
  2. Open internal/domain/repo.go and read the first 25 lines. The field comments explain that local checkout paths deliberately do not live there. Given the three tiers, say which tier does hold them and why that separation exists.
  3. Verify the epic claim yourself: grep for other definitions of epic-ness across internal/. Is IsEpic the only rule, or are there competing ones?
  4. Reaching back to Lesson 04: find out whether the gate actually enforces this. Open .golangci.yml, read the files: globs of the sdk-leaf rule (.golangci.yml:83-92), and answer two things — is internal/domain in that list, and what would the rule stop you doing in the packages that are?
You succeeded when You can state, without looking, which tier holds a repo's local checkout path and why it is not in fleet-db — and you can say why nothing in the gate would stop you giving internal/domain an HTTP client. It is not in sdk-leaf's globs, nor in any other depguard rule; its leafness is a convention held up by code review, not a machine-checked one. That gap is worth remembering: Lesson 04 taught that the gate is the spec, and this is the boundary of that claim.
