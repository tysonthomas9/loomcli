Read this before any step that starts a process

This machine is shared. Compose projects, ports and container state belong to whoever created them. Before any up: run podman ps, treat every stack you see as someone else's, and pick an unclaimed port block. Launch with your own project name and ports. Tear down only the project you started.

  • make local-mode-up defaults to project loomcli-local-mode on ports 8280 / 8282 / 8283 (Makefile:8, test/local-mode/docker-compose.yml:60,96,116). An up --build on a project name that already exists recreates that project's containers. Override all four: LOCAL_MODE_COMPOSE_PROJECT, LOCAL_MODE_FLEETDB_PORT, LOCAL_MODE_API_PORT, LOCAL_MODE_UI_PORT (.agent-skills/loom-pr-test/SKILL.md:98-106).
  • make fleetdb-regression-up has no override at all: the project name is hard-coded loomcli-fleetdb-regression and the ports are 8080 / 8082 / 8083 (test/fleetdb/docker-compose.regression.yml:34,90,164,196). It cannot be run in parallel, and make fleetdb-regression-down runs down -v --remove-orphans, destroying the volumes (Makefile:252). Ask before you start it.
  • make dev binds fixed ports :8080 and :3000 (Makefile:718-720). Check lsof -nP -iTCP:3000 -sTCP:LISTEN first; a listener you did not start belongs to another checkout.
  • The two pinned course trees are read-only. Do not run make hooks, make dev, or any up in them — they write to node_modules, to the machine, and to .git/hooks, which is per-clone and so reaches every other worktree of that clone (step 0.4). Build binaries into a scratch directory, never in place: the outputs are gitignored, so git status will not warn you. Do your task in your own working clone.

0. Once, before your first task

  1. Put the two repos side by side. Not a preference. Makefile:559-560 looks for ../fleet-db or ../../fleet-db and exports FLEET_DB_BIN when it finds a built binary there (Makefile:562-565); the compose stacks hard-code the build context ../../../fleet-db (test/local-mode/docker-compose.yml:40). Clone them anywhere else and you will chase this for an hour.
  2. Read the two orientation documents for the repo you are in. loomcli AGENTS.md then docs/loom-glossary.md — AGENTS.md opens by telling you to (AGENTS.md:5-10).
    fleet-db AGENTS.md, then docs/agents/index.md, docs/agents/domain-primer.md, docs/agents/codebase-map.md (AGENTS.md:17-26). Canonical architecture is docs/architecture.md; root ARCHITECTURE.md is marked "Retired pointer (do not use)" (AGENTS.md:34-36).
  3. Confirm the base branch with a human, then branch. Run it yourself — this is read-only and it is the fastest way to see why the question matters: 
    git rev-list --left-right --count origin/main...origin/v5
# loomcli at ce4df56fb prints:  1   1786
    Prefixes actually in use on origin (632 branches): feat/ 144, loom/ 133, fix/ 111, codex/ 13, test/ 11, docs/ 10, bot/ 8, refactor/ 6, epic/ 5, chore/ 5, ci/ 3. Pick feat/, fix/, chore/, docs/ or ci/. Leave loom/ and bot/ alone: the whole loom/ namespace is machine naming, not yours — loom/PUPPET-N 93, loom/stack/epic-… 20, loom/profiles-v2/… 9, loom/stack/task-… 6, loom/task/… 3, plus two one-offs. Never hand-write one. In fleet-db (162 branches): feat/ 59, loom/ 27, fix/ 26, docs/ 5, plus epic/fleet-db-<id> and integration/.
  4. Read the pre-push gate. Do not install it from a pinned tree. Git hooks are per-clone, not per-worktree. Both make hooks targets write to $(git rev-parse --git-common-dir)/hooks — the parent clone's directory, not yours. loomcli's Makefile says so out loud, "applies to all worktrees" (Makefile:682,688). The two pinned trees hang off clones carrying 83 and 48 live worktrees owned by other people, and neither hooks directory has a hook installed today, so installing one changes git push for all of them. Inspect instead — this is read-only: 
    cat scripts/hooks/pre-push
ls "$(git rev-parse --git-common-dir)/hooks" | grep -v sample   # empty = none installed
git worktree list | wc -l                                       # who else you would change
    loomcli 11 lines, runs make check unconditionally (scripts/hooks/pre-push:10-11); make hooks additionally needs pre-commit and golangci-lint on PATH and errors if either is missing (Makefile:683-692, checks at :689-690).
    fleet-db 17 lines, runs make gate, honours SKIP_GATE (scripts/hooks/pre-push:6-16). Its make hooks installs the hook and still exits non-zero: the loop copies pre-commit pre-push post-checkout post-merge (Makefile:249-252) but scripts/hooks/ holds only pre-push and test_hooks.sh, so three cps print No such file or directory, the last one sets the status, and make reports Error 1 — after pre-push is already installed. No hand copy is needed. Installing is a decision for a clone you own outright, not a step on this card.
  5. Build both binaries — into a scratch directory outside both repos. Almost everything downstream — the embedded fleet-db, the conformance suite, loom doctor — needs a real fleet-db executable it can find. Do not build in place: ./loom and ./fleet-db are both gitignored (loomcli/.gitignore:3, fleet-db/.gitignore:6), so a build into a pinned tree writes to a read-only checkout and git status never shows it. 
    mkdir -p /tmp/loom-scratch
go build -o /tmp/loom-scratch/loom ./cmd/loom
(cd ../fleet-db && go build -o /tmp/loom-scratch/fleet-db ./cmd/fleet-db)
export FLEET_DB_BIN=/tmp/loom-scratch/fleet-db
  6. Ask loom doctor whether it can see fleet-db. In local mode it prints the exact paths it checked and a remediation string (internal/cli/doctor/doctor_fleetdb.go:132-147). The search order is FLEET_DB_BIN → PATH → sibling of the loom binary → <LoomDir>/bin/fleet-db, documented at internal/bootstrap/embedded.go:526-532 and implemented at :542-580.

Telling each CLI which workspace you mean

  • loomcli --workspace is a root persistent flag, mirrored into LOOM_WORKSPACE in PersistentPreRunE (internal/cli/root.go:108,112-128). The data subtree deliberately does not redeclare it: a duplicate flag would shadow the root one and leave LOOM_WORKSPACE unset, which the fleet backend needs at construction time (internal/cli/data/root.go:10-14). So loom --workspace X data ready and LOOM_WORKSPACE=X loom data ready both work. That rule is about data, not the whole CLI — eight other subcommands do declare their own --workspace, including git pull/sync/pr/push as -W (grep -rn 'StringVarP\?(&[A-Za-z]*, "workspace"' --include='*.go' internal/cli | grep -v _test.go lists all nine).
  • fleet-db fdb is stdlib flag, so flags come before the command: fdb [flags] <command> [args] (cmd/fdb/main.go:164-186, usage at :345). fdb ready -json will not parse that flag. Env fallbacks are FLEET_SERVER, FLEET_SOCKET, FLEET_WORKSPACE, FLEET_ACTOR, FLEET_API_KEY, FLEET_TRANSPORT (:290-299), plus FLEET_TIMEOUT (:301-310), and an unset actor silently becomes $USER (:285-287).
Trap — ~/.loom/state.json is not config

It is a per-user cache. Its last_workspace is documented as "a UI hint only; runtime commands require LOOM_WORKSPACE or --workspace" (internal/bootstrap/statecache.go:19-32). If a command picks the wrong workspace, you did not set one — you did not inherit one.

Trap — two loom data flags do nothing

loom data claim <id> --actor someone-else claims as you. The flag is "captured for command-line parity" and never read by RunE (internal/cli/data/claim.go:9-12,18-28,32) — the effective actor is the backend's configured X-Actor.

loom data close --session and --force are built into CloseParams (internal/cli/data/close.go:27-31) and then dropped: the fleet backend marshals a body with Reason only (internal/backend/fleet/fleet.go:834-840). Closing twice is fine on purpose — an already-closed conflict is swallowed (internal/cli/data/close.go:32-40).

2. Work it

  1. Find the code before you write any. Use the decision tree on Finding Anything — CLI command, HTTP route, UI screen, domain type, persistence, each has one answer. Do not grep for the package name of a route; grep for its path string.
  2. Copy the pattern that is already there. The exemplar list is on Finding Anything under "Patterns you are expected to copy". A change that invents its own shape fails review before it fails the gate.
  3. loomcli Touched api/openapi.yaml? Regenerate. make gen-go-api (Makefile:426-432). Step 11 of 13 in make check-go regenerates the file into a temp dir and diffs it (Makefile:609-610), so a hand-edit fails the gate rather than shipping. This is loom's own API, not the fleet-db contract.
  4. fleet-db Adding a route? Three files move together. Register it on the mux with the literal form mux.HandleFunc("METHOD /path", …) — the coverage checker matches that regex over internal/api and cmd/fleet-db (scripts/harness/cmd/check_openapi_coverage/main.go:12-14,30-35). Add the path and the method to api/openapi.yaml. Keep any request struct's fields in exact sync with its schema: a reflection test pins them together, and its comment is the best paragraph in either repo on why (internal/api/openapi_request_parity_test.go:14-29).
  5. fleet-db Respect the declared layering and the key rule. internal/api may import only service, models, logging, config, resolution; internal/models may import nothing (harness/policy.yaml:3-56). Any new Redis key literal goes in internal/storage/keys.go and nowhere else (harness/policy.yaml:58-77). Both are linted by make harness-lint and make lint-keys.
  6. Do not set a status the API refuses to set. Nine built-in statuses exist (internal/models/status.go:11-27), but a plain update may write only open, blocked, deferred, review. closed needs the close endpoint, in_progress needs claim, and tombstone/pinned/hooked are server-managed (:77-94).
If your change touches the wire between the repos

There is no generated client and no shared code — loomcli hand-maintains its mirror of fleet-db's JSON in internal/backend/fleet/convert.go:12-15, and fleet-db rejects an entire request body over one unknown key (DisallowUnknownFields, fleet-db/internal/api/request.go:130-132). That asymmetry sets the deploy order: server first, then client. Adding a field to a request body before fleet-db knows it takes down every write that shares that body. Cross-repo compatibility commits are prefixed parity(scope): — 51 of those, plus six older bare parity:, so 57 in loomcli (git rev-list --count --grep='^parity' HEAD). Use the prefix; it is how these get found later. Full detail in Lesson 28.

The cross-repo contract test

This suite is not read-only on a shared machine

./internal/cli's TestMain calls killTestTmuxSessions before and after the run, and that function kills every tmux session on the host whose name starts with loom-test- or loom-e2e-test- (internal/cli/testmain_test.go:21, 28, 34-46), including another engineer's in-flight run. -run does not save you: TestMain executes in full regardless of which tests the filter selects. Sub-packages such as ./internal/cli/data are different packages and have no such TestMain. Same hazard as Lesson 26.

From the loomcli root, with both binaries built into the scratch directory from step 0.5:

FLEET_DB_BIN=/tmp/loom-scratch/fleet-db LOOM_BIN=/tmp/loom-scratch/loom \
  go test -tags issuebackend_e2e ./internal/cli \
  -run TestE2E_IssueBackendConformance_AllModes -v

Four subtests — fleetdb-local, fleetdb-cloud, fleet-direct, api-server — run the shared conformance suite against a real fleet-db process (internal/cli/issue_backend_conformance_e2e_test.go:30,34,57,76,100).

Trap — this test passes when it runs nothing

If either binary is missing it calls t.Skip, not t.Fatal (internal/cli/issue_backend_conformance_e2e_test.go:127-149). A green exit code is not evidence. Look for the four named subtests in the -v output before you write "verified" in a PR body.

Three things that make a local gate lie

  • Inherited desktop and runtime env. Variables like LOOM_WORKSPACE, LOOM_CONFIG_DIR, LOOM_FRONTEND_DIR and LOOM_NOTIFY_TOKEN make tests resolve your real desktop workspace instead of their fixtures. Re-run any suspect failure with a cleared env and a temp HOME — AGENTS.md gives the exact env -u … line (AGENTS.md:44-61).
  • A fresh worktree. check-frontend depends on ensure-frontend-deps, which runs npm install whenever node_modules/.package-lock.json is missing or stale (Makefile:194-201,628). A new worktree does not inherit ignored files, so your first gate there is slow. That is expected, not broken.
  • A stale installed hook. make dev runs ensure-hooks, which cmps the installed pre-push against scripts/hooks/pre-push and reinstalls on any difference (Makefile:709-710,719). The long comment above it (:694-708) explains the failure it exists to prevent: an old hook that leaks GIT_DIR into make check and makes ten packages fail forever.
In fleet-db the pre-push hook runs the full make gate, and that includes test-e2e against real containers (scripts/hooks/pre-push:12-16, Makefile:177). On a machine with no container runtime every push fails. SKIP_GATE=1 git push is the documented escape hatch (scripts/hooks/pre-push:6-10) — use it only when you know CI will cover you, because harness.yml re-runs make gate on the PR (.github/workflows/harness.yml:27-28).
Runtime evidence, safely

If the claim needs a real stack, follow .agent-skills/loom-pr-test/SKILL.md. Its non-negotiables (:17-24): use real make/loom workflows, never hand-create .agent.lock, FleetDB keys, sessions, transcripts or diffs as evidence, keep the real ~/.loom safe with a throwaway LOOM_CONFIG_DIR, and report blocked rather than fabricate. Your own project name and your own port block, every time (:98-106); tear down only that project (:256-260). Then report what you ran, the ports, and whether the backend was deterministic or a real CLI — and do not overclaim (:232-244).

4. Commit and open the PR

  1. Prefix the commit if it is a cross-repo compatibility fix. parity(scope): what changed. 57 such commits in loomcli. Put the symptom, the mechanism, the fix and the tests in the body.
  2. Write the PR body to fleet-db's contract — in both repos. Neither repo ships a pull-request template, and only fleet-db writes the rule down (docs/agents/contracts/pr-contract.md:3-11). Treat it as house style for both: 1. Summary of behaviour change. 2. Exact commands run for validation. 3. Test results and affected coverage areas. 4. Files changed and rationale. 5. Risk assessment. 6. Rollback strategy. 7. Any agent autofixes performed. Mandatory alongside it: harness gates pass, no unresolved legibility violations, review feedback addressed before merge (:13-16).
  3. State the evidence class, do not imply a stronger one. deterministic = orchestration only, real = real local backend, live = reaches a real external paid service (AGENTS.md:29-35). If a real path was blocked, say blocked — never fabricate state (.agent-skills/loom-pr-test/SKILL.md:22,244).
  4. Target the branch a human confirmed. Not the one gh defaults to. origin/main in loomcli is 1786 commits behind origin/v5.

5. Land the plane

Seven steps, mandatory, and byte-identical in both repos (loomcli/AGENTS.md:172-195 == fleet-db/AGENTS.md:55-78). Work is not complete until git push succeeds.

  1. File issues for remaining work. Anything that needs follow-up gets an issue now, not a TODO in your head. A cross-repo TODO in code cites the other repo's issue ID — e.g. // TODO(fleet-q6ox): … (internal/backend/fleet/fleet.go:850-851).
  2. Run quality gates, if code changed. Tests, linters, builds — section 3 above.
  3. Update issue status. loom data close <id> --reason "…" or fdb close <id>; update anything still in progress.
  4. Push to remote. This is the step people skip. 
    git pull --rebase
git push
git status   # MUST show "up to date with origin"
  5. Clean up. Clear stashes, prune remote branches.
  6. Verify. Everything committed and pushed.
  7. Hand off. Context for the next session.
The four rules under the checklist, verbatim

Work is NOT complete until git push succeeds · NEVER stop before pushing — that leaves work stranded locally · NEVER say "ready to push when you are" — YOU must push · If push fails, resolve and retry until it succeeds. (loomcli/AGENTS.md:191-195, fleet-db/AGENTS.md:74-78.)
