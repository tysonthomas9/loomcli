The Loom Glossary

This codebase uses ordinary English words as precise domain terms. Getting one of them wrong does not produce an error — it produces a confident sentence that means something else. This is the dictionary.

Use when reading any doc, PR, or issue in either repo Source docs/loom-glossary.md, CONTEXT.md, AGENTS.md Repos loomcli fleet-db

1. Trap words

Each of these has a general-English meaning, a general-software meaning, and a Loom meaning — and the three disagree. Confirm the Loom meaning before acting on any of them.

loom

The AI-agent orchestration platform this repo builds. Not the video product, not Java Project Loom, not a weaving metaphor anyone needs explained.

docs/loom-glossary.md:3-5
skill

A workspace-stored document entity — a SKILL.md body plus optional text files — loaded into an agent's worktree so the agent can use it while working.

Not the role config's skills: list. That field is a task-routing filter: its tag strings are matched against issue labels to score which tasks a role pulls. Same word, no shared mechanism. Say skill for the document and role skills (or routing tags) for the filter.

docs/loom-glossary.md:21-27
blocked

Deliberately two things, told apart by where you are looking. (a) A task's own status — the literal blocked status: a worker parked the task and declared a blocker, so a human must act. (b) A dependency relationship — an issue that cannot start because issues it depends on are still open.

Disambiguator is grammatical: the dependency sense always names what is blocking ("Blocked by 3 issues"); the status sense stands alone. Nothing translates between them. Do not invent a third word — "Stuck" was tried for the status sense and deliberately reverted.

docs/loom-glossary.md:124-138
stuck

A third thing that borrows the word without being either sense of blocked. task.stuck is a daemon event for a task that failed repeatedly across consecutive auto-mode invocations and was skipped so the loop could progress elsewhere. The loop gave up; the agent declared nothing. It is not an issue status and does not set one. AgentState "stuck" in the web UI is this sense.

docs/loom-glossary.md:145-149 (internal/events, TaskStuckData)
stage

A derived view, not a stored object. Nothing stores a stage: it is folded out of an issue's event history, where a stage is a contiguous run of that history with the same status and the same owner. Because the window is bounded, a Journey shows the stages that window supports — not necessarily the issue's whole life.

It is no longer only a client-side fold. The server derives the same thing under a different name — spans[], from GET /api/workspaces/{ws}/issues/{id}/journey — so if you go looking for stage code on the Go side, search for span. The load-bearing half of the definition is unchanged: derived, never stored.

docs/loom-glossary.md:156-160; internal/webui/service/journey.go:20, 62
phase

A runtime concept with storage behind it: the log of one stretch of agent work, planning or implementation, written to tasks/<id>/<phase>.log and surfaced as its own tab.

Remember it as a phase is something an agent ran; a stage is something the issue was.

docs/loom-glossary.md:162-166
sandbox

Almost always the L1 workflow-bundle container (LOOM_DRIVER_SANDBOX=container), which contains the DriverRun bundle only. The TaskRun leaf that runs the LLM and edits your code is not containerized on any local path.

docs/loom-glossary.md:107-110
trust level

An admission decision, not a confinement. untrusted means Loom refuses to run something. It never bounds what an already-running process can reach.

docs/loom-glossary.md:111-113
agent

Three distinct Go types share this word. domain.Agent is a long-lived assignment of a Role to repos (also called an "agentdef"). domain.AgentSession is one run of that assignment. entity.Agent is a legacy issue-shaped record with roles named polecat/witness/mayor, used by nothing live.

Test only a session starts and finishes at a time. If a sentence gives the agent a timestamp, it means AgentSession.

internal/domain/agent.go:493-499; internal/domain/control_plane.go:81-102; internal/entity/agent.go:42-66
epic

Not an object. An issue whose IssueType is "epic" — there is no Epic type, table, or service. Tasks belong to it through parent-child dependency edges, and agents never work on epics directly.

internal/cli/taskfilter.go:14-17
deterministic / real / live

The three evidence classes — what a test run actually proves. deterministic = orchestration only. real = a real local backend. live = reaches a real external or paid service, costs money, may mutate external state. Naming the wrong one in a PR is a correctness claim you did not earn.

Do not confuse these with the trap words: local, live, real, verify, gate. Two of them overlap the class names and two do not. local in particular is a provisioning word — where the thing runs — and is not an evidence class, so "evidence class: local" is exactly the sentence the handshake exists to stop you writing. See Lesson 02.

AGENTS.md:22 (trap words), AGENTS.md:29-36 (handshake)
The rule behind all of these

Before running anything slow or irreversible, AGENTS.md requires you to echo the request back as coordinates — (depth, realness, provisioning, polarity, target) — disambiguate any trap word instead of guessing, and state the evidence class of what you ran. If a real or live path is blocked, report blocked/unverified. Never fabricate state as evidence.

2. Core objects

Workspace

A fleet-db-scoped project container. Workspaces own repos, roles, agent definitions, issues, daemon profiles, and local runtime state.

docs/loom-glossary.md:9-10
Role

The reusable configuration for an agent: prompt selection, backend, model, task filter, tool policy, and role kind.

docs/loom-glossary.md:11-12
Agent

A named assignment that uses a role. Worker agents are supervised by daemon/runtime loops; interactive agents are launched in terminal tabs.

docs/loom-glossary.md:13-14
Skill scope

Where a skill applies. Workspace-scoped skills load for every loom-managed agent in the workspace; role-scoped skills load only for that role's agents and shadow a same-named workspace skill. Being in scope is what makes a skill load — there is no separate attach list.

docs/loom-glossary.md:28-31
Skill pack

A registered external git source of skills (repo, ref, path) synced into the workspace on demand. Synced skills keep their pack as provenance; a pack updates its own prior imports but never silently overwrites a skill from a different creator or source.

docs/loom-glossary.md:32-35

3. Roles and agents

role.kind — interactive

A human-in-the-loop terminal/orchestration agent. Opening its terminal runs the lead runtime, usually loom lead. Not daemon-supervised; it runs when its terminal is opened.

docs/loom-glossary.md:41-44
role.kind — worker

An autonomous task-loop agent launched by loom agent, loom plan, or loom task, and supervised by the daemon/runtime.

docs/loom-glossary.md:45-46
Lead

The default interactive role and terminal agent — but not the only possible interactive agent.

Subtlety Lead/orchestrator role names additionally opt into epic ownership and assignment delivery. kind=interactive alone does not grant those. Role kind selects runtime placement, not product authorization: epic-runner ownership stays name-based via epicrunner.IsLeadRole until Loom has an explicit capability field.

docs/loom-glossary.md:15-18, 52-54
Unset kind

domain.ResolveRoleKind preserves the legacy naming convention: roles named lead or orchestrator resolve to interactive; every other name resolves to worker.

docs/loom-glossary.md:48-50

4. Execution language

From CONTEXT.md, the ubiquitous-language doc for task execution. These terms are load-bearing in design docs and PR descriptions.

Repository Set

The exact collection of repository names selected as the preferred working context for a Task. It determines what appears in a TaskRun Root — but is not an authorization or filesystem-isolation boundary.

Avoid workspace, repository scope, repo allowlist

CONTEXT.md:7-9
Repository Access Policy

The independent policy governing which repositories an AI backend may read or modify. Not expressed by Repository Set membership.

CONTEXT.md:11-13
TaskRun Root

The directory an AI backend starts in for a TaskRun. It belongs exclusively to that TaskRun, contains one checkout per member of the Task Repository Set, and is reused only by scheduler retries of the same run.

Avoid workspace, global workspace, cross-repository worktree

CONTEXT.md:31-33
Task Change Set

An immutable version of the repository-keyed backend commits produced by an implementation or correction TaskRun and confirmed on shared remotes. Review and correction work always name the exact Task Change Set they consume.

Avoid shared working directory, patch-only handoff, uncommitted review state

CONTEXT.md:43-45
Task Branch

The stable branch a Task owns in each repository it changes. AI backends append Task commits to these branches, which later TaskRuns consume through Task Change Sets.

CONTEXT.md:47-49
Valid TaskRun Completion

A completion claim made only when every checkout is clean and every changed repository has a backend-authored commit confirmed on its Task Branch remote. A clean no-change result is valid; unfinished changes require Backend Continuation; an unrecoverable push failure fails the run.

Avoid loom auto-commit, successful dirty exit, best-effort push

CONTEXT.md:51-53
Backend Continuation

Another turn in the same native AI backend session and TaskRun Root, used when completion validation finds unfinished work.

Avoid cold scheduler retry, replacement backend session

CONTEXT.md:55-57
Git Push Proxy

The Loom-owned operation that pushes and verifies backend-authored commits without exposing remote credentials to the AI backend process.

Avoid loom-authored commit, backend credential access

CONTEXT.md:59-61
Review TaskRun / Correction TaskRun

A Review TaskRun evaluates an exact Task Change Set from its own TaskRun Root; whether it may modify code is decided by Repository Access Policy, not by repository selection. A Correction TaskRun starts from a reviewed Task Change Set, appends backend-authored commits to the Task Branches, and produces a new Task Change Set version.

CONTEXT.md:63-69

5. Streaming language

Precise enough that the distinctions are enforced in code. Recent work consolidated all SSE frame encoding behind a single writer.

SSE Frame

The unit of transmission on a Server-Sent Events stream, terminated by a blank line. Events, retry directives, and comments are all frames.

Avoid message, packet, raw SSE write

CONTEXT.md:73-75
Resumable Event

An event frame carrying an event ID, advancing the client's Last-Event-ID. A stream is only actually resumable when the server honors that ID on reconnect — that honoring rule is the stream's cursor contract. An ID the server never consults does not make its stream resumable.

CONTEXT.md:77-79
Non-resumable Event

An event frame without an event ID. It never moves the client's reconnect cursor — whether it announces stream state or carries a domain payload.

Avoid control frame, control event

CONTEXT.md:81-83
Retry Directive

A frame that only sets the client's reconnection delay. It dispatches no event and carries no data.

Avoid retry event

CONTEXT.md:85-87
Heartbeat Comment

A comment frame sent periodically to keep an idle connection alive. Its cadence belongs to the individual stream, and clients ignore its text.

Avoid keepalive event, shared heartbeat interval

CONTEXT.md:89-91

6. Isolation and trust

Three things that sound like a security boundary and are not

Sandbox contains the workflow bundle, not the agent that edits your code. Trust level decides whether Loom launches something, not what it can reach once running. read_only / allowed_tools / denied_tools are backend tool and approval policy — real restrictions where the backend has a mechanism, and a prompt preamble where it does not. Never an OS boundary.

docs/loom-glossary.md:102-121

Loom executes code at three levels and only one — the DriverRun bundle — can be containerized. The TaskRun leaf that runs the LLM and edits code, and daemon-supervised agents, run as host processes with the backend CLI's own sandbox switched off.

Egress mode

LOOM_DRIVER_SANDBOX_EGRESS=all|serve-only|none|delegated bounds what a containerized workflow can reach. Empty resolves per trust level: trusted → all, untrusted → serve-only (fail closed). serve-only runs --network=none plus a unix-socket relay so the workflow can dial serve and nothing else. delegated means a NetworkPolicy or host firewall enforces it outside the launcher.

AGENTS.md (Egress modes, SB4)
Read in full before you rely on any of this

docs/design/execution-isolation.md — the three-level model, the per-level mechanisms, the Daytona remote-isolation path, and an explicit list of what is not isolation.

7. Testing vocabulary

Testing claims here are made along four axes — depth, realness, provisioning, polarity — plus a target. The trap words are local, live, real, verify, and gate. Before anything slow or irreversible, echo the request back as those coordinates and state the evidence class of what you ran.

Known gap — verified 2026-09-03

AGENTS.md names docs/testing-terminology.md twice as the canonical map of this vocabulary. That file does not exist in the repo at ce4df56fb; a repo-wide search for the word realness matches AGENTS.md and nothing else. The four-axis model summarised above is therefore the whole of the written definition available to you today. Treat the axis names as reliable and the detailed matrix as unwritten — and do not spend an afternoon hunting for the file.
