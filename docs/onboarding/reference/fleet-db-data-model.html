1. The one rule

Everything on this card follows from this

The event is the write. Everything queryable is a projection of it. executeCommand validates the event, appends it, then tries to project it — and returns nil even when projection fails, because the log is the truth and a background projector will catch up (internal/service/issue_service.go:76-111, the bare return nil at :110). No service method writes an issue hash.

Two consequences you will trip over within a week. First: on the Redis backend the write methods on RedisStorage — ClaimIssue, AddDependency, ReleaseIssue, CompleteIssue — are not the write path. They exist to satisfy the composed Storage interface (32 sub-interfaces, internal/storage/storage.go:13-45) and to be driven by the backend-agnostic contract suite in internal/storage/storagetest/. TransitionStatus is not even that: it appears in no interface in storage.go, and every caller in the repo is a _test.go file inside internal/storage/. Second: the same semantics therefore exist twice — once in internal/projection/handlers.go (Redis) and once through those Storage interfaces in internal/projection/pg_handlers.go (Postgres). A new action must be handled in both.

The read/write seam handlers actually see is ProjectionContext — ProjectionReader (reads hit committed state) plus ProjectionWriter (writes buffer into a TxPipeline): internal/projection/writer.go:10, 22, 38, Redis implementation at internal/projection/redis_writer.go. That indirection is the only reason a second backend was possible.

The whole tracker command surface is 20-odd methods in one file, all the same shape: validate, build a *models.Event, call executeCommand. Copy one wholesale when you add another — internal/service/issue_service.go, 1,424 lines.

The CQRS direction inverts halfway through the repo

Tracker core is event-sourced: command → event → projection. The platform half (driver runs, task runs, triggers, leases — internal/storage/platform.go, 4,054 lines) writes its read model transactionally at command time and emits events afterwards as audit. Re-applying a stale heartbeat snapshot asynchronously would overwrite newer state, which is exactly why handleDriverRunLifecycle returns nil and carries a // harness:noop-ok marker for scripts/harness/check_projector_handler_noop.sh (internal/projection/handlers.go:1336-1338). Do not "fix" it, and do not assume tracker-core rules apply to platform.go.

Metadata keys, by action

All from internal/models/event.go:372-410. issue.close → reason. issue.claim → lock_ttl_seconds. issue.assign → assignee. dep.add / dep.remove → depends_on_id, dep_type. label.* → label. metadata.* → meta_key, meta_value. comment.add → comment_id, text. issue.defer → defer_until. workspace.update → repos_added, repos_removed. Reverts carry reverts, the event ID being reverted.

Why comment.add says text and the model says Body

The Comment model field was renamed Text → Body; the event metadata key could not follow, because it is persisted and renaming it would break replay of existing events. The reasoning is written down at internal/models/event.go:395-399, and the mismatch is visible in the handler, which reads MetaCommentText into a hash field called "body" (internal/projection/handlers.go:1014-1020). This is the worked example of the rule above. Persisted names are frozen.

Two streams, one entry ID

KEYS[1] is fleet-db:{ws}:events, KEYS[2] is fleet-db:{ws}:events:issue:{eid}. The second XADD reuses the first's generated ID, so a cursor is meaningful against either stream. Field order in ARGV is deterministic (fieldOrder, redis_eventstore.go:47-51). The identical script is the Go const appendEventLua at redis_eventstore.go:22-26 — and that is the copy that runs. See §9.

The "per-issue" stream is not only for issues

Append builds KEYS[2] from event.EntityID unconditionally (internal/storage/redis_eventstore.go:70-73). A role.create or skill.update event therefore lands in a key named fleet-db:{ws}:events:issue:<role-or-skill-name>. The word issue in that key is the historical name of the pattern, not a type claim — do not read it as one when you are scanning a keyspace.

5. Key schema

Prefix is fleet-db (internal/storage/keys.go:18). keys.go is the only file allowed to build a key — 215 builders (216 funcs, one of which is the assertValidWorkspace helper); 185 carry a // Pattern: line and 132 of those also carry // Redis type:. Most builders that take a workspace call assertValidWorkspace, which panics on a malformed key (keys.go:24-28) — but 47 of the 205 never reach it, directly or through a helper: the whole *Pattern / *Prefix family, plus WorkspacePrefixKey (:436), the builder the last table in this section cites. Those return a key built from an unvalidated workspace.

Copy that shape exactly when you add one: doc line, Redis type:, Pattern:, assert, concatenate. The comment block is not decoration — it is how the next person reads the schema without running anything.

6. Ready queue and blocked set

The score is the priority, 0 (critical) … 4 (backlog), default 2 (internal/models/priority.go:5-15). Lower score is higher priority, so a plain ascending ZRANGE is priority order.

PredicateConditionsWhere
IsReadyEligiblestatus == open and type != epic and not future-defer_untilinternal/storage/ready_eligible.go:35-49
IsReadyEligibleFullall of the above, and DirectBlockerCount + BlockedByDelta <= 0 — :58 rejects only a sum > 0, which is what the -1 delta trap below relies on — and not a member of {ws}:blocked:54-64

Both take a plain value struct — ReadyInput: no context, no client (ready_eligible.go:11-28). A pure predicate factored out of I/O, so it can be stated once and mirrored. The whole file is 65 lines.

Assignment is not an eligibility rule

Assigned issues sit in the ZSET. The default query filters them out at read time by setting Assignee to a pointer-to-empty-string (internal/storage/ready.go:449-455). So "why is this assigned issue in queue:ready" has the answer: because it is supposed to be. See Lesson 08.

Who maintains the queue — five ways, and only these five

  1. Inline field-level check on create A brand-new issue can have no blockers, so handleIssueCreate calls the cheap predicate and ZADDs. internal/projection/handlers.go:128-139
  2. readyState then updateReadyQueue On update, reopen, release, assign and undefer. internal/projection/helpers.go:191, 259
  3. reevaluateAfterBlockerRemoved On close, delete and dep-remove. internal/projection/helpers.go:284-313, called from handlers.go:360 (close), :526 (delete) and :886 (dep-remove)
  4. A full atomic Lua rebuild, after the pipeline commits shouldRebuildCache (internal/projection/rebuild_trigger.go:19-45) → projector.go:288-297 → RebuildBlockedCache (internal/storage/ready.go:244-246) → rebuild_blocked_cache.lua
  5. A direct, unconditional ZREM in the handler The subject issue leaves the queue outright, no predicate consulted: close (internal/projection/handlers.go:344), delete (:472), claim (:611), defer (:721), dep-add (:824). This is the "handlers update the queue inline" path referred to just below.

shouldRebuildCache is true for issue.close, issue.reopen, issue.delete, issue.defer and issue.undefer; for dep.add / dep.remove only when the dep_type metadata AffectsReadyWork(); and for issue.update only when the After payload carries a status key. It is false for claim, release and assign — those move between non-terminal statuses, and the handlers update the queue inline (rebuild_trigger.go:20-44).

The rebuild, in four phases

internal/storage/lua/rebuild_blocked_cache.lua, 138 lines. Read it end to end once — it is the clearest single statement of the whole model.

PhaseDoesLines
0Enumerate every ID by walking the nine idx:status:* SETs; first seen wins. An issue missing from all nine is invisible to the rebuild.:11-24
1Directly blocked = any member of deps:blocked_by:{id} whose status is missing, or is neither closed nor tombstone.:33-45
2BFS-propagate blocking down deps:children:*, depth capped at 50.:47-73
3Re-derive ready membership: open, not blocked, not epic, not future-deferred; score = priority, defaulting to 2.:75-106
4DEL both structures, then batched SADD / ZADD, 1000 members per call.:108-136

A Go reference implementation is kept beside it — rebuildBlockedCacheGo (internal/storage/ready.go:254) — and its doc comment says plainly that it has the TOCTOU race the Lua version exists to remove (ready.go:248-251). Production always takes the Lua path (ready.go:244-246). Lesson 19 walks this.

A handler's reads do not see the handler's own writes

ProjectionReader reads committed state; the handler's writes are still buffered in the uncommitted TxPipeline. So reevaluateAfterBlockerRemoved counts remaining blockers and then applies a -1 by hand, with the reason in the code: remaining-1 <= 0 // -1: the blocker edge SRem above has not committed yet (internal/projection/helpers.go:309). If you write a handler that reads back something it just wrote, you get the old value and no error.

The blocked in that table is the status sense of the word — a worker parked the task and declared a blocker. The dependency sense lives in {ws}:blocked, and nothing translates between them. The glossary is explicit about this; it is the highest-frequency vocabulary mistake in this repo.

Where each transition rule is enforced

  • Create may set only open or deferred — internal/service/commands.go:72-81.
  • PATCH goes through ValidateSettableStatus, which is the single definition of what a plain status write may set, shared with the agent set_status completion hook so the two cannot drift — the reasoning is written out at internal/models/status.go:59-94.
  • Claim accepts any IsClaimable status, plus the stale-takeover branch when this actor won the lock on an issue that is in_progress under someone else — internal/service/issue_service.go:535-545.
  • Terminal guard: ValidateModifiable (internal/service/status.go:19) rejects writes against a terminal status; wired into nine issueService methods — update, assign, defer, add/remove-dependency, add/remove-label, set/remove-metadata (internal/service/issue_service.go:303, 783, 827, 917, 987, 1035, 1087, 1141, 1208) — plus four revert paths (internal/service/revert.go:92, 379, 428, 489). Its own doc comment at status.go:14 names only four of those and is stale.
  • Derived set: allNonTerminalStatuses is computed from BuiltinStatuses() at init, in two independent copies — internal/projection/helpers.go:318 and internal/storage/indexer.go:49 — so handlers can SREM from every non-terminal index without a pre-read (handlers.go:600-604).
Adding a tenth status updates the Go lists and not the Lua

Both copies of allNonTerminalStatuses derive themselves from BuiltinStatuses(), so both pick up a new status automatically. But internal/storage/lua/rebuild_blocked_cache.lua:12 hard-codes the nine names in a Lua table. Issues in the new status become invisible to Phase 0, so they vanish from {ws}:blocked and queue:ready on the next sweep. The status_model harness gate (harness/policy.yaml:151-165) compares docs/architecture.md to status.go — not this script.

A parent-child edge is a blocking edge

handleDepAdd falls through the three informational branches and writes deps:blocks:{parent} and deps:blocked_by:{child} for both blocks and parent-child, then removes the child from queue:ready and adds it to {ws}:blocked (internal/projection/handlers.go:805-825). Adding a parent-child edge through dep.add therefore takes the child out of the ready queue until the parent closes. Creating an issue with parent_id set does not: handleIssueCreate writes only idx:parent and deps:children (handlers.go:117-121), no blocked_by edge, and still ZADDs the child straight into queue:ready (:137-139). The repo's own test says so in as many words — // CHILD should be blocked (parent-child is blocking), internal/projection/handlers_coverage_test.go:1880.

  • One parent per child — on Postgres only. internal/storage/postgres/dependency.go:62-71 returns ErrParentExists. Redis has no such check: service.AddDependency rejects terminal targets, duplicate (target, type) pairs and cycles, and nothing else (internal/service/issue_service.go:904-971), and handleDepAdd then overwrites deps:parent:{child} outright (internal/projection/handlers.go:812), leaving the child in the old parent's deps:children and idx:parent sets. The ERR:PARENT_EXISTS branch at internal/storage/redis.go:80-84 is in the contract-suite-only script — see §9.
  • Blocking propagates parent → child, transitively, capped at 50. Lua at lua/rebuild_blocked_cache.lua:57-73; the Go mirror uses maxTransitiveDepth = 50 at internal/storage/ready.go:36.
  • Closing a blocker unblocks its dependents inline. handleIssueClose reads deps:blocks:{closed}, SREMs both edge sets, and re-evaluates each dependent — handlers.go:349-365.
  • Informational types touch no ready or blocked state at all. Each of the three returns early — handlers.go:769-803.

9. The Lua scripts

Every script exists twice, and the copy is not the one that runs

47 files in internal/storage/lua/; 47 backtick const …Lua strings in internal/storage/*.go. The Go const is what runs — it is compiled into a redis.NewScript. There is no //go:embed of the lua/ directory; the only embeds in the repo are SQL migrations (internal/archive/migrate/embed.go, internal/storage/postgres/migrate/embed.go). Edit both, or scripts/harness/check_lua_go_sync.sh fails — it diffs them after stripping comments and blank lines, matching file to const by a lowercase-alphanumeric normalisation (check_lua_go_sync.sh:33-42).

The return protocol

Repo-wide convention: a script returns "OK" or "ERR:<CODE>[:<detail>]", and the Go wrapper parses it back into sentinel errors. Exemplars to copy: internal/storage/claim.go:102-121 and locks.go:52-59.

The atomicity guarantee, exactly

At most one actor holds {ws}:locks:issue:{id}, and re-acquisition by the current holder is a TTL refresh, never a failure. That is the whole guarantee. The status and assignee change that follows is not in the same atomic unit — it is a separate event and a separate pipeline. What makes it safe is ordering: the lock is taken first and the issue state is read after (internal/service/issue_service.go:510-518, comment: "to avoid TOCTOU"). Default TTL is 300 seconds (:500-503). Lesson 20 is the long version.

11. Traps

  • assertValidWorkspace panics. Any path that reaches an asserting key builder with an unvalidated workspace crashes the request goroutine instead of returning an error. Validate upstream — and do not read a clean call through a *Pattern / *Prefix builder as evidence the workspace was valid; those skip the assert (§5). keys.go:24-28
  • idx:assignee:unassigned is a literal key. An actor genuinely named unassigned collides with it. keys.go:491 vs :499
  • Projector dedup is strict equality, not <=. A range check would silently drop the out-of-order inline projections that concurrent executeCommand calls legitimately produce; the comment says so. internal/projection/projector.go:251-257
  • A failed projection advances only the in-memory cursor. advanceCursor touches wl.cursor and nothing else (projector.go:329-340); {ws}:projector:cursor is written only inside the successful pipeline (:269-271). So a poison event is skipped for the life of the process and retried after restart.
  • An unknown action does persist the cursor. Different path, different behaviour: log a warning, SET the Redis cursor, return nil. projector.go:226-247
  • acceptance_criteria cannot be written through any API. It is on the model (models/issue.go:60), stored (marshal.go:38), FTS-indexed (handlers.go:266) and supported by storage.IssueUpdate (filter.go:116) — but absent from both CreateIssueCmd (service/commands.go:24-46) and UpdateIssueCmd (:90-105).
  • UpdateIssueCmd covers 11 fields, not the issue. Title, Description, Status, Priority, Type, Design, DesignFormat, Notes, Owner, DueAt, ExternalRef. Assignee, Labels, Metadata, ParentID, Repo, DeferUntil and EstimatedMinutes each have their own endpoint — or none. service/commands.go:90-105
  • ReadyFilter exists twice, with different fields. internal/service/ready.go:33 has IncludeAssigned bool; internal/storage/ready.go:40 has an Assignee *string tri-state. Confusing them inverts the default.
  • "Integrity" means two different things. GET /api/v1/admin/workspaces/{key}/integrity (internal/api/workspace.go:260) runs service.CheckIntegrity, which checks referential integrity only — dangling parent_id, unmapped repo, dangling dep refs (internal/service/integrity.go:28-100). Ready-queue, blocked-set and index/hash parity live in RedisStorage.VerifyInvariants (internal/storage/invariants.go:51), which has no HTTP route and no production caller at all.
  • The dead-code linter cannot see those unused exported methods. make lint-deadcode only ever considers names starting with a lowercase letter — grep -E 'unreachable func: [a-z]', Makefile:158. deadcode prints a method as <receiver type>.<method>, so RedisStorage.ClaimIssue and RedisStorage.VerifyInvariants are dropped there and never reach the exclusion on :159 — which targets exported methods on unexported types, as Makefile:151-152 says in as many words. Exported methods on exported types are outside the linter's remit by construction.
  • Labels may not contain , or ; — but not for the stated reason. The comment says "labels are stored comma-separated" (models/issue.go:17-20); in Redis they are a JSON array (marshal.go:91-94). The real constraint is the comma-separated label / label_any query parameters — internal/api/ready.go:176-181, flattened by collectMultiValues → splitCSV (:229-258), with loomcli joining on commas before it sends (internal/backend/fleet/params.go:233-238). Nothing in either tree splits a label on ;, so that half of LabelSeparatorChars is unexplained by any code.
  • Empty collections are written, not omitted. marshalIssue deliberately writes "[]" and "{}" so the non-nil invariant is visible in a raw HGETALL, not only after passing through UnmarshalIssue. marshal.go:77-103
  • Metadata is bounded, labels are not indexed the same way. Metadata keys are URL-path-safe and ≤128 bytes, values ≤1024 bytes, ≤64 entries per issue — a best-effort command-time bound that concurrent writers can briefly exceed. internal/models/metadata.go:9-24

12. Reading a live keyspace

Shared machine — read this before you run anything

Compose stacks, ports and podman state on this machine are shared. Never run make local-mode-up or make local-mode-down against a compose project you did not create — up --build on an existing project name silently recreates someone else's containers. Before starting anything, run podman ps, treat every stack you find as owned by someone else, and pick your own compose project name and an unclaimed port block. Tear down only your own. Everything in this section is read-only, and the greps need no stack at all. See Lesson 03.

Against a Redis you started yourself

Read-only verbs only, and prefer --scan over KEYS:

redis-cli -p <your-port> --scan --pattern 'fleet-db:FLEET:idx:*'
redis-cli -p <your-port> TYPE      fleet-db:FLEET:queue:ready
redis-cli -p <your-port> ZRANGE    fleet-db:FLEET:queue:ready 0 -1 WITHSCORES
redis-cli -p <your-port> SMEMBERS  fleet-db:FLEET:blocked
redis-cli -p <your-port> HGETALL   fleet-db:FLEET:issues:FLEET-1
redis-cli -p <your-port> XRANGE    fleet-db:FLEET:events - + COUNT 5
redis-cli -p <your-port> GET       fleet-db:FLEET:projector:cursor

The scores in that ZRANGE are priorities, not timestamps. The HGETALL shows labels as [] and metadata as {} when empty — that is the invariant being deliberately observable, not a bug.

From the loomcli side

loomcli never speaks Redis to fleet-db; it speaks HTTP or RPC. loom data ready (internal/cli/data/ready.go:18-40) and loom data blocked (internal/cli/data/blocked.go:17-38) are the read-only surface onto the ZSET and the SET on this card — both say "(HTTP)" in their own help text. --assignee on ready is what lands on the storage-side Assignee tri-state described in §6.

In local mode the whole keyspace lives in a snapshot file

loomcli local mode runs an in-process miniredis and persists the entire fleet-db: prefix to a snapshot, so the embedded fleet-db subprocess that each loom invocation spawns can pick the data back up (internal/webui/localredis/manager.go:80-89). But maxStreamEntriesPerKey = 10000 caps how much of any one stream is serialized: newest entries are kept, older ones stay in the live miniredis and do not survive a restart (manager.go:64-70). If your local event history is shorter than you expected, that is why — and it is a local-mode property, not a fleet-db one. See Lesson 05.
