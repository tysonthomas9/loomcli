## Detail by theme

### 1. Store / persistence layer (the biggest cluster)

#### [high] Parallel store.Store implementations: memstore (in-memory) vs fleetdb (HTTP) per entity
`store-crud-parallel-impls` · kind=within-package · ~2500 LOC · **extract-shared** (effort medium, risk low, blast 3 files)

Instances:
- `internal/infra/memstore/agent.go:25-157` — agentStore CRUD against in-memory map with sentinel-error wrapping
- `internal/infra/fleetdb/agent.go:77-213` — agentStore CRUD as HTTP calls to /api/v1/.../agents, same store.AgentStore contract
- `internal/infra/memstore/repo.go` — in-memory RepoStore CRUD
- `internal/infra/fleetdb/repo.go:42-121` — HTTP RepoStore CRUD, identical method surface/validation semantics
- `internal/infra/memstore/store.go:158-232` — Store accessor methods Workspaces()/Repos()/Agents()/... returning each sub-store
- `internal/infra/fleetdb/client.go:164-242` — Client accessor methods — byte-for-byte parallel accessor list

**Home:** internal/store (interfaces already canonical); add a store/storetest conformance suite covering every sub-store so both impls verify against ONE spec

**Approach:** Do NOT merge the impls — keep memstore (validation/sentinel-errors/sort/clone) and fleetdb (wire-marshalling + remote delegation) separate; that fake-vs-client split is intentional and load-bearing. Instead extend internal/store/storetest with a per-entity conformance suite (mirroring the existing await_suite.go) that asserts the shared observable contract — CreateThenGet, duplicate→ErrAlreadyExists, missing→ErrNotFound, List ordering, patch semantics — and run it against both Store and Client (Client behind an integration/build tag against a real or fake fleet-db). This pins the spec once so the two re-derived bodies can't drift silently.

**Why real / caveats:** Opened agent.go and repo.go in both packages plus both accessor blocks. The CRUD method BODIES are genuinely different logic, not duplication: memstore does real validation order, ErrInvalid/ErrAlreadyExists/ErrNotFound wrapping, List sort-by-Name, and deep clone; fleetdb only marshals wire structs and delegates validation/ordering/errors to the server, and has logic with no memstore analog (repo Create/Delete fire extra workspace add_repos/del_repos PATCH side-calls; agent Update has the agentUpdateHasFleetDBFields short-circuit). Merging these would erase the distinction. What IS real duplication is (a) the accessor blocks (store.go:157-235 vs client.go:163-242) — verified byte-for-byte 1:1 mirrors of ~30 methods differing only in receiver, but these are trivial trait-style getters that an interface already forces, so consolidating them is not worth it; and (b) the genuinely risky gap: the two impls must satisfy ONE store.* spec yet only storetest/await_suite.go exists as shared conformance coverage (confirmed: it's the lone file in storetest/), so behavioral contract (error sentinels, ordering, patch semantics) is independently re-derived per entity and drift is undetected. The distinction to preserve: memstore owns behavior, fleetdb owns transport — only the externally observable contract should be shared, via tests, not via merged code.

#### [high] Hand-written deep-clone-on-read across every memstore entity
`memstore-deep-clone-on-read` · kind=within-package · ~350 LOC · **adopt-existing** (effort medium, risk medium, blast 18 files)

Instances:
- `internal/infra/memstore/agent.go:159-165 (cloneAgent)` — shallow-copy + per-slice append([]T(nil),...) to defend the map from caller mutation
- `internal/infra/memstore (35 clone funcs)` — cloneAgentCommand/Session/Artifact/AwaitInstance/Connector/Driver/DriverRun/Repo/Role/TaskRun/TriggerBinding/Workspace/... one bespoke deep-copy per entity
- `internal/infra/memstore/store.go:149 (clonePtr), worker_profile.go:172 (cloneStringSlice), control_plane.go:270 (cloneMap), platform_helpers.go:70/81 (cloneJSON/cloneRawMessage)` — generic clone primitives exist but inconsistently used — many cloners re-inline append([]string(nil),...) instead of calling cloneStringSlice

**Home:** internal/infra/memstore — route every cloner through the existing primitives (clonePtr/cloneStringSlice/cloneMap/cloneJSON), or replace with one reflect/generics/codegen deep-copy so Read paths cannot leak shared pointers when a slice field is added

**Approach:** Keep one bespoke cloner per entity (field lists genuinely differ) but route every reference-field copy through the existing primitives: replace inline append([]string(nil),...) with cloneStringSlice, inline map copies with cloneMap, and nil-pointer copies with clonePtr. Do NOT collapse to a single reflect/generics deep-copy, which would erase deliberate per-cloner distinctions.

**Why real / caveats:** Verified genuine duplication: cloneAgent (agent.go:159-165), cloneNode (control_plane.go:254-260), and cloneTriggerBinding (platform_helpers.go:25-31) all hand-inline append([]string(nil), x...) for every slice field, while cloneWorkerProfile (worker_profile.go:158-170) already routes the same operations through cloneStringSlice/cloneMap/clonePtr — proving the canonical primitives exist and adoption is partial. The shared shape (out := *x; deep-copy each ref field; return &out) is real re-implementation, and the real hazard is correctness: a newly-added slice/map field silently aliases the stored object unless the author remembers to extend that entity's bespoke cloner. However, distinctions MUST be preserved that rule out a single merged function: cloneJSON returns json.RawMessage(`{}`) on empty whereas cloneRawMessage returns nil (omitempty round-trip); redactedTriggerBinding clones then clears WebhookSecret; cloneConnector copies a []byte sealed credential, not []string. These are semantic, not mechanical. Hence adopt-existing (consistent use of clonePtr/cloneStringSlice/cloneMap/cloneJSON) rather than merge or a reflect-based deep-copy. Risk is medium because cloneStringSlice preserves nil (append on nil input would yield a non-nil empty slice) so each conversion must be checked against the field's nil-sensitivity; blast radius ~18 files across the memstore package.

`fleetdb-wire-structs-toDomain-bodies` · kind=within-package · ~900 LOC · **extract-shared** (effort high, risk medium, blast 8 files)

Instances:
- `internal/infra/fleetdb/agent.go:20-75 (+ :78-108 Create, :142-169 Update)` — agentWire + toDomain() plus separate inline body structs re-listing the same fields 3-4x; agentUpdateHasFleetDBFields is a 4th copy
- `internal/infra/fleetdb/repo.go:16-40 + :43-57 + :94-106` — repoWire + toDomain + inline Create body + inline Update body — same field list 3-4x
- `internal/infra/fleetdb/role.go:37, connector.go:100/131/162, daemon.go:59, platform_outbox.go:121/165, platform_await.go:53, workspace.go` — ~16 XWire structs each with hand-written toDomain (11 toDomain grep-confirmed)
- `internal/infra/fleetdb/body_helpers.go:5-15` — only bodyPtr + bodyTimeRFC3339NanoPtr exist; most files still hand-roll anonymous body structs

**Home:** internal/infra/fleetdb — make each XWire the SINGLE source for both decode (toDomain) and encode (fromCreate/fromUpdate or omitempty-pointer toWire) so create/update/response share one struct; expand body_helpers.go

**Approach:** Adopt the map[string]any + helper-builder pattern already present in body_helpers.go (bodyPtr/bodyTimeRFC3339NanoPtr) and connector.go across the remaining ~8 files: replace each inline Create/Update body struct literal with a per-entity body builder that calls the shared ptr helpers, eliminating the pointer-vs-value duplicate field lists and the agentUpdateHasFleetDBFields hand-roll (replace with len(body)>0). Do NOT try to make a single XWire struct serve both decode and encode.

**Why real / caveats:** Genuinely the same field set re-listed 3-4x: verified in agent.go (agentWire values, Create body values, Update body pointers, agentUpdateHasFleetDBFields enumeration) and repo.go (wire + Create values + Update pointers) with identical JSON tags and semantics. This is a real drift trap. However the proposed home ('make each XWire the single source for decode+encode') is unsafe and would erase necessary distinctions: (1) wire structs carry derived read-only fields (live_status, active_task_id, created_at, workspace_key, state) that must never be sent on Create/Update; (2) Create uses value+omitempty fields while Update needs pointer fields to distinguish 'unset' from 'set-to-zero' (PATCH semantics) — a single struct cannot express both. The correct, lower-blast consolidation already exists in-repo: connector.go builds bodies as map[string]any and body_helpers.go has bodyPtr/bodyTimeRFC3339NanoPtr. Extending that pattern collapses the per-field duplication without merging the three roles. Effort is high because 8 files / 14 inline literals must each be converted and re-tested against fleet-db's strict contracts; risk is medium because a dropped omitempty or wrong key silently changes the wire payload sent to fleet-db.

**Approach:** Create one shared JS redaction module (e.g. sdk/redact.js) holding shannonEntropy + redactSecretsInText + the SECRET_PATTERNS layered detector ported from redact.go. Have both local-task-runner.ts and runtime-adapters.js call it; retire runtime-adapters' substring-only redactText/redactEntry by routing redactTranscriptEntries through the entropy+pattern path (keeping the exact-secret scrub as the first layer), and keep the same public SDK exports pointing at the shared impl. As a follow-up, generate the full gitleaks ruleset into SECRET_PATTERNS (or call the Go redactor over the migration boundary) to close the entropy-only gap on the JS plane.

**Why real / caveats:** Verified all three instances by reading them. local-task-runner.ts:674-767 is a self-described verbatim port of redact.go (same 4.5 entropy literal, same [A-Za-z0-9+_=-]{10,} segment regex, same JSON-escape guard, same sort/merge/REDACTED rebuild), with gitleaks swapped for 8 curated patterns and a comment at :691-696 explicitly flagging the 180-rule set as a follow-up. shannonEntropy genuinely appears three times with the 4.5 literal (Go, local-task-runner) and is entirely ABSENT from runtime-adapters.js, which does naive substring replace of a caller-supplied secrets[] array with [redacted]. That absence is a real security divergence, not cosmetic: a high-entropy or gitleaks-shaped secret the agent echoes that is NOT in the known-env secrets list leaks on the daytona path (runtime-adapters.js:215 -> redactTranscriptEntries). Distinction that MUST be preserved: runtime-adapters' contract is exact-value scrub of known env secrets; local-task-runner already supersets this (scrubToken for exact env values THEN redactSecretsInText for entropy/pattern), so consolidating onto the layered impl strictly adds coverage and loses nothing. extract-shared (not merge) is right because these live in two different JS files on two runner paths and there is no single existing JS helper to adopt; the Go canonical can't be called directly from JS without a migration boundary. Risk is medium, not low, because redactText/redactTranscriptEntries are public SDK exports (sdk/index.js, index.d.ts, runtime-adapters.d.ts) — behavior change (now also redacting unknown high-entropy strings, replacement token differs REDACTED vs [redacted]) is observable to SDK consumers and the d.ts surface must stay stable.
