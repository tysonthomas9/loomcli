Loom — User Stories

Loom is an agent-management CLI and web UI for running multiple AI coding agents in parallel. Each agent works in its own git worktree, picks tasks from a shared issue tracker (fleet-db), and integrates back through a structured push/pull/sync workflow. Supports Claude Code, Codex, Cursor, Gemini, OpenCode backends.

What you can do with loom

Loom turns "AI agent" from a chat bot into a long-running, supervised worker that picks tasks off a board, writes designs, implements code in its own git worktree, and pushes results — repeatedly, in parallel, across many agents and machines.

The product wraps a few hard things behind one CLI + web UI: worktree isolation so agents don't stomp each other, a shared task store (fleet-db) so they coordinate, terminal-attachable runtimes so you can watch any agent live, and structured artifacts (logs, diffs, transcripts) so you can audit what happened after the fact.

The newest direction is the Lead Agent / Epic Runner: a long-lived "manager" agent owns one epic at a time, spawns short-lived ephemeral workers for each child task, and gives you one terminal to chat with it about progress.

Who uses it
Solo developer
Runs planner/coder agents on their own machine to chip through a backlog while they focus elsewhere.
Dogfood operator
Validates that agents actually pick tasks, write designs, implement them, and leave usable evidence.
Team lead
Sees which agents own what, why things are blocked, and approves designs before code lands.
Platform engineer
Debugs local + distributed runner failures from logs, sessions, and artifacts.
Setup
1

First-run onboarding

Solo developer
As a developer who just installed loom, I want a guided checklist so that I get from loom serve to a running agent without reading docs or jumping into the CLI.
Trigger
User opens http://localhost:8080 for the first time.
Flow
  1. OnboardingFlow appears with a server-driven checklist.
  2. "Create workspace + first repo" — one combined modal accepting local path or git clone URL (no dead-end empty workspaces).
  3. "Verify repo" — RepoChecksPanel runs checks (default branch, gate command, push remote).
  4. "Set up backend" — BackendSetupPanel can install a missing CLI, run interactive login, or show env-var instructions via an embedded terminal.
  5. "Create agent" — CreateAgentModal binds a role to the repo.
  6. "Create issue" — first task seeded.
  7. "Run agent" — first visible run, with a live terminal you can watch.
Outcome
One workspace, one repo, one ready backend, one agent, one issue, one visible run — all without leaving the browser.
Surfaces
OnboardingFlow BackendSetupPanel WorkspaceRepoWizard RepoChecksPanel EmbeddedTerminal
2

Configure an AI backend

Solo developer
As a developer I want to install and log into Claude, Codex, Cursor, or Gemini from the UI so that agents have a model to talk to.
Backends
claude · codex · cursor · gemini · opencode (each is a thin shim around the vendor's CLI).
Flow
  1. Settings → AI Backends shows readiness per backend (installed? logged in? auth-ready?).
  2. Pick a backend → BackendSetupPanel previews the exact install command, requires an explicit click, then runs it in an embedded terminal.
  3. For login: panel runs the vendor's interactive auth in the same terminal.
  4. Server polls readiness; checklist ticks itself off.
Key rule
Loom never stores API keys at rest. Auth lives in the vendor CLI's own store or the operator's shell.
CLI
# Pick a backend per call, env, or workspace
loom plan falcon --backend codex
LOOM_BACKEND=codex loom plan falcon
loom daemon profile set --backend codex
3

Define an agent role

Solo developer
As a developer I want named roles with specific prompts, tool allow-lists, and budget caps so that "reviewer" and "implementer" behave differently and stay in their lanes.
Concepts
Role = prompt + tool allow/deny + read-only flag + budget. Reused across agents.
Agent definition = name + role + repo. The thing you actually run.
CLI
loom role set reviewer --prompt-file ./prompts/reviewer.txt
loom role set reviewer --allowed-tools Read,Grep --read-only
loom agentdef add falcon --role reviewer --repo my-app
Built-in roles
plan (writes designs), task (implements approved designs), lead (orchestrates).
Issue tracking
4

Create & triage issues

Team lead
As a team lead I want a real issue tracker inside loom so that the same tasks agents pick up are also the tasks I plan against.
Issue model
type (task / epic / feature / bug), status (open → in_progress → review → done / blocked), priority, assignee, labels, parent, dependencies, design, notes, repo.
Mutations
From the UI (CreateIssueModal, IssueDetailPanel) or CLI (loom data create/show/update/close). Mutations broadcast over SSE — every connected tab updates live.
Bulk ops
BulkActionToolbar in the Table view: assign, label, close, change status across N issues at once.
5

Plan tasks via Kanban

Team lead
As a team lead I want a drag-and-drop board so that I can sort the backlog visually and watch agent progress.
View
KanbanPage shows swim-lanes grouped by status, priority, or type. Cards show task ownership, current run signal, blocked badge.
Live updates
When an agent claims a task, the card visibly moves; when it closes a task, the card lands in done.
Alternates
Table view for power users, Graph view (React Flow) for dependencies, Files view to browse repo, Observability view for traces.
6

Model task dependencies

Team lead
As a team lead I want to declare "task B blocks task C" so that an epic runner only starts ready work and skips blocked work.
Flow
  1. Open IssueDetailPanel → Dependencies → "Add depends-on".
  2. Graph view re-renders with the new edge.
  3. Backend now classifies B as "ready" (no open deps) and C as "blocked" until B closes.
Why it matters
The epic runner (#12) only dispatches ready tasks. Dependency edges turn into orchestration logic for free.
Solo agent work
7

Run a planning agent

Solo developer
As a developer I want an agent to write a design for an unplanned task so that I can review the approach before any code is written.
CLI
loom plan falcon                # single task, then exit
loom plan falcon --auto         # keep claiming tasks-without-designs
loom plan falcon -a -m 5         # cap at 5 tasks
loom plan falcon -a -t 30        # exit after 30 min idle
What an agent does
  1. Acquires worktree lock.
  2. Queries fleet-db for tasks without an approved design.
  3. Claims one; backend (claude/codex/…) writes a design into the issue's design field.
  4. Marks task as needing review; loops or exits.
Visibility
UI shows an agent card the moment the process starts — before the model talks. Task Sessions tab populates with transcript, logs, current state.
8

Run a coding agent

Solo developer
As a developer I want an agent to implement an approved design so that approved plans turn into committed code automatically.
CLI
loom task falcon --auto
Selection rule
Picks tasks with approved design, skips tasks marked [Need Review] or already in-progress, skips epics.
Each task
Claim → implement (edits files in the worktree) → run gate command if configured → commit → close task → move on. Failures land as failed or preflight_failed with a readable reason.
9

Approve a design before code is written

Team lead
As a team lead I want to gate implementation on design approval so that the agent doesn't burn budget building the wrong thing.
Flow
  1. Planning agent fills in design and tags the issue [Need Review].
  2. Implementer agents skip [Need Review] tasks automatically.
  3. Lead reviews via IssueDetailPanel; approves or edits the design.
  4. Approval clears the review label; coding agents now pick it up.
10

Auto-mode for an unattended backlog burn

Solo developer
As a developer I want to start an agent before lunch and come back to N closed tasks so that throughput isn't bound by my keystrokes.
CLI
loom task falcon -a -m 10 -t 60
# up to 10 tasks; bail if idle 60 min; Ctrl+C anytime
Exit conditions
Ctrl+C, --max-tasks reached, or --idle-timeout with no work.
Summary on exit
Tasks completed, reason for exit, total wall time.
Epic orchestration (newest feature)
11

Talk to a Lead agent

Team lead
As a team lead I want a long-lived "manager" agent I can chat with about the backlog so that I can hand off epic-level planning without losing context.
What a Lead is
A persistent agent with role_name=lead and a resumable terminal session. Reconnect after a refresh — scrollback replays.
Surface
Agents page → pick the lead in the left rail → center is the lead's terminal → right panel shows open epics/tasks (or the active epic if one is bound).
Usage
Chat about strategy, ask it to triage the backlog, or kick off an epic run by typing loom epic run --parent E2E-1 right into its terminal.
12

Run an epic

Team lead
As a team lead I want the lead agent to drive a whole epic to completion so that I assign work at the epic level, not the task level.
Trigger
Click "Run Epic" in the right panel or type loom epic run --parent E2E-1 in the lead terminal.
What happens
  1. Backend rejects if the lead is already running a different epic (one epic per lead).
  2. Lead's agent.parent is set to the epic ID — that's the lock.
  3. Reconcile loop starts: read ready tasks, spawn an ephemeral worker per ready task up to concurrency cap, sleep, repeat.
  4. Each worker is a deterministically-named ephemeral agent pinned to one task — claim, work, commit, close, exit.
  5. Lead terminal streams the reconcile output: [epic-run] 3 ready, 1 blocked, 2 active workers.
Drain
Loop exits when no open children remain and all spawned workers have stopped. Lead remains bound to the epic until you tell it otherwise — completion does not auto-clear ownership.
13

Inspect an ephemeral worker mid-run

Solo developer
As a developer I want to peek at any worker the lead spawned so that I can debug a slow or stuck task without stopping the whole epic.
Flow
  1. Left rail shows the lead with its live workers nested underneath: + worker-auth-1 active.
  2. Click a worker → center terminal switches to that worker's PTY → scrollback replays.
  3. Right panel stays scoped to the epic so context is preserved.
Single-use
An ephemeral worker is pinned to one task. It may retry the same attempt after process failure but it will never claim a second task — that keeps task→worker mapping deterministic.
14

Review a finished worker

Team lead
As a team lead I want logs, diff, transcript, and cleanup actions for a worker that already finished so that I can audit attempts and reclaim disk after the fact.
Where
Finished workers leave the live rail and appear in "worker history" / task attempt history.
What's preserved
Per session-artifact-contract.md: transcript, logs, token usage, diff, commit, test result, cleanup state, error class. The PTY is gone but the evidence isn't.
Cleanup
First-class action: delete worktree, archive artifacts. Reclaims disk without losing persisted evidence.
Fleet operation
15

Supervise many agents with the daemon

Platform engineer
As an operator I want one process that keeps N agents alive so that crashes auto-restart and I don't babysit terminals.
CLI
loom daemon profile set --max-agents=10
loom daemon                       # start supervising
loom daemon status                # health, active agents, queues
Behavior
Reads daemon profile from fleet-db → reconciles desired vs actual agent state every tick → starts missing, restarts crashed (with backoff), drains gracefully on SIGTERM. Owns the agent lifecycle, not the model traffic.
16

Multi-node fleet

Platform engineer
As an operator I want agents on multiple machines coordinating via shared state so that throughput scales beyond one box.
CLI
loom serve --fleet-mode --redis-addr=redis.prod:6379
LOOM_FLEET_DB_URL=https://fleet.example.com loom daemon
What fleet-mode unlocks
Cross-node task claims, shared JWT signing, stale server detection, fleet worker API routes, decentralized claim leases.
Off by default
Most users stay local; the same code paths back both — local is "fleet mode with one node".

Sync all worktrees

Solo developer
As a developer I want one command to push completed work and pull integration changes across every worktree so that I don't merge-hop manually across 10 directories.
CLI
loom push --all             # push every worktree to its target
loom pull --all             # pull main into every worktree
loom sync                   # both, in order
loom reset falcon main      # hard reset worktree to main
AI conflict resolution
When a merge conflict happens, an agent backend can resolve it interactively rather than aborting.

Watch the Monitor view

Team lead
As a team lead I want one dashboard that tells me what every agent is doing right now so that I notice slow tasks and idle agents at a glance.
Surface
MonitorPage in the web UI, or loom monitor for a terminal dashboard.
Shows
Per-agent: name, role, backend/model, lifecycle state, current task, runtime provider, stale/offline indicator, latest error. Per-project: ready/blocked counts, queue depth, heartbeat health.
20

Recover a stuck agent

Platform engineer
As an operator I want clear "this is why your agent is stuck" states + a one-button recover action so that I don't dig through logs to clear a lock.
Preflight failure
Missing backend auth, missing tools, missing worktree, missing gate command, missing git remote — surfaced as a discrete state before the model starts.
Recovery
loom recover falcon            # clears locks, resets task claims
Failure modes covered
Per failure-modes-recovery-ux.md: stalled worker, preflight failed, gate failed, push failed, ungraceful crash, orphan claim.
21

Switch backend mid-flight

Solo developer
As a developer I want to try Codex on the next task without redoing setup so that I can compare backends in-place.
Resolution order
--backend flag > LOOM_BACKEND env > daemon profile > default claude.
Per-agent override
Agent definitions can pin a backend; daemon-spawned agents inherit it.
CLI
loom task falcon --backend codex
Glossary
workspace
Top-level container — usually one team/project. Has its own repos, agents, issues.
repo
A git repository tracked inside a workspace. Agents work in its worktrees.
worktree
Per-agent git checkout on its own branch — agents never share working dirs.
role
Prompt + tool allow/deny + budget. Reusable across agents.
agent definition
Named binding of (role, repo). What you actually start.
agent (runtime)
A running process serving an agent definition. Has state: active, idle, stopped, dead.
ephemeral worker
Short-lived agent spawned by a lead to do one task, then exit.
lead
Long-lived agent that owns one epic at a time and spawns workers for it.
fleet-db
Shared state store (issues, agents, sessions, leases). Embedded locally or remote in cloud mode.
backend
The AI model CLI behind an agent — claude / codex / cursor / gemini / opencode.
session
One agent-task execution unit with a transcript, logs, and artifacts.
artifact
Persistent evidence from a run — transcript, logs, diff, test result, token usage.
gate command
Per-repo test/lint command an agent must pass before closing a task.
daemon
Local supervisor process that keeps the configured agents alive.
fleet mode
Multi-node operation — agents coordinate across machines via shared Redis + fleet-db.
