Code review — the two requested commits

9aef2ae5 — Fix FleetDB agent orchestrator writes Partial

Drops orchestrator_session_id from FleetDB's Create/Update bodies; adds a guard so an orchestrator-only Update becomes a GET.
What it does
  1. Removes OrchestratorSessionID from both the POST /agents body struct and the PATCH /agents/{name} body struct.
  2. Adds agentUpdateHasFleetDBFields(): if the patch contains only OrchestratorSessionID (or no FleetDB-supported field at all), Update returns the current agent via Get instead of issuing an empty PATCH.
  3. Three new tests cover create-omit, update-omit, and the orchestrator-only-no-PATCH path.
Why
FleetDB's PATCH/POST schemas use strict DisallowUnknownFields decoding and reject any field they don't list. The comment says session attribution belongs on AgentSession rows, not Agent rows.
Issue I found
Callers still read agent.OrchestratorSessionID after Update — e.g. internal/cli/epic/run.go:336: 
if effectiveOrchestratorID == "" {
    effectiveOrchestratorID = strings.TrimSpace(updated.OrchestratorSessionID)
}
On the FleetDB path the field is now never written, so updated.OrchestratorSessionID is always "". Confirmed in the E2E below: after updateLeadBinding, the API reports "orchestrator_session_id": null on nova despite the lead's session ID being passed in via LOOM_ORCHESTRATOR_SESSION_ID.
Workers and the lead still get the right ID via the env-var propagation path (the comment says session attribution lives on AgentSession), but the existing read-back at run.go:336 falls back to empty and silently degrades any downstream code that depends on it.
Verdict
Fix itself is correct and the tests are tight. The follow-up work is to either (a) stop reading updated.OrchestratorSessionID on the post-Update path, or (b) actually fetch the orchestrator session from the AgentSession row.

6fca80d9 — Fix pre-push gate git environment Looks good

Replaces unset GIT_DIR GIT_WORK_TREE with a loop that unsets every var from git rev-parse --local-env-vars.
What it covers
15 variables on this system, including GIT_INDEX_FILE, GIT_PREFIX, GIT_OBJECT_DIRECTORY, GIT_COMMON_DIR, GIT_ALTERNATE_OBJECT_DIRECTORIES, GIT_CONFIG_PARAMETERS, etc. The old fix left all 13 others set; subprocess git calls in tests could still leak back to the host repo.
Two minor gaps
  1. Test only covers scripts/hooks/pre-push. The companion .githooks/pre-push got the same fix but the new TestPrePushHookClearsGitLocalEnv only validates one of the two files. The two files are sequenced differently (one runs the beads-sync branch check first; one has set -euo pipefail, one doesn't) so they can drift.
  2. Silent failure if git rev-parse fails. The construct while … do unset; done < <(git rev-parse --local-env-vars) uses a process substitution. If the inner command exits non-zero, the loop iterates over zero lines and the unset never happens. .githooks/pre-push doesn't have set -euo pipefail so this regression mode is undetected.
Verdict
Net improvement, ship it. The gaps are minor and could be follow-up tasks: either add a second test for .githooks/pre-push, or factor the two scripts to share a sourced helper.

Bug #A — loomcli sends a forbidden status field on agent-command POST Blocking

Every spawn-worker attempt hit HTTP 400 from fleet-db; not a single task ran.
Repro
Ran the seeded Slack-clone epic. The reconcile loop tried to dispatch SLACK-2 (the only ready task) every tick for the full 180-second timeout and logged this on each attempt:
[epic-run] spawn for SLACK-2 failed: enqueue start command for slack-1-slack-2-129db47c:
  fleetdb: POST /api/v1/SLACK/agent-commands: HTTP 400:
  unknown field "status": domain: invalid value
[epic-run] 1 ready, 3 blocked, dispatched 0 (active 0/2)
  …repeated until SIGTERM…
Root cause
internal/infra/fleetdb/control_plane.go:658: 
body := map[string]any{
    "command_id":       in.CommandID,
    "target_agent_id":  in.TargetAgentID,
    "target_node_id":   in.TargetNodeID,
    "session_id":       in.SessionID,
    "type":             in.Type,
    "payload":          in.Payload,
    "status":           domain.AgentCommandQueued,   // ← rejected
}
FleetDB's createCommandRequest at internal/api/control_plane.go:657-664 has no status field; the server hardcodes Status: models.AgentCommandQueued on line 685. Strict JSON decoding (DisallowUnknownFields) rejects the body.
Pattern
This is the same class of bug as 9aef2ae5 — loomcli sending fields fleet-db's strict schema doesn't accept. The fix shape is identical: drop "status" from the POST body. fleet-db sets it server-side.
Suggested fix
body := map[string]any{
    "command_id":      in.CommandID,
    "target_agent_id": in.TargetAgentID,
    "target_node_id":  in.TargetNodeID,
    "session_id":      in.SessionID,
    "type":            in.Type,
    "payload":         in.Payload,
}
Plus a test that asserts the body has no status key — same shape as the new tests in agent_test.go from 9aef2ae5.
Why CI doesn't catch it
The smoke epic_runner_codex.sh probably bundles an older fleet-db that tolerated the extra field. The dev-container build pulls the current fleet-db source — that's why it surfaces here and not in the existing E2E.

Server panic during the failed run: storage: invalid workspace key "Hello-World" in key builder.
Source

Diagnosis
Some webui handler is calling GET /api/v1/Hello-World — using the repo name ("Hello-World") where fleet-db expects a workspace key. fleet-db's assertValidWorkspace rejects keys with hyphens (workspace keys allow only [A-Z0-9_]) and panics rather than returning an error.   2. fleet-db: panicking on input validation is a bug — return 400 instead. The panic-recover middleware shields the server, but a malformed key shouldn't reach a panic in the first place.

Harness note — driving wterm via input events

First attempt failed (agent-browser type timed out); the fix was to inject text via the hidden TEXTAREA's value setter + dispatch an InputEvent, then submit with a real press Enter.
Why type failed
The terminal isn't a real <input> or <textarea>. It's a <div role="textbox"> (custom "wterm" widget) that programmatically focuses a hidden TEXTAREA on click. agent-browser's high-level type tried to fill the div directly and timed out because the div is not a fillable element.
What worked
  1. Click the wterm div — focus moves to the hidden TEXTAREA.
  2. Inject text via InputEvent('input', { data, inputType: 'insertText' }) on the focused TEXTAREA. The wterm widget reads the input event payload and forwards bytes over the WebSocket, then clears the textarea.
  3. agent-browser press Enter — a real KeyboardEvent that the wterm widget forwards as a submit keystroke to Codex.
Snippet: 
agent-browser eval --stdin <<'EOF'
const ta = document.activeElement;  // hidden TEXTAREA after click
const setter = Object.getOwnPropertyDescriptor(
  window.HTMLTextAreaElement.prototype, 'value').set;
setter.call(ta, 'please run epic SLACK-1 …');
ta.dispatchEvent(new InputEvent('input',
  { bubbles: true, data: 'please run …', inputType: 'insertText' }));
EOF

Pass 5 — both fixes applied, full epic drains

Bug I fix

Diagnosis
Not a wire-format mismatch like Bug A. defaultLeaseTTL in supervisor.go:156 was 2 minutes. Real-codex worker turns regularly run 5+ minutes. No periodic heartbeat loop on the agent lease (only IPC mutations renew). So the lease expired before the worker's first IPC mutation, and validateIPCLease at daemon_ipc.go:305 rejected the close with ErrInvalidTransition. 
// supervisor.go — before
defaultLeaseTTL = 2 * time.Minute

// after
// defaultLeaseTTL must outlive a typical real-codex turn (often 5+
// minutes) so the lease is still Active when the worker calls
// loom data close. There is no periodic heartbeat loop on the agent
// lease today (only IPC mutations renew it), so a short TTL silently
// fails task completion after a long codex session.
defaultLeaseTTL = 30 * time.Minute

// daemon_ipc.go — also bumped the renewal TTL to match
Heartbeat(ctx, ..., 30*time.Minute)
Note
This is a hotfix. The structural fix is a periodic heartbeat loop in the worker process that renews the lease every ~30 s independent of IPC mutations. Filed as a follow-up.

N1 — `loom data list --type=epic` now filters correctly

Cause
Fleet-db's listIssues endpoint expects ?type=, not ?issue_type=. loomcli was sending the wrong query param so the filter was silently ignored.
Fix
internal/backend/fleet/params.go:148 — setNonEmpty(q, "issue_type", …) → setNonEmpty(q, "type", …). Regression test in params_test.go asserts the wire query has type=… and no issue_type=….

N2 — `loom data show` returns `parent`

Cause
fleet-db's GET /issues/{id} returns parent_id at the top level. Loomcli's Get projected the wire to types.IssueDetails without copying parent across, so detailsToDetailData's parent assignment was a no-op.
Fix
internal/backend/fleet/fleet.go:336-343 — after wire.toIssue(), project wire.parent() onto details.Parent so it flows through to IssueData.Parent. New test TestGet_PopulatesParent in fleet_test.go.

Bug #E + N3 — shared backend command path for Run Epic

What landed
New endpoint POST /api/workspaces/:ws/epics/:id/run with body {"lead": "<name>"}:
  1. Validates the lead exists and has role_name = lead (or orchestrator).
  2. Rejects with HTTP 409 if the lead is already bound to a different epic ("lead nova is already running epic E2E-2") — closes the spec's "one epic per lead" rule.
  3. Rejects with HTTP 409 if a different lead already owns the requested epic ("epic SLACK-1 is already claimed by lead nova") — closes N3 (silent two-leads-on-one-epic).
  4. Idempotent re-bind to the same epic returns 200.
  5. On success, patches lead.parent atomically via the existing AgentService.UpdateAgent.

internal/webui/handlers/epics/module.go + handlers.go + handlers_test.go (7 test cases covering bind, the two conflict rejections, idempotency, non-lead-role rejection, missing-lead, blank body). Wired into internal/webui/app/server_modules.go alongside the existing agents + onboarding modules.
